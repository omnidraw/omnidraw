Omnidraw widgets are generated app surfaces that run on the infinite canvas. A widget can be a chart, form, board, gallery, table, timer, or control panel.

Each published widget revision can contain:

- **UI**: the visible interface mounted from an immutable browser artifact.
- **Collaborative state**: versioned JSON state owned by each placed widget instance.
- **Server functions**: optional, short-lived backend calls with validated inputs and outputs.
- **Resources**: explicit database, key-value, or secret-store slots bound to the published revision.

## Collaborative state

Each placed widget instance has its own centrally managed JSON state. Two instances of the same revision do not share mutable state unless the widget deliberately coordinates through an external resource.

The UI reads and changes state through the Omnidraw SDK. The host applies compare-and-swap updates and keeps the canvas item pinned to its immutable definition and revision identity.

## Server functions

Server functions run only when invoked. They are bounded by time, memory, output, and log limits, and their input and output schemas are validated at the host boundary.

Use function effects deliberately:

- `fn` performs pure computation and cannot access resources.
- `fx` reads declared resource slots.
- `tx` may read and write declared resource slots.

Functions are not background workers. Do not use them for timers, sleeps, long-lived loops, HTTP servers, or durable continuations.

## Draft Preview

Draft Preview is a durable, frame-owned full-stack authoring revision. An open Preview follows committed draft edits automatically, streams install/build/validation progress, and keeps the last known good UI interactive while a replacement builds. The frame survives application restart and remounts its exact retained active revision rather than rebuilding solely because the process changed. Its UI calls the exact retained Preview server artifact with the selected resource bindings, so function and resource behavior can be reviewed before publication. Selected resource permissions are real in Preview, including permitted writes.

Preview state is ephemeral authoring-session state and does not become published-instance state. Runtime and build failures are scoped to and visible in the owning Preview; **Retry** and **Reset** provide explicit recovery. **Pause/Resume Live Updates** coalesces newer revisions locally, while **Cancel Build** targets only the exact pending build shown by the frame.

Publishing release-signs and commits the reviewed Preview construction—immutable source, UI, optional server artifact, function descriptors, provenance, and resource bindings—without rerunning npm or the widget build. The Preview title bar uses the exact mounted revision. The draft detail page requires a ready frame-owned Preview, shows its canvas/frame and revision identity, requires you to choose when several are available, and rechecks that selection before committing. A stable confirmation key makes a lost-response retry idempotent, while a changed binding revision or binding-plan digest fails closed. Canvas instances remain pinned to the revision that was placed.

## Build prerequisite

Widget UI projects own their npm dependencies, package-lock-v3 file, and build script. A draft-private warm workspace runs frozen `npm ci` when package or lock inputs change and the guest-controlled `npm run build` for each required construction; Capsule then validates the resulting `dist/` before it can be signed or loaded. Node.js/npm remain prerequisites for the default host runner. Operators may instead select the optional Docker runner with an immutable image digest and bounded CPU, memory, PID, filesystem, and cleanup policy. Build scripts still run with the selected runner's authority, so operators must treat package installation and build plugins as trusted build-server work rather than Capsule-sandboxed browser code.

## Supported UI authoring

Plain DOM is the default. React is the supported component-library path: use a `.tsx` entry, import from `react` and `react-dom/client`, and pin `react`/`react-dom` to `19.2.7`, `@types/react` to `19.2.17`, and `@types/react-dom` to `19.2.3`. The trusted build selects Capsule's reviewed JSX transform and verifies the exact closed package projection; widgets do not choose build plugins. Other UI libraries, remote ESM/CDN imports, dynamic imports, and runtime package loaders are unsupported.

Request only the public Capsule API groups the UI actually uses. `DOM` is
explicit and mandatory; add `NETWORK`, `FILES`, `CLIPBOARD`, `DIALOGS`,
`CANVAS_2D`, `WEBGL`, `WEBGPU`, `AUDIO`, or `VIDEO` only when needed.
`CANVAS_2D`, `WEBGL`, and `WEBGPU` are mutually exclusive. Capsule supplies
the selected groups' normal budgets; use a partial budget override only when
Preview diagnostics show a measured need. An API-group request describes
compatibility—it does not grant host, network, file, or resource authority.

## Widget UI limits

Widget UI code runs from a signed, immutable artifact inside the Capsule browser sandbox. It does not receive direct access to the host page, canvas engine, database, credentials, or Bun process objects. DOM access and communication with collaborative state, server functions, and widget channels are limited to the public Capsule API groups and capabilities declared by the published revision.

The practical rule is:

- Put visible interaction in the widget UI.
- Put persistent instance state in collaborative state.
- Put bounded backend work in server functions.
- Access infrastructure only through declared resource slots.
- Let Omnidraw own placement, artifact verification, authorization, and runtime isolation.

## Using secret stores

Secret values are masked by default in the resource workspace. A local operator may deliberately reveal one stored value; it is cleared when hidden, when the view changes, and after inactivity.

AI resource tools can create and rotate secrets with approval, but they cannot reveal plaintext. Published `fx` or `tx` functions can read a bound secret slot only when the revision declares and receives the required permission.

Secret-store database pages and write-ahead logs are encrypted at rest with independent keys stored in the main control database. Protect complete backups because they may contain both encrypted resource data and the corresponding keys.
