# B73 - AI widget scaffold: resolve workspace dependency protocols before npm install
[Overview](../BASED.md)

Generated widget creation copies the SDK's development-only `catalog:`
Capsule dependency into a standalone package, causing npm to reject the
scaffold before the agent can author the requested widget.

## Context

The SDK workspace manifest intentionally uses `catalog:` so local development
tracks the repository's current Capsule version. Its npm build already resolves
that protocol in the staged `dist/package.json`.

Widget scaffolding currently reads the raw value from
[`packages/sdk/package.json`](../../packages/sdk/package.json) through
[`CONSTANTS.ts`](../../packages/service-agent/src/workspace/CONSTANTS.ts) and
writes it into the generated widget's dependencies and overrides. The next
step runs npm, which does not support Bun's catalog protocol and exits with
`EUNSUPPORTEDPROTOCOL`. The temporary draft is then correctly rolled back.

The fix belongs at the standalone-manifest boundary. The SDK development
manifest must remain workspace-oriented, while generated widget manifests must
contain concrete registry-compatible dependency specifiers.

The first correction selected the older public SDK/Capsule pair. B74 later
proved that this fixes npm installation but breaks the runtime bridge against a
newer local host. The completed boundary now emits the current exact SDK and
Capsule versions; local development publishes that staged SDK to Verdaccio,
while compiled/release use remains on the public npm config and must wait until
the exact closure is published.

## Plan

### 1. Resolve the SDK dependency for standalone widgets

- Keep the SDK workspace manifest on `catalog:`.
- Resolve the SDK version and its Capsule catalog entry to exact versions.
- Keep local development and public release registries separate while using
  the same dependency version closure.
- Fail clearly if a referenced catalog entry is absent or if another local-only
  protocol reaches the standalone boundary.
- Build and publish the staged SDK before local dev starts.

### 2. Preserve the npm package boundary

- Keep generated widget package dependencies concrete and registry-compatible.
- Do not copy `catalog:`, `workspace:`, `file:`, or `link:` into widget source.
- Leave SDK distribution staging responsible for its own public manifest.

### 3. Add regression coverage

- Test catalog resolution, ordinary registry ranges, missing entries, and
  rejected local protocols.
- Test the real production constants so future workspace manifest changes
  cannot leak a local protocol into generated widgets.
- Run the focused service-agent tests, typecheck, and functional-core checks.
