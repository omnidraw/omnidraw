# B39 - ai wizard: actor tab stale after new actor candidate
[Overview](../../BASED.md)

After a new actor candidate is set by the chat/tool run, the Actor tab should show it immediately when opened. It currently stays stale until tab navigation happens again.

## Context

Affected area:
- [`packages/canvas/src/components/AiWizzard/`](../../packages/canvas/src/components/AiWizzard/)
- [`packages/canvas/src/components/AiWizzard/index.tsx`](../../packages/canvas/src/components/AiWizzard/index.tsx)
- [`packages/canvas/src/components/AiWizzard/tabs/ActorTab.tsx`](../../packages/canvas/src/components/AiWizzard/tabs/ActorTab.tsx)
- [`packages/canvas/src/components/AiWizzard/tabs/ChatTab.tsx`](../../packages/canvas/src/components/AiWizzard/tabs/ChatTab.tsx)

User report:
- A new actor candidate is set in chat.
- User moves to Actor tab.
- Actor tab is not updated.
- Only after moving tabs back and forth again does the Actor tab update.
- Looks like a Solid `set`/state sync issue.

Screenshot reference from report:
- `/var/folders/pf/mzkxrfrj2zbcv5wfsln5h0rw0000gn/T/pi-clipboard-a8e23cba-e4da-4516-aa90-84dedbfff200.png`

Current likely cause from quick inspection:
- `AiWizzard/index.tsx` owns `vcJson` and passes it to `ActorTab` as `actor={vcJson()}`.
- `vcJson` is updated on initial `wizzard.connect`, explicit reconnect, approve flow, and Actor/Tool tab edits.
- Live agent events update `messageHistory`, but do not appear to refresh `vcJson` when a successful `vc_set_actor_candidate` tool result arrives.
- `ChatTab.tsx` has an `isSetActorCandidateToolResult(...)` helper, suggesting the chat can detect successful candidate tool results, but that signal is not currently used to refresh the parent manifest state.
- `ActorTab.tsx` also keeps its own local `manifest` signal and reads `draftManifest.read(...)` in a `createEffect`, but that effect is keyed only by props like `widgetId/sessionId`; it does not refresh merely because a new candidate was set while the tab was hidden/already mounted.

Expected behavior:
- Once `vc_set_actor_candidate` succeeds, the latest candidate manifest is reflected in `AiWizzard` state.
- Opening Actor tab immediately shows the candidate without requiring an extra tab switch.
- If a candidate is revised multiple times, Actor tab shows the latest revision.
- If the user is already on Actor tab while a new candidate arrives, the tab updates without manual navigation.

## Plan

1. Reproduce and confirm state flow.
   - Run the AI wizard flow that calls `vc_set_actor_candidate`.
   - Observe whether `messageHistory` receives the tool result before `vcJson` updates.
   - Confirm whether `ActorTab` is mounted while hidden or remounted on tab changes.

2. Decide the canonical refresh trigger.
   - Preferred: centralize manifest/candidate refresh in `AiWizzard/index.tsx` when successful candidate-related events/messages arrive.
   - Avoid relying on `ActorTab` tab activation as the only refresh mechanism.
   - Keep `ActorTab` mostly a view/editor of the passed manifest plus explicit save/read actions.

3. Wire successful `vc_set_actor_candidate` to refresh manifest state.
   - Reuse or move the `isSetActorCandidateToolResult` detection from `ChatTab.tsx` if needed.
   - When a successful `vc_set_actor_candidate` tool result appears in live events or connected history, call `draftManifest.read(...)` or `wizzard.connect(...)` and update `vcJson` with the actor candidate manifest.
   - Guard against races with `sessionId`, `widgetId`, and stale async responses.
   - If the tool result payload already contains the candidate manifest, consider using it directly only if the shape is reliable; otherwise fetch the latest via the API.

4. Make Actor tab sync robust.
   - Review `ActorTab.tsx` local `manifest` mirror and `createEffect` comparison using `untrack(manifest)`.
   - Ensure a new `props.actor` value always calls `syncForm(nextManifest)`.
   - Consider removing local `manifest` duplication or making it a derived source plus local form fields, if that simplifies stale state behavior.
   - Ensure `manifestSource` becomes `actor-candidate` for candidates, not always `connected`, when appropriate.

5. Add/adjust tab activation refresh only as a fallback.
   - If there is no clean live candidate event hook, refresh on switching into Actor tab.
   - Prefer not to require switching away and back; one switch into Actor should be enough.
   - Use a refresh nonce or explicit `onActorTabOpen` handler rather than an unkeyed effect that can spam the API.

6. Verify edge cases.
   - Candidate set while on Chat tab, then first switch to Actor tab shows latest candidate.
   - Candidate revised while already on Actor tab updates form/state.
   - Candidate approval still updates Actor tab from `actor-candidate` source to `file` source.
   - Tool tab and Preview tab continue using the same latest `vcJson`.
   - New chat/session clears stale actor data as expected.

## NOTES

- This is likely a state ownership problem: `messageHistory` is live, but the manifest/candidate state used by Actor tab is not refreshed at the same time.
- Best fix should update `vcJson` in the parent as soon as the candidate changes, so all tabs see the same latest manifest.
- Avoid a fix that only works after a second tab switch; first navigation into Actor must be enough.
