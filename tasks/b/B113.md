# B113 - published widget Config: update icons without rebuilding
[Overview](../BASED.md)

Published-only widgets expose a read-only Config document, so their icon cannot
be changed from the product UI. Allow one digest-fenced icon update through the
existing metadata-only publication boundary without creating a draft or
rebuilding executable files.

## Context

The published Config branch in
[`WidgetDetailPage.tsx`](../../apps/frontend/src/shell/framework/feature/sidebar/widgets/WidgetDetailPage.tsx)
shows only **Published Config is read-only** and serialized JSON. This blocks a
published-only widget such as Small CRM from using the visual icon picker
planned in [B112](B112.md).

An icon is presentation metadata, not executable Config.
[`fnProjectWidgetPresentation`](../../packages/sdk/src/contracts/core/fn.filesystem-manifest.ts)
includes `tool.icon`, while
[`fnProjectWidgetExecutableManifest`](../../packages/sdk/src/contracts/core/fn.filesystem-manifest.ts)
contains only `schemaVersion`, `ui`, `server`, and resource requirements.
Changing only the icon therefore must not require a portable build, accepted
build generation, Capsule construction, release signing, or replacement of
runtime files.

A crash-safe metadata-only writer already exists:

- [`WidgetFilesystemManagementService.publishMetadata`](../../apps/backend/src/shell/widget/WidgetFilesystemManagementService.ts)
  verifies that executable identity and resource bindings are unchanged;
- [`publishWidgetMetadata`](../../apps/backend/src/shell/agent/widget-filesystem/publication/write-publication.ts)
  validates and atomically replaces only published `omnidraw.json`, with
  rollback and writer-lock handling;
- [`WidgetFilesystemManagementService.test.ts`](../../apps/backend/tests/WidgetFilesystemManagementService.test.ts)
  proves metadata publication does not construct, sign, require an accepted
  build, or change Capsule, `dist/`, or `release.json` bytes.

The current high-level operation cannot serve a published-only edit. It reads
its candidate from a healthy draft, and the low-level
[`TPublicationDigestFence`](../../apps/backend/src/shell/agent/widget-filesystem/publication/typed.ts)
and `observeFence` hook are hard-coded to a draft tree digest. Published Config
also has no mutation in the private RPC contract.

Do not work around this by materializing, editing, publishing, and deleting a
draft. Materialization requires a release-attested source artifact, creates an
unrelated mutable source folder, and can conflict with an existing divergent
draft. A published icon update should use the observed published manifest as
its authority and leave every draft untouched.

This is a narrow product capability. Name, description, label, group, priority,
resources, source, and executable settings remain read-only on the published
route. The icon value remains the existing SDK contract: `null`, one known
`{ lucidIcon }`, or one valid `{ svgIcon }`.

## Plan

![Published Config currently exposes only read-only JSON](B113.png)

1. Add one private operation for a published icon update, for example
   `widget.publication.updateIcon`, with:
   - `widgetKey`;
   - `expectedPublishedManifestDigestSha256`;
   - `expectedCatalogDigestSha256`;
   - `icon: TOmnidrawToolIcon | null` validated by the existing SDK contract.
2. In `WidgetFilesystemManagementService`, refresh and fence the catalog,
   require one healthy publication, compare the exact published manifest
   digest, and construct a candidate by changing only `tool.icon` on the
   current published manifest. Recompute and assert the executable digest is
   identical to the current release before entering the publication writer.
3. Generalize the publication fence so full publication remains fenced to its
   captured draft while direct metadata mutation can be fenced to the captured
   published manifest/folder identity. Keep the fence explicit and
   source-aware; do not weaken it to an unfenced path or duplicate the atomic
   metadata writer.
4. Reuse `publishWidgetMetadata` to atomically replace only `omnidraw.json`.
   Keep `release.json`, `capsule.artifact`, `dist/`, optional server files,
   function descriptors, and the authoring-source artifact byte-identical.
5. After B112 provides the visual picker, render it on published Config with a
   **Save icon** action and concise metadata-only help. Keep the rest of the
   published Config visible and read-only. Disable save when unchanged, busy,
   or invalid, and retain inline failure plus notification behavior.
6. Refresh the shared catalog after success so the selected header, sidebar,
   grouping projection, and subsequent publication reads observe the new icon.
   Do not mutate or hide a separate draft; if it now differs from the
   publication, the existing draft-row projection should show that difference
   truthfully.
7. Add service, RPC-contract, frontend, stale-fence, and byte-identity tests.
   Update the publication-actions description in
   [`llm.widget-system.md`](../../docs/internal/llm.widget-system.md) and the
   published Config reference in the
   [screen atlas](../../docs/internal/screens/SCREENS.md).

## Acceptance criteria

- A healthy published-only widget can select a Lucide icon, custom SVG/emoji,
  or no icon from its Config tab and save it directly.
- The request is rejected when the observed published manifest or catalog has
  changed; a stale form never overwrites a newer icon.
- The backend candidate differs from the current publication only at
  `tool.icon`.
- The update performs zero build, accepted-generation, Capsule-construction,
  package-manager, and signing work.
- `release.json`, `capsule.artifact`, every `dist/` and optional server/function
  file, and `dist/.omnidraw-authoring-source.artifact` are byte-identical before
  and after the update.
- Published `omnidraw.json` contains exactly the selected valid icon value, and
  the refreshed sidebar/detail header render it.
- No draft is created, rewritten, published, or deleted. An existing divergent
  draft remains independent and visible according to normal catalog rules.
- All other published Config fields remain read-only.
- No public SDK API or manifest schema changes, and no public-package version
  bump, are required.

## NOTES

- Dependency: implement or coordinate with [B112](B112.md) so draft and
  published Config share one picker and validation behavior.
- The public manifest field is intentionally spelled `lucidIcon`; do not rename
  the serialized contract while presenting **Lucide** in the UI.
- Metadata publication changes the current published manifest deliberately;
  “published folder is immutable” means authors do not edit runtime files
  directly, not that the authority cannot atomically replace approved metadata.
- The supplied screenshot is the current published-only Config reference.
