# B119 - canvas selection overlay escapes above application dialogs
[Overview](../BASED.md)

Opening an application dialog over a Canvas leaves the selected item's blue transformer outline and handles above the backdrop and dialog. Contain Canvas-owned layers below application portals without clearing the user's selection.

## Context

The reported path opens the resource-creation portal in [`CreateResourceDialog.tsx`](../../apps/frontend/src/shell/framework/feature/sidebar/components/CreateResourceDialog.tsx) while an AI Chat widget frame is selected on `/c/:id`. Its backdrop and content use the application-level `40`/`50` bands in [`SidebarDialog.module.css`](../../apps/frontend/src/shell/framework/feature/sidebar/components/SidebarDialog.module.css).

The installed `@omnidraw/cangine` version declared by [`packages/canvas/package.json`](../../packages/canvas/package.json) renders the DOM selection surface at `z-index: 2147483646`. That extreme internal band is intentional: transformer chrome must remain above opaque widget portals. However, the public Canvas root in [`Canvas.tsx`](../../packages/canvas/src/components/Canvas.tsx) and [`base.css`](../../packages/canvas/src/base.css) does not establish a stacking context. The selection surface therefore escapes the Canvas component's local layer system and competes directly with body-level application portals, outranking both the modal backdrop and content. The same missing boundary can let other Canvas-owned overlays ignore app-level modal dimming.

Selection-overlay suppression already exists for the distinct canvas-maximized widget state in [`runtime.ts`](../../packages/canvas/src/runtime.ts). A normal application modal should not reuse that shell state, clear selection, or require every dialog owner to coordinate with the Canvas runtime. The component boundary should keep Cangine's internal ordering intact while making the complete Canvas one application-level stacking unit.

This changes public Canvas runtime CSS under `src/`, so [`packages/canvas/package.json`](../../packages/canvas/package.json) needs a semantic patch release marker and [`bun.lock`](../../bun.lock) regeneration under the repository publishing rules.

## Plan

![Selected AI Chat transformer rendering through the Create resource dialog](B119.png)

1. Establish an explicit stacking context on the public Canvas root so Cangine's high selection surface, widget portals, selection-style UI, and toolbar remain ordered inside the component but cannot escape above application-level portals.
2. Keep the selected node and focused widget identity unchanged while a modal is open; closing the dialog must reveal the same selection and working transformer without a runtime remount.
3. Add a Canvas component regression for the stacking-boundary contract and frontend browser acceptance that selects a widget frame, opens a sidebar creation dialog, and proves the backdrop/dialog cover every Canvas-owned visual before the selection reappears after close. Exercise at least Create resource and ensure the shared sidebar dialog styles also protect Create canvas, rename, and delete flows.
4. Bump the Canvas package patch version, regenerate the lockfile, and run the targeted Canvas/frontend tests, browser acceptance, package typechecks, and public package build.

## NOTES

The failure is not caused by the dialog form or by stale selection state. Raising each dialog above `2147483646` would duplicate knowledge of a Cangine implementation detail and leave other application overlays exposed. Suppressing selection per dialog would also scatter Canvas-runtime coordination across modal owners and risks losing the visible selection contract after close.

The screen atlas documents resource creation as an app-shell modal and Canvas selection as component-owned chrome in [`SCREENS.md`](../../docs/internal/screens/SCREENS.md). The fix restores that ownership relationship; a new atlas capture is unnecessary unless implementation materially changes either intended surface beyond correct occlusion.
