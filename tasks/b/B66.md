# B66 - actor clone copy write burst crashes Turso DB
[Overview](../BASED.md)

Use the minimal repro in `.tmp/turso-actor-write-race` to close the actor clone/DB write crash path and add regression coverage.

## Context
The repro confirmed the failure (`cell_get: idx ...`) can be triggered in a minimal harness that replays widget-clone-like DB churn:
- `actor_instances` insert
- immediate `updateInstanceMachine`
- immediate `updateInstanceStatus`
- occasional `deleteInstance`

Important repro files for handoff:
- `.tmp/turso-actor-write-race/scripts/repro.ts`
- `.tmp/turso-actor-write-race/README.md`

Observed in repro:
- concurrent mode reproduces quickly under burst pressure.
- serialized mode also reproduces in the same harness (so issue may be deeper than simple in-process concurrency, but this still gives a deterministic stress path tied to actor write storms).

## Plan
### 1) Freeze failing invariant
- Preserve and pin the failing harness inputs and command lines that reproduce quickly.
- Add a short test harness command in the task as a permanent repro contract.

### 2) Identify and implement safest fix surface
- Start in database write boundary first:
  - add single write serialization path in `DbServiceTurso` for actor mutation methods (instance insert/update/delete, definition insert/update/delete, connection writes) **or** move actor mutation calls behind the same serialized queue in actor orchestration.
- Keep writes deterministic and in one place so call sites don’t each need ad-hoc guards.
- Preserve existing semantics/errors (including migration lock/error behavior and constraint handling).
- Evaluate queue placement:
  - Option A: wrapper methods in `packages/service-db/src/DbServiceTurso.ts` that serialize actor methods.
  - Option B: in `packages/service-actor/src/ActorSupervisor.ts` methods only (`createInstance`, `removeInstance`, `persistActorMachineSnapshot`) if we only want actor-frontend writes.
- Also verify lock-path behavior for `multiprocess_wal` and DB reopen in dev.

### 3) Validate against repro
- Run:
  - `cd .tmp/turso-actor-write-race && ITERATIONS=500 BATCH_SIZE=40 WITH_DELETE=1 bun run repro:concurrent`
  - `cd .tmp/turso-actor-write-race && ITERATIONS=500 BATCH_SIZE=40 bun run repro:serialized`
  - `cd .tmp/turso-actor-write-race && ITERATIONS=20 BATCH_SIZE=10 bun run repro:insert-only`
- Re-run existing app startup/copy flow after implementation.

### 4) Regression test
- Add a regression test that exercises concurrent actor operations and asserts the service remains stable (no panic + expected row counts).
- Keep it close to actor DB boundary:
  - Unit/integration test in `packages/service-db` for `actor.insertInstance/updateInstanceMachine/updateInstanceStatus/deleteInstance` with Promise.all burst writes.
- If harness testing is preferred, add a deterministic integration test script under `packages/service-actor/tests` and gate in CI with a conservative iteration count.

### 5) Hardening and cleanup
- Add regression notes to task and E29 completion logs.
- If needed, add temporary debug logging around actor write failures and lock acquisition to narrow future repros.
