# B66 - widget portals: keep Capsule layout intrinsic while canvas zooms
[Overview](../BASED.md)

Keep published widget content fitted to its Cangine frame and prevent canvas
zoom from changing the widget's internal responsive layout.

## Context

Cangine gives the widget content host intrinsic CSS dimensions and applies
camera zoom to the outer portal transform. Vibecanvas currently derives the
Capsule viewport from `geometry.viewportBounds`, which is already camera
projected, and passes camera zoom as Capsule `scale`. Capsule then applies the
projected width and height directly to the child runtime, leaving blank space
inside the intrinsic host and causing `vw`-based widget layouts to reflow.

Relevant files:

- [`packages/ui-ai-chat/src/canvas-extension/index.ts`](../../packages/ui-ai-chat/src/canvas-extension/index.ts)
- [`packages/ui-ai-chat/src/widget-runtime/mount-widget-ui-artifact.ts`](../../packages/ui-ai-chat/src/widget-runtime/mount-widget-ui-artifact.ts)
- [`packages/ui-ai-chat/src/widget-runtime/fn.capsule-viewport.ts`](../../packages/ui-ai-chat/src/widget-runtime/fn.capsule-viewport.ts)
- [`packages/ui-ai-chat/tests/widget-runtime/`](../../packages/ui-ai-chat/tests/widget-runtime/)

## Plan

![Published widget content shrunk inside its frame after canvas zoom](B66.png)

1. Derive Capsule width and height from the intrinsic portal content host,
   never from camera-projected bounds.
2. Use portal device pixel ratio for Capsule `scale`; keep camera zoom solely
   in Cangine's outer transform.
3. Remove the transformed `getBoundingClientRect()` fallback from widget
   artifact mounting.
4. Add regressions proving zoom does not alter guest layout dimensions while
   frame resize still does.
5. Run focused package tests, typecheck, functional-core lint, and frontend
   build verification.

No new mockup is needed. The supplied failure screenshot is the authoritative
visual reference, and the screen atlas already covers the intended hosted
widget frame.
