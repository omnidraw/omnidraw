# B48 - AI widgets: pin Preview revisions and make Publish rollback complete
[Overview](../BASED.md)

Preview and Publish currently expose three integrity gaps: Preview can run code from a mutable draft while reporting an earlier revision, failed publication can leave partially changed resource bindings behind, and changing a published slug can leave the previous installed widget directory active. Treat Preview as an immutable revision and Publish as one recoverable operation across installed files, canonical files, resource bindings, and definition reloads.

## Context

The issues below were confirmed by tracing the current backend implementation after S86. They are related because they all cross the boundary between a shared mutable draft and a supposedly stable runtime or published result.

### P1 — Preview is not revision-pinned

[`WidgetDraftController.buildPreview`](../../packages/service-agent/src/widget-drafts/WidgetDraftController.ts) checks `expectedRevision`, validates the draft, and checks the revision again. It then reads the manifest and widget sources directly from the mutable draft directory and passes that same directory to `Actor` as `rootDir`.

`Actor.start()` spawns its child asynchronously. The child loads the actor function registry from `rootDir` after the controller has already accepted the revision. A workspace edit can therefore occur between the last revision check and the child loading the functions. Manifest data, returned widget sources, and running actor code are not guaranteed to come from one revision even though Preview reports the accepted revision.

The returned Preview DTO does correctly distinguish `revision`, `currentRevision`, and `stale`, but that detects later draft changes; it does not prove that the original Preview was built from a coherent immutable revision.

The static source map and already-loaded function registry do not automatically update after every ordinary edit. The defect is the missing snapshot guarantee, not a claim that all later edits always hot-reload the running actor.

### P1 — Resource bindings are outside publication rollback

[`WidgetDraftController.publish`](../../packages/service-agent/src/widget-drafts/WidgetDraftController.ts) publishes files, reloads definitions, reconciles resource bindings, optionally reloads instances, and commits the filesystem snapshot.

[`txReconcileResourceBindings`](../../packages/service-agent/src/core/tx.reconcile-resource-bindings.ts) performs individual `bindResource` calls followed by individual `unbindResource` calls. The batch is not atomic. If a later binding mutation fails, earlier changes remain. A failure after reconciliation, such as `reloadDefinitionInstances`, also leaves the complete new binding set in place.

The publication catch path rolls back canonical and installed files and reloads definitions, but does not restore the previous binding set. The current `TActorServiceReloader.listResourceBindingsForDefinition` contract exposes only slot and resource IDs even though persisted bindings also contain read/write access, so the agent layer cannot faithfully snapshot and restore the old scopes through its current interface.

### P2 — A published slug change leaves the old installation behind

Publishing computes and protects only the destination for the new manifest slug. [`WidgetWorkspace.beginDraftPublish`](../../packages/service-agent/src/workspace/WidgetWorkspace.ts) backs up that new installed path, and [`txPublishWidgetDraft`](../../packages/service-agent/src/core/tx.publish-widget-draft.ts) replaces that destination. Neither operation discovers or removes the installed directory named by the previously published manifest.

If `Weather` was installed as `config/widgets/weather` and its draft changes the slug to `weather-v2`, republishing creates `config/widgets/weather-v2` while leaving `config/widgets/weather` intact. Definition discovery scans both directories and indexes results by manifest name, so duplicate installations can make the selected manifest path depend on filesystem enumeration and can produce definition synchronization errors.

## Fixed decisions

### Preview snapshot contract

- A successful Preview represents exactly one accepted draft revision.
- Create a private immutable snapshot through `WidgetWorkspace` while coordinating with the draft write lane.
- Recheck `expectedRevision` inside the coordinated snapshot operation, not only in the controller before it.
- Read the manifest and widget sources from the snapshot.
- Use the snapshot directory as the Actor `rootDir`.
- Store snapshot ownership with the preview entry.
- Delete the snapshot when Preview is refreshed, reset, replaced, closed, or fails to build.
- Never delete the shared draft while disposing a preview.
- Snapshot creation must fail closed and clean temporary directories after partial copy or validation failure.
- The workspace write lane coordinates structured workspace writes. Because Bash and external editors are not filesystem-isolated, implementation must also detect a draft change across snapshot creation instead of claiming the lock controls arbitrary filesystem mutation.

### Binding replacement contract

- Add one actor-service operation that replaces the complete binding set for one definition transactionally.
- The input and rollback snapshot include slot, resource ID, `allow_read`, and `allow_write` semantics.
- Validate every desired binding and scope before committing any replacement.
- Execute replacement inside the existing definition/resource lifecycle gates so actor starts cannot observe a half-replaced set.
- `txReconcileResourceBindings` must delegate to the atomic operation; it must not emulate atomicity with a loop of public bind/unbind calls.
- Publishing captures the complete previous binding set before mutation.
- Any failure after binding replacement restores both filesystem state and the previous binding set, then reloads definitions and affected instances into the restored state.
- If compensation itself fails, return and persist a specific recovery error. Do not report a normal publication failure while silently leaving mixed state.

The database transaction cannot include filesystem changes. Publication therefore remains a coordinated transaction with durable or explicitly checked compensation across the filesystem and database boundaries.

### Slug policy

- Short term: reject changing `manifest.slug` after the first successful publication.
- Compare the draft slug with the previously published canonical manifest before mutating canonical or installed files.
- Return an actionable validation/publication error naming the immutable published slug.
- A new widget may still choose any safe unused slug.
- Do not silently delete or migrate an old installed directory in the short-term fix.

Supporting slug renames later requires a separate transaction that locks both old and new installed destinations, backs up both, removes the old installation, writes the new installation, reloads definitions, and rolls both paths back on failure.

## Plan

### 1. Add causal regression tests

- Reproduce an edit between Preview revision acceptance and Actor child loading; assert the running actor and returned sources cannot mix revisions.
- Assert Preview uses a private snapshot path and the shared draft remains editable and unchanged.
- Assert refresh, reset, close, replacement, and build failure remove their owned snapshots.
- Reproduce a multi-binding replacement where a later binding is invalid or fails; assert no partial new bindings remain.
- Reproduce a failure after successful binding replacement, including instance reload failure; assert the previous full binding set and scopes are restored with the previous files.
- Publish once, change only the slug, and assert republish is rejected before either installed directory changes.

### 2. Introduce workspace-owned Preview snapshots

- Add a bounded snapshot lifecycle API to `WidgetWorkspace` rather than copying draft paths directly in the controller.
- Use unique backend-owned temporary paths outside the model-visible shared draft namespace.
- Coordinate revision verification and copy with the per-widget write lane.
- Verify the source revision did not change across snapshot materialization.
- Extend `TPreviewEntry` to own snapshot cleanup.
- Ensure Actor shutdown occurs before removing its root directory.

### 3. Add transactional definition-binding replacement

- Extend the actor service and database service with a complete replace operation.
- Preserve read/write access exactly when listing, replacing, and restoring bindings.
- Validate manifest requirements, resource readiness, resource kind, and requested scope before the database commit.
- Serialize replacement against actor starts and resource lifecycle operations.
- Replace the sequential reconciliation loop with the new operation.

### 4. Coordinate Publish compensation

- Capture the previous complete binding set before publication mutations begin.
- Track whether binding replacement committed.
- On any subsequent failure, roll back files, reload the restored definition, restore bindings atomically, and restore/reload affected instances.
- Define deterministic error precedence when the original operation and compensation both fail.
- Preserve the existing successful publication event only after every file, binding, reload, and commit step succeeds.

### 5. Reject published slug changes

- Read the previous canonical manifest for an existing publication.
- Reject a different slug before `beginDraftPublish` or installed-path mutation.
- Keep existing same-slug collision and concurrent-publish protection.
- Document that renaming a widget or its installed slug requires creating a new widget until a multi-path rename transaction is implemented.

### 6. Verify the complete lifecycle

- Run focused service-agent, service-actor, and service-db tests.
- Run functional-core lint for new or changed `fn`, `fx`, and `tx` files.
- Run the full frontend/application build because Preview and Publish DTO behavior is consumed by the shared-draft UI.
- Manually verify Preview refresh and failed Publish recovery with a resource-backed actor widget.

## Acceptance criteria

- Preview manifest, sources, and Actor functions always originate from one immutable snapshot of the reported revision.
- Editing the shared draft after Preview build cannot change the running Preview; it only marks that Preview stale until refresh.
- Preview snapshot directories are removed on every normal and exceptional disposal path.
- A failed binding replacement leaves the complete previous set unchanged.
- A failure after binding replacement restores previous files, bindings, access scopes, definitions, and affected instance behavior.
- Publish emits success only after filesystem, binding, definition, and instance work is committed.
- Republishing an existing widget with a different slug fails before changing either the old or proposed installed path.
- Republishing with the original slug continues to work and retains current rollback behavior.
- Concurrent Preview edits, publishes, and binding operations do not expose mixed revisions or partially replaced bindings.

## NOTES

- Category: bug.
- Priority: P1 because Preview revision identity and persisted resource authorization can diverge from reported publication state.
- The slug defect is P2 but belongs here because the same publication transaction must define installed-path ownership and rollback.
- Keep the cooperative Bash trust model established by S85; do not describe the workspace write lane as a filesystem sandbox.
- S86 is assumed complete. Use its final dated chat/workspace paths when choosing temporary snapshot roots; do not restore legacy `chat-cwd` assumptions.
- In-place widget name changes remain unsupported independently of slug handling.
- This task does not authorize a general widget rename feature.
