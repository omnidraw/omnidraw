# B81 - cli: shutdown crashes with "Runtime cannot shutdown from state 'stopping'" on Ctrl+C
[Overview](../../BASED.md)

Stopping `bun run dev` (or any `serve` run) with Ctrl+C can print an
unhandled-rejection stack trace instead of exiting cleanly.

## Context
Reported log:

```
[cli] stop agent-service
error: Runtime cannot shutdown from state 'stopping'.
      at shutdown (packages/runtime/src/create-runtime.ts:176:19)
      at <anonymous> (apps/cli/src/main-app.ts:93:19)
      at onSignal (apps/cli/src/setup-signals.ts:5:10)
```

`apps/cli/src/setup-signals.ts` registers `onSignal` independently for both
`SIGINT` and `SIGTERM` via `process.once`. Each signal type only fires its
handler once, but `onSignal` itself can still run twice overall if both
signals arrive (e.g. the dev process supervisor sends `SIGINT` then escalates
with `SIGTERM` shortly after). `apps/cli/src/main-app.ts:92-95` wires
`onSignal` to `runtime.shutdown()`, and `packages/runtime/src/create-runtime.ts:175-177`
throws when `shutdown()` is invoked while state is already `'stopping'`:

```ts
if (state === 'booting' || state === 'stopping') {
  throw new Error(`Runtime cannot shutdown from state '${state}'.`);
}
```

Because `onSignal` does `void shutdown()` (fire-and-forget), the second
call's throw becomes an unhandled rejection that Bun prints. The first
shutdown still completes and the process still exits 0, so this is not a
functional break, but it prints a scary stack trace on a normal stop.

Related, but separate/lower priority noise from the same log: `apps/cli/src/plugins/orpc/OrpcPlugin.ts:78-79`
logs every oRPC error via a blanket `onError` interceptor, including expected
control-flow errors like `previewTargetNotFound()`
(`packages/api/src/widget/api.preview.ts:6`) and cancelled widget runtime
loads (`packages/api/src/widget/api.runtime-load-widget.ts:134`). Not part of
this bug's fix, noted for awareness only.

## Plan
Make shutdown re-entrant-safe so a second signal cannot throw. Prefer one of:
- `setup-signals.ts`: guard `onSignal` so only the first invocation calls
  `shutdown`; subsequent signals are no-ops (or force-exit if already
  shutting down).
- `create-runtime.ts`: make `shutdown()` idempotent while `'stopping'` by
  returning the in-flight shutdown promise instead of throwing.
