# B40 - widgets: clone-drag creates multiple copies
[Overview](../../BASED.md)

Alt/clone-dragging one widget should create exactly one new widget. It currently creates multiple copies after mouse release when several widget definitions are registered.

## Context

User report:
- In `@packages/canvas/`, cloning a widget by dragging creates 3 new copies after mouse release instead of 1.
- Report says this happens for widgets only.
- Entry point mentioned: [`packages/canvas/src/plugins/widget/Widget.plugin.ts`](../../packages/canvas/src/plugins/widget/Widget.plugin.ts)

Affected files found during investigation:
- [`packages/canvas/src/plugins/widget/Widget.plugin.ts`](../../packages/canvas/src/plugins/widget/Widget.plugin.ts)
- [`packages/canvas/src/services/widget/WidgetManagerService.ts`](../../packages/canvas/src/services/widget/WidgetManagerService.ts)
- [`packages/canvas/src/services/widget/fx.attach-widget-listener.ts`](../../packages/canvas/src/services/widget/fx.attach-widget-listener.ts)
- [`packages/canvas/src/services/widget/tx.create-widget-clone-drag.ts`](../../packages/canvas/src/services/widget/tx.create-widget-clone-drag.ts)
- [`packages/canvas/src/services/element/ElementService.ts`](../../packages/canvas/src/services/element/ElementService.ts)

Current flow:
1. `Widget.plugin.ts` loads actor definitions and calls `widgetMangerService.registerWidget(...)` once per actor definition.
2. `WidgetManagerService.registerWidget(...)` registers one ElementService definition per widget kind.
3. Widget listener in `fx.attach-widget-listener.ts` starts clone drag on `dragstart` + Alt:
   - calls `safeStopDrag(portal.node)`
   - calls `portal.startDragClone({ node: portal.node, selection: portal.selection.selection })`
4. `startDragClone` delegates to `ElementService.createDragClone(...)`.
5. `ElementService.createDragClone(...)` loops every matching definition and currently does not stop after the first successful handler.
6. Each matching widget definition calls `txCreateWidgetCloneDrag(...)`, creating its own preview clone.
7. On `dragend`, every preview clone finalizes and persists, so the user sees multiple new copies.

Likely root cause:
- `WidgetManagerService.registerWidget(...)` uses a broad `matchesNode`:

```ts
matchesNode: (node) => {
  const type = node.getAttr(ELEMENT_DATA_ATTR)?.type;
  return type === 'widget' || type === 'ui-widget';
},
```

- This means every registered widget definition matches every widget node, regardless of `data.kind`.
- If 3 actor/widget definitions are registered, one widget node matches all 3 definitions, so 3 clone-drag handlers run.
- `matchesElement` is already kind-specific, but `matchesNode` is not.

Secondary contributing bug:
- `ElementService.createDragClone(...)` comment says it runs handlers “until one handles it”, but implementation loops all definitions:

```ts
let didHandle = false;
for (const definition of definitions) {
  const result = definition.createDragClone?.(args);
  if (result !== undefined) {
    didHandle = Boolean(result) || didHandle;
  }
}
return didHandle;
```

- For clone-drag, handlers are side-effectful. Continuing after one returns `true` can duplicate clone setup.

Expected behavior:
- Alt/clone-drag one widget creates exactly one new widget.
- It should not depend on how many actor/widget definitions are registered.
- The cloned element should preserve the source widget kind and reset per-instance data as intended.
- Non-widget clone behavior should not regress.

## Plan

1. Reproduce/confirm with multiple registered widgets.
   - Register or load at least 3 widget definitions.
   - Alt-drag one widget.
   - Confirm 3 preview/final cloned elements are created.

2. Fix widget node matching.
   - In `WidgetManagerService.registerWidget(...)`, change `matchesNode` to check `ELEMENT_DATA_ATTR.kind === wConfig.id` in addition to type.
   - Keep `widget` and `ui-widget` supported.
   - Consider a safe local type guard or inline check.

3. Fix clone dispatch semantics.
   - Update `ElementService.createDragClone(...)` to return immediately when a definition returns `true`.
   - Preserve `false` behavior for non-handling definitions.
   - This should align implementation with the existing “until one handles it” comment.

4. Audit adjacent lifecycle dispatches.
   - `attachListeners`, `updateElement`, `getTransformOptions`, and `toElement` intentionally aggregate or layer definitions.
   - Only clone-drag startup appears side-effectful and should short-circuit.
   - Verify no existing multi-definition clone behavior depends on running more than one handler.

5. Add regression coverage if practical.
   - Prefer a service/unit test around `ElementService.createDragClone(...)` short-circuiting.
   - Add or adjust widget matching test if there is existing test harness for widget definitions.
   - At minimum, manually verify in canvas.

6. Verify behavior.
   - One registered widget kind: alt-drag creates 1 copy.
   - Multiple registered widget kinds: alt-drag creates 1 copy.
   - Dragging shape/image clone still creates 1 copy.
   - Normal widget move still persists x/y once.
   - Widget DOM portal cleanup/recreation still works after clone/undo/redo.

## NOTES

- Main bug is probably not in `Widget.plugin.ts` itself; that file exposes the issue because it registers multiple actor-backed widgets.
- The number of copies likely equals the number of widget definitions whose broad `matchesNode` returns true.
- The observed “3 new copies” suggests 3 widget definitions were registered in that runtime.
- `txCreateWidgetCloneDrag(...)` itself appears to create one preview/final clone per invocation; duplication comes from multiple invocations.
- Proposed `matchesNode` fix:

```ts
matchesNode: (node) => {
  const data = node.getAttr(ELEMENT_DATA_ATTR);
  return (data?.type === "widget" || data?.type === "ui-widget") && data.kind === wConfig.id;
},
```

- Proposed `createDragClone` fix:

```ts
for (const definition of definitions) {
  const result = definition.createDragClone?.(args);
  if (result === true) {
    return true;
  }
}
return false;
```
