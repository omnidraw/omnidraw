# B49 - AI chat: reconnect race drops approval session scope
[Overview](../BASED.md)

Overlapping AI chat connections can temporarily remove the active session while the UI lists approvals. The request then fails with `No connected agent session`, and an ordinary duplicate reconnect can also cancel pending approvals.

## Context

The observed failure originates in [`AgentService.listChatApprovals`](../../packages/service-agent/src/AgentService.ts), which calls `#assertChatScope`. That guard requires both of these process-local records to agree:

- `#chatWidgetIds.get(sessionId) === widgetId`
- `sessionMap[widgetId][sessionId]` contains a live agent session

The guard is correct: approval reads and resolutions must never cross widget/session ownership. The error means an approval-list request arrived outside the lifetime of that exact connected session; it does not mean approval data itself failed to parse or persist.

The race is created by the current reconnect lifecycle:

1. `AgentService.connectChat` sees that the same session ID is already associated with the widget.
2. It calls `#disposeAgentSession`, which removes `sessionMap[widgetId][sessionId]`, removes the session-to-widget mapping, unsubscribes the old runtime, and cancels the chat's pending approvals.
3. `connectChat` restores the mapping, then awaits workspace, transcript, and Pi session setup before installing the replacement `sessionMap` entry.
4. An approval `list`, `get`, or `resolve` request during that gap fails `#assertChatScope`.

Overlapping connections make the window observable. In [`AiChat`](../../packages/canvas/src/components/AiChat/index.tsx), the connect completion check compares only the current session ID and `chatConnectNonce`. Two requests for the same session and nonce can both look current. An older completion may therefore call `approval.list` while a newer connection has disposed the session and is still rebuilding it. Multiple mounted chat surfaces reusing one session ID can produce the same ownership conflict. The repeated CLI stack trace indicates that more than one approval-list request reached this window.

This has user-visible consequences beyond noisy logs:

- pending approvals may be canceled by a duplicate UI reconnect
- approval cards can disappear or fail to load
- concurrent connection completions can overwrite the active `sessionMap` entry
- stale callbacks can operate against a newer connection generation

## Fixed decisions

### Connection ownership

- Serialize connection lifecycle changes per `sessionId`; two connects must not dispose, create, or publish the same session concurrently.
- Give every connection attempt a generation/token and allow only the current generation to commit `#chatWidgetIds`, `sessionMap`, subscriptions, or UI state.
- Treat an ordinary repeated connect for the same widget/session as idempotent reuse. It must not destroy the live runtime or cancel approvals.
- Make intentional runtime replacement explicit in the connect contract, for example a typed reconnect/refresh mode used after credential or model-setting changes.
- An explicit replacement, widget ownership change, new-chat action, service shutdown, or real disconnect may cancel approvals belonging to the retired runtime. That cancellation must remain deliberate and observable.
- If a superseded connection finishes setup, dispose only the session entry it created; it must never remove or overwrite the newer generation.

### Frontend freshness

- Allocate a unique request token for every `chat.connect` invocation, including calls with the same session ID and settings nonce.
- Only the latest exact request may install message history, mark the chat connected, or call `approval.list`.
- Invalidate pending approval refreshes when a newer connection begins, not only when the session ID changes.
- Keep event-stream filtering by widget/session, but do not use it as a substitute for connection-attempt freshness.

### Approval behavior

- Keep `#assertChatScope` strict. Returning an empty approval list for an ownership mismatch would hide the race and could mask incorrect widget/session routing.
- Expose a stable session-not-connected error code if stale requests remain possible at transport boundaries, so the frontend can ignore an expected superseded request without logging an unhandled stack trace.
- Do not persist approval secrets or broaden the existing process-local approval trust model.

## Plan

### 1. Reproduce the causal race

- Delay replacement session creation after the old session is disposed.
- Start two connects for the same widget/session and issue `approval.list` between their completions.
- Assert the current implementation exposes the missing-session window and cancels a pending approval.
- Reproduce a stale frontend connect completion that refreshes approvals after a newer connect has started.

### 2. Make backend connection transitions linearizable

- Add a per-session connection lane and generation ownership in `AgentService`.
- Separate idempotent connection reuse from explicit runtime replacement.
- Build a replacement session before publishing it where possible, then atomically swap the process-local ownership records.
- Ensure cleanup is generation-scoped and cannot delete a newer connection.
- Preserve pending approvals during idempotent reuse; cancel them only when the owning runtime is intentionally retired.

### 3. Pin frontend work to one connection attempt

- Replace the session/nonce-only stale-response test with an exact request-generation check.
- Start approval loading only from the latest committed connection response.
- Suppress expected stale-generation failures while continuing to surface genuine connection and authorization errors.

### 4. Add lifecycle regressions

- Cover duplicate same-scope connect reuse without approval cancellation.
- Cover explicit reconnect replacement and deterministic old-runtime cleanup.
- Cover overlapping connects where only the newest generation commits.
- Cover one session ID changing widget ownership without cross-widget approval access.
- Cover new-chat and shutdown cancellation behavior.
- Cover the frontend stale-completion sequence and assert only one valid approval refresh occurs.

## NOTES

- Category: bug.
- Suggested priority: P2. The bug does not appear to bypass approval authorization, but it can cancel legitimate pending approvals and make chat state unreliable.
- The two conditions inside `#assertChatScope` currently share one error message. Tests should determine which record was missing without weakening the public error surface.
- `ApprovalCoordinator` is intentionally process-local. This task fixes ownership and timing; it does not make approvals durable across a service restart.
- Do not fix this only by returning `[]` from `approval.list`. That would silence the symptom while leaving session overwrites and approval cancellation intact.
