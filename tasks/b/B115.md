# B115 - ci: align SDK tests with the normalized 0.7.0 release marker

[Overview](../BASED.md)

The public-package normalization changed `@omnidraw/sdk` to `0.7.0` but left
two SDK test fixtures pinned to `0.13.0`. Align the stale test metadata so final
architecture acceptance validates the qualified and published package set.

## Context

[GitHub Actions run 32346794757](https://github.com/omnidraw/vibecanvas/actions/runs/32346794757)
fails only in the SDK package-boundary test after public builds, typechecks, and
the other workspace tests pass. The failing assertion in
[`package-boundaries.test.ts`](../../packages/sdk/tests/package-boundaries.test.ts)
expects `0.13.0`, while [`package.json`](../../packages/sdk/package.json) and
[`public-package-set.json`](../../public-package-set.json) qualify the SDK as
`0.7.0`.

Commit `71edeb6245a8ddd305e71c3eaf3eea56c4bd6a85` intentionally normalized the
SDK manifest, package set, lockfile, consumer fixtures, and backend source-check
expectation to `0.7.0`, but did not update the package-boundary assertion or the
dependency metadata in
[`portable-build.test.ts`](../../packages/sdk/tests/portable-build.test.ts).
That commit's own workflow run failed with the same expected `0.13.0`, received
`0.7.0` mismatch. The later sidebar-only commit merely inherited the failure.

The `0.7.0` marker is authoritative: it is consistent across the release
metadata and was published on npm under the `omnidraw-workspace` tag before the
investigated run. Reverting the manifest or package set to `0.13.0` would undo
the release normalization and is outside this repair.

## Plan

1. Change the SDK package-boundary version assertion from `0.13.0` to `0.7.0`
   without weakening its exact release-marker check.
2. Change the portable-build fixture dependency metadata to the same `0.7.0`
   marker so the external-project fixture describes the package it symlinks.
3. Confirm no other SDK test fixture retains the obsolete `0.13.0` package
   version, while leaving unrelated Capsule `0.13.0` history and documentation
   untouched.
4. Rebuild the SDK, run the focused SDK tests, and run final architecture
   acceptance to prove the workflow advances beyond the original failure.

  not changed by this test-only repair.

  actionable failure after the original version mismatch is resolved.

  32346794757 is not evidence of a sidebar regression.
