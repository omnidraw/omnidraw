# B32 - binary: bundle Turso native addon beside compiled executable
[Overview](../BASED.md)

Make the compiled Vibecanvas binary load Turso by shipping the platform `.node` addon beside the executable and bypassing the package loader that fails under `/$bunfs/root/main.js`.

## Context

CI fails in the binary test because the compiled Bun executable cannot load `@tursodatabase/database`'s optional native package from inside Bun's embedded filesystem. The failure happens before the server starts, when `DbServiceTurso` imports and constructs Turso.

Relevant files:

- [.github/workflows/test.yml](../../.github/workflows/test.yml)
- [scripts/build.ts](../../scripts/build.ts)
- [scripts/test-binary.ts](../../scripts/test-binary.ts)
- [apps/cli/src/setup-services.ts](../../apps/cli/src/setup-services.ts)
- [packages/service-db/src/DbServiceTurso/DbServiceTurso.ts](../../packages/service-db/src/DbServiceTurso/DbServiceTurso.ts)

Minimal working proof lives at `/tmp/turso-compiled-bun-demo`.

Important packaging constraint: this does not bundle Turso inside the single Bun executable. Native Node-API `.node` addons are real dynamic libraries, so a naked-system install must include both the compiled `vibecanvas` executable and the matching Turso sidecar file.

Expected release/package shape:

```txt
dist/vibecanvas-linux-x64/
  bin/vibecanvas
  native/turso.linux-x64-gnu.node
```

The runtime loader should resolve the sidecar relative to the executable/package location, not from `node_modules`.

The proof uses this shape:

- copy the platform Turso native addon into `native/`
- compile the Bun app
- copy `native/` beside the compiled executable
- compute the native addon path from `dirname(process.execPath)` in compiled mode
- load the addon with `createRequire(import.meta.url)(absoluteNativeAddonPath)`
- wrap native `Database` with `DatabasePromise` from `@tursodatabase/database-common`

`NAPI_RS_NATIVE_LIBRARY_PATH` is not enough for `@tursodatabase/database@0.6.0` because its generated loader assigns `nativeBinding = require(path)` without returning it, then overwrites the value with `undefined`. Importing the `.node` file with `with { type: "file" }` also fails because Bun requires Node-API modules to be loaded with `require()` or `process.dlopen()`.

## Plan

1. Add a small local Turso native loader module for compiled builds.
2. Keep the existing `@tursodatabase/database` path for normal Bun/dev/test runs.
3. During `scripts/build.ts`, copy the correct platform native addon into each `dist/vibecanvas-*/native/` package.
4. Ensure package archives and npm platform packages include the `native/` folder.
5. Extend binary tests to fail fast with a useful native-addon error if the file is missing.
6. Verify install paths on a naked system where repo `node_modules` does not exist.

## NOTES

- Proof output showed both source and compiled runs creating/querying Turso-backed SQLite files successfully.
- The working demo intentionally does not rely on `@tursodatabase/database`'s generated `index.js` loader.
- The final deployable unit is not a single-file binary; it is a small directory/package containing the executable plus the platform-native Turso `.node` sidecar.
- Linux artifacts must match libc/architecture, for example `turso.linux-x64-gnu.node` for glibc x64 and a separate musl build if we support musl targets.
