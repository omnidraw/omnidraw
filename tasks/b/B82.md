# B82 - ci: Linux Turso preflight changes `.tshm` mtime despite unchanged database bytes
[Overview](../BASED.md)

Final architecture acceptance fails on Linux because the database recovery
tests treat an expected Turso shared-WAL coordination timestamp update as a
durable database mutation.

## Context

[GitHub Actions run 31303578353](https://github.com/omnidraw/vibecanvas/actions/runs/31303578353)
fails in `bun run test:final-acceptance` during the `database recovery` suite.
Two cases in
`packages/service-db/src/verification/baseline-recovery.test.ts` fail:

- rejecting an old or unknown schema fingerprint;
- rejecting a weakened custom domain.

Both failures come from `expectRejectedWithoutMutation`. `snapshotTree`
records `mtimeMs` for every database-home entry, then compares the full tree
before and after read-only preflight. On the Linux runner, only
`main.db-tshm.mtimeMs` differs. Its path, type, mode, size, and SHA-256 digest
remain identical; `main.db` and `main.db-wal` are also unchanged.

`preflightDbServiceDatabase` correctly opens Turso 0.7.2 with
`readonly: true`, `fileMustExist: true`, and `multiprocess_wal`. Turso uses
`.tshm` as mmap-backed shared WAL coordination and registers reader slots
during reads. Linux records that coordination activity as a sidecar mtime
change even after the reader slot returns to its original bytes. The same
targeted test passes on macOS, so the existing assertion is platform-sensitive.

The current Capsule lockfile change did not introduce the failure. The same
two tests have failed in Linux CI since the snapshot assertion was introduced
in commit `a04fb57b` on 2026-08-04.

Relevant files:

- `packages/service-db/src/verification/baseline-recovery.test.ts`
- `packages/service-db/src/DbServiceTurso/DbServiceTurso.ts`
- `scripts/test-final-acceptance.ts`
- `package.json` (`db:recovery:test`)

## Plan

### 1. Model durable mutation accurately

Update the recovery-test snapshot comparison so an mtime-only change to a
`*-tshm` coordination sidecar is allowed. Continue comparing the sidecar's
existence, file kind, mode, size, and SHA-256 digest, and keep the existing
strict comparison for the database, WAL, and other home entries.

Rename assertion wording such as "without touching" when necessary so the
test promises no durable content or layout mutation rather than no operating
system metadata activity.

### 2. Preserve the production coordination mode

Keep `readonly: true` and `multiprocess_wal` in database preflight. Do not
disable multi-process WAL to satisfy the test: `.tshm` participation is needed
for a reader to observe and coordinate with the authoritative WAL state.

If the product requirement is instead literal zero metadata changes, stop and
redesign preflight around a safe database snapshot or an upstream Turso
non-registering inspection API; silently mixing single-process and
multi-process modes is not an acceptable shortcut.

### 3. Verify on both platform paths

Run the targeted recovery suite and final architecture acceptance locally,
then verify the Linux GitHub Actions job. Confirm the original rejection
messages still match and deliberate database, WAL, or `.tshm` byte changes
still fail the snapshot assertion.

## NOTES

- This should be a test-only correction. Per published-package policy, it does
  not require a package version bump.
- Turso's `.tshm` sidecar is writable shared coordination even when the
  database connection is logically read-only; `readonly` protects database
  contents, not coordination metadata.
- Prefer a path-specific timestamp exception over disabling all mtime checks.
