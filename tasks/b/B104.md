# B104 - AI Chat: resolved automatic approvals render as pending prompts
[Overview](../BASED.md)

Automatic protected operations execute correctly, but the frontend projects
their resolved events as new pending requests. Remove the phantom approval
buttons, preserve canonical lifecycle status, and show one actionable surface
per genuinely manual request.

## Context

The reported state is internally contradictory: the approval card says
`Decision: policy`, proving the backend already selected and executed the
automatic path, while the same card is labeled `PENDING` and still offers
**Reject** and **Approve**.

![Automatic policy decision incorrectly rendered as two pending prompts](B104.webp)

The backend contract and publisher use the lifecycle field `type` with
`created`, `resolved`, or `canceled`:

- [`contract.ts`](../../apps/backend/src/shell/api/agent/contract.ts) validates
  `type` on approval events.
- [`AgentService.ts`](../../apps/backend/src/shell/agent/AgentService.ts)
  publishes the coordinator's exact lifecycle event.
- [`ApprovalCoordinator.ts`](../../apps/backend/src/shell/agent/approval/ApprovalCoordinator.ts)
  emits no `created` event for `always-approve`; it emits the terminal event
  with `decisionSource: policy` after guarded execution.

The private frontend adapter in
[`adapters.ts`](../../apps/frontend/src/shell/chat/adapters.ts) instead reads an
`action` field and defaults every event to `created`. The public component then
correctly renders that mistranslated event as pending in
[`index.tsx`](../../packages/component-ai-chat/src/chat/components/index.tsx).
The chat view also renders the same pending approval both beside its matching
tool call and in the floating approval rail, making one request look like two.

The observed database write completed automatically in under one second. The
earlier tool error in that transcript was SQLite statement validation and was
not an approval failure.

## Plan

### 1. Preserve canonical event lifecycle

- Normalize approval lifecycle from the backend's canonical `type` field.
- Do not add or retain a compatibility event shape unless a current producer
  is identified and covered by a contract test.
- Preserve decision, decision source, reviewer reason, and cancellation reason.

### 2. Render only genuine pending work as actionable

- A policy-approved event must enter the executed state without ever exposing
  manual action buttons.
- Reviewer-approved, reviewer-rejected, canceled, failed, and user-resolved
  events must retain their terminal state.
- Render one actionable card for one manual approval. Prefer the inline card
  when its tool-call row exists; use the floating rail only when the pending
  approval has no matching visible tool call.

### 3. Add regressions at the application boundary

- Cover canonical `created`, `resolved`, and `canceled` event translation in
  the frontend adapter.
- Cover an automatic `resolved/approve/policy` event reaching the component as
  executed with no Reject or Approve button.
- Cover a manual created event and prove it is not duplicated between inline
  and floating surfaces.
- Run focused frontend, component AI Chat, and backend approval tests.

## Acceptance criteria

- `always-approve` executes through the guarded backend path without showing
  Reject or Approve at any point.
- The UI never labels an event with `decisionSource: policy` as pending.
- Created manual approvals remain actionable.
- Resolved, canceled, rejected, failed, and stale approvals remain terminal.
- One manual approval is displayed once, not both inline and floating.
- Frontend tests fail if approval lifecycle translation reads the wrong field.
