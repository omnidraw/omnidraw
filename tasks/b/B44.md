# B44 - ai wizard: preview loses mentioned resource after continuation prompt
[Overview](../BASED.md)

An AI-generated database widget enters the actor error state in Preview after a normal mentionless continuation such as `yes continue`. The generated SQL succeeds against the selected database; the host silently replaced the draft's resource binding intent with an empty prompt selection, started Preview despite the invalid binding plan, and reduced the resulting plain error to `Actor resource call failed.`

## Context

### Observed reproduction

On 2026-07-13 the user created `Manual QA Data Viewer` with this conversation:

1. `create an example widget to render data from @Manual QA Database i just want to see if it works`
2. The Wizard inspected the selected database, created and approved an actor candidate, and scaffolded the draft.
3. The user replied `yes continue` without repeating the mention.
4. The AI implemented the actor and widget and `vc_validate_widget_files` reported the files as valid.
5. Preview started but displayed:

```text
Preview: error
Actor resource call failed.
Could not load the database.
```

The relevant generated manifest declared one required read-only DB slot and one named operation:

```json
{
  "database": {
    "kind": "db",
    "required": true,
    "scope": ["read"],
    "arbitrarySql": false,
    "operations": {
      "listQaRows": {
        "effect": "read",
        "sql": "SELECT id, title FROM qa_rows ORDER BY id",
        "result": "rows"
      }
    }
  }
}
```

The actor called it from `fx.loadRows`:

```ts
await portal.resources.db("database").invoke("listQaRows", {})
```

The exact SQL was executed independently through a read-only connection against `Manual QA Database`; it returned rows successfully and `qa_rows` contained 250 rows. Do not fix this by changing the SQL, table, result mapping, or database contents.

### Confirmed failure chain

The persisted Pi session contained two resource-selection records:

```text
09:03:28 resources=[Manual QA Database]
09:08:05 resources=[]
09:08:05 user="yes continue"
```

[ChatTab.tsx](../../packages/canvas/src/components/AiWizzard/tabs/ChatTab.tsx) always sends `resourceIds: submit.mentions.map(...)`, including an empty array for a message without mentions.

[AgentService.promptWizzard](../../packages/service-agent/src/AgentService.ts) appends a new `vibecanvas.widgetResourceSelection` record whenever `resourceIds` is defined. The empty array therefore replaces the previous selected database.

Preview and publish both consult the latest selection record. Because the host had multiple ready DB resources, [planImplicitResourceSelections](../../packages/service-agent/src/tools/resource-bindings.ts) correctly refused to guess which database should fill the required slot.

[AgentService.startDraftActorWizzard](../../packages/service-agent/src/AgentService.ts) then mishandled that expected planning failure:

1. It converted the failed binding plan into an empty `directBindings` map.
2. It still created and started the draft actor.
3. The actor's first DB call threw a plain `Error(bindingPlan.message)`.
4. [toSafeActorResourceError](../../packages/service-actor/src/resources/ActorResourceError.ts) mapped the non-`ActorResourceError` to the generic `RESOURCE_PROVIDER_UNAVAILABLE / Actor resource call failed.` response.

This is why the UI showed a runtime actor error instead of an actionable binding error before Preview started.

### Contract conflict to resolve deliberately

[llm.widget-system.md](../../docs/internal/llm.widget-system.md) currently says resource selection is latest-prompt scoped and that a prompt without mentions revokes explicit selection authority. That single selection concept is being used for two different purposes:

1. **Draft binding intent** — which concrete resources Preview and Publish should bind to manifest slots over the lifetime of the draft.
2. **Prompt-local AI authority** — which resources the model may treat as explicitly selected for sensitive tools such as `vc_propose_db_change` in the current prompt.

An ordinary implementation continuation must not erase draft binding intent. At the same time, preserving a Preview binding must not accidentally broaden prompt-local authority for AI-proposed database changes.

The fix must represent these lifetimes separately. One acceptable design is:

- keep an always-appended prompt-local selection record, including empty selections;
- keep a separate draft binding-selection record that changes only when a prompt includes mentions or the user performs an explicit clear/rebind action;
- make `vc_propose_db_change` and other prompt-authority checks use the prompt-local record;
- make Preview and Publish use the persistent draft binding record;
- make a new non-empty mention replace the corresponding draft binding intent deterministically;
- never infer a resource when multiple compatible resources exist.

Equivalent designs are acceptable if they preserve the same security and lifecycle boundaries. Do not merely stop writing empty records if that causes sensitive AI tools to keep treating an old mention as authorization in later prompts.

### Secondary validation defects discovered

These did not cause the observed Preview error, but they made the AI's `Widget draft files are valid` claim unreliable:

- The generated actor used `TFxArgs & { data: TData }`; the supported typed form is `TFxArgs<TData>`. The generated form produces TypeScript spread errors.
- The scaffold installed registry `@vibecanvas/sdk@0.1.0`, whose `dist/actor.d.ts` does not expose `portal.resources`, while the current workspace SDK does.
- [tx.validate-widget-files.ts](../../packages/service-agent/src/core/tx.validate-widget-files.ts) validates the manifest, required paths, and registry text but does not compile actor/widget TypeScript.

Do not mistake these compile-time defects for the resource-binding regression. They should be corrected or split into a separately linked task, but the root regression test below must fail because the Preview binding is lost, not because TypeScript compilation fails.

## Expected behavior

- Mentioning `Manual QA Database` establishes the concrete DB binding intent for the current Wizard draft.
- A routine follow-up such as `yes continue` does not remove that draft binding.
- Preview starts with an ephemeral direct binding to the mentioned database and the on-enter named operation succeeds.
- Publish persists the same intended definition binding unless the user explicitly replaces or clears it.
- A prompt without a mention may still revoke prompt-local authority for sensitive AI tools.
- A new explicit DB mention replaces the prior DB draft binding when the manifest has one compatible DB slot.
- If a required slot cannot be planned, Preview returns `ready: false` with an actionable binding reason and does not start an actor child.
- Missing or ambiguous bindings never degrade into the generic `Actor resource call failed.` message.
- Multiple compatible resources are never selected implicitly.

## Plan

### 1. Separate prompt selection from draft binding intent

- Define and persist distinct session data for prompt-local selection and draft binding selection.
- Give each record a clear custom-entry type and typed schema.
- Migrate all readers intentionally:
  - `vc_list_resources` selection markers;
  - `vc_inspect_resource` authorization if applicable;
  - `vc_propose_db_change` prompt-local checks;
  - Preview binding planning;
  - Publish binding planning.
- Decide how the UI explicitly clears a draft binding. Do not overload an ordinary no-mention prompt as an invisible clear action.
- Preserve deterministic same-kind slot mapping and refusal to guess.

### 2. Make Preview binding planning fail before actor startup

- If `#wizzardResourceBindingPlan` returns `ok: false`, return a not-ready draft actor result immediately.
- Add a stable reason such as `resource-binding-invalid` and preserve the actionable planner message.
- Do not create an actor, spawn the actor child, publish a ready snapshot, or install a gateway with an empty binding map.
- If a resource call somehow targets an unavailable direct binding after startup, throw a typed `ActorResourceError` with a specific safe code/message rather than a plain `Error`.
- Ensure the Preview UI renders the not-ready reason without also presenting a misleading widget-runtime error state.

### 3. Preserve Publish semantics

- Make `vc_publish_widget` consume the same persistent draft binding intent as Preview.
- Verify Preview and Publish cannot silently choose different resources for the same unchanged manifest/session.
- Preserve definition-level binding scope as the manifest scope and never exceed it.

### 4. Add the causal regression test first

Add an integration-style test in [draft-actor.test.ts](../../packages/service-agent/tests/draft-actor.test.ts) that reproduces the observed order exactly:

1. Provide two ready DB resources: `QA Database` and `Manual QA Database`.
2. Create a draft manifest with one required read-only DB slot named `database` and a named `listQaRows` operation.
3. Record an explicit mention of `Manual QA Database`.
4. Process a second user prompt, `yes continue`, with no mentions.
5. Start Preview.
6. Let an `onEnter` actor function invoke the named DB operation through the normal draft actor resource gateway.
7. Assert `callWithDirectResourceBinding` receives the `Manual QA Database` resource ID, the `database` requirement, and read-only scope.
8. Return representative rows containing SQLite `bigint` IDs and assert the actor reaches a loaded snapshot instead of `error`.

The test must fail on the current implementation because the second prompt clears the selection and the host has multiple DBs. It must not bypass `AgentService`, call the binding planner directly, use only one available DB, or manually inject a direct binding after Preview starts.

### 5. Add boundary regressions

- Add a prompt-Wizard test proving an empty prompt-local selection still prevents `vc_propose_db_change` from using an earlier mention.
- Add a test proving the persistent draft binding remains available to Preview/Publish after that same prompt-local revocation.
- Add a test proving a new explicit mention switches the persistent DB binding.
- Add a test proving an explicit clear action removes draft binding intent.
- Add a fail-fast Preview test with two DBs and no draft binding: `ready: false`, actionable reason, no actor running, and no resource gateway call.
- Add a publish test proving the post-continuation definition binding targets `Manual QA Database`.
- Add or extend [ChatTab.render.test.ts](../../packages/canvas/tests/components/AiWizzard/tabs/ChatTab.render.test.ts) to verify the composer/API payload semantics for mentioned, mentionless, and explicit-clear submissions.
- Keep the existing security regression that rejects DB-change proposals without a resource selected in the current prompt.

### 6. Harden generated-code validation

- Ensure newly scaffolded drafts resolve an SDK declaration/runtime pair that includes actor resources.
- Add a resource-using scaffold fixture that typechecks `portal.resources.db(...).invoke(...)` and uses `TFxArgs<TData>` or the canonical equivalent.
- Either make `vc_validate_widget_files` run a bounded TypeScript validation or change its result/UI wording so it does not claim source validity without compilation.
- Keep this validation test separate from the causal Preview-binding regression so failures identify the correct layer.

### 7. Update documentation

- Update [llm.widget-system.md](../../docs/internal/llm.widget-system.md) with the separate prompt-authority and draft-binding lifetimes.
- Document explicit replace/clear behavior.
- Document that Preview refuses to start when required resource planning fails.
- Keep the distinction between ephemeral Preview bindings and persisted Publish bindings.

## Acceptance criteria

- The causal integration test fails before the fix and passes afterward.
- Repeating the original conversation without repeating the mention loads `qa_rows` in Preview.
- The captured direct binding uses the originally mentioned `Manual QA Database`, never the other ready DB.
- The prompt-local DB-change tool remains unauthorized after a no-mention continuation.
- Preview with genuinely missing/ambiguous binding intent does not start an actor and shows an actionable message.
- Publish after a continuation persists the intended database binding.
- Generated resource actor code is checked against the same SDK contract the runtime provides.
- The generic `Actor resource call failed.` message is absent from the binding-planning failure path.
- No test passes merely because the fixture exposes only one ready database.

## NOTES

- Category: bug.
- Primary ownership: host/Wizard selection lifecycle and Preview admission.
- The generated SQL and live database were verified independently; they are not the root cause.
- The generated guest has separate typing defects, but changing guest row conversion or error UI cannot repair the missing host binding.
- Current documentation accurately describes the implemented latest-prompt behavior, but that behavior conflates two authority lifetimes and must change with the implementation.
- Human approval for exact AI-proposed DB mutations remains a separate gate and must not be weakened by this fix.
- Preview bindings remain ephemeral; Publish bindings remain definition-level and persisted.
