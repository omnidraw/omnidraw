# B54 - widget publish: successful publication leaves the draft behind
[Overview](../BASED.md)

Consume a widget draft only after publication commits successfully, then leave one published catalog entry and no stale draft route, mount, or Preview lifecycle.

## Context

The reported screen shows a successful **Widget published** notification while the selected `blobby` draft remains beside the new published row. This is not only a missed frontend refresh.

Investigation found the persistence cause:

- [`packages/service-agent/src/workspace/WidgetWorkspace.ts`](../../packages/service-agent/src/workspace/WidgetWorkspace.ts) implements `beginDraftPublish` by copying the draft into the canonical published directory. Its `commit()` removes publication backups but deliberately never removes `draftRoot/<name>` or chat mounts that point to it.
- That retention was an explicit S83 decision, but it no longer matches the desired product lifecycle: successful Publish should consume the draft; editing the published widget again should require **Edit as draft**.
- [`packages/service-agent/src/core/tx.publish-widget-draft.ts`](../../packages/service-agent/src/core/tx.publish-widget-draft.ts) normalizes and rewrites `vibecanvas.json` in the canonical copy, not in the retained draft. The backend therefore commonly reports the two trees as `different`, so [`packages/ai-chat/src/sidebar/widgets/fn.widget-catalog.ts`](../../packages/ai-chat/src/sidebar/widgets/fn.widget-catalog.ts) correctly renders both rows. Hiding the row in the browser would only mask the retained draft and is not a valid fix.
- [`packages/ai-chat/src/sidebar/widgets/WidgetDetailPage.tsx`](../../packages/ai-chat/src/sidebar/widgets/WidgetDetailPage.tsx) remains on the draft route and reloads draft detail after success. Once the backend consumes drafts, this flow must navigate to published detail instead.
- The screenshot also exposes a related publication-staging leak: an installed `.publish-backup-*` directory sits below the actor discovery root while definitions reload, so [`packages/service-actor/src/ActorSupervisor.ts`](../../packages/service-actor/src/ActorSupervisor.ts) temporarily discovers it and emits an **Ignored duplicate actor definition** warning for the widget being published. The unrelated `sdk-test` duplicate shown in the capture is a separate existing definition conflict.

## Plan

![Successful publication leaves a duplicate draft row and exposes a transient backup manifest](B54.webp)

### 1. Lock the intended lifecycle with regression tests

- Reproduce first publication from a draft and republishing an edited published widget.
- Assert that a successful commit leaves the canonical and installed published trees, removes the managed draft tree, removes all chat workspace symlinks to that draft, and returns no draft from draft/detail/catalog APIs.
- Assert that validation, stale-revision, permission, publication, instance-reload, binding, and recovery failures preserve the exact draft and its chat mounts so the user can repair and retry.
- Assert that rollback restores the previous published/installed version for republish failures without consuming the draft.
- Capture the current `different` relation after manifest normalization to prove why frontend-only filtering is insufficient.

### 2. Make draft consumption part of publication commit

- Extend the `WidgetWorkspace` publication transaction so draft cleanup occurs only after validation, canonical/installed publication, binding replacement, definition reload, and instance transition have succeeded.
- Preserve an exact recoverable draft until the transaction is authoritative; do not delete mutable source early or rebuild a failed draft from the normalized published copy.
- On commit, remove the draft directory and every owned chat mount targeting it. Never remove unrelated files or non-owned symlinks.
- Keep commit/rollback idempotent and release publish locks on every path.
- Make cleanup failure explicit: do not report `published: true` while a managed draft remains. Either complete cleanup or compensate publication and return the existing typed failure/recovery result.

### 3. Close draft-only runtime state

- Coordinate publication with `WidgetDraftController` Preview ownership so active Preview actors/snapshots for the consumed draft are closed before final draft removal.
- Ensure late Preview requests/events cannot recreate state or turn a successful publication into an unhandled error.
- Define persisted Preview-frame behavior after publication: it must not continue pretending an editable draft exists. Remove/close it through the host flow where available, or show a stable published/closed state until the frame is removed.
- After publication, a new edit cycle starts only through `widgets.ensureDraft` / **Edit as draft**, producing a fresh draft copied from the current published source.

### 4. Reconcile frontend state and navigation

- On successful publication from draft detail, refresh authoritative catalog state and replace the draft URL with `/widgets/published/<name>` instead of reloading the now-deleted draft route.
- Ensure sidebar selection moves to the single published row and the draft badge/row disappears without a full page reload.
- Apply the same success reconciliation to the Preview title-bar publication flow planned in [S99](../s/S99.md).
- Keep failure on the draft surface with diagnostics and editable source intact.
- Treat events as invalidation only; do not optimistically hide the draft before backend commit succeeds.

### 5. Keep publication backups out of actor discovery

- Move installed rollback backups outside the recursively scanned widget-definition tree while retaining same-filesystem recovery where required.
- Add a defensive actor-discovery exclusion for known publication/reconcile transient directories so a reload cannot treat staging manifests as definitions.
- Verify publishing no longer emits a duplicate-definition warning referring to `.publish-*` or `.publish-backup-*`.
- Preserve legitimate duplicate-definition diagnostics such as the unrelated canonical-versus-`sdk-test` warning in the supplied screen.

### 6. Verify end to end

- Cover first publish and republish from draft detail, and Preview publication once S99 lands.
- Cover multiple chats mounted to the same shared draft, active and persisted Previews, selected sidebar state, and reconnect after publication.
- Verify **Edit as draft** recreates exactly one draft after publication and that a second publish consumes it again.
- Run service-agent workspace/controller/management tests, AI Chat sidebar/detail/Preview tests, service-actor discovery tests, package typechecks, functional-core checks, and the relevant frontend build.

## Acceptance criteria

- After successful Publish, the widget has one published sidebar row and no draft row.
- The backend draft directory, draft API result, draft detail route, and owned chat draft mounts are gone after commit.
- The user lands on the published widget detail page without a reload.
- **Edit as draft** is the only way to start another editable draft from that published widget.
- Any failed publication leaves the draft, mounts, and editable content intact and restores the previous publication when applicable.
- Active or persisted Previews cannot continue claiming the consumed draft is editable/current.
- Publication does not emit duplicate-definition warnings for its own transient staging or backup directories.
- Legitimate duplicate actor definitions remain diagnosable.

## NOTES

- Root cause is an outdated backend lifecycle contract, not stale Solid state: S83 intentionally retained drafts and chat mounts after publication.
- Canonical manifest normalization explains the visible `Source relationship: different` after success; catalog projection is behaving according to its equality contract.
- Draft cleanup must happen after the full coordinated publication succeeds. Deleting before actor/resource/instance transition would destroy the user's recovery source.
- Coordinate implementation order with S99 because both detail and Preview publication entry points need the same post-success lifecycle.
- The supplied 2704×1520 PNG was stored as a 102,000-byte lossless WebP (`B54.webp`) instead of the 477,632-byte source.
