# B54 - widget publish: retain the draft but show it only after edits
[Overview](../BASED.md)

Keep the shared draft and Preview lifecycle after publication, but record the exact clean draft revision so the catalog shows only the published row until the draft is edited again.

## Context

The reported screen shows a successful **Widget published** notification while the selected `blobby` draft remains beside the new published row. This is not only a missed frontend refresh.

Investigation found the persistence cause:

- [`packages/service-agent/src/workspace/WidgetWorkspace.ts`](../../packages/service-agent/src/workspace/WidgetWorkspace.ts) copies the draft into canonical publication while intentionally retaining the shared draft and chat mounts.
- [`packages/service-agent/src/core/tx.publish-widget-draft.ts`](../../packages/service-agent/src/core/tx.publish-widget-draft.ts) normalizes and rewrites `vibecanvas.json` in the canonical copy, not in the retained draft. Raw tree equality therefore commonly reports `different` immediately after success even though the user has made no new edit.
- The catalog needs an authoritative clean-revision baseline: publication records the exact accepted draft revision, `same` hides the draft row, and the next content edit changes the revision to `different` and reveals the row.
- [`packages/ai-chat/src/sidebar/widgets/WidgetDetailPage.tsx`](../../packages/ai-chat/src/sidebar/widgets/WidgetDetailPage.tsx) should navigate to published detail after success while leaving the draft and Preview usable.
- The screenshot also exposes a related publication-staging leak: an installed `.publish-backup-*` directory sits below the actor discovery root while definitions reload, so [`packages/service-actor/src/ActorSupervisor.ts`](../../packages/service-actor/src/ActorSupervisor.ts) temporarily discovers it and emits an **Ignored duplicate actor definition** warning for the widget being published. The unrelated `sdk-test` duplicate shown in the capture is a separate existing definition conflict.

## Plan

![Successful publication leaves a duplicate draft row and exposes a transient backup manifest](B54.webp)

### 1. Lock the intended lifecycle with regression tests

- Reproduce first publication from a draft and republishing an edited published widget.
- Assert that a successful commit leaves canonical and installed publication, the managed draft tree, all owned chat mounts, and active/persisted Preview state.
- Assert that the clean draft is related as `same` and omitted from sidebar projection until its content revision changes.
- Assert that validation, stale-revision, permission, publication, instance-reload, binding, and recovery failures preserve the exact draft and its chat mounts so the user can repair and retry.
- Assert that rollback restores the previous published/installed version for republish failures without consuming the draft.
- Capture that canonical normalization changes raw tree fingerprints while the clean revision still yields relation `same`.

### 2. Persist the clean draft revision on publication commit

- Persist the accepted draft revision only after validation, canonical/installed publication, binding replacement, definition reload, and instance transition succeed.
- Keep the draft directory and all owned chat mounts unchanged.
- Store revision state outside widget source/discovery trees and update it atomically as part of commit.
- Keep commit/rollback idempotent and never advance the clean baseline on failure.

### 3. Preserve Preview runtime state

- Keep active Preview actors/snapshots and persisted Preview frames mounted after publication.
- Refresh the publishing Preview against the retained draft so it does not enter a draft-not-found failure state.
- Keep late Preview requests/events valid because the draft remains the editable source.

### 4. Reconcile frontend state and navigation

- On successful publication from draft detail, refresh authoritative catalog state and replace the URL with `/widgets/published/<name>`.
- Ensure sidebar selection moves to the single published row and the draft badge/row disappears without a full page reload.
- Apply the same invalidation and Preview refresh to the title-bar publication flow from [S99](../s/S99.md).
- Keep failure on the draft surface with diagnostics and editable source intact.
- Treat events as invalidation only; do not optimistically hide the draft before backend commit succeeds.

### 5. Keep publication backups out of actor discovery

- Move installed rollback backups outside the recursively scanned widget-definition tree while retaining same-filesystem recovery where required.
- Add a defensive actor-discovery exclusion for known publication/reconcile transient directories so a reload cannot treat staging manifests as definitions.
- Verify publishing no longer emits a duplicate-definition warning referring to `.publish-*` or `.publish-backup-*`.
- Preserve legitimate duplicate-definition diagnostics such as the unrelated canonical-versus-`sdk-test` warning in the supplied screen.

### 6. Verify end to end

- Cover first publish and republish from draft detail, and Preview publication once S99 lands.
- Cover multiple chats mounted to the same shared draft, active and persisted Previews, selected sidebar state, and reconnect after publication.
- Verify a later edit reveals exactly one draft row and that a second publish marks it clean and hides it again.
- Run service-agent workspace/controller/management tests, AI Chat sidebar/detail/Preview tests, service-actor discovery tests, package typechecks, functional-core checks, and the relevant frontend build.

## Acceptance criteria

- After successful Publish, the widget has one published sidebar row while the clean draft row is hidden.
- The backend draft directory, draft API result, draft detail route, owned chat mounts, and Preview remain available after commit.
- The user lands on the published widget detail page without a reload.
- Editing any draft content changes the relation to `different` and reveals the draft row without requiring a new draft copy.
- Any failed publication leaves the draft, mounts, and editable content intact and restores the previous publication when applicable.
- Active and persisted Previews continue using the retained draft after publication.
- Publication does not emit duplicate-definition warnings for its own transient staging or backup directories.
- Legitimate duplicate actor definitions remain diagnosable.
