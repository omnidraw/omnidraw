# B41 - binary: Turso `UPDATE ... RETURNING` crashes on actor instance with medium HTML state
[Overview](../BASED.md)

Coolify production binary `0.4.2` crashes on restart because actor startup updates persisted actor rows with `UPDATE ... RETURNING *`. Turso native mis-handles that shape when the table has the actor updated-at self-trigger and a later actor row stores medium-sized HTML in JSON state.

## Findings
Production copied DB:
- `UPDATE actor_instances SET status = ? WHERE id = ?` succeeds for all three actor ids.
- `UPDATE actor_instances SET status = ? WHERE id = ? RETURNING ...` crashes for `b5a22f6e-aef9-4001-bd45-736cce138a08`.
- The same `RETURNING` update for `0730c76f-e205-4af0-a1ca-8393c4436325` updates the dashboard row but returns the URL resolver row. That is a data-return correctness bug even when it does not crash.
- `RETURNING rowid` and `RETURNING 1 AS ok` do not crash.
- Dropping `actor_instances_updated_at_after_update` makes the URL resolver `UPDATE ... RETURNING id, actor_definition_name, status, updated_at` succeed.
- Shrinking the URL resolver `machine_context` from 23583 bytes to `{"ok":true}` makes the same `UPDATE ... RETURNING` succeed.

Clean minimal DB:
- No production DB corruption is required.
- A fresh Turso DB with a STRICT `actor_instances` table, an AFTER UPDATE self-trigger, and a later JSON row around 12k-23k bytes reproduces the Turso pager panic.
- With some payload sizes, updating the large row returns the first row instead of the updated row.
- Larger payloads like 30k, 50k, and 100k did not reproduce in the same minimal matrix, so the failure depends on Turso page/overflow layout, not simply "large string bad".

## Likely Cause
This is a Turso native engine bug triggered by the combination of:
- `UPDATE ... RETURNING` on `actor_instances`
- AFTER UPDATE trigger that writes back to `actor_instances.updated_at`
- STRICT table/custom domain setup
- JSON `machine_context` values that create a specific b-tree/overflow-page layout

The application-level trigger is the URL HTML Resolver actor storing fetched HTML in actor state. On server restart, actor-service reloads persisted actors and calls `txActorUpdateInstanceStatus`, which uses `RETURNING *`; Turso then either returns the wrong row or panics in the pager.

## Mitigation Options
Build/runtime mitigation:
- Bump the release CI binary build from Bun `1.3.10` to latest Bun, currently `1.3.14`.
- Specifically update `.github/workflows/release-vibecanvas.yml` jobs that compile/test/publish release artifacts with `bun-version: "1.3.10"`.
- Rebuild the binary and confirm the crash banner no longer reports `Bun v1.3.10`.
- Re-run [B41.repro.sql](/Users/omarezzat/.codex/worktrees/d654/vibecanvas/tasks/b/B41.repro.sql) and the split-statement control under the new Bun-compiled binary/native stack.

Short-term safest app fix:
- Stop using `RETURNING *` on actor instance updates.
- Use plain `UPDATE ... WHERE id = ?`, then a separate `SELECT ... WHERE id = ?` if the updated row is needed.
- This matched the probe: no-returning updates succeeded for all production actor ids.

Additional hardening:
- Replace the self-updating `updated_at` trigger with explicit `updated_at = datetime('now')` in update statements, or avoid returning rows from statements that can fire this trigger.
- Avoid persisting fetched full HTML in actor state; store large HTML in files/media/blob storage and keep actor state as metadata plus reference.
