# B89 - AI Chat: first connection races durable canvas insertion

[Overview](../BASED.md)

A newly placed AI Chat can render optimistically and call `agent.chat.connect`
before its exact canvas item—or, during initial canvas startup, the canvas
snapshot—is durably readable by `CanvasService`. The first connection then
shows a user-facing **Connection** error with `CHAT_SCOPE_INVALID`; pressing
**Try again** works after the canvas command settles.

## Report

Observed during manual testing on 2026-08-11:

```text
CanvasServiceError: Canvas 'd7c1aeaa-f990-45c6-88d5-6b7a7a72f650' was not found.
code: "NOT_FOUND"

error: The AI Chat element is not present on the requested canvas.
code: "CHAT_SCOPE_INVALID"
```

Reproduction:

1. Open a canvas and place a new AI Chat.
2. Observe that the first automatic connection may show **Connection** error.
3. Press **Try again**.
4. The same exact connection succeeds without any user configuration change.

The race is timing-dependent, so a delayed machine or a canvas created shortly
before the AI Chat placement makes it easier to observe.

## Confirmed cause

The canvas intentionally projects local mutations before durable server
acknowledgement:

- `CanvasDocumentService.#performCommitMutation` applies the scene reduction,
  installs a pending transaction, and returns the optimistic projection before
  `#transport.execute(command)` settles.
- The AI Chat canvas extension registers and renders a portal from that
  optimistic node.
- The `AiChat` component immediately runs `agent.chat.connect` from a Solid
  effect.
- Production `chatScope.validate` reads only the durable `CanvasService` item
  and correctly requires the exact ID, widget-frame kind, and AI extension.
- `AgentService.#assertVerifiedChatCanvas` maps a false result to
  `CHAT_SCOPE_INVALID`.

Therefore the browser can display and connect an AI Chat whose durable item is
not visible to the server yet. Retry succeeds only because persistence finishes
in the meantime.

Relevant boundaries:

- `packages/canvas/src/services/CanvasDocumentService.ts`
- `packages/ui-ai-chat/src/canvas-extension/index.ts`
- `packages/ui-ai-chat/src/chat/components/index.tsx`
- `apps/cli/src/setup-services.ts`
- `packages/service-agent/src/AgentService.ts`

## Safety boundary

Do not weaken or bypass `chatScope.validate`. A browser-provided canvas/widget
pair is not authority, and a truly absent, deleted, replaced, wrong-kind, or
non-AI item must still fail closed.

Coordinate readiness at the exact optimistic-to-durable boundary. Preferred
solutions are either:

1. delay the initial Chat connection until the exact insertion command is
   durably acknowledged; or
2. add a narrowly bounded exact-ID readiness wait that is available only for a
   known newly pending AI Chat insertion and is canceled on rejection,
   replacement, deletion, navigation, or shutdown.

Do not add an unconditional retry loop, accept the local projection as durable
authority, or make all `CHAT_SCOPE_INVALID` errors retryable.

## Causal tests

1. Defer the canvas transport acknowledgement after optimistic AI Chat
   projection. The portal may render, but no connection error is shown and the
   first connection succeeds after the exact acknowledgement.
2. Reject the insertion command. The chat never connects under local-only
   identity and normal canvas recovery/error handling remains authoritative.
3. An already durable AI Chat connects immediately without an added delay.
4. A truly missing, deleted, replaced, wrong-kind, or non-AI item still returns
   `CHAT_SCOPE_INVALID` without gaining authority through a generic retry.
5. Navigation, portal disposal, canvas deletion, and shutdown cancel a pending
   readiness wait and cannot connect the stale item afterward.
6. **New chat** on an existing durable AI Chat changes only session identity and
   reconnects without waiting for an unrelated canvas mutation.
7. A newly created canvas plus immediate AI Chat placement passes continuously
   under an intentionally delayed database/canvas transport.

## Acceptance criteria

- A newly placed AI Chat establishes its first connection without requiring
  **Try again**.
- The browser never receives a transient `CHAT_SCOPE_INVALID` merely because
  its exact insertion is still pending.
- Server-side durable canvas scope remains the only connection authority.
- Failed or superseded canvas mutations cannot create an agent session.
- Existing durable chats and explicit reconnects do not gain unnecessary
  latency.

## NOTES

- No mockup is useful. This is a lifecycle/readiness race in an existing error
  state, and the causal sequence is the required evidence.
- Existing UI coverage verifies that a generic first connection failure can be
  retried successfully; it does not coordinate optimistic canvas insertion
  with the initial connection and therefore does not catch this bug.

### LOGS

- 2026-08-11: Fixed the race at the browser's exact durable-readiness seam.
  The portal displays a connecting state while `CanvasDocumentService.item`
  has no accepted row, mounts AI Chat immediately after acceptance, and stops
  waiting if the optimistic node disappears or changes kind. Server-side
  `chatScope.validate` remains unchanged and authoritative. Added readiness
  and full affected-package regression coverage.
