# B36 - actor timeouts only trigger in error state
[Overview](../BASED.md)

Actor manifest timeout transitions such as `timout:1000ms` are only scheduled for the base `error` state, so widgets that enter `waiting.*` states can get stuck forever.

## Context

The Todo List widget defines a temporary celebration state and expects the actor runtime to leave it after one second:

- `local-volume/config/widgets/todo-list/vibecanvas.json`
  - `ready.on["in.celebrate"]` targets `waiting.celebrating`.
  - `waiting.celebrating.on["timout:1000ms"]` targets `ready` via `tx.finishCelebration`.
- `local-volume/config/widgets/todo-list/actor/tx.startCelebration.ts`
  - sets `mood: "celebrating"`.
- `local-volume/config/widgets/todo-list/actor/tx.finishCelebration.ts`
  - sets `mood: "normal"`.
- `local-volume/config/widgets/todo-list/widget/main.ts`
  - disables the Celebrate button unless `actor.state.value === "ready"`.
  - shows celebration UI while state is `waiting.celebrating` or mood is `celebrating`.

Observed behavior:

- The actor reaches `waiting.celebrating` and stays there.
- The timeout transition does not fire.
- On reload/server restart, if persisted state is `waiting.celebrating`, the timeout still does not fire.

Runtime files involved:

- `packages/service-actor/src/Actor.ts`
  - owns in-memory actor state/data.
  - queues inbox messages.
  - schedules timeout recovery only when `this.#state === "error"`.
  - scans only `actor.states.error?.on` for timeout-like messages.
  - currently matches the misspelled message format `timout:<ms>ms`.
- `packages/service-actor/src/ActorSupervisor.ts`
  - loads persisted actor instances with their `machine_state` and `machine_context`.
  - starts actors on service init/reload.
  - persists actor machine snapshots after ack events.
- `packages/service-actor/tests/Actor.test.ts`
  - already has coverage for `timout:*` automatic recovery from `error`.
- `packages/service-actor/tests/ActorSupervisor.test.ts`
  - has persistence/reload-oriented tests and can cover persisted waiting-state behavior if needed.
- `packages/service-agent/src/systemprompts.ts`
  - tells generated widgets that automatic recovery uses `timout:xxxxms` only for `error`.
  - may need wording update if generic timeout transitions become a supported actor feature.
- `docs/internal/llm.widget-system.md`
  - describes actor lifecycle and known gaps; may need a small update if timeout semantics are clarified.

Current conceptual mismatch:

- Existing runtime concept: `timout:xxxxms` is an automatic error recovery mechanism only.
- Widget author expectation: timeout transitions are generic delayed transitions for any state, especially `waiting.*`.

Additional naming issue:

- The runtime and prompts use `timout`, not `timeout`.
- If we support generic timeout transitions, prefer supporting correct `timeout:<ms>ms` while preserving legacy `timout:<ms>ms` for compatibility.

## Plan

### 1. Decide the intended semantics

Support generic state timeout transitions:

- Any current state can declare an automatic timeout transition in `actor.states[currentState].on`.
- Supported message names:
  - `timeout:<ms>ms` as the corrected/public spelling.
  - `timout:<ms>ms` as backward-compatible legacy spelling.
- Timer should be scheduled when:
  - actor starts in a state with a timeout transition.
  - actor enters a state with a timeout transition after a successful transition.
  - actor enters implicit `error` state and `error` declares a timeout transition.
- Timer should be cleared when:
  - leaving the state.
  - actor closes.
  - scheduling a replacement timer.
- Internally enqueued timeout messages should bypass `inputMsgSchema` validation, because they are system messages, not widget inputs.

### 2. Update `Actor.ts`

Likely changes:

- Rename `#errorTimeout` to a generic timer field, e.g. `#stateTimeout`.
- Rename `#scheduleErrorTimeoutIfNeeded()` to something like `#scheduleStateTimeoutIfNeeded()`.
- Rename `#clearErrorTimeout()` similarly.
- Replace `#getErrorTimeoutMessage()` with a helper that inspects the current state's `on` map:
  - `this.#vsJson.actor.states[this.#state]?.on ?? {}`
  - find timeout entries using `/^time?out:(\d+)ms$/` is not sufficient for `timout`; use explicit alternatives like `/^(?:timeout|timout):(\d+)ms$/`.
  - sort by delay and choose the shortest timeout if more than one is declared.
- When the timer fires:
  - confirm the actor is still in the same state for which the timer was scheduled.
  - enqueue the timeout message with a generated message id.
  - call `#processQueue()`.
- Keep direct `inbox("timeout:...", {})` from the widget invalid unless the timeout message is explicitly in `inputMsgSchema`; system-generated timeout delivery should remain internal.

### 3. Tests required

Add/update tests in `packages/service-actor/tests/Actor.test.ts`.

Must include:

- Generic waiting-state timeout:
  - create a test actor with `ready -> waiting.celebrating` on `celebrate`.
  - `waiting.celebrating.on["timeout:20ms"]` runs a noop or data-reset function and targets `ready`.
  - assert actor returns to `ready` after timeout.
  - assert an `ack` event is emitted with `inputName === "timeout:20ms"`.
- Legacy spelling compatibility:
  - either keep existing `timout:20ms` error recovery test passing, or add a waiting-state variant using `timout:20ms`.
- Startup/reload conceptual case:
  - instantiate an actor with initial/persisted state `waiting.celebrating` and a timeout transition.
  - call `start()` and assert timeout fires without a user message.
  - This directly covers the user question: on reload in `waiting.celebrating`, timeout should trigger.
- Negative/control behavior:
  - direct user `actor.inbox("timeout:20ms", {})` should still fail if the message is not declared in `inputMsgSchema`, or document if this behavior intentionally changes.

Optional supervisor-level test in `packages/service-actor/tests/ActorSupervisor.test.ts`:

- Insert an actor instance in DB with `machine_state: "waiting.celebrating"`.
- Start supervisor.
- Assert DB eventually persists `machine_state: "ready"` after timeout ack.
- This is more integrated and proves reload/persistence end-to-end, but may need a local fixture manifest/functions if current fixtures do not have waiting timeout states.

## NOTES

Manual probe result before fix:

- Starting an actor directly in `waiting.celebrating` with the Todo List manifest and waiting longer than one second leaves it stuck in `waiting.celebrating`.
- Events emitted were only `status.changed` and initial `state.changed` from `booting` to `waiting.celebrating`.
- Calling `actor.inbox("timout:1000ms", {})` directly throws `UNKNOWN_INPUT_MESSAGE`, because timeout messages are not in `inputMsgSchema`. That is okay for widget/user input; automatic runtime delivery should bypass `inbox()` validation.

Important implementation detail:

- `Actor.#processQueue()` can already process queued timeout messages because the internal queue stores `msgName` and looks up the transition from current state. It does not validate against `inputMsgSchema` at processing time. The scheduler should push directly to `#queue`, as the current error-timeout code already does.

Potential pitfall:

- `ActorSupervisor.reload()` loads missing actors but does not replace existing `actorMap` entries. Runtime code changes require process restart; manifest changes may require actor recreation/restart if the actor is already loaded.
