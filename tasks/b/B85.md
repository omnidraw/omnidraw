# B85 - ci: align the canvas release marker with its public runtime changes
[Overview](../BASED.md)

Final acceptance reaches the canvas-kernel architecture gate but rejects the
workspace because `@omnidraw/canvas` still declares `0.6.0` while the release
contract correctly expects `0.6.1` after public runtime changes.

## Context

[GitHub Actions run 31374501802](https://github.com/omnidraw/vibecanvas/actions/runs/31374501802)
fails at `scripts/architecture-boundaries.test.ts:847`:

```text
Expected: "0.6.1"
Received: "0.6.0"
```

Commit `51c175a9` (`A112`) changed public code in
`packages/canvas/src/extension.ts` and `packages/canvas/src/runtime.ts`, and
updated the architecture release map to `0.6.1`. It did not update
`packages/canvas/package.json`, so `bun.lock` and the generated distribution
manifest remained at `0.6.0`.

The failing head commit `87928fc1` only changes the frontend/dev loopback
binding. Earlier Linux runs stopped first in the database-recovery suite; once
B82 fixed that gate, final acceptance exposed this older version drift.

## Plan

1. Bump only `@omnidraw/canvas` from `0.6.0` to the already-reserved `0.6.1`.
2. Regenerate `bun.lock` so its workspace package record matches the manifest.
3. Build the canvas kernel and run the focused architecture boundary.
4. Push the repair and monitor the sequential final-acceptance workflow for
   the next hidden failure.

No mockup or diagram is useful for this package-metadata correction.
