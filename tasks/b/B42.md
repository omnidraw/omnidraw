# B42 - release: macOS binary freezes after unsafe automatic upgrade
[Overview](../BASED.md)

The published macOS arm64 `0.4.4` executable freezes in the dynamic loader before Vibecanvas or Bun application code starts. The automatic upgrade path checksum-verifies the release archive but replaces the working executable without proving the candidate can launch, so a broken release can disable every command, including `vibecanvas --version` and `vibecanvas upgrade`.

## Context

Observed installed executable:

```text
path: /Users/omarezzat/.vibecanvas/bin/vibecanvas
reported version after temporary re-sign: 0.4.4
published SHA-256: cd8622c480b411f545d9b95e77c410ab5a9cc920e9a2d110ad0eb6569c4db14e
```

The installed file exactly matched the published `vibecanvas-v0.4.4` Darwin arm64 release asset. This rules out an incomplete download or local file corruption.

Basic commands froze before producing output:

```sh
vibecanvas --version
vibecanvas --help
```

Attempts to terminate them left several processes in macOS `UE` state with approximately 32 KB RSS. Sampling a stuck process showed only:

```text
Main Thread
└── _dyld_start
```

No Vibecanvas startup log, Bun application frame, Turso call, actor startup, or database access occurred. This is separate from [B41](B41.md).

## Findings

### Published Darwin artifact fails signature verification

The downloaded `0.4.4` release asset fails:

```sh
codesign --verify --strict --verbose=4 ./vibecanvas
```

with:

```text
invalid signature (code or signature have been modified)
```

Ad-hoc signing a temporary copy made the same binary launch immediately and print `0.4.4`:

```sh
codesign --force --sign - ./vibecanvas
./vibecanvas --version
```

This is a diagnostic/local workaround, not the intended production release process.

### Older release evidence needs careful interpretation

The published `0.4.2` and `0.4.3` Darwin arm64 assets also fail formal `codesign` verification, even though the user's previous installed executable launched successfully. The exact working file was overwritten by the upgrader and is no longer available for byte-for-byte inspection.

Known release-runtime delta:

```text
0.4.2 / 0.4.3: Bun 1.3.10
0.4.4:         Bun 1.3.14
```

Do not conclude that invalid signing alone explains why only the new installed binary freezes. Establish whether Bun `1.3.14` changed cross-compiled Mach-O/signature behavior by building a minimal executable matrix on Linux and macOS. The current evidence establishes that the `0.4.4` artifact is unusable on the affected machine and that re-signing repairs it.

### Darwin releases are built on Ubuntu

[release-vibecanvas.yml](../../.github/workflows/release-vibecanvas.yml) currently runs `scripts/build.ts` on `ubuntu-latest` and cross-compiles all targets, including Darwin arm64.

[build.ts](../../scripts/build.ts) calls `Bun.build({ compile: { target: "bun-darwin-arm64" } })`, checks binary marker portability, and writes a checksum. It does not verify the Mach-O signature or execute Darwin artifacts on macOS before publishing.

Bun's official [macOS executable signing guide](https://bun.com/docs/bundler/executables) performs signing on macOS and recommends JIT/runtime entitlements for compiled JavaScript executables:

```xml
<key>com.apple.security.cs.allow-jit</key>
<true/>
<key>com.apple.security.cs.allow-unsigned-executable-memory</key>
<true/>
<key>com.apple.security.cs.disable-executable-page-protection</key>
<true/>
<key>com.apple.security.cs.allow-dyld-environment-variables</key>
<true/>
<key>com.apple.security.cs.disable-library-validation</key>
<true/>
```

For public distribution, decide between Developer ID signing plus notarization and an explicitly documented interim ad-hoc signature. In either case, the final published bytes must be signed first and checksummed afterward.

### Normal upgrade bypasses candidate validation

[cmd.upgrade.ts](../../apps/cli/src/plugins/cli/cmds/cmd.upgrade.ts) already has `dryRunUpgradeCandidate()`, which downloads, checksum-verifies, extracts, and executes a candidate. Normal `applyUpgrade()` does not use it. Instead it launches the remote installer:

```text
curl -fsSL https://vibecanvas.dev/install | bash -s -- --version <version> ...
```

The installer replaces `~/.vibecanvas/bin/vibecanvas` after archive checksum verification. It does not verify the Darwin signature or execute the candidate before replacement.

The existing dry run is also insufficient as the safety boundary:
- candidate execution has no timeout;
- a loader freeze can wait forever;
- it does not run `codesign --verify` before spawning on macOS;
- it does not verify that stdout matches the requested version;
- it is opt-in rather than mandatory before installation;
- it does not own atomic replacement or rollback.

### Automatic update explains the installed version

The user intentionally ran `vibecanvas upgrade` from `0.4.2` to `0.4.3`. Curl installations default to automatic stable updates. The installed executable was later overwritten with `0.4.4` at `2026-07-10 13:18:04 +0200`, about five minutes after the `0.4.4` GitHub release was published at `2026-07-10 13:12:59 +0200`.

The broken file therefore came from a later automatic update, not necessarily the user's earlier explicit `0.4.2 -> 0.4.3` command.

## Plan

### 1. Reproduce and isolate the build regression

- Build a minimal `console.log` single-file Darwin arm64 executable with Bun `1.3.10` and `1.3.14` on both Linux and macOS runners.
- Record `file`, `otool -l`, `codesign -dvvv`, `codesign --verify --strict`, SHA-256, and `--version`/execution results.
- Repeat with the real Vibecanvas entrypoint to distinguish a Bun cross-compiler problem from post-build mutation.
- Confirm whether the native Turso addon is unrelated by testing `--version`, which must exit before service initialization.
- Report a minimal upstream Bun issue if `1.3.14` produces a new invalid/unlaunchable cross-compiled Mach-O.

### 2. Build and validate Darwin artifacts on macOS

- Split the release build into platform-native jobs instead of building every target on Ubuntu.
- Build Darwin arm64 on a macOS arm64 runner with the pinned Bun version.
- Add a checked-in entitlements plist based on Bun's documented executable requirements.
- Sign the final executable after compilation and after any operation that could mutate its bytes.
- For production releases, configure Developer ID signing and notarization; document any temporary ad-hoc-signing phase explicitly.
- Generate the executable checksum only after signing.
- Verify with `codesign --verify --deep --strict --verbose=4`.
- Execute `vibecanvas --version` and the binary smoke suite on the macOS runner before artifact upload.
- Merge per-platform artifacts into the existing release manifest/publish job without rebuilding them.

### 3. Make upgrade installation transactional

Replace the remote-installer call in normal `applyUpgrade()` with an in-process candidate workflow:

```text
resolve release
→ download archive/checksum to a temporary directory
→ verify archive checksum
→ extract candidate and native addon
→ run platform validation
→ run bounded candidate smoke test
→ verify exact target version
→ create backup beside installed binary
→ atomically rename candidate into place
→ restore backup if finalization fails
```

Requirements:
- Never mutate the installed executable before all candidate checks pass.
- On macOS, run signature verification before spawning the candidate so an invalid Mach-O cannot create an unkillable loader-stuck process.
- Apply a short timeout to candidate execution on every platform.
- Treat timeout, signal, non-zero exit, malformed output, and version mismatch as validation failures.
- Preserve the currently working binary and native addon on every failure path.
- Ensure binary and native addon are replaced as one recoverable installation unit.
- Do not automatically sign a downloaded candidate in the upgrader; that would mutate checksum-verified release bytes and hide a release-pipeline failure.

### 4. Harden the standalone installer

- Apply the same download, platform validation, smoke-test, backup, and rollback guarantees in [install.sh](../../scripts/install.sh).
- Share a documented validation contract between the TypeScript upgrader and shell installer even if implementation languages differ.
- Ensure a manual reinstall cannot overwrite a working binary with the same broken artifact.

### 5. Change automatic-update failure behavior

- A failed candidate validation must become `update-available`/`error`, not a partial installation.
- Keep the current version running and show a concise actionable diagnostic.
- Record the failed target version and reason to avoid retrying the same invalid release on every startup.
- Add an explicit retry/check path after a corrected release becomes available.

### 6. Add regression coverage

- Unit-test candidate validation decisions separately from file mutation.
- Test checksum mismatch, invalid macOS signature, hanging candidate, killed candidate, non-zero exit, wrong reported version, missing native addon, and atomic-replacement failure.
- Add an integration fixture where the candidate never exits and assert the installed binary remains byte-identical.
- Add a release CI assertion that every published target is tested on its target OS/architecture where supported.
- Add a macOS test proving the final archive can be extracted and executed from a fresh temporary directory.

### 7. Recover the affected release

- Publish a corrected patch release rather than relying on users to ad-hoc sign `0.4.4`.
- Mark `0.4.4` as affected in release notes/documentation.
- Provide the temporary local recovery command only as an emergency workaround:

```sh
codesign --force --sign - ~/.vibecanvas/bin/vibecanvas
```

- Warn that already stuck `UE` processes may require logout/restart before they disappear.

## NOTES

- `codesign` in the upgrader is a rejection guard, not the primary repair. The release pipeline must produce a valid artifact.
- Checksum verification proves the downloaded bytes match the published bytes; it does not prove those bytes are executable on the target platform.
- The exact previously working installed `0.4.2`/`0.4.3` file was overwritten, so claims about why it launched must remain hypotheses until reproduced.
- A Docker-based local Linux cross-compile comparison was attempted, but the local Docker daemon was not running. Reproduce in CI or another Linux environment.
- Do not conflate this loader failure with B41's Turso pager panic; `--version` never reaches database startup.
- Signing policy: CI currently applies an explicit ad-hoc signature on the native macOS runner with Bun's runtime entitlements. `VIBECANVAS_CODESIGN_IDENTITY` is the transition point for a Developer ID identity; public notarization remains required before claiming a notarized distribution.
