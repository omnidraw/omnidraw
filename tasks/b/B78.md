# B78 - Preview does not hot-reload on AI edits; initial bundle is slow
[Overview](../BASED.md)

AI edits to a widget draft do not update a live Preview frame, and the app's
initial load pulls a 9.2 MB main bundle because the Capsule host and the whole
canvas page are statically imported.

## Context

The notification pipeline from an AI edit to the browser already works:

- `edit`/`patch`/`write`/`bash` call `onDraftChanged`
  (`packages/service-agent/src/tools/tool.workspace-files.ts`) →
  `AgentService.#publishWidgetDraftsChanged` (`AgentService.ts`) →
  `widgetCatalog.refresh()` (`apps/cli/src/setup-services.ts`) → catalog change
  event → `widget.catalog.events` stream (`packages/api/src/widget/api.catalog-events.ts`)
  → frontend `startWidgetCatalogEventStream`
  (`packages/ui-ai-chat/src/canvas-extension/index.ts`).
- `widget.preview.open` server-side already rebuilds and reuses a validated
  construction when the digest is unchanged
  (`packages/service-agent/src/widget-filesystem/preview/index.ts`).

The bug: the frontend catalog handler only remounts published
`widget-instance` frames. `fnCanvasWidgetMountSignature` sets
`publishedCatalogEpoch: null` for a `widget-preview`, so the preview frame's
portal signature never changes on a draft edit and its mounted Capsule artifact
is never rebuilt. `TWidgetPreviewOwner` has no public `refresh()` either.

Loading: `CapsuleWidgetHostCoordinator` statically imports
`createCapsuleHost`/`createDefaultCapsuleBrowserPlatform`/`CapsuleMemoryArtifactCache`
from `@omnidraw/capsule`, and the canvas page is statically imported in the
frontend router root, so the QuickJS host lands in the initial 9.2 MB bundle.
The Capsule docs require lazy-loading the host at the first widget boundary
(`docs/internal/llm.capsule.md` "Lazy loading and population").

## Plan

### 1. Preview hot-reload

- Add a public `refresh()` to `TWidgetPreviewOwner`
  (`packages/ui-ai-chat/src/canvas-extension/preview-owner.ts`) that re-runs
  `preview.open` and remounts the new artifact, coalescing concurrent refreshes
  so a burst of edits collapses to the latest build.
- Track live preview owners by `widgetKey` in
  `packages/ui-ai-chat/src/canvas-extension/index.ts` (registered in the
  `widget-preview` portal branch, removed on unmount).
- In the catalog event handler, call `refresh()` for matching preview owners on
  `remount: 'keys'`/`'all'`, debounced so an AI tool burst triggers one rebuild.
- Keep the published `widget-instance` remount path unchanged.

### 2. Lazy Capsule host

- In `CapsuleWidgetHostCoordinator.ts`, replace static value imports with a
  dynamic `await import('@omnidraw/capsule')` inside `#createHost` (keep
  type-only static imports and the `TWidgetCapsuleHostFactory` injectable seam).
- This moves Capsule host + QuickJS loader out of the initial main bundle.

### 3. Route-level code splitting

- Convert `CanvasPage`, `WidgetPage`, `ResourcePage` in
  `apps/frontend/src/index.tsx` to `@solidjs/router` `lazy()` so the welcome
  page does not download the canvas/Capsule bundle.

### 4. Verify

- canvas-contract + service-agent + ui-ai-chat typecheck/tests.
- Rebuild frontend and compare main bundle size.
- Manual: create widget → place Preview → AI-chat edit a file → confirm the
  preview frame rebuilds without a manual reload.

## NOTES

- 4 `ui-ai-chat` tests (`preview-owner`, `fxWidgetCapsuleViewport`) already fail
  on the clean base under `bun test` because they need jsdom; the package uses
  vitest (`node ./node_modules/vitest/vitest.mjs --run`) where all 188 pass.
- The `widget-instance` published path already remounts on catalog change; only
  `widget-preview` was missing.
- `@omnidraw/capsule-omnidraw/host/fn.error` was added as a light subpath so the
  error mappers can be imported without pulling the heavy capsule root. The
  published `dist` exports map was regenerated and the boundary test updated
  (six → seven subpaths).
- Main frontend bundle dropped from 9.2 MB to ~17 kB; canvas (~2 MB),
  ai-chat (~2.3 MB), and the Capsule QuickJS chunk (~4.6 MB) now load lazily.
