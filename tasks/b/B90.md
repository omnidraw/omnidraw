# B90 - AI widget Preview: failed mounts are uninspectable and diagnostics collapse

[Overview](../BASED.md)

AI Chat can successfully check, build, and validate a widget while its visible
Preview fails, then reach a diagnostic dead end: Preview-mode inspection only
accepts an already-ready exact frame, the agent cannot create that prerequisite,
and artifact mount exceptions are reduced to `BROWSER_MOUNT_FAILED` without the
underlying safe runtime diagnostic. Validation copy also sounds like runtime
Preview execution succeeded when it only proves construction/build acceptance.

## Report

Observed during manual testing on 2026-08-11 with the database-backed **Little
Phonebook** widget (`little-phonebook`):

1. `npm run check` passes.
2. `npm run build` passes and the host accepts the build.
3. `od_widget_validate` reports:

   ```text
   Widget 'Little Phonebook' construction is valid and the Preview build passed.
   ```

   Its structured result says `validationScope: "construction"` and
   `previewExecution: "passed"`.
4. The user-visible canvas Preview fails.
5. `od_widget_preview_inspect({ mode: "preview" })` returns:

   ```text
   PREVIEW_UNAVAILABLE: The exact current canvas Preview is unavailable for inspection.
   ```

6. `od_widget_preview_inspect({ mode: "artifact" })` fails at `mount` with only:

   ```text
   BROWSER_MOUNT_FAILED: The isolated Preview inspection browser could not complete the requested run.
   ```

No safe guest/Capsule exception or `widget://` source location is returned, so
the agent cannot identify whether startup failed because of authored UI code,
server-function wiring, Capsule execution, or another runtime boundary.

The original report's canvas ID and artifact digests are intentionally not a
required task contract. Reproduction must use the process-owned current
canvas/widget/generation rather than teaching tests or tools to accept captured
browser identifiers.

## Verification

### Confirmed: failed Preview state is excluded from inspection

Production Preview discovery in `apps/cli/src/setup-services.ts` requires
exactly one durable `widget-preview` item for the verified chat canvas and
active widget target. `WidgetPreviewService.inspect` then additionally requires
an exact live host session whose phase is already `ready`, plus a current
accepted generation match. A missing, failed, still-mounting, retired, or stale
frame becomes the same `PREVIEW_UNAVAILABLE` dead end instead of diagnostic
state.

A verified canvas and active editable target do not imply that a Preview frame
exists. That distinction is valid, but the returned error does not say which
prerequisite is absent or how the agent can establish it.

### Confirmed: the model cannot establish the prerequisite

The fixed agent tool registry exposes `od_widget_preview_inspect`, whose
contract explicitly does not build, publish, or mutate canvas layout. Opening a
draft Preview is only a browser UI callback (`openDraftPreviewBeside`) wired
through `ChatTab` and the AI Chat canvas extension. There is no model-callable
operation that can create/refresh an exact diagnostic Preview or inspect a
failed pre-ready session.

### Confirmed: mount rejection loses the actionable cause

`PreviewInspectionBrowserService` wraps a rejected shell mount in
`BROWSER_MOUNT_FAILED` unless the rejection is already a trusted service error.
The wrapper discards the original exception. The failure projector then emits
fixed generic browser wording and has no diagnostics collection on the failed
result path. Runtime events and source mapping are projected only after a
successful mount returns a browser result.

Consequently the first startup exception can never reach AI Chat through this
path, even if it is safe, structured, and source-mappable.

### Confirmed: validation wording overstates its evidence

`od_widget_validate` invokes `WidgetPreviewService.buildCheck`, which rebuilds
and waits for host acceptance. It does not mount the current canvas Preview,
run a manifest-bound resource call, or inspect visible runtime behavior. The
phrases `previewExecution: "passed"` and “Preview build passed” are therefore
easy to misread as runtime verification.

### Not confirmed: server-function proxy transformation failure

The reported portable distribution contains the SDK's intentional
registration-only callable that throws when invoked in a browser. That output
is not the accepted Capsule UI artifact. The host builder separately removes
server implementation modules and inserts generated client modules at the same
paths before the UI distribution build.

Existing Capsule boundary coverage imports a named function through
`../server/functions.server` and verifies that the UI build receives a
generated `createServerFunctionProxy` module while private server source is
withheld. This covers the same import form as `../server/main.server`; only the
filename differs. The actual Little Phonebook accepted artifact was not
available in this worktree, so its visible runtime failure and exact cause are
not independently reproduced. Do not label the proxy transformer as broken
without a failing accepted-artifact integration test.

## Safety boundary

Do not relax exact chat/canvas/widget/generation authority to make inspection
available. Browser-provided canvas, element, session, resource, or generation
identifiers remain non-authoritative. A diagnostic mount must derive identity
from the verified chat target, accepted manifest, and process-owned generation.

Preserve existing redaction and bounded-output rules. Raw stacks, host paths,
resource IDs, credentials, provider details, SQL data, and arbitrary guest text
must not pass through merely because mount failed. Surface only trusted,
classified, bounded diagnostics and verified widget-relative source locations.

Inspection must not silently execute protected writes. Manifest-bound reads may
run under normal Preview policy; writes remain approval-gated or explicitly
reported as not exercised.

## Plan

### 1. Make Preview unavailability structured and actionable

- Split absent, mounting, failed, retired/stale, ambiguous, and generation-
  mismatched Preview states.
- Return only safe process-owned state such as whether an exact frame exists,
  whether its accepted generation is current, and the required next action.
- Keep exact authority checks before and after asynchronous work.

### 2. Make failed Preview startup inspectable

- Retain a bounded failed-session diagnostic record through the Preview
  lifecycle, or create a process-owned diagnostic clone from the exact accepted
  generation and manifest runtime policy.
- Expose one agent-callable path that can establish that diagnostic execution
  without publishing or mutating canvas layout.
- Clearly report whether evidence came from the visible frame or a diagnostic
  clone; never imply pixel or session identity.

### 3. Preserve mount diagnostics

- Capture the earliest trusted Capsule/guest/function/resource startup event
  before rejecting mount.
- Project its classified code, safe message, stage, retryability, and verified
  `widget://` location when available.
- When artifact mode cannot exercise required server/resource authority,
  return a specific incompatibility/not-exercised result instead of a generic
  browser failure.

### 4. Make validation claims exact

- Rename the result field/copy so it says construction and accepted artifact
  build passed while live Preview runtime was not exercised.
- Keep runtime verification solely in successful targeted Preview inspection.

### 5. Verify server-function transformation at the accepted boundary

- Add an end-to-end accepted-artifact fixture whose UI imports named functions
  from the manifest's exact `server.entry` module.
- Prove the Capsule UI artifact contains the generated proxy, excludes the SDK
  registration callable and private implementation, and completes a bounded
  `fx` database read under manifest-owned authority.
- If that test passes, diagnose the original visible failure from the newly
  preserved runtime event instead of changing the transformer speculatively.

## Causal tests

1. Construction/build acceptance returns wording that explicitly says live
   Preview runtime was not exercised.
2. No exact Preview frame returns structured `absent` state and an actionable
   diagnostic next step without leaking canvas or element IDs.
3. A current-generation frame that fails before `ready` remains diagnosable and
   returns its first trusted startup failure rather than `PREVIEW_UNAVAILABLE`.
4. Mounting, failed, stale-generation, retired, ambiguous, and truly absent
   frames remain distinct; none fall back to newest/first/global state.
5. A diagnostic clone uses the exact accepted artifact, manifest references,
   function descriptors, runtime policy, and generation, and reports that it is
   not the visible frame.
6. A newer source edit/build, Preview replacement, chat replacement,
   navigation, cancellation, timeout, or shutdown revokes diagnostic work and
   cannot return success for the old generation.
7. A shell-mount startup exception returns one bounded classified diagnostic
   with a mapped `widget://` location when the source map verifies it.
8. Untrusted/raw exceptions, host paths, secrets, resource IDs, provider text,
   and SQL data remain redacted or suppressed on the failed-mount path.
9. Artifact mode for a resource-backed server widget reports resources as not
   available/not exercised and never claims manifest-bound behavior.
10. A fixture importing named functions from `../server/main.server` receives
    generated proxies in the accepted Capsule UI artifact, with no server
    registration callable or private server source present.
11. The fixture completes a manifest-bound database read in Preview diagnostic
    mode; protected writes still require normal approval.
12. Existing exact-scope, generation-fence, deny-by-default network, output-
    budget, cancellation, and cleanup tests continue to pass.

## Resolution

Completed on 2026-08-12. Preview inspection now derives a diagnostic clone from
the exact process-owned accepted generation when the visible frame is absent or
failed. Results identify `executionTarget: diagnostic_clone`, preserve the
visible `previewState`, and provide a bounded `nextAction`; mounting, retired,
ambiguous, and generation-mismatched states remain distinct and fail closed.

The inspection shell retains the exact failed job until cleanup, allowing the
browser service to validate one bounded startup snapshot after mount rejection.
Only canonical classified runtime events pass through, and the existing
artifact/generation fence, redaction, byte budget, and verified `widget://`
source-map projection still apply. Artifact mode now reports resource bindings
as unavailable, while Preview mode retains manifest-bound reads and blocks
protected writes.

`od_widget_validate` now reports `acceptedArtifactBuild` together with
`livePreviewRuntime: not_exercised` and `resources: not_exercised`. The accepted
Capsule boundary fixture imports a named function from the exact manifest entry
`../server/main.server`, proves the generated proxy replaces private server
source, and the Preview diagnostic fixture completes a bounded manifest-owned
database read.

## Acceptance criteria

- AI Chat can diagnose an exact accepted widget generation even when its visible
  Preview never reaches `ready`.
- Preview unavailability explains the safe state and next action instead of
  collapsing every prerequisite failure into `PREVIEW_UNAVAILABLE`.
- Failed mount results preserve an actionable trusted diagnostic and verified
  widget-relative source location when available.
- Validation never claims that live Preview/runtime/resource behavior passed
  when only construction and artifact build acceptance ran.
- Artifact mode never implies resource-backed parity and reports unsupported
  authority explicitly.
- Exact durable scope, generation fencing, resource authority, write approval,
  redaction, output bounds, and cleanup remain fail-closed.
- The server-proxy hypothesis is resolved by accepted-artifact integration
  evidence before any transformer change.

## NOTES

- No mockup is useful. This is a lifecycle, authority, and diagnostic-protocol
  defect; state-transition tests are the useful evidence.
- This report verifies the diagnostic dead end in source. It does not claim to
  have reproduced the Little Phonebook's underlying visible runtime failure.
- A119 allowed `PREVIEW_UNAVAILABLE` when no current frame existed. This report
  captures the missing product workflow revealed by manual testing: an
  unavailable/failed frame plus no model-callable way to establish diagnostic
  execution leaves the requested create-and-verify workflow incomplete.
