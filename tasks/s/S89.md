# S89 - actor resources: add independent key-value file persistence
[Overview](../BASED.md)

Create the host-owned physical persistence adapter shared by `KvResource` and `SecretStoreResource`. The adapter gives every resource its own bounded, lifecycle-managed Turso file while leaving the existing providers on control-database persistence until S90 and S91 switch them.

## Dependencies

- Decision from [E30](../e/E30.md).
- S90 and S91 depend on this task.

## Context

`KvResource` and `SecretStoreResource` currently receive `DbServiceTurso['actorResource']['keyValue']` from [`ActorService.ts`](../../packages/service-actor/src/ActorService.ts). Their entries are stored in the control database's `actor_resource_key_values` table by:

- [`DbServiceTurso.ts`](../../packages/service-db/src/DbServiceTurso/DbServiceTurso.ts)
- [`fx.actor-resource.ts`](../../packages/service-db/src/DbServiceTurso/fx.actor-resource.ts)
- [`tx.actor-resource.ts`](../../packages/service-db/src/DbServiceTurso/tx.actor-resource.ts)
- [`fn.actor-resource-row.ts`](../../packages/service-db/src/DbServiceTurso/fn.actor-resource-row.ts)
- [`010-add-actor-resource-key-values.sql`](../../packages/service-db/src/DbServiceTurso/migration-files/010-add-actor-resource-key-values.sql)

The existing semantics that the new adapter must preserve are:

- JSON-compatible values, including stored `null` distinct from a missing key;
- ordered literal prefix/search/cursor listing with default and hard limits;
- revisions starting at one and incrementing on every successful explicit write;
- last-write-wins `set`;
- atomic create/update compare-and-set;
- expected-revision delete;
- stable `created_at` and changing `updated_at` timestamps;
- no cross-resource transaction.

[`DbResource.ts`](../../packages/service-actor/src/resources/DbResource.ts) already establishes useful host-file patterns: host-derived paths, path-safe resource IDs, per-resource write tails, in-flight tracking, cached handles, provisioning cleanup, physical verification, deletion after drain, and provider shutdown. Do not reuse its guest SQL surface or draft/apply machinery. Extract or reproduce only the small physical lifecycle behavior genuinely shared by key-value files.

## Fixed decisions

### Ownership and paths

The physical key-value adapter belongs under `packages/service-actor/src/resources/`. `DbServiceTurso` remains responsible only for the resource catalog, bindings, lifecycle status, and DbResource coordination metadata.

Use host-derived paths only:

```text
<dataRoot>/actor-resources/kv/<resource-id>/data.db
<dataRoot>/actor-resources/secret-store/<resource-id>/data.db
```

The catalog name, actor arguments, keys, secret names, and values must never participate in path construction. Validate resource IDs before every filesystem operation using the same bounded safe alphabet used by `DbResource` or a shared local pure helper.

### Physical format

Each file owns one entry table. It does not repeat `resource_id` in every row because the physical file is the isolation boundary.

Use a small host-private metadata table with exactly one row containing:

- resource ID;
- exact resource kind (`kv` or `secretStore`);
- physical format version, initially `1`.

Use an entry table equivalent to:

```text
key TEXT PRIMARY KEY
value TEXT containing valid JSON
revision INTEGER >= 1
created_at timestamp
updated_at timestamp
```

Use `STRICT`, a JSON-validity check, and an updated-at trigger where supported by the current Turso adapter. Serialize all values deliberately rather than relying on adapter-dependent JSON return behavior. The secret provider will store only JSON strings, but the shared physical format remains JSON-capable.

Metadata verification must reject a file copied into the wrong resource/kind path. Missing, corrupt, foreign, or unsupported-format files must never be silently initialized during ordinary open/reconciliation.

### Runtime behavior

- Provisioning is the only operation allowed to create a file/schema.
- Ordinary reads/writes use `fileMustExist` behavior.
- Writes are serialized per resource, not globally across every resource.
- CAS is one conditional database write, not read-then-unconditional-write.
- Reads and writes are tracked so deletion and shutdown can drain safely.
- Open handles are lazy and bounded. Use an injectable limit with a documented default; evict only idle handles and never close a handle with in-flight work or a queued write.
- A failure in one physical resource must not close or poison unrelated resources.
- `close()` must reject new work, drain/settle tracked work, and close every handle while continuing after individual close failures.

### Migration and security scope

There is no resource data migration or backfill because resources have not been deployed. S89 does not change current runtime callers and does not touch migration `010`; S91 performs final control-database cleanup after both providers have moved.

Independent files improve lifecycle and operational isolation. They do not make secret values confidential. Encryption, OS keychain integration, master-key recovery, remote storage, backup UI, resource forks, and cross-resource transactions are out of scope for these three tasks.

## Plan

### 1. Introduce actor-local persistence contracts

Add actor-local entry/page/write result types and a narrow persistence interface used by both providers. Keep database handles, paths, native rows, and SQL out of the interface.

The interface must cover:

- `get` and `has`;
- `count` with optional literal prefix/search;
- bounded ordered `list` with cursor;
- `set`;
- expected-revision `delete`;
- `compareAndSet` with `null` meaning create-if-missing;
- provision, reconcile/verify, delete, and close lifecycle operations.

Use actor-local DTOs rather than `TActorResourceKeyValue` from `service-db`. Prefer camel-cased service DTOs at the adapter boundary so database row naming does not leak into the providers. Keep JSON assertion/serialization and list-bound logic in local pure `fn.*.ts` helpers following the functional-core file rules.

### 2. Implement deterministic path and schema creation

Create a stateful adapter such as `ActorResourceKeyValueStore` configured with:

- `dataRoot`;
- expected kind and fixed path segment;
- native database factory;
- maximum open handles;
- query timeout where injectable testing is useful.

Provisioning must:

1. validate resource ID and exact kind;
2. create only the expected kind root and new resource directory;
3. open the new file and apply host pragmas;
4. create metadata, entry table, and trigger atomically where possible;
5. write the singleton identity/format row;
6. close and reopen/verify the file;
7. remove the new directory on failure without touching sibling resources.

Reject pre-existing resource directories instead of adopting unknown contents.

### 3. Implement reads and writes

Port the current SQL semantics from service-db into the physical adapter:

- parameterize every value;
- parse JSON values consistently;
- use `substr`/`instr` or an equally literal mechanism so `%` and `_` are not wildcard syntax;
- order by key and request `limit + 1` for cursor detection;
- preserve missing versus stored JSON `null`;
- avoid native `UPDATE ... RETURNING` because this repository has known Turso failures around that path;
- query the successful row after writes when a complete result is required;
- ensure two concurrent CAS operations with one expected revision produce one winner.

Keep the per-resource write queue authoritative for write ordering, while the conditional SQL remains authoritative for CAS correctness.

### 4. Add bounded handle lifecycle

Track, per resource:

- opening/open handle promise;
- in-flight operations;
- write tail;
- last-use/LRU position;
- blocked/deleting state.

Opening a handle must verify metadata before exposing it. Handle-open failure must remove the failed cache entry. Eviction must skip busy resources and run after operations settle; if every candidate is busy, defer eviction rather than violating lifecycle safety. Tests must prove that opening more resources than the configured cap does not leave an unbounded number of handles.

Deletion must drain calls/writes, close the handle, and recursively remove only the validated resource directory. A failed removal remains an error for the provider saga to persist; it must not pretend deletion succeeded.

### 5. Add focused physical-store tests

Add deterministic temporary-directory tests under `packages/service-actor/tests` for:

- provisioning both path kinds and verifying exact physical paths;
- metadata identity/kind/format verification;
- rejection of traversal/invalid IDs;
- all JSON value families and stored `null`;
- literal prefix/search/cursor/count behavior and hard limits;
- revision increments, set, expected delete, create CAS, update CAS, and concurrent stale CAS;
- physical isolation for equal keys in different files;
- restart persistence after closing and reconstructing the adapter;
- missing/corrupt/swapped file reconciliation without silent recreation;
- cleanup after failed provisioning;
- delete after drain and failure-safe sibling preservation;
- bounded lazy handles, idle eviction, and shutdown despite one close failure.

Use a fake/counting database factory only for lifecycle assertions; exercise real temporary Turso files for persistence and concurrency behavior.

### 6. Verify architecture boundaries

S89 must not switch `KvResource`, `SecretStoreResource`, `ActorService`, API contracts, SDK portals, or the control migration. Confirm the new adapter has no dependency on actor manifests/bindings and exposes no guest SQL capability.

Run at minimum:

- `bun --filter @vibecanvas/service-actor test`
- `bun --filter @vibecanvas/service-actor typecheck`
- `bun run lint:functional-core`

## Execution order

1. Define actor-local entry/results/persistence contracts.
2. Add pure identity, JSON, row parsing, and pagination helpers.
3. Implement physical provisioning and verification.
4. Implement read/write/CAS operations.
5. Add write serialization, in-flight tracking, bounded handles, deletion, and close.
6. Add real-file and lifecycle tests.
7. Run focused checks and record measured handle/file behavior.

## Acceptance criteria

- A reusable actor-local adapter can provision independent KV and secret-store files at the fixed host paths.
- The adapter preserves current entry, pagination, revision, delete, and CAS semantics.
- A resource file verifies its own ID, kind, and format before use.
- Missing/corrupt/swapped files are rejected rather than recreated.
- Writes serialize per resource while unrelated resources can proceed independently.
- Handle count is bounded and idle eviction cannot close active work.
- Delete and shutdown drain and close safely.
- No production provider has switched yet and no control migration/data migration is changed.
