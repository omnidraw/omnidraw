# S53 - normalize functional-core extension into reusable core
[Overview](../BASED.md)

Separate the functional-core validation rules from the Pi extension adapter so Pi, CLI, and future Codex hooks can share one implementation.

## Context

The current Pi extension lives at `.pi/extensions/functional-core` and is the de facto source of truth for `fn.*.ts`, `fx.*.ts`, and `tx.*.ts` rules.

Important files:
- `.pi/extensions/functional-core/README.md`
- `.pi/extensions/functional-core/index.ts`
- `.pi/extensions/functional-core/fn-check.ts`
- `.pi/extensions/functional-core/fx-check.ts`
- `.pi/extensions/functional-core/tx-check.ts`
- `.pi/extensions/functional-core/functional-core-lint.ts`
- `.pi/extensions/functional-core/lib/`

Today the reusable validators are exported, but the files still mix core validation logic with Pi-specific hook registration, UI notifications, and tool-call blocking. Normalize this first so future adapters do not depend on Pi-shaped modules.

## Plan

### Phase 1 - inventory current behavior

Read the extension and tests. Identify every public behavior that must remain unchanged for Pi and CLI usage.

### Phase 2 - extract reusable core

Move path matching, rules text, validation functions, report formatting, and edit-preview helpers behind a small reusable API that has no Pi dependency.

### Phase 3 - keep Pi behavior stable

Rebuild the Pi extension as a thin adapter over the reusable core. Keep system prompt injection and write/edit blocking behavior equivalent.

### Phase 4 - verify

Run existing tests and the functional-core lint command. Update README with the new adapter/core boundary.

- Codex support should wait for this task so it can consume the normalized API instead of copying Pi logic.
