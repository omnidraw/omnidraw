# S84 - simplify AI Chat frontend to user-controlled widget drafts
[Overview](../BASED.md)

After S83 is complete, simplify its canvas frontend into one focused AI Chat experience backed by the shared widget draft workspace. Preserve the strongest S83 interaction work while removing the canvas change-set product model and automatic companion preview.

## Prerequisite

Complete [S83](S83.md) first. S84 begins from the finished, tested S83 implementation and treats it as the migration baseline.

## Outcome

When S84 is complete:

- AI Chat is the only AI-specific widget on the canvas.
- The agent can create a scaffolded widget draft and edit its missing implementation through tools.
- Widget drafts live in the shared backend widget workspace and are not owned by a chat or canvas change set.
- Chat sessions keep independent transcripts without owning widget drafts.
- The user explicitly opens Preview for a selected widget draft.
- The user explicitly publishes a selected widget draft.
- The model cannot preview, publish, approve, or reject.
- Settings remains available from the generic widget title bar and replaces the chat body.
- No wizard, candidate phase, Actor view, State view, Configuration view, Changes view, Tool view, checkpoint UI, or automatic preview companion remains.

## Fixed decisions

- Keep the product name **AI Chat**. Do not restore wizard terminology.
- Use one stable model tool registry; do not add frontend workflow phases.
- The backend agent working directory is shared and independent of conversation identity.
- Every widget draft has one logical directory under the shared widget workspace, keyed by widget name.
- AI Chat is conversation UI, not draft ownership.
- There is no canvas-owned change set and no `agent.changeSet.*` frontend API.
- Widget creation is a model tool because deterministic scaffolding belongs in the backend.
- Widget editing uses restricted filesystem tools.
- Widget validation is available to the model and may also be triggered by the user.
- Preview and publish are direct user actions, never model tools.
- Preview is contextual and user-opened; it is not automatically placed on the canvas.
- Protected resource writes retain direct human approval.
- Settings remains a title-bar action.

## Model tools assumed by the frontend

The frontend should render activity for one stable tool registry:

### Widget drafts

- `vc_widget_create`
- `vc_widget_validate`
- `read`
- `edit`
- `patch`
- `grep`

`vc_widget_create` accepts a typed actor/widget definition and generates the manifest, actor registry, types, function stubs, widget entrypoint, styles, package configuration, and validation baseline. The model then implements the product-specific function and UI code with filesystem tools.

### Resources

- `vc_resource_list`
- `vc_resource_inspect`
- `vc_resource_create`
- `vc_resource_update`
- `vc_resource_delete`
- `vc_resource_read`
- `vc_resource_write`

### General

- `web_fetch`

The frontend must not infer workflow phases from tool names. It renders tool execution as compact, expandable activity.

## Target AI Chat UI

AI Chat contains:

1. Chat transcript.
2. Compact tool execution rows.
3. Pending protected-resource approval cards.
4. A compact widget-draft strip or list.
5. Chat composer.
6. Settings replacement page opened from the title bar.

### Widget-draft entry

Each draft entry shows only useful user-facing state:

- widget name
- new or modified status
- draft revision
- validation status
- Preview button
- Publish button

Draft entries come from backend widget-draft APIs. The frontend must not discover drafts by parsing assistant prose or tool-result text.

### User-triggered preview

Clicking Preview opens a contextual dialog or responsive sheet for that widget draft.

The preview surface contains:

- interactive widget rendering
- loading state
- current draft revision
- build or refresh state
- validation or build errors relevant to preview
- Close action with focus restoration

It does not contain:

- actor state
- actor messages
- state transitions
- state-machine visualization
- resource configuration view
- generic Changes view
- checkpoints
- publish controls unrelated to the selected widget

Opening Preview may build the current draft revision. A changed revision marks the open preview stale and offers Refresh; it must not silently represent an old revision as current.

### User-triggered publish

Clicking Publish starts the publish flow for exactly one widget draft and expected draft revision.

The UI must:

- show validation blockers before publishing
- identify stale draft revisions
- show publication progress
- show success or failure
- refresh published widget definitions after success
- never allow an assistant message or tool result to synthesize the user click

If product policy requires a confirmation or immutable approval record, that confirmation is created from the user's Publish action. The model still has no publish-request or approval tool.

## Required API surface

S84 consumes simple chat, widget-draft, preview, publication, approval, and event APIs.

### Chat

- `agent.chat.connect`
- `agent.chat.prompt`
- `agent.chat.cancel`
- `agent.chat.newSession`
- `agent.events`

Chat scope contains canvas authorization context and conversation identity. It does not own a widget draft.

### Widget drafts

- `agent.widgetDraft.list`
- `agent.widgetDraft.get`
- `agent.widgetDraft.validate`
- `agent.widgetDraft.discard`, if draft discard remains a user feature

Public draft responses include:

- stable draft ID or logical widget name
- display name
- new or modified state
- current draft revision
- validation summary
- preview availability
- publish readiness
- timestamps where useful

Never expose absolute server filesystem paths.

### Preview

- `agent.widgetPreview.get`
- `agent.widgetPreview.build`
- `agent.widgetPreview.refresh`
- `agent.widgetPreview.reset`, only when needed for recovery

Preview responses are pinned to a widget draft revision and return only data needed by the interactive preview and its diagnostics.

### Publication

- `agent.widgetPublish.publish` or a user-only `agent.widgetPublish.request`

Input includes:

- widget draft identity
- expected draft revision
- any required user confirmation token or policy context

The frontend must distinguish validation failure, stale revision, permission failure, publication failure, and success.

### Protected resource approvals

- `agent.approval.list`
- `agent.approval.get`
- `agent.approval.resolve`

Approval records are operational records scoped by authorization context. They do not belong to a canvas change set.

### Tool execution recovery

If transcript restoration alone cannot reconstruct structured tool rows:

- `agent.toolExecution.list`
- `agent.toolExecution.get`

These records are conversation-scoped and independent of widget draft ownership.

### Events

Support small invalidation events such as:

- `widget-draft.created`
- `widget-draft.changed`
- `widget-draft.validated`
- `widget-preview.changed`
- `widget.published`
- `approval.created`
- `approval.resolved`
- `resource.changed`
- `tool-execution.changed`

Events carry stable IDs and revisions. Full state is fetched through APIs.

## Plan

### Lane 1 - remove canvas change-set frontend ownership

- Replace all `agent.changeSet.*` consumers with the S84 API surface.
- Remove change-set IDs, artifact IDs, checkpoint IDs, and change-set lifecycle from AI Chat state.
- Model widget drafts directly with stable draft identity and revision.
- Keep conversation identity independent from draft identity.

### Lane 2 - preserve and simplify AI Chat

- Keep streaming, message reconciliation, Markdown, tool rows, images, mentions, cancellation, model preference, and reconnect behavior.
- Keep normal assistant replies compact and inline.
- Render the stable tool registry without phase-specific actions.
- Refresh draft and approval queries from events and reconnect.

### Lane 3 - retain title-bar Settings

- Preserve generic title-bar action support in the widget host.
- Register Settings as the AI Chat title-bar action.
- Keep Settings as a replacement page.
- Restore chat state when returning.

### Lane 4 - add direct widget-draft UI

- Query widget drafts from `agent.widgetDraft.list`.
- Render compact draft entries.
- Reflect create, edit, and validate tool outcomes through refreshed backend state.
- Add accessible Preview and Publish buttons.

### Lane 5 - replace automatic companion preview

- Remove automatic preview-widget creation and canvas placement.
- Remove companion selection coordination and persisted companion layout state.
- Reuse the safe preview sandbox in a contextual dialog or sheet.
- Keep preview revision pinning, loading, errors, refresh, responsive behavior, and focus restoration.
- Exclude all actor-oriented and multi-view preview UI.

### Lane 6 - implement user-only publication

- Start publication only from the draft entry's Publish button.
- Require expected draft revision.
- Surface validation and stale-revision failures before or during publication.
- Refresh draft state and published widget registration after success.
- Ensure model events and tool results cannot invoke the publish handler.

### Lane 7 - retain resource approvals without change sets

- Keep the generic approval card and direct resolution behavior.
- Remove change-set references from approval mapping and UI state.
- Add typed renderers only where resource operation details benefit from them.
- Keep secret values outside transcript and approval details.

### Lane 8 - cleanup and verification

- Remove the AI Preview widget registration.
- Remove Actor, State, Configuration, Changes, Tool, and checkpoint surfaces.
- Remove obsolete change-set and companion-preview styles, types, coordinators, and tests.
- Keep generic host infrastructure that benefits AI Chat and other UI widgets.
- Update documentation and regenerate `FILES.md` according to repository workflow.

## Test plan

### AI Chat

- Restores persisted history on connect.
- Merges streamed message updates without duplicates.
- Keeps one row per tool call.
- Cancels a running prompt.
- Sends text, images, mentions, model, and thinking level correctly.
- Reconnects without retaining obsolete event iterators.

### Settings and widget host

- Settings opens from the widget title bar.
- Back to chat restores scroll and composer state.
- Title-bar actions work in contained and fullscreen modes.
- Cloning AI Chat creates a fresh conversation/session ID.

### Widget drafts

- A scaffolded widget appears after a draft-created event and refetch.
- File edits update draft revision and status.
- Validation state updates from the backend.
- Draft state is not inferred from assistant text.

### Preview

- No preview opens automatically.
- Preview opens only from the user's Preview button.
- Preview is pinned to the requested draft revision.
- A newer draft revision marks the preview stale.
- Closing restores focus to Preview.
- No actor, state, configuration, changes, or checkpoint navigation appears.

### Publish

- No tool result or assistant content can invoke publish.
- Publish starts only from a trusted user click.
- Expected-revision conflict is visible.
- Validation failure blocks publication clearly.
- Success refreshes published widget registration and draft status.

### Protected resource approvals

- Pending approvals render without change-set data.
- Approve and Reject require direct button actions.
- Stale and failed approvals are distinct.
- Unknown details use a safe structured renderer.
- Secret values never render.
