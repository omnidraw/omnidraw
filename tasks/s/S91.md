# S91 - actor resources: move SecretStoreResource out of the control database
[Overview](../BASED.md)

Switch `SecretStoreResource` to an independent physical file, preserve all secret redaction guarantees, and remove the now-unused actor resource key-value table and persistence namespace from the Vibecanvas control database.

## Dependencies

- Blocked by [S89](S89.md) and [S90](S90.md).
- Completes the implementation selected by [E30](../e/E30.md).

## Context

[`SecretStoreResource.ts`](../../packages/service-actor/src/resources/SecretStoreResource.ts) currently reuses `DbServiceTurso['actorResource']['keyValue']` while enforcing a separate public kind and interface:

- values must be non-empty strings;
- actor `get` may return plaintext only to the explicitly authorized actor call;
- `list`, `set`, `delete`, and CAS conflict results omit plaintext;
- management list/get/write surfaces expose names and metadata, never values;
- safe error serialization removes secret-bearing fields.

After S90, `ActorService` temporarily routes KV operations to a physical provider while secret-store management still calls the old control DB namespace. S91 removes that temporary split and then deletes the obsolete control persistence code.

Control-database code to remove or narrow includes:

- `DbServiceTurso.actorResource.keyValue` in [`DbServiceTurso.ts`](../../packages/service-db/src/DbServiceTurso/DbServiceTurso.ts);
- KV reads/page types in [`fx.actor-resource.ts`](../../packages/service-db/src/DbServiceTurso/fx.actor-resource.ts);
- KV writes/results in [`tx.actor-resource.ts`](../../packages/service-db/src/DbServiceTurso/tx.actor-resource.ts);
- KV row parsing/list limits in [`fn.actor-resource-row.ts`](../../packages/service-db/src/DbServiceTurso/fn.actor-resource-row.ts);
- `ZActorResourceKeyValue` / `TActorResourceKeyValue` in [`model.ts`](../../packages/service-db/src/model.ts);
- actor-resource key-value limits in [`CONSTANTS.ts`](../../packages/service-db/src/CONSTANTS.ts);
- [`010-add-actor-resource-key-values.sql`](../../packages/service-db/src/DbServiceTurso/migration-files/010-add-actor-resource-key-values.sql) and its source/embedded registration;
- direct persistence tests in [`DbServiceTurso.actor-resources.test.ts`](../../packages/service-db/src/tests/BunServiceTurso/DbServiceTurso.actor-resources.test.ts) and migration-table assertions in [`tx.migrations.test.ts`](../../packages/service-db/src/tests/BunServiceTurso/tx.migrations.test.ts).

The generic resource catalog and binding tables from migration `009` remain. DbResource draft/apply control tables remain. Only entry contents leave the control database.

## Fixed decisions

### Storage and lifecycle

A secret store lives at:

```text
<dataRoot>/actor-resources/secret-store/<resource-id>/data.db
```

It uses S89's format-v1 key-value file and records exact `secretStore` kind metadata. It must reject a KV file copied into its directory even though the entry schemas are structurally compatible.

Provision, ready reconciliation, deletion, handle eviction, write serialization, and shutdown follow the same physical adapter rules as KV. Failures remain isolated to one resource.

### Confidentiality scope

The independent file is plaintext-at-rest JSON storage. This task improves operational isolation, export/deletion boundaries, and future encryption replaceability; it does not improve confidentiality by itself.

Do not claim encryption or add ad hoc application-level cryptography. OS keychain/master-key lifecycle, encrypted backups, key rotation/recovery, use-only network capabilities, hostile guest sandboxing, and cloud secret managers require a separate deliberate design.

Existing accidental-disclosure protections remain mandatory:

- no plaintext in list/count/write/delete/CAS-conflict results;
- no plaintext in catalog/resource DTOs;
- no plaintext in safe errors, logs, events, snapshots, or test failure fixtures;
- no plaintext management `get` endpoint;
- actor plaintext is returned only from the authorized actor resource `get` call.

### No data migration

Resources are not deployed, so do not add a table-to-file copy, dual read, fallback, backfill, or compatibility migration.

Remove migration `010` from fresh source/embedded migration registration rather than adding a new data migration. A numbering gap is acceptable. Existing local development databases may retain an unused table until reset; runtime code must never read it. Document the reset expectation rather than silently adopting or copying old rows.

## Plan

### 1. Inject the physical store into SecretStoreResource

Change `SecretStoreResource` to depend on S89's actor-local persistence interface. Implement/delegate:

- exact-kind physical provisioning;
- `reconcileReady = true` and physical identity/health verification;
- drain-safe close/delete;
- provider shutdown.

Preserve operation names, permission effect classification, and actor IPC return shapes for `get`, `has`, `list`, `set`, `delete`, and `compareAndSet`.

Validate the persisted value type after parsing. A malformed non-string entry must return a safe secret operation error without echoing the value or raw row.

### 2. Centralize secret management methods on the provider

Expose provider-level management operations used by `ActorService` so the facade never reaches into the raw store:

- count/list names and metadata;
- get metadata/has without returning plaintext;
- compare-and-set write with metadata-only result;
- expected-revision delete;
- current revision lookup needed to construct safe conflict details.

Reuse one secret-name/value validation path for actor and management calls. Keep plaintext inside the smallest operation scope and do not cache decoded values in provider objects.

### 3. Remove ActorService's temporary split backend

Construct and retain the physical `SecretStoreResource` beside the KV provider in [`ActorService.ts`](../../packages/service-actor/src/ActorService.ts). Pass `dataRoot`, database-factory/handle-limit configuration as defined by S89, and register the concrete provider with the generic manager.

Route every `secretStore` management operation through the concrete provider. After this change, no `ActorService` resource-data method may access `config.db.actorResource.keyValue`.

Preserve:

- list/count filters and cursors;
- metadata-only secret reads;
- metadata-only mutation results;
- optimistic expected revisions;
- `SECRET_CONFLICT`, `SECRET_NAME_INVALID`, and `SECRET_VALUE_INVALID` behavior;
- the stable API/AI-tool/frontend contract.

### 4. Add physical secret-store lifecycle and redaction tests

Update provider/manager/service fixtures to use temporary physical files and cover:

- create writes exactly one secret-store resource file;
- actor instance A stores a token and actor instance B reads it through the same definition binding;
- two stores with the same secret name are isolated;
- rebind switches subsequent calls and rebinding back restores access to the first file;
- data survives service stop/reconstruction/startup;
- a missing/corrupt/swapped ready file marks only that store `error` and is not recreated;
- delete remains blocked while bound, then closes/removes the exact unbound directory;
- stale CAS does not overwrite or return the newer plaintext;
- management list/get/write/delete shapes omit plaintext;
- sentinel plaintext is absent from serialized errors, catalog/API responses, AI tool results, events, logs, and value-free actor results;
- shutdown closes both KV and secret providers even if one close fails.

Retain explicit actor IPC coverage proving authorized `get` can carry the plaintext to the actor child. Redaction is not a reason to break the intended secret retrieval use case.

### 5. Remove service-db entry persistence

Once both providers and management paths use physical stores:

1. remove `actorResource.keyValue` from `DbServiceTurso`;
2. remove KV function imports and methods from `fx.actor-resource.ts` / `tx.actor-resource.ts` while retaining catalog/binding functions;
3. remove service-db KV row/page/result types and parsers;
4. remove service-db-only key-value list constants;
5. remove `ZActorResourceKeyValue` and `TActorResourceKeyValue` from the control model;
6. remove migration `010` and its imports/entries from `list-migration-files.ts` and generated `_embedded-migrations.ts`;
7. update migration registration/order tests to accept the intentional numbering gap;
8. change fresh-schema tests to assert `actor_resource_key_values` is absent;
9. remove direct control-DB KV behavior tests now covered by the physical adapter/provider suites.

Do not remove the unrelated global application `kv` table or `DbServiceTurso.keyValue` API from migration `006`.

Do not add `DROP TABLE actor_resource_key_values` or a copy migration. Existing local databases with the old table simply stop using it and can be reset because there is no deployed resource data.

### 6. Verify API, tools, frontend, and build behavior

The external resource-data contract should not change. Run or update only where internal type ownership leaks:

- `packages/api-actors` resource handlers and safe error mapping;
- `packages/service-agent` resource inspection/write tools and approval redaction;
- frontend generic resource page secret editor/list/delete behavior;
- actor IPC/SDK secret portal tests;
- source and embedded migration synchronization;
- compiled binary/native Turso addon tests;
- fresh-start resource creation in source and compiled modes.

A secret store should never be inspectable through the DbResource SQL APIs, and physical paths must remain absent from all public DTOs.

## Acceptance criteria

- Every newly created secret store owns one verified file under the fixed secret-store path.
- Secret-store actor and management operations never access the Vibecanvas control DB for entry data.
- KV and secret-store files verify exact kind identity and cannot be interchanged.
- Plaintext survives authorized actor `get` but is absent from every value-free management/result/error/log/event surface.
- Secret data survives restart and physical resources remain isolated.
- Missing/corrupt/swapped files fail closed without silent recreation.
- The control database retains resource catalogs/bindings but has no actor resource entry API or table on fresh installs.
- Migration `010` is removed without a copy/backfill/drop migration; existing local development DBs may be reset.
- The unrelated global `kv` table/API remains untouched.
- API, AI tools, frontend, IPC/SDK, and compiled behavior remain compatible.

## NOTES

Independent secret-store files are an operational boundary, not an encryption boundary. Keeping the physical adapter narrow and actor-local is what allows a later encrypted provider to replace storage without changing manifests, bindings, IPC, SDK methods, or management DTOs.
