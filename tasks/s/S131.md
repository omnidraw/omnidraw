# S131 - canvas: use Cangine 0.5.3 and own the Capsule portal bridge
[Overview](../BASED.md)

Upgrade the workspace from `@omnidraw/cangine` 0.5.1 to 0.5.3 and move the
small Capsule viewport bridge out of Cangine and into `ui-ai-chat`, where the
embedded-runtime policy belongs.

## Context

Cangine 0.5.3 removes the unpublished optional entrypoint
`@omnidraw/cangine/integrations/capsule`. The root package and the public
`/types`, `/geometry`, `/scene`, `/testing`, `/backend`, and `/editor`
entrypoints are otherwise unchanged. The authoritative consumer guide is
[`docs/internal/llm.cangine-documentation.md`](../../docs/internal/llm.cangine-documentation.md).

The removed runtime exports are:

- `createCapsulePortalRegistration`;
- `decideCapsulePortalAdmission`;
- `normalizeCapsulePortalDiagnostics`;
- `portalGeometryToCapsuleViewport`;
- `readPortalContentCssSize`;
- `CAPSULE_PORTAL_ADMISSION_CEILINGS`; and
- `CAPSULE_PORTAL_VIEWPORT_BOUNDS`.

All `TCapsulePortal*` types were removed with that entrypoint. Omnidraw does
not consume the registration, admission, diagnostics, scheduling, mount, or
lifecycle adapters. It consumes only `portalGeometryToCapsuleViewport` and
`readPortalContentCssSize` in:

- [`packages/ui-ai-chat/src/canvas-extension/index.ts`](../../packages/ui-ai-chat/src/canvas-extension/index.ts);
- [`packages/ui-ai-chat/src/canvas-extension/fx.capsule-portal-viewport.ts`](../../packages/ui-ai-chat/src/canvas-extension/fx.capsule-portal-viewport.ts);
- [`packages/ui-ai-chat/src/widget-runtime/mount-widget-ui-artifact.ts`](../../packages/ui-ai-chat/src/widget-runtime/mount-widget-ui-artifact.ts); and
- [`packages/ui-ai-chat/tests/canvas-extension/fx.capsule-portal-viewport.test.ts`](../../packages/ui-ai-chat/tests/canvas-extension/fx.capsule-portal-viewport.test.ts).

The application already owns the important bridge: it registers each portal
through `engine.portals.register()`, mounts the Capsule-backed runtime into the
provided host, forwards Cangine geometry and visibility into the runtime
owner, and returns asynchronous cleanup that destroys the mounted runtime.
Cangine 0.5.3 keeps that generic registration and cleanup contract. This task
must therefore relocate two small conversion/read helpers, not introduce a
second portal manager or recreate the removed general-purpose adapter.

The workspace pins 0.5.1 in the root, `canvas`, `canvas-contract`, and
`ui-ai-chat` manifests. The lockfile, packed-entrypoint contract test,
frontend diagnostics, trace fixture, and reproduction-trace tests also record
0.5.1 explicitly and must agree on 0.5.3 after the upgrade.

Scene schema remains `1.0.0`. Existing `portalId` values, canvas rows, widget
state, snapshots, collaboration data, and persisted scene nodes require no
migration. No mockup is useful because this is an ownership and dependency
change with no intended visual result.

## Plan

### 1. Pin and qualify Cangine 0.5.3

- Change every workspace dependency pin for `@omnidraw/cangine` from 0.5.1 to
  exactly 0.5.3 in the root, `packages/canvas`, `packages/canvas-contract`, and
  `packages/ui-ai-chat` manifests.
- Regenerate `bun.lock` with Bun and verify it resolves the immutable 0.5.3
  package, integrity, and transitive dependency set rather than retaining a
  stale local-registry 0.5.1 artifact.
- Update the controlled-editor consumer contract to assert the packed 0.5.3
  `/editor`, `/scene`, and package metadata paths.
- Update application diagnostics, reproduction-trace fixtures, scripts, and
  exact-version test expectations from 0.5.1 to 0.5.3. Do not alter fields
  whose value is intentionally caller-provided or `unknown`.
- Verify the retained public entrypoints resolve in Bun and TypeScript and the
  browser build does not rely on an unsupported deep import.

### 2. Make the Capsule viewport conversion application-owned

- Remove every import from `@omnidraw/cangine/integrations/capsule`.
- Keep the generic `context.engine.portals.register({ portalId, mount,
  onGeometryChange, onVisibilityChange })` flow in `canvas-extension/index.ts`.
  Do not wrap it in a replacement registration abstraction.
- Replace `portalGeometryToCapsuleViewport` with a small local conversion from
  Cangine's retained `TPortalGeometry` plus application visibility to
  Capsule's public `CapsuleViewport`.
- Preserve the current invariant that guest CSS layout width and height come
  from the unscaled portal content host, canvas zoom does not resize intrinsic
  guest layout, and `geometry.devicePixelRatio` becomes Capsule viewport
  scale.
- Continue to normalize final values through the existing
  [`fn.capsule-viewport.ts`](../../packages/ui-ai-chat/src/widget-runtime/fn.capsule-viewport.ts)
  bounds: integer CSS-pixel dimensions, scale `0.25..8`, distance
  `0..1_000_000`, priority `-100..100`, and occlusion `0..1`.
- Preserve current presentation defaults: visible portals use `visible` and
  priority `100`; hidden portals use `hidden` and priority `0`; distance and
  occlusion remain `0`.
- Treat missing host or geometry deterministically during mount/unmount races:
  a missing host yields zero CSS size, while missing geometry must use a safe
  scale until Cangine publishes the first geometry update.

### 3. Own portal-host CSS measurement at the browser edge

- Replace `readPortalContentCssSize` with one local browser-edge read helper
  shared by canvas portal viewport updates and the initial artifact mount.
- Read the content box dimensions used by the current bridge and return finite,
  non-negative CSS-pixel width and height. Keep fractional browser measurement
  until `fnWidgetCapsuleViewport` performs the public Capsule normalization.
- Inject the DOM read through an `fx.*.ts` portal instead of directly reading
  runtime globals inside a functional-core file.
- Keep `fxWidgetCapsuleViewport` as an impure read with exactly two parameters:
  `portal: TPortal` and `args: TArgs`. Its exported name must continue to start
  with `fx`, imports must obey the functional-core leaf rules, and it must not
  access `window`, `document`, `globalThis`, `process`, `console`, or `fetch`
  directly.
- If pure conversion logic moves into a new `fn.*.ts` sibling, export only
  `fn*` functions and types, keep imports type-only except permitted
  `fn.*`/`fx.*`/`tx.*`/`CONSTANTS` leaves, and keep it deterministic and
  state-free.
- Reuse this local read/conversion path in
  `mount-widget-ui-artifact.ts`; do not leave a second implementation with
  different rounding, bounds, or zero-size behavior.

### 4. Preserve generic portal lifecycle and durable data

- Keep Cangine responsible for portal registration identity, placement,
  transform, clipping, visibility, input gating, mount generations, and stale
  cleanup.
- Keep Omnidraw responsible for Capsule admission/runtime policy, artifact
  mounting, viewport forwarding, diagnostics, guest channels, and runtime
  destruction.
- Preserve asynchronous cleanup from portal mounts. Unmount must still clear
  application ownership immediately and return/perform the awaited Capsule
  destroy without blocking scene transactions.
- Preserve geometry updates before mount, visibility updates, remounts,
  unregister/re-register reconciliation, runtime replacement, and teardown.
- Do not change scene schema `1.0.0`, rewrite `portalId`, add a database
  migration, or touch persisted canvas/widget-state payloads.
- Do not copy the removed admission ceilings, viewport constants,
  `TCapsulePortal*` type family, or unused diagnostics/scheduling APIs into
  Omnidraw.

### 5. Prove the removed subpath is gone from the consumer

- Update the focused viewport tests to use application-owned test portals and
  helpers rather than importing their expected behavior from the removed
  Cangine adapter.
- Cover zoom independence, host resize, device-pixel-ratio propagation,
  visibility/priority mapping, missing host, missing geometry, fractional and
  invalid dimensions, and public Capsule bounds.
- Cover initial artifact mount measurement and subsequent Cangine geometry and
  visibility callbacks so both paths produce the same normalized viewport.
- Retain or add focused lifecycle coverage for asynchronous Capsule destroy,
  remount, stale cleanup, and portal unregistration.
- Add a package-boundary assertion that the installed 0.5.3 package exposes
  the supported root/subpaths and that production source contains no
  `@omnidraw/cangine/integrations/capsule` import or `TCapsulePortal*` type.
- Run `ui-ai-chat` tests and typecheck, `canvas` tests and typecheck,
  `canvas-contract` tests and typecheck, functional-core lint, the frontend
  production build, and `git diff --check`.
- Update [`FILES.md`](../../FILES.md) for any added, deleted, or materially
  repurposed implementation file.

## Acceptance criteria

- Every workspace consumer resolves exactly `@omnidraw/cangine` 0.5.3.
- No production or test source imports
  `@omnidraw/cangine/integrations/capsule` or references removed
  `TCapsulePortal*` types/exports.
- `engine.portals.register()` remains the only Cangine-to-application portal
  lifecycle boundary.
- Capsule widgets retain intrinsic CSS layout across canvas zoom, update after
  host resize and device-pixel-ratio changes, and receive correct visible/hidden
  priority state.
- Initial mount and later geometry updates use one application-owned viewport
  normalization contract.
- Portal cleanup still supports and correctly isolates asynchronous Capsule
  destruction across unmount, remount, unregister, and runtime teardown.
- Scene schema stays `1.0.0`; existing `portalId` data opens without migration
  or rewrite.
- Root, `/types`, `/geometry`, `/scene`, `/testing`, `/backend`, and `/editor`
  consumer paths remain valid, and frontend/browser packaging succeeds.
- Targeted tests, typechecks, functional-core lint, frontend build, and
  `git diff --check` pass with exact results recorded in the task log.

## NOTES

- This source-breaking change affects only a former optional subpath that had
  not reached an official npm publication. No compatibility shim should be
  published from Cangine or retained indefinitely in Omnidraw.
- Omnidraw currently uses only two removed helpers. Copying the rest of the
  removed integration would recreate upstream coupling without a consumer.
- Cangine's `TPortalGeometry` and generic portal types remain public and are
  valid inputs to the application-owned bridge.
