# S90 - actor resources: move KvResource out of the control database
[Overview](../BASED.md)

Switch `KvResource` and every KV management-data path to S89's independent physical file adapter while preserving the actor IPC, SDK, API, AI-tool, and frontend contracts.

## Dependencies

- Blocked by [S89](S89.md).
- Must land before [S91](S91.md), which moves secret stores and removes the shared control-database persistence.

## Context

[`KvResource.ts`](../../packages/service-actor/src/resources/KvResource.ts) currently accepts `DbServiceTurso['actorResource']['keyValue']`. Its provider lifecycle is effectively empty:

- `provision()` creates no physical data;
- `delete()` relies on a control-database foreign-key cascade;
- `reconcile()` verifies only the catalog kind;
- it has no handles to close.

[`ActorService.ts`](../../packages/service-actor/src/ActorService.ts) constructs the provider from `config.db.actorResource.keyValue` and bypasses the provider for resource-management operations:

- `countResourceData`;
- `listResourceData`;
- `getResourceDataEntry`;
- `setResourceDataEntry`;
- `deleteResourceDataEntry`.

Those methods serve the stable API in [`api.resources.ts`](../../packages/api-actors/src/api.resources.ts), the resource tools in [`tool.resources.ts`](../../packages/service-agent/src/tools/tool.resources.ts), and the generic resource page in [`GenericResourcePage.tsx`](../../apps/frontend/src/feature/resource/GenericResourcePage.tsx). Their external shapes and optimistic revision behavior must not change.

The generic [`ActorResourceManager.ts`](../../packages/service-actor/src/resources/ActorResourceManager.ts) already coordinates creation/deletion sagas, marks lifecycle states in the catalog, blocks bindings/calls, drains actor calls, invokes provider lifecycle methods, and closes providers. Keep it generic; do not construct or special-case `KvResource` inside the manager.

## Fixed decisions

- A KV resource lives at `<dataRoot>/actor-resources/kv/<resource-id>/data.db`.
- The resource catalog and definition bindings remain in `DbServiceTurso`.
- KV entries no longer use the control DB after this task.
- There is no resource data migration/backfill. Existing local test/development resource rows may be reset.
- Public manifest, binding, IPC, SDK, API, management DTO, AI-tool, and frontend contracts remain source-compatible.
- S90 leaves the old shared service-db key-value namespace temporarily because `SecretStoreResource` still uses it until S91.
- KV export, backup UI, watch/subscriptions, TTL, quotas, forks, cloud sync, and cross-resource transactions remain out of scope.

## Plan

### 1. Inject the physical store into KvResource

Change `KvResource` to depend on S89's narrow actor-local persistence interface, not `DbServiceTurso` or a service-db nested property type.

The provider must own/delegate the complete physical lifecycle:

- `provision` validates exact `kv` kind and creates the file;
- `reconcileReady = true` so startup verifies files even for catalog rows marked ready;
- `reconcile` verifies physical identity, format, and health without creating missing data;
- `delete` drains/closes and removes the physical directory;
- `close` closes the adapter/handles.

Do not expose the physical adapter, file path, or handle through actor calls. Preserve the current actor operation names and result shapes for `get`, `has`, `list`, `set`, `delete`, and `compareAndSet`.

### 2. Keep validation and stable errors at the provider boundary

Preserve:

- key max length and non-blank validation;
- list prefix/cursor/limit validation;
- JSON-compatible runtime validation;
- `null` as a stored value inside a non-null entry envelope;
- current `KV_*` stable error codes and safe details;
- read/write effect classification used by function-class and binding scope enforcement.

Remove service-db row assumptions such as `resource_id`, `created_at`, and `updated_at` from provider code by mapping from the actor-local entry DTO. Avoid duplicating JSON validation between actor dispatch and management calls: expose provider-level management methods or one shared local validation path.

### 3. Recompose ActorService

In [`ActorService.ts`](../../packages/service-actor/src/ActorService.ts):

1. construct a KV physical store using `dataRoot` and an optional injected database factory/handle limit for tests;
2. retain the concrete `KvResource` instance as a private field;
3. register it with `ActorResourceManager` exactly as today;
4. route KV management operations through the provider/store rather than `config.db.actorResource.keyValue`.

During the S90/S91 intermediate state, `#withReadyDataResource` may branch by kind:

- `kv` -> physical `KvResource` management methods;
- `secretStore` -> existing control-database persistence.

Keep this branch local to `ActorService`; do not add storage-specific management methods to `ActorResourceManager`. `withReadyResource` must continue to hold the resource lifecycle gate around each management operation so deletion cannot race a management read/write.

### 4. Preserve management behavior

The KV management facade must preserve:

- bounded preview JSON from [`fn.resource-data.ts`](../../packages/service-actor/src/resources/fn.resource-data.ts);
- count and list filters;
- cursor behavior;
- full value only from the explicit KV get path;
- compare-and-set create/update used by `setResourceDataEntry`;
- expected-revision delete and `KV_ENTRY_CONFLICT` details;
- no raw SQL/native/path errors.

Update `fn.resource-data.ts` and its tests to consume actor-local entries instead of `TActorResourceKeyValue` where appropriate. Do not change API schemas or frontend editor behavior merely because storage moved.

### 5. Update service-actor fixtures and tests

Tests that directly instantiate providers currently use:

```text
new KvResource(db.actorResource.keyValue)
```

Update them to use temporary data roots and the physical store. Keep control DB setup for catalogs/bindings only.

Add or adapt coverage for:

- create produces catalog state `ready` only after a verified physical file exists;
- failed provisioning persists an actionable resource error and cleans partial files;
- actor A writes and actor B reads through one definition binding;
- rebinding switches subsequent calls to another physical file;
- equal keys in two resources remain physically isolated;
- values survive `ActorService.stop()`, reconstruction, and startup reconciliation;
- ready startup with a missing/corrupt/swapped KV file marks only that resource `error` and does not recreate it;
- binding/function-class permission tests remain unchanged;
- CAS concurrency still yields one stale-revision winner;
- management list/get/set/delete behavior and value previews remain unchanged;
- deletion is blocked while bound, then closes/removes exactly the unbound resource directory and catalog row;
- one KV failure does not affect secret-store or DbResource operations;
- `ActorResourceManager.close()` closes the KV provider even if another provider close fails.

Use real temporary files in integration tests. Do not make direct SQL inspection of the physical file the primary behavioral assertion except for schema/identity tests owned by S89.

### 6. Verify downstream contract compatibility

No downstream source changes should be necessary unless typing exposes an accidental service-db row dependency. Verify:

- actor resource IPC and SDK tests;
- `api-actors` resource data handlers/tests;
- service-agent resource tool tests, including optimistic writes;
- frontend typecheck/resource page tests if DTO inference changes;
- compiled/native-addon build path, because KV now opens native Turso files in normal use rather than only DbResource use.

The existing secret redaction behavior remains on the old backend until S91 and must not regress during the temporary branch.

### 7. Update architecture notes

Update `packages/service-actor/AGENTS.md` to describe KV as independent while clearly noting that secret stores remain in the control database only until S91. Add no misleading confidentiality claim.

Run at minimum:

- `bun --filter @vibecanvas/service-actor test`
- `bun --filter @vibecanvas/service-actor typecheck`
- `bun --filter @vibecanvas/api-actors test`
- `bun --filter @vibecanvas/service-agent test`
- relevant frontend typecheck/tests if inferred types move
- `bun run lint:functional-core`
- affected compiled binary/native-addon checks

## Execution order

1. Convert `KvResource` to the actor-local persistence contract and real lifecycle.
2. Construct/retain the KV provider in `ActorService`.
3. Route KV management operations through the provider.
4. Update local mapping helpers and direct-instantiation test fixtures.
5. Add restart, reconciliation, deletion, isolation, CAS, and management integration coverage.
6. Verify API, tool, frontend, IPC, and compiled behavior.
7. Update architecture notes and task logs.

## Acceptance criteria

- Every newly created KV resource owns one verified file under the fixed KV path.
- No KV actor or management operation reads/writes `actor_resource_key_values`.
- KV values survive service restart and remain isolated by physical file.
- Missing/corrupt/swapped files become resource-local errors and are never silently recreated.
- Provider creation, deletion, reconciliation, drain, and shutdown participate in the existing manager saga.
- Actor IPC/SDK and management/API/tool/frontend behavior remain source-compatible.
- Secret stores still work on the temporary old persistence until S91.
- No data migration/backfill or control-table removal occurs in this task.
