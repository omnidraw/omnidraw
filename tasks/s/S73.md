# S73 - cli upgrade: replace fixed download marker with streamed progress
[Overview](../BASED.md)

Make `vibecanvas upgrade` report smooth, truthful byte-level download progress instead of appearing frozen at the fixed 85% phase marker.

## Context

The curl-install upgrade path in [`apps/cli/src/plugins/cli/cmds/cmd.upgrade.ts`](../../apps/cli/src/plugins/cli/cmds/cmd.upgrade.ts) emits `Downloading candidate` at 85% and then waits for `Promise.all()` to download the release archive and checksum. `downloadFile()` passes the complete response to `Bun.write`, so it exposes neither transferred bytes nor intermediate progress. A slow or stalled GitHub release download therefore looks frozen at 85%.

The progress renderer already suppresses exact duplicate events, but smooth byte progress needs explicit throttling to avoid excessive terminal writes. Downloads also need cancellation and an inactivity timeout so a dead connection fails clearly. The `initSync()` deprecation warning observed before the progress line is unrelated to this task.

This task supersedes the narrow symptom recorded by completed bug [B4](../b/B4.md), which did not implement download-byte reporting. It overlaps with open bug [B42](../b/B42.md), because the affected machine also has compiled macOS `vibecanvas` processes frozen during startup; S73 owns the transfer implementation and diagnostics, while B42 remains responsible for the safety of replacing and launching the installed binary.

## Reproduction findings

Observed on macOS arm64 on 2026-07-11:

- Two separate upgrade attempts left `vibecanvas-upgrade-*` temporary directories behind.
- Both attempts successfully wrote the 77-byte `vibecanvas-darwin-arm64.sha256` file.
- Neither attempt created the `vibecanvas-darwin-arm64.tar.gz` destination file.
- The same 37,718,779-byte GitHub release archive downloaded successfully with `curl` in approximately 18 seconds, so general GitHub access and the release asset were healthy.
- The evidence localizes the 85% wait to the archive branch of `Promise.all()`, specifically the `fetch` response consumed through `Bun.write(destinationPath, response)`, rather than checksum download, extraction, or verification.
- The current implementation has no inactivity timeout, so this stalled archive operation can wait forever.
- Multiple orphaned compiled `vibecanvas` processes were in macOS `UE` state, and sampling showed `_dyld_start`; investigate this under B42 and ensure S73 tests the compiled binary rather than assuming source-mode Bun behavior is equivalent.
- The `initSync()` deprecation warning is unrelated to the stalled transfer.

## Plan

### 1. Define download progress semantics

- Add a download progress payload that reports downloaded bytes and optional total bytes.
- Reserve a bounded portion of overall upgrade progress for transfer work, then keep extraction, checksum verification, candidate validation, installation, and completion in monotonically increasing ranges.
- Treat `Content-Length` as optional; never fabricate a percentage when the server or proxy does not provide a total.

### 2. Stream downloads to disk

- Replace the observed hanging `Bun.write(destinationPath, response)` path: consume `Response.body` incrementally and write chunks to the destination without buffering the complete release asset in memory.
- Use an explicitly controlled file sink whose open, write, flush, and close lifecycle is covered in source mode and in the compiled macOS binary.
- Report cumulative bytes after chunks are written.
- Preserve HTTP status validation and ensure partial files are closed and removed when transfer fails or is cancelled.
- Follow redirects through `fetch` while using the final response metadata for the byte total.

### 3. Aggregate candidate downloads

- Track archive and checksum transfer state independently if they remain concurrent.
- Compute combined progress from total transferred bytes divided by total expected bytes only when usable totals are known.
- Prefer a simpler sequential checksum-then-archive flow if concurrency makes truthful aggregation or cleanup unnecessarily complex; the archive dominates transfer time.
- Map the transfer ratio into the reserved overall range without allowing progress to move backward.

### 4. Render smooth terminal updates

- Throttle progress callbacks by time and/or visible percentage so network chunk frequency does not flood stdout.
- Show transferred and total sizes when known, for example `Downloading candidate 42.7 MB / 80.1 MB`.
- Show an indeterminate label with transferred bytes when total size is unknown.
- Keep non-TTY output useful and sparse rather than printing every chunk.

### 5. Detect stalled downloads

- Use an `AbortController` for each transfer.
- Add an inactivity timeout that resets whenever a chunk arrives, rather than imposing an unrealistically short timeout on the entire archive.
- Return a clear error identifying the stalled asset and preserve the existing failed-upgrade handling.

### 6. Cover behavior

- Unit test progress ratio calculation, overall-range mapping, monotonic updates, unknown totals, and throttling decisions as pure functions where practical.
- Test streamed download behavior with known and missing `Content-Length`, multiple chunks, HTTP errors, mid-stream failures, and inactivity cancellation.
- Add a regression test proving a completed checksum cannot hide a stalled archive branch indefinitely.
- Test archive/checksum aggregation or the selected sequential flow.
- Run the CLI upgrade dry-run against a controlled local endpoint that can stream slowly, omit `Content-Length`, and deliberately stop mid-response before testing a real GitHub release asset.
- Exercise the real macOS arm64 archive in both source mode and a compiled CLI build; confirm the archive destination appears and grows while downloading.
- Verify TTY and non-TTY output, successful install flow, cleanup of temporary/partial files, and actionable stalled-download errors.
- Coordinate with B42 before considering the end-to-end automatic replacement path safe on macOS.
