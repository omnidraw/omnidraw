# S51 - canvas performance
## Widget connection mesh drag performance report

### 1. Problem

Dragging a widget in a dense widget-connection mesh was extremely expensive.

Old perf sample:

```json
{
  "scenario": "current-widget-connection-full-sync-per-drag-frame",
  "widgetCount": 80,
  "connectionCount": 459,
  "dragFrameCount": 60,
  "elapsedMs": 2710.507,
  "batchDrawCalls": 110340,
  "layerFindCalls": 61,
  "layerFindOneCalls": 27540,
  "linePointWrites": 27540,
  "lineMoveToBottomCalls": 27540,
  "syncCalls": 60,
  "workScore": 11425480
}
```

The hot path was widget drag:

```ts
widgetNode.on("dragmove", () => {
  portal.syncConnections?.(widgetNode)
})
```

That called `txSyncWidgetConnections()` once per drag frame.

The original `txSyncWidgetConnections()` did a **full mesh sync** every time:

1. `layer.find(...)` all widget nodes.
2. Build `widgetById`.
3. For every widget:
   - inspect all input connections.
   - find source widget.
   - sync the connection line.
4. For every connection:
   - `layer.findOne(#lineId)`.
   - rewrite line points.
   - call `moveToBottom()`.
   - sync source and target handles.
5. Batch draw.

This means dragging **one widget** refreshed **all 459 connections** every frame.

With 60 frames:

```txt
459 connections * 60 frames = 27,540 line updates
```

That explains:

```txt
linePointWrites: 27540
lineMoveToBottomCalls: 27540
layerFindOneCalls: 27540
```

And because handle updates call `moveToTop()` / `position()` and trigger Konva internal redraw scheduling, `batchDrawCalls` exploded:

```txt
batchDrawCalls: 110340
```

---

## 2. Core insight

During widget drag, only connections attached to the moving widget need to move.

If widget `A` moves, then only these lines need point recalculation:

- connections where `A` is the target/input widget
- connections where `A` is the source/output widget

All other connection lines are geometrically unchanged.

So the sync operation needs two modes:

```ts
scope: "all" | "attached"
```

Use cases:

- `"all"`:
  - hydration
  - create/delete/reconnect
  - resize
  - undo/redo
  - general full refresh

- `"attached"`:
  - dragmove hot path only

## 3. Implemented solution

### 3.1 Add sync options

I changed the sync args from:

```ts
type TArgsSyncWidgetConnections = {
  node: Konva.Group;
};
```

to:

```ts
type TWidgetConnectionSyncScope = "all" | "attached";

type TArgsSyncWidgetConnections = {
  node: Konva.Group;
  scope?: TWidgetConnectionSyncScope;
  syncHandles?: boolean;
};
```

Defaults:

```ts
const scope = args.scope ?? "all";
const syncHandles = args.syncHandles ?? true;
```

This preserves old behavior for all existing callers.

---

### 3.2 Drag now uses attached-only sync

Old:

```ts
widgetNode.on("dragmove", () => {
  portal.syncConnections?.(widgetNode)
})
```

New:

```ts
widgetNode.on("dragmove", () => {
  portal.syncConnections?.(widgetNode, {
    scope: "attached",
    syncHandles: false,
  })
})
```

Why `syncHandles: false` during drag?

Established connection handles are local to each widget boundary and do not need to be rewritten every drag frame. The widget node itself is moving, so its child handles move with it automatically. For the opposite endpoint, that widget is not changing either.

Only the line endpoints need point updates.

On `dragend`, the code still does a normal sync:

```ts
portal.syncConnections?.(widgetNode)
```

That full/default sync refreshes handles if needed.

---

### 3.3 Pass sync options through WidgetManagerService

The `fxAttachWidgetListener` portal type changed from:

```ts
syncConnections?: (node: Konva.Group) => void;
```

to:

```ts
syncConnections?: (
  node: Konva.Group,
  args?: { scope?: "all" | "attached"; syncHandles?: boolean }
) => void;
```

Then `WidgetManagerService` forwards the options:

```ts
syncConnections: (connectionNode, syncArgs) => txSyncWidgetConnections({
  Circle: Konva.Circle,
  Group: Konva.Group,
  Line: Konva.Line,
}, {
  node: connectionNode,
  ...syncArgs,
}),
```

This was needed in both normal widget listener setup and clone setup.

## 4. Internal optimizations in `tx.sync-widget-connections.ts`

### 4.1 Cache widget node map on the layer

Old code rebuilt widget list every sync:

```ts
const widgets = layer.find((node) => {
  return node instanceof portal.Group
    && node.getAttr(ELEMENT_DATA_ATTR)?.type === "widget";
});
const widgetById = new Map(widgets.map((widget) => [widget.id(), widget]));
```

New code stores a cache on the layer:

```ts
const WIDGET_NODE_MAP_ATTR = "__widgetNodeMap";
```

For full sync:

```ts
buildWidgetNodeMap(portal, layer)
```

always rebuilds the cache.

For attached sync:

```ts
getWidgetNodeMap(...)
```

reuses the cached map if it exists and the moving node is still in the same layer.

Why this works:

- A full sync happens during setup/hydration and creates the cache.
- Drag hot path can reuse the cache.
- If cache is missing/stale for the active node, attached sync falls back to rebuilding it.

Impact:

```txt
layerFindCalls: 61 -> 1
```

---

### 4.2 Cache connection line refs on the layer

Old code did this for every connection update:

```ts
const existingLine = args.layer.findOne(`#${lineId}`);
```

That caused:

```txt
layerFindOneCalls: 27540
```

New code stores line refs:

```ts
const WIDGET_CONNECTION_LINE_MAP_ATTR = "__widgetConnectionLineMap";
type TConnectionLineMap = Map<string, Konva.Line>;
```

Resolution logic:

```ts
const cachedLine = lineById.get(lineId);
if (cachedLine instanceof Line && cachedLine.getLayer() === args.layer) {
  return cachedLine;
}

lineById.delete(lineId);

const existingLine = args.layer.findOne(`#${lineId}`);
if (existingLine instanceof Line) {
  lineById.set(lineId, existingLine);
  return existingLine;
}
```

Why this works:

- Existing rendered lines are stable Konva node objects.
- If a cached line is destroyed or moved off layer, `getLayer()` check fails.
- Then it falls back to `findOne()` once.
- New lines are added to the cache immediately.

Impact:

```txt
layerFindOneCalls: 27540 -> 0
```

In the perf test, the initial full sync populates the line map before instrumentation, so the drag loop has zero `findOne()` calls.

---

### 4.3 Stop `moveToBottom()` on existing line updates

Old:

```ts
if (existingLine instanceof Line) {
  existingLine.points([...]);
  existingLine.moveToBottom();
}
```

New:

```ts
if (existingLine instanceof Line) {
  existingLine.points([...]);
}
```

New lines still do:

```ts
args.layer.add(line);
line.moveToBottom();
```

Why this works:

- Z-order only needs to be established when the line is created.
- Moving the same line to bottom every frame is redundant.
- Existing connection lines already live behind widgets after creation.

Impact:

```txt
lineMoveToBottomCalls: 27540 -> 0
```

This is low-risk because visual order is preserved for newly created lines.

---

### 4.4 Attached-only sync

Full sync still iterates all widgets:

```ts
widgetById.forEach((target) => {
  syncWidgetInputConnections(...)
});
```

Attached sync only handles:

#### Inputs attached to moving node

```ts
syncWidgetInputConnections({
  target: args.node,
  targetData: nodeData,
  ...
});
```

This covers connections where the dragged widget is the target/input widget.

#### Outputs attached to moving node

```ts
syncAttachedWidgetOutputConnections({
  source: args.node,
  sourceData: nodeData,
  ...
});
```

This covers connections where the dragged widget is the source/output widget.

For output connections, the source widget only stores:

```ts
{
  id,
  targetWidgetId
}
```

The line geometry lives on the target input connection:

```ts
{
  id,
  sourceWidgetId,
  line: {
    sourceArc,
    targetArc,
    waypoints
  }
}
```

So attached output sync does:

1. read source output connection
2. find target widget by `targetWidgetId`
3. read target input connection with same `id` and source id
4. sync using that input connection’s line geometry

Pseudo:

```ts
const target = widgetById.get(connection.targetWidgetId);
const targetData = target?.getAttr(ELEMENT_DATA_ATTR);

const inputConnection = targetData.connections?.inputs?.find((candidate) => {
  return candidate.id === connection.id
    && candidate.sourceWidgetId === source.id();
});
```

Why this works:

- The persisted model stores complete line geometry on the target input.
- The source output is just a backlink.
- To update a source-attached line, we must resolve target input metadata.

Impact:

```txt
linePointWrites: 27540 -> 720
```

Why 720?

The dragged node in the perf test has 12 attached connections:

```txt
12 attached connections * 60 frames = 720
```

---

### 4.5 Avoid duplicate line syncs

I added:

```ts
const syncedConnectionIds = new Set<string>();
```

Both input and output sync check:

```ts
if (args.syncedConnectionIds.has(connection.id)) return;
args.syncedConnectionIds.add(connection.id);
```

Why this matters:

If a widget somehow has a connection represented in both traversals, we avoid double-updating the same line in one sync call.

## 6. Why batchDraw dropped so much

The code still calls:

```ts
layer.batchDraw();
```

once per sync.

So expected explicit calls from drag loop are:

```txt
60
```

But perf reported:

```txt
900
```

That means Konva/internal operations still schedule additional draws, likely from line point changes or node mutation. But the count dropped from:

```txt
110,340 -> 900
```

because we stopped:

- handle rewrites during drag
- handle `moveToTop()` calls
- line `moveToBottom()` calls
- full-mesh line mutations

So the biggest `batchDraw` win is mostly from reducing the number of mutated nodes per frame.

# Ranked improvements by impact

## 1. Sync only attached connections during drag

### Impact

Highest.

This changes work from:

```txt
all connections * frames
```

to:

```txt
attached connections * frames
```

In test:

```txt
459 * 60 = 27,540
12 * 60 = 720
```

This is the core optimization.

### Implement first?

Yes. This is the main win.

### Risk

Medium.

Need to ensure full sync still happens for:

- initial render
- create connection
- delete connection
- resize
- hydration
- undo/redo
- dragend cleanup

### How to implement

Add `scope?: "all" | "attached"` to `txSyncWidgetConnections`.

On dragmove:

```ts
portal.syncConnections?.(widgetNode, {
  scope: "attached",
  syncHandles: false,
});
```

Keep default `scope: "all"` for all other callers.

## 2. Skip handle sync during drag

### Impact

Very high for `batchDrawCalls`.

Handles are child nodes of widgets. During drag, they move automatically with their parent. Repositioning them every frame is redundant.

### Implement second?

Yes, together with attached-only sync.

### Risk

Low-medium.

If handle positions depend on live widget size changes, resize/full sync still handles that. Drag does not change size.

### How to implement

Add:

```ts
syncHandles?: boolean
```

Then in `syncConnectionLine`:

```ts
if (!args.syncHandles) return;
```

Call drag sync with:

```ts
syncHandles: false
```

### Impact

Medium-high.

### Implement fifth?

Yes, but after attached-only sync.

### Risk

Medium.

Widget set may change on create/delete/hydrate. Safer approach:

- Always rebuild cache on full sync.
- Reuse cache only on attached sync.

```ts

```

Full sync:

```ts

```

Attached sync:

```ts
const cached = layer.getAttr(WIDGET_NODE_MAP_ATTR);
if valid, reuse; else rebuild.
```

## Summary

The optimization works because it changes drag sync from “refresh the whole graph” to “refresh only edges adjacent to the moving node.”

Old drag frame:

```txt
update 459 connection lines
find 459 line nodes
reorder 459 lines
rewrite handles for 459 connections
```

New drag frame:

```txt
update 12 attached connection lines
find 0 line nodes after cache warmup
reorder 0 existing lines
rewrite 0 handles
```

That produced:

```txt
workScore: 11,425,480 -> 91,720
elapsedMs: 2710.507 -> 3.662
```

The safest implementation path is:

1. scoped attached sync
2. skip handle sync during drag
3. stop `moveToBottom` on existing lines
4. cache line refs
5. cache widget node map
6. only then consider dynamic layers
