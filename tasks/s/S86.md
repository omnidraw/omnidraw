# S86 - human-readable dated AI chat storage and stable chat identity
[Overview](../BASED.md)

Replace the flat, implementation-named AI chat folders with one human-readable chat hierarchy grouped by UTC creation date. Make Vibecanvas chat identity explicit, unique across creation and cloning, and directly usable as the chat directory name without an ID-to-path database.

## Why this task exists

The current storage works, but it describes implementation mechanics instead of product concepts:

```text
<dataPath>/pi/agent/
  sessions/<session-id>/
  chat-cwd/<session-id>/
  widget-cwd/<widget-name>/
  widget-drafts/<widget-name>/
  sdk/
```

This layout has several problems:

- One logical chat is split between `sessions/<id>` and `chat-cwd/<id>`.
- `chat-cwd` and `widget-cwd` say how a path is used, not what it contains.
- Flat UUID folders are difficult to browse, sort, discuss, back up selectively, or diagnose by hand.
- `sessionId` names the Vibecanvas chat identity, while Pi also creates a different internal session ID inside each transcript. The distinction must be documented even though the persisted field name remains unchanged for compatibility.
- Creation time is not visible without opening a transcript or inspecting filesystem metadata.
- The frontend currently creates IDs in more than one lifecycle path without one identity contract.
- AI UI-widget cloning copies the source payload, so a clone can inherit the source chat identity.
- `initialPayload` is currently a registered object rather than a per-widget factory, so repeated AI widget creation can reuse the same value created at plugin registration.

The desired result is boring to inspect: open `agent/chats`, choose a date, choose a chat, and find both its history and its workspace together. The stable chat ID remains the directory name, so lookup does not require a separate index.

## Preflight findings and blockers

The design is feasible without changing Pi or adding a database. The following internal blockers must be handled as part of S86.

### 1. Chat identity is not guaranteed unique in every frontend path

[`Ai.plugin.ts`](../../packages/canvas/src/plugins/ai/Ai.plugin.ts) registers:

```ts
initialPayload: { sessionId: crypto.randomUUID() }
```

That object is created once when the plugin is registered. [`fx.draw-host.ts`](../../packages/canvas/src/services/widget/fx.draw-host.ts) reuses `initialPayload`, and [`tx.create-widget-clone-drag.ts`](../../packages/canvas/src/services/widget/tx.create-widget-clone-drag.ts) clones a UI widget's payload unchanged. A new or cloned AI widget can therefore inherit an existing conversation identity.

S86 must introduce per-instance payload creation and explicit clone identity behavior before the chat ID is trusted as a unique directory key. Undo and redo must retain the clone's already-created ID rather than creating another ID on every replay.

### 2. Existing persisted canvases already contain the correct identity field

The AI widget payload is stored in the Automerge canvas document as `payload.sessionId`. Existing canvases must continue to open their existing chats. S86 cannot reinterpret, regenerate, or silently replace a legacy UUID because that would disconnect the widget from its transcripts and files.

Keep the persisted and API field named `sessionId`. Only new values adopt the dated format. This avoids a risky rewrite of Automerge documents and means the upgrade migration can focus on filesystem operations. In code and documentation, describe this value as the Vibecanvas chat ID and distinguish it from Pi's internal session ID.

### 3. Pi resume behavior is cwd-sensitive

[`AgentService.ts`](../../packages/service-agent/src/AgentService.ts) passes an explicit transcript directory to `SessionManager.continueRecent(cwd, sessionDir)`. Pi filters those files by the absolute `cwd` stored in each JSONL header. Changing the workspace path without updating the header makes an existing transcript look unrelated and can cause Pi to start a new transcript.

[`tx.session-cwd.ts`](../../packages/service-agent/src/core/tx.session-cwd.ts) already rewrites the header cwd before `continueRecent`. S86 must preserve this ordering and add migration coverage for the new path. The Pi transcript's own header `id` remains Pi-owned and must not be replaced with the Vibecanvas chat ID.

### 4. Existing widget mounts use relative links

Current mounts such as:

```text
chat-cwd/<id>/widgets/Weather -> ../../../widget-drafts/Weather
```

become invalid if either side is moved without recreating the link. Migration must first identify and validate backend-owned mounts, move durable folders safely, and then recreate links using a newly calculated relative target. On Windows, the equivalent junction contract must remain supported.

### 5. A chat workspace may contain more than mounts

Bash starts in the chat workspace and is not sandboxed, so ordinary files beneath the chat root are valid. This is not a blocker. Migration simply moves the complete workspace rather than reconstructing it from widget-mount records.

### 6. Current chat-ID validation is broader than the new contract

[`fn.names.ts`](../../packages/service-agent/src/workspace/fn.names.ts) accepts any safe-looking single segment up to 200 characters. It is not a strict dated-ID parser and is not a complete Windows filename rule. S86 needs an explicit new-ID grammar while continuing to accept legacy safe IDs through a separate compatibility branch.

## Outcome

When S86 is complete:

- Every newly created AI chat has one immutable, globally unique `sessionId` that acts as its Vibecanvas chat ID.
- A new `sessionId` contains a readable UTC timestamp plus a full random UUID.
- The chat's directory leaf is exactly its `sessionId`.
- New chats are grouped under `chats/YYYY-MM-DD/`, with the date derived from the validated ID.
- A chat's Pi history and working directory live beneath the same chat folder.
- The workspace still exposes mounted widgets through `workspace/widgets/<name>`.
- Editable drafts and published snapshots are grouped under `widgets/drafts` and `widgets/published`.
- New AI widget creation, New Chat, Edit Existing Widget, clone-drag, undo, and redo all obey one identity lifecycle.
- Existing UUID `sessionId` values continue to open without rewriting canvas documents.
- Pi resumes the existing transcript after a workspace path migration.
- No separate ID-to-directory index is required for new chats.
- Legacy chats use one explicit `chats/legacy/<legacy-id>` bucket because their creation date cannot be derived reliably from their ID.
- TypeScript migration `014` moves the v0.4.7 filesystem into the new layout before services use it.
- Migration is idempotent, forgiving of unknown user files, and non-destructive on collisions or ambiguous state.
- Documentation distinguishes the Vibecanvas chat `sessionId` from Pi's internal session ID.

## Fixed decisions

### Identity

- Keep `sessionId` in canvas payloads, API contracts, and events. It is already durable user data and does not need a schema rename to improve the directory layout.
- Refer to it as the Vibecanvas chat ID where conceptual clarity matters. Pi's transcript/session ID remains a separate Pi-owned value.
- A new chat ID uses this filesystem-safe shape:

```text
YYYY-MM-DDTHH-mm-ss-SSSZ--<full-uuid>
```

Example:

```text
2026-07-18T07-51-37-118Z--cebc287c-52c5-4658-a3ff-6f968af1401e
```

- Use UTC. A chat must stay in the same date group when the host timezone changes.
- The timestamp is created in the frontend because the canvas element and its identity are created there today. It is descriptive grouping metadata, not a security authority.
- Use the full UUID, not an eight-character suffix. Directory creation still rejects an existing mismatched chat rather than treating a statistical guarantee as proof.
- Do not put `/` in `sessionId`. Identity remains one safe filesystem segment.
- Do not use a mutable title in identity or path lookup.
- Do not rename a chat directory when a future title changes.

### Path derivation

- Parse and validate a new formatted `sessionId` with one shared deterministic contract.
- The first ten characters produce the date bucket.
- New chat lookup is direct and contains no search or index:

```text
chatRoot = <agentRoot>/chats/<YYYY-MM-DD>/<sessionId>
```

- A valid legacy ID that does not match the new grammar resolves directly to:

```text
<agentRoot>/chats/legacy/<legacy-id>
```

- Invalid IDs fail before any filesystem access.
- A formatted-looking but invalid date or UUID is invalid; it must not fall back to the legacy bucket.

### Ownership

- One chat owns its metadata, Pi transcript history, workspace directory, and mount set.
- A chat does not own shared widget draft content or published widget content.
- `workspace/widgets/<name>` remains the model-visible lexical namespace and the structured file-tool security boundary.
- Generic read/edit/patch/grep continue to require a validated mount.
- Bash starts in `workspace`, with the same explicit non-sandbox warning established by S85.
- Removing or resetting a chat mount never deletes a shared draft.

### Upgrade compatibility

- Existing `payload.sessionId` remains authoritative and is not rewritten.
- Existing UUID values are preserved exactly.
- Existing arbitrary safe IDs such as UUIDs and historical test IDs resolve to the migrated legacy bucket.
- Compatibility is for persisted IDs, not for generating new legacy IDs.
- Filesystem compatibility is handled once by migration `014`; normal runtime code uses only the new roots after migration.

```text
<dataPath>/pi/agent/
  chats/
    2026-07-18/
      2026-07-18T07-51-37-118Z--cebc287c-52c5-4658-a3ff-6f968af1401e/
        chat.json
        history/
          2026-07-18T07-51-37-118Z_<pi-session-id>.jsonl

            Hacker News Overview -> ../../../../../widgets/drafts/Hacker News Overview

      4464085d-66d8-4baf-bbab-2c8574e4bd2f/
        chat.json
        history/

  widgets/
    drafts/
      Hacker News Overview/

        actor/

    published/
      Hacker News Overview/
        vibecanvas.json
```

The relative link shown above is illustrative. Implementation must calculate it with the path library instead of hardcoding the number of `..` segments.

Keep `sdk`, authentication, models, and settings in their current locations. S86 is about chat identity and workspace readability, not reorganizing every Pi-owned file.

## Chat metadata

Create `chat.json` when a chat is first materialized:

```json
{
  "version": 1,
  "sessionId": "2026-07-18T07-51-37-118Z--cebc287c-52c5-4658-a3ff-6f968af1401e",
  "createdAt": "2026-07-18T07:51:37.118Z",
  "legacy": false
}
```

Rules:

- Metadata is descriptive and helps a human identify the directory.
- The directory selected from the validated `sessionId` remains lookup authority.
- Metadata mismatch is corruption and fails visibly; metadata must not silently redirect lookup.
- Legacy metadata uses `legacy: true`; `createdAt` may be omitted when it cannot be established without guessing.
- Do not put model credentials, authorization context, resource selections, secret values, absolute paths, or mutable runtime state in `chat.json`.
- A future optional title may be added to metadata, but it does not affect identity or directory names.

## Identity lifecycle

### New AI widget

Replace static UI-widget `initialPayload` reuse with a per-instance payload factory or equivalent lifecycle hook. Each new AI widget receives a fresh `sessionId` at element creation time.

Do not mutate a shared registered payload object. Persist the generated ID into the canvas element in the same CRDT commit that creates the element.

### Existing canvas hydration

Use a valid `payload.sessionId` exactly as stored. Generate and persist a new dated `sessionId` only when the field is absent. Never generate a replacement merely because the referenced chat currently has no transcript files; an empty chat is valid.

### New Chat and Edit Existing Widget

Both actions use the same injected ID generator as initial creation. They update the canvas payload before connecting the new chat. They must not remove or mutate the previous chat's history or workspace.

### Clone

A cloned AI widget is a new chat:

- Generate one new `sessionId` when the clone is created.
- Preserve safe user preferences such as model and thinking level when desired.
- Never copy `sessionId` from the source.
- Undo removes the clone element but does not reuse the source identity.
- Redo restores the clone with the same already-generated `sessionId`; it does not create another chat on each redo.

Implement clone payload behavior as an explicit widget lifecycle policy rather than hardcoding AI-specific field knowledge inside generic clone code.

## Storage path API

Centralize path derivation so `AgentService`, `WidgetWorkspace`, migrations, tests, and transcript management do not independently concatenate path fragments.

The semantic operations should include:

- Parse and classify a chat ID as `dated` or `legacy`.
- Return the chat root.
- Return the chat workspace path.
- Return the chat history path.
- Return shared draft and published roots.
- Create and verify `chat.json`.

Keep deterministic parsing and path selection in pure functions. Keep filesystem discovery and metadata reads in `fx.*` helpers. Keep directory creation and migration in `tx.*` helpers, following the repository functional-core rules.

Do not expose absolute storage paths through the API or agent tool results.

## Migration engine extension

[`list-migration-files.ts`](../../packages/service-db/src/DbServiceTurso/list-migration-files.ts) currently returns only SQL file assets, and [`tx.migrations.ts`](../../packages/service-db/src/DbServiceTurso/tx.migrations.ts) only reads SQL text, executes it, hashes it, and records its filename. Extend this into an ordered union:

```ts
type TMigration =
  | { type: 'sql'; name: string; path: string }
  | {
      type: 'typescript';
      name: string;
      version: string;
      run: (portal: TMigrationPortal, args: TMigrationArgs) => Promise<TMigrationResult>;
    };
```

Required behavior:

- TypeScript migrations are statically imported by `list-migration-files.ts`, so Bun compiles them into the executable.
- They are executable modules, not `{ type: "file" }` assets and not dynamically imported source paths.
- The build's embedded-migration generator continues embedding `.sql` assets only. Discovery tests separately verify registered `.sql` and `.ts` migrations.
- A TypeScript migration receives the database plus explicitly injected filesystem operations and `dataDir`; it does not read runtime globals directly from a `tx.*.ts` file.
- The migration runner records its stable `name` and a hash derived from an explicit migration `version` contract after successful completion.
- A migration is recorded only after its SQL or TypeScript operation succeeds. File operations are not falsely treated as part of a SQLite transaction.
- TypeScript migration results may include bounded warnings for preserved unknown entries. Warnings do not expose secrets or absolute paths outside the configured data root.
- Registration order is explicit and deterministic; do not rely only on filesystem enumeration.

The worktree already contains the unreleased `014-add-actor-resource-name-keys.sql`. Because the last published release, 0.4.7, contains only migrations `000` through `008`, S86 may reserve `014-migrate-agent-storage.ts` for the filesystem migration and renumber the unreleased name-key SQL to `015-add-actor-resource-name-keys.sql`. Update registration, embedded SQL generation, and tests together. Developer databases that ran unreleased migrations are test data, not a published compatibility contract; document the reset or repair step for those databases.

Development repair note: the migration runner recognizes the former unreleased `014-add-actor-resource-name-keys.sql` name as an alias of `015-add-actor-resource-name-keys.sql`. When the recorded and current SQL hashes match, it renames the migration record and does not execute the schema change twice. A mismatched hash fails visibly instead of guessing.

## Filesystem migration 014

### Published source layout

The only released upgrade source is `vibecanvas-v0.4.7`. Its agent storage is:

```text
<dataDir>/pi/agent/
  sessions/<sessionId>/
  widget-cwd/<ai-widget-element-id><sessionId>/
  auth.json
  models.json
  settings.json
```

The v0.4.7 `widget-cwd` entry is a per-chat wizard workspace. Its name concatenates the AI canvas element UUID and the chat UUID. It is not the newer canonical published-widget root, even though the later S83 implementation reused the same folder label for a different purpose.

No version after 0.4.7 has been published. Migration 014 therefore targets this released structure first. It may recognize current development-only `chat-cwd`, `widget-drafts`, and named canonical `widget-cwd` entries to preserve local worktrees, but those shapes must not make the production migration destructive or brittle.

### Old roots

Migrate from:

```text
sessions/<sessionId>/
widget-cwd/<widget-element-uuid><sessionId>/

# optional unreleased development shapes
chat-cwd/<sessionId>/
widget-drafts/<widget-name>/
widget-cwd/<widget-name>/
```

to:

```text
chats/legacy/<sessionId>/history/
chats/legacy/<sessionId>/workspace/
widgets/drafts/<widget-name>/
widgets/published/<widget-name>/
```

Do not manufacture a date for legacy IDs from mutable file modification times. An explicit `legacy` bucket is more honest and keeps lookup derivable from the ID without an index.

### Forgiving migration policy

Migration must be:

- Run before accepting chat connections.
- Idempotent after interruption or restart.
- Restricted to direct children with validated names and IDs.
- Collision-aware and non-overwriting.
- Non-destructive until the complete destination is verified.
- Able to handle a transcript-only chat, workspace-only chat, empty chat, and chat present in both roots.
- Able to preserve ordinary workspace files created by Bash.
- Able to preserve all JSONL transcript files, not only the newest one.
- Able to recreate valid backend widget mounts after paths move.
- Able to preserve and report malformed, unrecognized, or unowned entries without following them.
- Safe when destination directories already contain the exact previously migrated data.
- Explicit about cleanup: remove an old empty root only after all its managed children migrate successfully.

Migration runs on user machines whose folders may contain manual edits, partial old runs, `.DS_Store`, arbitrary files, unexpected directory names, or broken links. Unknown content is not permission to delete, overwrite, recursively merge, or abort the entire application.

Classify outcomes deliberately:

- A recognized entry that can be moved safely is migrated and verified.
- An already-migrated identical entry is treated as success.
- An unknown or ambiguous entry is preserved at its source and returned as a warning.
- A source/destination collision preserves both sides and returns a warning unless continuing would make known data unreachable.
- A transient filesystem failure during a recognized move throws before migration 014 is recorded, allowing an idempotent retry on the next start.
- Root directories are removed only when empty. Leftover unknown entries keep the old root in place without affecting the new runtime roots.

Use staging directories and atomic renames within the same data volume where practical. Do not recursively merge two non-empty conflicting directories. Migration success means all safely recognized work was handled and all unrecognized work was preserved, not that every old directory became empty.

### Mount migration order

The implementation must choose and test an order that never mistakes a broken link for a valid mount:

1. Inspect old mounts while their targets still resolve.
2. Record only validated backend-owned mount names and target kinds.
3. Move or stage shared widget roots.
4. Move the complete chat workspace.
5. Remove the old mount entries inside the moved workspace.
6. Recreate links or junctions against the new draft root using calculated targets.
7. Verify every recreated mount resolves to the exact expected direct child.
8. Only then remove obsolete source directories.

Published mounts from older layouts must be handled by the existing compatibility rule: AI Chat ends with draft mounts only. Do not preserve a direct published mount as current editable authority.

### Transcript migration order

1. Move every chat's JSONL files into its new `history` directory.
2. Rewrite current session header cwd values to the new `workspace` path.
3. Call `SessionManager.continueRecent(newWorkspace, historyDir)` only after normalization.
4. Assert through an integration test that the existing latest transcript is resumed instead of creating an unrelated empty transcript.

## Session identity terminology

Keep the serialized field `sessionId` to avoid an Automerge data migration and coordinated public API rename. In documentation and local type aliases, make the two meanings explicit:

- Vibecanvas `sessionId`: stable identity of the complete AI chat and its directory.
- Pi session ID: identity stored in one Pi JSONL transcript header and filename.

Do not replace Pi's transcript ID, and do not couple chat directory naming to a Pi transcript filename. One Vibecanvas chat may contain multiple Pi transcripts in its `history` directory.

## Implementation plan

### 1. Introduce and test the chat identity contract

- Add a pure generator formatter that receives injected time and randomness.
- Add a strict parser/classifier for new dated IDs and legacy IDs.
- Define UTC formatting without `:`, `/`, `\\`, spaces, or filesystem-reserved characters.
- Validate real calendar dates, timestamp shape, UUID shape, maximum length, and legacy safe-segment rules.
- Add direct path derivation tests for dated and legacy IDs.

### 2. Fix frontend identity creation and cloning

- Replace static registered AI `initialPayload` with per-instance payload creation.
- Prefer a generic `createInitialPayload()` widget configuration hook that is invoked for each created element instead of reusing one registered object.
- Use one generator for initial creation, missing-ID hydration, New Chat, and Edit Existing Widget.
- Add a generic widget clone-payload lifecycle hook.
- Make AI clone behavior replace identity while preserving allowed preferences.
- Persist the clone's generated identity so undo/redo is stable.
- Keep existing `payload.sessionId` values unchanged.

### 3. Add the chat storage layout abstraction

- Introduce one path model rooted at `<dataPath>/pi/agent`.
- Derive `chats/<date>/<sessionId>` or `chats/legacy/<sessionId>`.
- Derive `history`, `workspace`, shared draft, and shared published paths.
- Create and validate `chat.json`.
- Update `WidgetWorkspace` to use the new roots while preserving its mount-validation boundary.

### 4. Extend the migration runner and implement migration 014

- Extend `listMigrationFiles()` and `txRunMigrations()` with statically imported TypeScript migrations.
- Give TypeScript migrations an injected database/filesystem/data-directory portal and stable version hash.
- Register `014-migrate-agent-storage.ts`; renumber the unreleased resource-name SQL migration to 015.
- Treat the v0.4.7 `sessions/<sessionId>` plus `widget-cwd/<widgetId><sessionId>` layout as the released source contract.
- Discover old roots without following arbitrary symlinks.
- Preflight all collisions before destructive moves.
- Migrate shared widget roots and per-chat roots with staging and idempotent recovery.
- Preserve arbitrary chat workspace files.
- Recreate owned draft mounts against the new root.
- Normalize all transcript cwd headers.
- Preserve conflicting, malformed, and unknown state and return bounded actionable warnings.

### 5. Update AgentService orchestration

- Run storage initialization and migration before chat connections.
- Resolve workspace and history from `sessionId` through the centralized path model.
- Preserve the order: ensure/migrate workspace, normalize transcript cwd, then continue Pi.
- Pass `workspace` as cwd to Pi services, file tools, and Bash.
- Keep active mount records and draft actor behavior unchanged semantically.

### 6. Clarify identity without changing persisted fields

- Keep API contracts, canvas payloads, event scoping, and authorization DTOs on `sessionId`.
- Document where `sessionId` means the Vibecanvas chat identity and where Pi owns a separate session ID.
- Avoid ambiguous local variables when both identities exist in the same function.

### 7. Update documentation

- Update [`packages/service-agent/AGENTS.md`](../../packages/service-agent/AGENTS.md) with the new ownership tree.
- Update tool prompt wording from generic chat cwd to the concrete chat workspace where useful, without exposing absolute paths.
- Update S83's implemented-layout notes.
- Regenerate [`FILES.md`](../../FILES.md) only if implementation adds or removes indexed source files.

## Required tests

### Identity

- Two consecutive AI widget creations receive different chat IDs.
- Two creations in the same millisecond still differ through the UUID.
- New Chat and Edit Existing Widget receive fresh IDs.
- Cloning creates a fresh ID distinct from the source.
- Clone undo/redo retains the clone ID.
- An existing UUID `sessionId` is used without modifying the canvas document.
- Malformed timestamps, invalid calendar dates, separators, traversal segments, Windows-reserved characters, and malformed UUIDs are rejected.

### Paths and metadata

- A dated ID resolves to `chats/YYYY-MM-DD/<same-id>`.
- A legacy UUID resolves to `chats/legacy/<same-id>`.
- The directory leaf equals `sessionId` exactly.
- Metadata is created once and remains stable.
- Metadata mismatch does not redirect or overwrite a chat.
- UTC grouping is unchanged under different host timezone settings.

### Migration

- SQL and TypeScript migrations execute in explicit registration order.
- A TypeScript migration is compiled into the release binary and records its stable name/version hash only after success.
- The release build embeds SQL assets but does not attempt to load `.ts` source files at runtime.
- A fixture matching the exact v0.4.7 `sessions` and concatenated `widget-cwd` structure migrates.
- A legacy chat with history and mounts migrates completely.
- Transcript-only, workspace-only, empty, and multiple-transcript chats migrate.
- Ordinary Bash-created files survive.
- A valid mount is recreated and resolves to the shared draft.
- An unowned or escaping link is not followed.
- Interrupted migration can be rerun.
- A source/destination collision leaves both sides intact and returns a bounded warning.
- Unknown files and directories remain untouched and do not block startup.
- A transient recognized-operation failure leaves migration 014 unapplied and retries safely.
- Existing UUID canvas identity reconnects to the migrated legacy chat.
- Old roots are removed only when empty and fully migrated.

### Pi continuation

- Header cwd is rewritten to the new workspace.
- `continueRecent` resumes the existing most recent JSONL file.
- Pi's internal transcript ID remains unchanged.
- Reconnect does not create a new transcript solely because storage moved.

### Workspace tools

- `read`, `edit`, `patch`, and `grep` still require `workspace/widgets/<name>/...` mounts.
- Bash starts in the new workspace.
- Shared edits remain visible across two chats mounting the same draft.
- Publish, validation, preview, and draft actor startup still resolve the correct shared draft.
- Unix symlink and Windows junction adapter contracts remain covered.

### Verification

- Run service-agent, api-agent, and canvas package tests.
- Run affected package typechecks.
- Run functional-core lint for any new `fn/fx/tx` files.
- Run `git diff --check`.
- Inspect a copy of a real 0.4.7-style local-volume fixture; never run destructive migration tests against the developer's live local-volume.

## Non-goals

- Human chat titles or automatic title generation.
- Renaming chat directories when titles change.
- Searching chats by title.
- A chat database or ID-to-path index.
- Changing Pi's JSONL format or internal session IDs.
- Exposing absolute storage paths to the frontend or model.
- Sandboxing Bash.
- Per-chat copies of shared widget drafts.
- Widget source version control, checkpoints, or merge history.
- Reorganizing auth, model, settings, or SDK storage beyond what path migration requires.
- Deleting abandoned chats or drafts automatically.

## NOTES

- A UUID is not required by AgentService. Current validation accepts broader safe strings, and the frontend currently chooses the value.
