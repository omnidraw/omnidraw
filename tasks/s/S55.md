# S55 - store images as blob not base64
[Overview](../../BASED.md)

Store image media in Turso as binary blobs instead of base64 text, and rename the `files` table to `media_files` before this migration ships.

## Context
Current image storage work should target the existing, undeployed migration file only:
- `packages/service-db/src/DbServiceTurso/migration-files/003-add-files.sql`

Do not create a new migration because this schema has not deployed yet. Rewrite migration `003-add-files.sql` in place.

Required schema direction:
- Rename table `files` -> `media_files`.
- Replace text/base64 payload storage with a Turso-supported `BLOB` column.
- Use Turso blob behavior from `docs/external/llm.turso.md`.

Primary end-to-end use case:
- Image elements only.
- Canvas image plugin path: `packages/canvas/src/plugins/image`.

This must work through the full stack, not just the schema layer.

## Plan

### 1. Map current image flow end to end
- Find every read/write path that references the current `files` table or image base64 storage.
- Trace image creation from `packages/canvas/src/plugins/image` through canvas services, API/orpc, db service, and back to render/hydration.
- Identify the data contract currently passed around: file id, mime/type, filename, width/height metadata, base64 text, data URL, or URL endpoint.
- Record which parts are persisted in the canvas CRDT element data versus stored in the database.

### 2. Rewrite migration 003 in place
- Edit `packages/service-db/src/DbServiceTurso/migration-files/003-add-files.sql` only; do not add migration `004`.
- Rename the table from `files` to `media_files`.
- Replace any base64/text content column with a blob column.
- Keep required metadata columns needed by image elements, such as id, mime type, size, created timestamp, and any existing ownership/canvas references.
- Update indexes/constraints/triggers in the same migration to use `media_files` names.

### 3. Update db service contracts
- Rename db methods/types from generic file naming to media-file naming where it improves clarity.
- Ensure writes accept binary data (`ArrayBuffer`, `Uint8Array`, or `Blob` depending on current stack conventions) instead of base64 text.
- Ensure reads return binary data or a response/stream suitable for browser image rendering.
- Ensure no server path converts binary image bytes into base64 for storage.

### 4. Update API/orpc routes
- Update routes that upload, fetch, or reference stored image content to use `media_files`.
- Make request/response payloads binary-safe.
- Preserve image element references by id/URL instead of embedding base64 in element data.
- Confirm client fetch/render path can load the blob-backed image.

### 5. Update canvas image plugin
- In `packages/canvas/src/plugins/image`, remove assumptions that persisted images are base64/data URL text.
- Keep image element data small: store media file id and render URL/reference, not raw image bytes.
- On create/paste/upload, send binary image bytes to the stack and persist the returned media id/reference in the element.
- On render/hydrate/reload, resolve media id/reference and display the image.

### 6. Migration/reset expectations
- Because migration `003` is undeployed, reset local/dev databases as needed instead of writing compatibility migrations.
- Check seed/test fixtures that expect table `files` or base64 text and update them to `media_files` + blob.

### 7. End-to-end verification
- Run the stack with all related parts needed for image elements.
- Create or paste an image element.
- Confirm DB row is created in `media_files` with blob bytes, not base64 text.
- Reload the canvas and confirm the image still renders.
- Move/resize/delete normal image element flows and confirm no regressions.
- If there is a public image fetch endpoint, open it directly and confirm it serves correct content type and bytes.

### 8. Tests/checks
- Add/update db tests for inserting and reading blob-backed media files.
- Add/update API tests for image upload/fetch if existing harness covers it.
- Add/update image plugin tests only where current test setup can cover the behavior without excessive integration complexity.
- Run package checks and the relevant app stack before marking done.
