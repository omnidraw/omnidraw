# S92 - db migrations: squash the unreleased post-0.4.7 migration tail
[Overview](../BASED.md)

Replace the churn-heavy, unreleased control-database migration tail with a small final-state upgrade from the last published schema, and make the published migration boundary explicit and verifiable.

## Context

Git history identifies `vibecanvas-v0.4.7` as commit `5cfe5404e92ec87b64af9b7a6ba9a11b4bcf862f`, dated 2026-07-11 14:58:58 +02:00. Its migration registry contains only:

- `000-add-automerge.sql`
- `001-add-auth-tables.sql`
- `002-add-canvas.sql`
- `003-add-media-files.sql`
- `004-add-filesystems.sql`
- `005-add-actor.sql`
- `006-add-key-value.sql`
- `007-add-actor-instance-error.sql`
- `008-add-tool-groups.sql`

No Vibecanvas version has been released since `0.4.7`, so migrations added after `008` have no published compatibility obligation and may be replaced before the next release. The unreleased files were introduced as follows:

- Commit `920fc89512c531d2f542954a537eb3766dc301a2` on 2026-07-12 added `009-add-actor-resources.sql`, `010-add-actor-resource-key-values.sql`, and `011-add-db-resources.sql`.
- Commit `5b40414b09ffa93f44b4aab32caefab0275e14c3` on 2026-07-13 added `012-replace-db-resource-migrations.sql` and `013-add-db-resource-restore-source.sql`.
- Commit `cd13a0671c80c268c88f6a7eac8b634143c02e8a` on 2026-07-18 added the TypeScript filesystem migration `014-migrate-agent-storage.ts` and `015-add-actor-resource-name-keys.sql`.

The current tail is inefficient and obscures the schema that a `0.4.7` user actually needs:

- `010-add-actor-resource-key-values.sql` creates control-database entry storage that S89-S91 deliberately removed in favor of independent physical resource files.
- `011-add-db-resources.sql` creates the abandoned schema/version migration model; `012-replace-db-resource-migrations.sql` immediately drops all of it and creates the final draft/apply model.
- `013-add-db-resource-restore-source.sql` adds `source_apply_id` to a table created one migration earlier.
- `015-add-actor-resource-name-keys.sql` adds `name_key` to the actor-resource table created in `009`.
- `list-migration-files.ts` and `_embedded-migrations.ts` must carry every transitional file and a legacy rename alias even though none shipped.
- `txRunMigrations` stores migration hashes but skips an applied migration by name without verifying its stored hash. That makes the hash column ineffective at detecting accidental edits to published migrations.

## Fixed decisions

### Published boundary

Treat `000` through `008` as the immutable published prefix. Preserve their filenames, ordering, and bytes. Do not rewrite old migrations merely to make a fresh schema prettier.

Treat every migration after `008` as an unreleased tail that may be replaced until the next release is cut. Once the next release ships, its complete registered sequence becomes immutable too.

The supported production upgrade contract for this refactor is:

```text
empty database -> current schema
v0.4.7 schema/history -> current schema
```

Intermediate databases that already applied the unreleased `009`-`015` sequence are local development artifacts, not production upgrade inputs. Reset them rather than adding permanent repair migrations or aliases. Document that reset requirement before implementation.

### Squashed tail

Replace the unreleased SQL tail with two cohesive final-state migrations:

1. `009-add-actor-resources.sql` creates the final actor-resource catalog and binding schema, including `name_key`, its index/constraints/triggers, and no shared actor-resource entry table.
2. `010-add-db-resource-drafts.sql` creates only the final DB-resource draft/apply schema, including `source_apply_id` from the start. It must never create the abandoned schema/version/configuration/block tables or domains.

Keep the agent-storage filesystem move as a separate typed migration because it changes external filesystem state rather than the control-database schema. Renumber it to the next sequence position, update its public migration name, and remove unreleased compatibility aliases rather than preserving the old `014` name.

Do not merge all post-release work into one giant SQL file: actor-resource catalog ownership, DB-resource workflow metadata, and filesystem data movement have different failure and review boundaries.

### Registry and integrity policy

Keep one explicit ordered migration registry as the runtime source of truth. Source and compiled/embedded registration must expose the same ordered names; generated embedded assets must not invent a second order.

Use the stored hash as an integrity check:

- calculate the current descriptor hash before deciding an exact-name migration is already applied;
- fail with an actionable immutable-migration error when an applied migration name has a different stored hash;
- preserve the existing typed-migration version in its deterministic hash input;
- ensure a failed SQL or typed migration is never recorded;
- do not use `legacyNames` to conceal edits to unreleased history after this squash.

Before enabling strict hash verification, prove that hashes produced for the published `000`-`008` files match a real `0.4.7` migration history. If historical runtime/hash behavior cannot be reproduced exactly, stop and design a one-time, explicit compatibility rule for only the published prefix; never silently accept arbitrary mismatches.

### Canonical schema verification

Tests must build a `0.4.7` fixture from the tagged `000`-`008` migration contents or a checked-in equivalent fixture, then run only the current tail. Do not recreate the old schema from current mutable files and call that an upgrade test.

Verify the final schema structurally: tables, columns, domains/checks, foreign keys, indexes, triggers, and absence of transitional objects. Keep application model/parser assertions aligned, but do not treat TypeScript types as proof of database shape.

## Plan

### 1. Capture the release baseline

- Record the `vibecanvas-v0.4.7` tag commit, date, ordered migration registry, and hashes for `000`-`008` in the migration test fixture or release-boundary documentation.
- Confirm the package/binary released at `0.4.7` used the same embedded migration bytes and hash algorithm as the source registry.
- Add a test that fails if any published migration is reordered, renamed, removed, or edited.

### 2. Define the exact final control schema

- Derive the actor-resource schema from current model/query requirements after S89-S91, including final name-key behavior and the absence of shared KV/secret entry persistence.
- Derive the DB-resource schema from the current draft/apply coordinator, including restore provenance.
- Inventory every expected domain, table, column, foreign key, index, trigger, and constraint before rewriting SQL.
- Confirm that the global `kv` table from migration `006` remains unrelated and untouched.

### 3. Rewrite the unreleased SQL tail

- Fold the final actor-resource name-key definition into `009-add-actor-resources.sql`.
- Remove `010-add-actor-resource-key-values.sql` completely.
- Replace the create-then-drop DB-resource sequence with `010-add-db-resource-drafts.sql` containing only the final schema and `source_apply_id`.
- Remove the obsolete `011`, `012`, `013`, and `015` SQL files and every transitional domain/table expectation.
- Do not add a migration that copies or drops data from unreleased local-development schemas.

### 4. Renumber and isolate the typed filesystem migration

- Rename `014-migrate-agent-storage.ts` and its migration identity to the next ordered slot after the two SQL migrations.
- Keep its migration version explicit and its retry/idempotency behavior unchanged unless tests expose a sequencing defect.
- Update typed migration imports, tests, temporary filenames, and diagnostics to the new stable identity.
- Ensure absence of a filesystem portal remains a deliberate, tested behavior and cannot falsely imply that existing production data was migrated.

### 5. Simplify registration and embedded assets

- Update `list-migration-files.ts` to register exactly the immutable prefix plus the three coherent tail steps.
- Remove the unreleased legacy-name repair path and aliases made unnecessary by the release boundary.
- Regenerate `_embedded-migrations.ts` and verify source/embedded SQL names and ordering are identical.
- Verify compiled-binary asset inclusion for the rewritten SQL files and typed migration runtime dependencies.

### 6. Enforce migration immutability

- Change the runner to compare stored and current hashes for exact-name applied migrations before skipping them.
- Return a clear error naming the changed migration and explaining that published migrations are immutable.
- Preserve record-after-success semantics for both SQL and typed migrations.
- Add deterministic tests for matching hashes, mismatched hashes, retry after failure, duplicate execution, and typed migration version changes.

### 7. Replace transitional tests with release upgrades

- Remove tests that intentionally apply `011` and then verify `012` drops it, and remove the unreleased `014`/`015` rename-repair test.
- Add a fresh-install test asserting the exact final schema and exact migration record order.
- Add a `v0.4.7` upgrade test that starts with the tagged `000`-`008` schema and migration rows, preserves representative canvas/actor/tool-group data, and reaches the same final schema as a fresh install.
- Assert that `actor_resource_key_values`, `db_resource_schemas`, `db_resource_schema_migrations`, `db_resource_configurations`, and `db_resource_migration_blocks` never exist in either path.
- Compare schema metadata between fresh install and `0.4.7` upgrade, excluding only nondeterministic engine metadata.
- Retain the filesystem migration's released-layout, development-layout, collision, retry, and idempotency coverage under its new identity.

### 8. Document the workflow and verify release packaging

- Document the immutable-prefix/mutable-tail rule and how to find the last released migration from a release tag.
- Document that developers reset databases which consumed a rewritten unreleased tail; do not normalize those databases in production code.
- Add a release checklist item that freezes the current migration tail when a version is published.
- Run focused service-db and actor-resource tests, functional-core lint, typechecks, embedded asset generation checks, compiled binary/native-addon checks, full relevant builds, and `bun run generate:files` if implementation changes indexed workspace files.

## Acceptance criteria

- Migration files `000`-`008` are byte-for-byte unchanged and protected by a published-boundary regression test.
- A clean database and a genuine `v0.4.7` database both reach the same final control schema.
- The registered post-`0.4.7` tail has exactly two cohesive SQL migrations plus one typed filesystem migration.
- No migration creates the removed actor resource entry table or the abandoned DB-resource schema/version model.
- `actor_resources.name_key` and `db_resource_apply_runs.source_apply_id` exist in their tables' initial creation SQL.
- Source and embedded SQL migration order match exactly, and the compiled application contains every required asset.
- Applied migration hashes are verified; edits to an applied published migration fail clearly instead of being silently skipped.
- SQL and typed migrations are recorded only after success and remain retryable/idempotent where required.
- No permanent compatibility code is added for unreleased `009`-`015` development histories; the reset policy is documented.
- Existing `0.4.7` canvas, actor, and tool-group data survives the upgrade fixture.
