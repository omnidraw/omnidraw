# S85 - agent tool UX: name-addressed resources, visible results, and Pi Bash
[Overview](../BASED.md)

Make the fixed AI Chat tool registry easy for the calling agent to use end to end. Resource tools use human-readable names, stable IDs remain an internal persistence detail, every follow-up value is visible in model content, and the registry includes Pi's built-in Bash tool.

## Context

S83 established a phase-free registry and isolated chat working directories, but the first end-to-end resource exercise exposed a broken handoff:

- [`vc_resource_list`](../../packages/service-agent/src/tools/tool.resources.ts) puts resource records in tool-result `details` while the model-visible `content` says only how many resources exist.
- The same split affects resource inspection, reads, mutation results, and widget validation diagnostics. The UI/runtime can see useful data that the calling agent cannot.
- Resource tools currently require long `resourceId` values. Those IDs are useful for durable bindings and approval execution, but are poor model-facing handles.
- [`fnToolSuccess`](../../packages/service-agent/src/tools/fn.result.ts) and `fnToolError` make it easy to accidentally rely on `details` as the only data channel.
- [`AI_CHAT_TOOL_NAMES`](../../packages/service-agent/src/tools/CONSTANTS.ts) does not include Bash, even though build, test, package, formatting, and general workspace inspection are normal implementation work.

S85 is a tool-contract and agent-runtime task. It does not change the approval UI or its timeout behavior.

## Outcome

When S85 is complete:

- An agent can discover a resource, inspect it, read or write its data, rename it, and delete it using the resource's name only.
- Model-callable resource schemas never accept or require a resource ID.
- Persistent widget-resource bindings and protected-operation execution still use stable internal resource IDs, so a resource rename does not break an existing binding or retarget an approved operation.
- Every safe value needed for reasoning or a subsequent tool call is present in the model-visible content block.
- `details` remains optional host/UI metadata and is never the sole carrier of a usable result.
- Secret plaintext is absent from model content, runtime details, transcripts, summaries, errors, and approval-safe projections.
- Widget validation visibly returns its diagnostics, rather than only `valid` or `invalid`.
- Every conversation receives the same exact 16-tool registry, including Pi's built-in `bash` tool.
- The system prompt describes the actual tool contracts, name resolution, widget mount workflow, Bash scope, and protected-operation boundary.

## Fixed decisions

- Human-readable resource names are the public agent handle.
- Resource IDs are internal host identities. They may be stored in bindings, approval records, and durable database apply records, but are not emitted to the model or accepted by model-callable resource tools.
- Resource names are unique across all resource kinds after normalization. Name lookup never silently chooses among collisions.
- A rename changes the public handle only. Stable bindings continue to reference the same internal ID.
- Resolve a resource name to an ID on the server before creating a protected approval. The immutable approval arguments retain that ID.
- Do not use a resource ID as a pagination cursor. Pagination cursors are opaque host tokens.
- `content` is the calling agent's contract. `details` is not assumed to be model-visible.
- Structured tool results use explicit safe model DTOs. Do not automatically serialize arbitrary `details` into model content.
- Keep protected create, update, delete, and data-write operations behind the existing direct user approval boundary.
- Do not add approval, reject, publish, preview, or resource-binding tools for the model.
- Add Pi's exported `createBashToolDefinition` implementation as `bash`; do not build a second shell protocol.
- Bash is registered through Vibecanvas's normal per-call authorizer and starts in the chat cwd.
- Bash changes the workspace trust boundary: cwd is a starting directory, not a filesystem sandbox. A shell command can traverse outside it. This is accepted for the cooperative local-user model and must be stated honestly in code comments, prompt text, and tests.
- Keep `read`, `edit`, `patch`, and `grep` because they remain more precise and produce clearer edit activity than shell equivalents.
- There is still one phase-free registry. Adding Bash does not restore a two-phase system or a dynamic tool switch.

## Model-visible result contract

### Principle

If a field can influence the next decision or be passed to another tool, it must appear in `content`. Tests must inspect the same content blocks the provider model receives.

Replace the positional result helpers in [`fn.result.ts`](../../packages/service-agent/src/tools/fn.result.ts) with an explicit API that separates safe model data from optional UI details. The exact TypeScript names may vary, but the semantic shape is:

```ts
type TToolSuccess<TModelData, TDetails = TModelData> = {
  summary: string;
  modelData?: TModelData;
  details?: TDetails;
};

type TToolFailure<TModelData = never, TDetails = TModelData> = {
  code: string;
  message: string;
  retryable?: boolean;
  modelData?: TModelData;
  details?: TDetails;
};
```

For structured tools, render one bounded text content block containing the summary followed by a labelled JSON object for `modelData`. Errors visibly include a stable code and message. Keep the representation simple and deterministic; the agent must not need to scrape prose to recover a name, diagnostic, cursor, status, or result index.

Text-native tools may retain their natural payload:

- `read`: file content and line/bounds metadata
- `grep`: path, line, match text, and truncation marker
- `web_fetch`: final URL, HTTP status, content type, truncation/SPA metadata, and fetched body
- `bash`: Pi's normal command output, exit status, timeout/cancellation state, and truncation notices

These tools still must not hide control metadata exclusively in `details`.

### Safety

- Construct `modelData` from explicit safe DTOs; never pass a provider object, native config, environment, absolute path, or unknown exception wholesale.
- Redact secret-store set values before building summaries, approval details, error objects, or model results.
- Add whole-result serialization tests that search `content`, `details`, and errors for supplied secret sentinel values.
- Bound arrays, strings, SQL schema output, command output, and fetched content before rendering them.

## Resource identity and resolution

### Public name model

Define one shared resource-name normalization rule used by create, rename, list ordering, lookup, and persistence:

- trim surrounding whitespace
- normalize Unicode consistently
- reject empty names, control characters, and names longer than 120 characters
- compare case-insensitively with one deterministic locale-independent rule
- preserve the accepted display spelling in `name`
- enforce uniqueness across `kv`, `secretStore`, and `db`

Enforce uniqueness at the resource service/database mutation boundary, not only as a tool preflight, so concurrent create or rename requests cannot introduce duplicates.

The migration must audit existing data. Do not auto-rename a collision and do not pick one matching row arbitrarily. Legacy collisions remain visible as a host repair condition and name-targeted calls fail with `RESOURCE_NAME_AMBIGUOUS` until a user-facing/admin path repairs them. New creates and renames cannot add another collision.

### Lookup helper

Add one reusable service operation that resolves normalized `resourceName` to exactly one resource:

```ts
resolveResourceByName(resourceName, { requireReady: boolean })
```

It returns stable typed errors:

- `RESOURCE_NOT_FOUND`
- `RESOURCE_NAME_AMBIGUOUS`
- `RESOURCE_NOT_READY`
- `RESOURCE_KIND_MISMATCH`

Inspection uses `requireReady: false` so the agent can understand provisioning, migration, and error states. Data reads and writes use `requireReady: true`.

### Durable identities

After resolving a name:

- widget-resource binding rows continue to store `resourceId`
- approval `exactArgs` store `resourceId`, never a second late name lookup
- database draft/apply records continue to store the internal ID
- execution rechecks that the stored ID still exists and is compatible
- a rename between approval request and execution does not change the target
- safe approval UI may show the name and kind, but must not depend on the name as execution identity

Concrete IDs remain absent from `vibecanvas.json`, guest code, prompt prose, model-visible results, and tool input schemas.

## Resource tool contracts

### `vc_resource_list`

```ts
type TResourceListInput = {
  kind?: 'kv' | 'secretStore' | 'db';
  cursor?: string;
  limit?: number; // 1..100, default 20
};
```

Model-visible output:

```ts
type TResourceListOutput = {
  resources: Array<{
    name: string;
    kind: 'kv' | 'secretStore' | 'db';
    status: string;
  }>;
  nextCursor: string | null;
};
```

Sort deterministically by normalized name, kind, and stable internal tie-breaker. `nextCursor` is a bounded opaque host cursor and is never the raw resource ID. Empty pages still return `resources: []` and `nextCursor` visibly.

### `vc_resource_inspect`

```ts
type TResourceInspectInput = {
  resourceName: string;
};
```

Always return safe base metadata, including non-ready resources:

```ts
{
  resource: { name, kind, status, createdAt, updatedAt },
  ready: boolean,
  bindingCount: number,
  currentlyDeletable: boolean,
  deleteBlockedReason: string | null,
  capabilities: { inspect: boolean, read: boolean, write: boolean, rename: boolean, delete: boolean },
  // bounded kind-specific metadata
}
```

For KV and secret stores, include bounded key metadata, counts, and truncation/cursor information. Never include secret plaintext. For databases, include bounded schema objects and explicitly state that no rows were read. Deletability is a current observation, not a reservation; deletion rechecks bindings after approval.

### `vc_resource_create`

Keep the existing kind-specific create input with `{ kind, name }` and optional SQLite engine. On success, visibly return `{ resource: { name, kind, status } }`. The agent follows up using the returned name.

### `vc_resource_update`

Use an explicit rename contract:

```ts
type TResourceUpdateInput = {
  resourceName: string;
  newName: string;
};
```

Resolve `resourceName` once before approval, freeze the stable ID in approval arguments, enforce unique `newName` again during execution, and visibly return the new `{ name, kind, status }`.

### `vc_resource_delete`

```ts
type TResourceDeleteInput = {
  resourceName: string;
};
```

Resolve before approval, freeze the ID, recheck bindings during execution, and visibly return `{ deleted: true, resourceName }`. Do not return the deleted ID.

### `vc_resource_data_read`

Remove the redundant resource-kind discriminator from every query; the resolved resource determines which operations are valid.

```ts
type TResourceDataReadInput = {
  resourceName: string;
  queries: Array<
    | { operation: 'get'; key: string }
    | { operation: 'has'; key: string }
    | { operation: 'list'; prefix?: string; cursor?: string; limit?: number }
    | { operation: 'sql'; sql: string; parameters?: TDbParameter[] }
  >;
};
```

Use an array consistently, including one read. Reject operations unsupported by the resolved kind with a stable per-index error. Return ordered visible results:

```ts
{
  resource: { name, kind, status },
  results: Array<{ index: number; ok: true; value: unknown } | { index: number; ok: false; error: { code, message } }>;
}
```

Secret `get` is unsupported. Secret `has` and `list` expose only existence and key metadata. Database reads remain one bounded read-only SQLite statement per array item with bound parameters.

### `vc_resource_data_write`

```ts
type TResourceDataWriteInput = {
  resourceName: string;
  operations: Array<
    | { operation: 'set'; key: string; value: TJson | string }
    | { operation: 'delete'; key: string }
    | { operation: 'sql'; sql: string; parameters?: TDbParameter[] }
  >;
};
```

Use the resolved kind to validate value types and supported operations. Preserve the existing batch bounds, KV/secret semantics, SQLite durable draft/apply path, exact server-held approval arguments, and stated atomicity. Return ordered visible result objects with indexes, safe errors, atomicity, and safe database apply status. Never echo a secret set value.

## Widget and file tool UX

- `vc_widget_create` visibly returns the normalized widget name, lexical mount path, draft status, and created file paths needed for follow-up reads.
- `vc_widget_load` visibly returns the widget name, lexical mount path, and whether published content overwrote the draft.
- Its description and prompt must state that it mounts only a draft. `syncFromPublished: true` first overwrites/creates that draft from published content; a published directory is never mounted.
- `vc_widget_validate` visibly returns `ok`, bounded errors, warnings, checked files, and truncation flags. An invalid result must contain enough diagnostics for the agent to repair the widget.
- `read`, `edit`, `patch`, and `grep` keep lexical `widgets/<name>/...` paths. Edit results visibly state the path and applied replacement count; patch results state the path; grep retains visible match locations and truncation.
- Tool descriptions name the expected follow-up tool instead of relying on prompt-only knowledge.

## Pi Bash tool

Create a small registry adapter around Pi's exported `createBashToolDefinition(cwd, options)`:

- tool name remains `bash`
- cwd is the conversation's `chat-cwd/<chat-id>`
- the existing `authorize({ chatId, toolName: 'bash', context })` check runs for every call
- cancellation is forwarded
- use Pi's process lifecycle, output streaming/truncation, and exit reporting
- configure a finite default timeout and a bounded caller override supported by the Pi definition; document the chosen values next to registry constants
- preserve Pi's normal shell semantics rather than inventing a partial command language

Do not describe Bash as restricted to mounted widget files. It can use relative traversal, absolute paths, subprocesses, the network, and inherited executable lookup unless the host process is separately sandboxed. The system prompt should tell the agent:

- start work from the chat cwd
- prefer `read`, `edit`, `patch`, and `grep` for normal mounted-widget changes
- use Bash for builds, tests, formatting, package commands, and tasks the structured tools do not cover
- quote paths and avoid destructive commands unless the user explicitly requested them
- do not use shell permission to claim approval, publication, or protected resource mutations occurred
- resource mutations still go through the resource tools and approval coordinator

If environment sanitization is already defined for agent subprocesses, reuse it. Do not invent a claim that environment filtering creates filesystem isolation.

## NOTES

- The reported approval timeout is intentionally outside S85 because the UI has not yet been updated.
- A count-only list result is not a discovery result. The test boundary must be the provider-visible content, not internal `details`.
- Name addressing improves agent ergonomics; stable ID storage preserves rename-safe host semantics. Both are required and serve different layers.
- Bash deliberately weakens the isolation claim of the restricted file tools. S85 must update that claim rather than implying Pi's cwd parameter is a security boundary.
