# S83 - simplify AI chat around canvas change sets, stable tools, and generic approvals
[Overview](../BASED.md)

Replace the phase-driven, single-candidate AI workflow with one canvas-owned active change set, an always-available typed tool registry, individual human approvals for protected operations, and an automatically created companion preview frame.

This task is the concrete implementation direction following the broader S82 investigation. S82 remains useful as migration and problem context, but S83 deliberately chooses a smaller product and backend model.

## Fixed decisions

- The active change set belongs to the canvas, not to a chat, widget, actor, or provider session.
- A canvas has one active change set.
- The active change set may have immutable checkpoints, but there are no branches in this task.
- Publishing always requires explicit human approval.
- Every protected operation receives its own approval; approval bundles are out of scope.
- Database, KV, secret-store, destructive, permission, external-side-effect, and other live writes require approval.
- Reversible writes to isolated drafts do not require approval.
- The preview frame is created automatically when the first previewable widget draft appears.
- The preview frame is a separate `ui-widget` placed next to AI Chat, never a global dialog.
- Tool availability does not change by chat phase.
- Actor candidate and implementation phases are removed rather than generalized.

## Outcome

When S83 is complete:

- One AI Chat can inspect and change many widgets, actors, and resources.
- Multiple AI Chat surfaces on the same canvas contribute to the same active change set.
- Chats keep independent transcripts, but draft ownership and approval state are canvas-level.
- The agent uses the same discoverable tool registry throughout a conversation.
- Backend policy validates each tool call from its target, requested capability, permissions, and current revisions.
- High-level creation tools generate the correct widget and actor boilerplate before the model edits implementation details.
- Tool results explicitly report which entities were read, drafted, changed, previewed, or submitted for approval.
- Protected tools create immutable approval requests instead of executing immediately.
- The frontend renders generic approval cards with operation-specific details and Approve or Reject actions.
- Approval executes only the exact reviewed payload after backend revalidation.
- The frontend can query changed artifacts and preview candidates without parsing chat messages.
- A companion preview frame lists only widgets with draft changes and provides Preview, State, Configuration, and Changes views.

## Context

The current AI workflow couples a chat session to one widget draft and a global actor-candidate flow. Candidate approval changes the available tool set, hidden prompts advance phases, and preview actions are anchored to individual chat messages. This becomes difficult when one request needs to update several widgets, actors, bindings, and resources.

The replacement should be centered on durable product objects rather than model workflow state:

- conversation: transcript, composer state, provider session, and local UI state
- canvas: authorization and active change-set owner
- change set: all current draft changes on the canvas
- draft artifact: one new, modified, or deleted widget, actor, binding, resource configuration, or related artifact
- checkpoint: immutable snapshot of the active change set
- tool execution: auditable read, draft write, protected proposal, validation, preview, or failure
- approval request: immutable human decision for exactly one protected operation
- preview candidate: previewable widget draft derived from the active change set

The backend is implemented first. Its contracts must let a future frontend reconstruct the complete current state without replaying or interpreting prose in the chat transcript.

## Principles

- Tools express product operations, not chat phases.
- Tool policy is checked on every call; it is not represented by enabling and disabling whole tool sets.
- Draft changes are cheap, reversible, revisioned, and automatically persisted.
- Live writes are explicit, individually approved, revision-aware, and auditable.
- Model confirmation is never human approval.
- An approval is stale if its payload, target revision, permission context, or required dependency changes.
- Boilerplate belongs to backend scaffold services, not to prompt instructions.
- Stable entity IDs are used across renames; paths and display names are not authority.
- The frontend reads structured artifact and approval references from APIs and tool results.
- Events notify clients that state changed; query APIs remain the source of truth.

## Backend model

### Canvas active change set

Introduce a persisted `CanvasChangeSet` with:

- change-set ID
- canvas ID
- monotonically increasing revision
- lifecycle: active, publishing, or closed
- draft artifact references
- checkpoint references
- validation summary
- created and updated timestamps

There is exactly one active change set per canvas. Opening AI Chat resolves or creates this record. Closing or deleting a chat does not delete it.

### Draft artifact

Each `DraftArtifact` stores:

- stable artifact ID and kind
- target entity ID when editing an existing entity
- state: new, modified, or deleted
- base published revision
- current draft revision
- draft storage reference
- validation state and diagnostics reference
- dependencies on other draft or published artifacts
- preview capability and latest preview reference
- contributing conversation and tool-call IDs for audit only

Widget and actor drafts remain separate artifacts even when one scaffold operation creates both. Dependencies connect them.

### Checkpoint

A checkpoint is an immutable snapshot of one active change-set revision.

- Checkpoints can be created manually and at important backend boundaries.
- Restoring a checkpoint creates a new active change-set revision; history is not rewritten.
- Checkpoints are not branches and cannot diverge independently.
- Checkpoint creation and restoration are direct user commands, not implicit model authority.

### Tool execution envelope

Every tool result uses one structured envelope containing:

- tool-call ID and tool name
- conversation ID, canvas ID, and active change-set ID
- status: completed, failed, or awaiting-approval
- entity references read by the tool
- draft artifact references created or changed by the tool
- preview references created or invalidated by the tool
- approval request ID when applicable
- compact model-facing summary
- paginated detail reference for large results
- diagnostics and retry metadata

This envelope is the frontend and audit contract. Chat prose is not used to discover what changed.

## Stable tool registry

Remove global candidate and implementation phases. Register supported tools for the entire conversation and enforce each call through backend policy.

### Read tools

- Discover widgets, actors, resources, bindings, and tool groups.
- Inspect entity metadata and relationships.
- Read widget and actor draft files.
- Inspect schemas and run bounded read-only database queries.
- Read the active change set, checkpoints, validation results, approvals, and preview candidates.

Read tools do not require approval, but still enforce visibility and secret boundaries.

### Draft tools

- Create a widget-only draft.
- Create an actor-backed widget draft.
- Open an existing widget or actor as a draft.
- Apply targeted draft file or manifest edits.
- Change draft metadata, icon, bindings, and tool configuration.
- Validate one artifact or the active change set.
- Create or restore a checkpoint.
- Build or reset a draft preview.

These tools write only to the active change set and normally do not require approval.

Creation tools call typed scaffold services. For example, actor-backed widget creation generates the manifest, actor types and transition files, widget entrypoint, styles, resource slots, and validation baseline in one operation. The model receives the created artifact references and edits only the product-specific behavior.

### Protected tools

Protected tools never execute directly from a model call. They create an individual approval request for:

- publishing one selected draft artifact and its explicitly required dependencies
- executing one database mutation
- executing one KV or secret-store write
- deleting or replacing a published entity
- changing permissions or live resource bindings
- invoking an external side effect
- any future operation declared by policy as approval-required

Adding a protected tool must not require a new approval subsystem or a bespoke chat authority flow.

## Generic approval system

### Approval request

Store one immutable `ApprovalRequest` per protected operation with:

- approval ID
- canvas, conversation, tool-call, and change-set IDs
- operation kind and renderer hint
- target entity references
- exact executable payload and payload hash
- human-readable summary
- operation-specific structured details such as SQL or code diff
- risk level and warnings
- required permission
- target and change-set revision preconditions
- expiry
- status: pending, approved, rejected, stale, executing, executed, or failed
- user decision and audit timestamps

### Resolution

Use generic direct APIs such as list/get/resolve approval rather than model-callable approve tools.

Approve must:

1. Verify the request is pending, unexpired, and owned by the canvas.
2. Recheck user permission.
3. Recalculate the payload hash and revision preconditions.
4. Mark changed requests stale instead of executing them.
5. Execute the exact reviewed payload once.
6. Store the result and affected entity revisions.

Reject records the decision and guarantees that the protected operation cannot execute from that request.

Publishing always follows this path. Individual approval means a database mutation approval cannot also authorize publishing, and one widget publish approval cannot silently include unrelated widgets.

## Backend APIs for the future frontend

Provide typed APIs for:

- get active canvas change set
- list changed draft artifacts
- get draft artifact summary and details
- create, list, and restore checkpoints
- list preview candidates
- build, refresh, reset, and inspect a preview
- list and inspect tool executions
- list and inspect approval requests
- approve or reject one approval request
- read validation and dependency summaries
- request publish approval for one selected artifact

Responses must be sufficient after reconnect. Event replay is not required to reconstruct state.

## Frontend

### AI Chat frame

Keep AI Chat focused on:

- conversation
- compact tool rows
- changed-artifact chips
- validation and failure summaries
- generic approval cards
- links that select an artifact in the companion preview frame

The chat queries changed artifacts from the canvas change set. It does not infer changes from message text or rely on a preview button remaining visible in an old tool result.

### Automatic companion preview frame

When the first previewable widget draft appears and no companion exists:

- create a separate `ui-widget` preview frame
- place it next to the originating AI Chat frame using normal canvas placement logic
- associate it with the canvas active change set, not one message
- do not steal focus
- persist its position, size, selected artifact, and selected view

Only changed widget drafts appear in the preview selector. Unchanged published widgets are excluded.

The frame provides:

- Preview: interactive revision-pinned widget preview
- State: actor state, messages, transitions, diagnostics, and optional state-machine visualization
- Configuration: metadata, icon, resource bindings, tool access, and permissions
- Changes: changed files, validation, dependencies, checkpoints, discard, and publish request

Changing the selected draft changes all four views. The frame is not a global dialog and may remain open independently of the chat scroll position.

## Events

Keep events small and use them only to invalidate or refresh query state:

- change-set changed
- draft artifact changed or validated
- checkpoint created or restored
- approval created or resolved
- protected execution completed or failed
- preview candidate added, changed, or removed
- artifact published or discarded

Event payloads carry stable IDs and revisions. Full state comes from APIs.

## Migration and removal

- Map existing active widget drafts into the canvas active change set when recoverable.
- Keep historical chat transcripts readable.
- Replace actor-candidate state with draft artifact metadata.
- Remove hidden phase-transition prompts.
- Remove phase-based tool selection.
- Remove model-callable actor approval and publish authority.
- Route current database proposals through generic approval requests.
- Replace message-anchored preview dialogs with companion preview selection.
- Delete compatibility code after active drafts and API callers are migrated.

## Plan

### Lane 1 - contracts and persistence

Define and persist canvas change sets, draft artifacts, checkpoints, tool execution envelopes, approval requests, and preview candidates.

### Lane 2 - backend tool simplification

Introduce the stable tool registry, per-call policy checks, canvas context, structured result envelopes, and scaffold-backed draft tools. Remove phase transitions only after the replacement path is covered.

### Lane 3 - generic approvals

Implement approval creation, query, resolution, staleness, execution, and audit. Migrate database writes and publish first, then other protected writes.

### Lane 4 - preview backend

Derive preview candidates from changed widget drafts and expose revision-pinned preview, state, configuration, change, and diagnostic APIs.

### Lane 5 - frontend

Render artifact references and generic approval cards in chat. Automatically create the companion preview frame and implement its selector and four views.

### Lane 6 - migration cleanup

Migrate recoverable drafts, remove actor candidate and phase machinery, remove old preview dialogs, update documentation, and delete compatibility code.

## NOTES

### Explicit non-goals

- Multiple active change sets or branches per canvas.
- Approval bundles or one approval authorizing several operations.
- Automatic publishing after validation.
- Phase-specific tool registries.
- A model-callable approval command.
- Global preview dialogs.
- Treating events as the authoritative state store.
- Loading every canvas entity into the initial model context.
