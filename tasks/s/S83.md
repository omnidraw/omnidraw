# S83 - isolated AI Chat workspaces over shared widget folders
[Overview](../BASED.md)

Replace session-phase widget workflows with isolated per-chat working directories that mount explicitly selected shared drafts. Published widgets have one canonical snapshot in `widget-cwd`; AI Chat edits only folders in the separate draft root.

This is a backend and agent-runtime task. It does not change the frontend. It does not introduce canvas change sets, checkpoints, fingerprints, revision hashes, or a custom version-control system.

## Fixed decisions

- Chats keep independent transcripts, provider sessions, and cwd directories.
- A chat cwd is `<dataPath>/pi/agent/chat-cwd/<chat-id>` and never contains a provider session ID.
- Every chat cwd starts with an empty `widgets/` directory.
- A chat sees only widgets explicitly loaded into that conversation.
- `vc_widget_load` mounts a selected draft into the chat's `widgets/` directory and can explicitly overwrite it from published content first.
- On Unix, a mount is a backend-created directory symlink.
- On Windows, the backend may use a directory junction or backend virtual mount when symlink creation is unavailable.
- The agent cannot create arbitrary symlinks, junctions, or mounts.
- Published widgets have exactly one canonical folder at `<dataPath>/pi/agent/widget-cwd/<widget-name>`.
- New unpublished widgets live at `<dataPath>/pi/agent/widget-drafts/<widget-name>`.
- `vc_widget_create` creates a complete unpublished draft folder and mounts it into the invoking chat.
- Loading an existing draft never copies its files. `syncFromPublished: true` explicitly overwrites or creates that shared draft from the canonical published snapshot.
- Multiple chats loading the same widget resolve to the same real folder, so edits are immediately shared.
- Unloading or deleting a chat mount removes only the link. It never deletes the published widget or unpublished draft folder.
- Widget names and mount names use one human-readable filesystem-safe normalization rule and reject collisions.
- A widget rename is not an in-place rename. Renaming means creating and publishing a new widget; the previous published widget remains independent.
- Published folders are never mounted into AI Chat. All AI edits happen in shared drafts, and publishing snapshots the draft into the canonical published folder without retargeting mounts.
- Publishing and approval are not AI tools. Existing user-controlled publishing and approval remain outside S83.
- Every conversation receives the same exact 15-tool registry. There is no phase 1, phase 2, candidate, or implementation tool switch.
- Backend authorization is checked per tool call.
- There is no `CanvasChangeSet`, `DraftArtifact`, checkpoint, preview-candidate database, immutable base snapshot, fingerprint, payload hash, or revision ledger.

## Filesystem model

```text
<dataPath>/pi/agent/
  chat-cwd/
    <chat-a>/
      widgets/
        Weather -> ../../../widget-drafts/Weather
        Timer   -> ../../../widget-drafts/Timer
    <chat-b>/
      widgets/
        Weather -> ../../../widget-drafts/Weather

  widget-cwd/                      # canonical published widget folders
    Weather/
      vibecanvas.json
      src/
      ...

  widget-drafts/                   # new, unpublished widget folders
    Timer/
      vibecanvas.json
      src/
      ...

  conversation-sessions/           # transcript/provider state only
    ...
```

The chat cwd provides isolation and discoverability. The link target provides sharing. Neither the chat cwd nor transcript storage owns widget files.

## Ownership boundaries

### Conversation

A conversation owns:

- Its transcript
- Its provider-session state
- Its `chat-cwd/<chat-id>` directory
- Its set of widget mounts

A conversation does not own:

- A published widget folder
- An unpublished widget draft folder
- A candidate actor
- A publish phase
- A checkpoint
- A change set

### Published widget root

`widget-cwd/<widget-name>` is the canonical published snapshot and is never mounted into AI Chat.

- Reconciliation creates a canonical folder only when it is missing.
- Reconciliation never overwrites an existing canonical folder.
- Explicit sync copies the canonical folder into `widget-drafts/<name>` and overwrites any current draft.
- Validation and AI file tools read only the mounted draft.
- The existing publish service validates a draft snapshot and updates the canonical folder.
- Deletion uses the existing published-widget deletion boundary and then removes or archives the canonical folder.

### Unpublished widget root

`widget-drafts/<widget-name>` stores every AI-editable widget, including new widgets and published widgets explicitly synced for editing.

- Creating a new draft must not collide with a published widget, another draft, or an existing mount in the invoking chat. Explicit sync may create the same-name draft for a published widget.
- Other chats may load the same draft explicitly with `vc_widget_load`.
- Publish validates the draft, snapshots it into `widget-cwd/<widget-name>`, registers or updates the published widget, and leaves every chat mount on the draft.
- A failed publish leaves the draft and its mounts intact.
- Removing a mount never removes the draft.
- Abandoned draft deletion remains an existing user-controlled backend operation; it is not an AI tool in S83.

### Rename behavior

S83 does not support renaming a published widget in place.

- The directory name is the published widget name.
- Changing the declared name inside an already published widget folder fails validation with guidance to create a new widget.
- A renamed widget is created in `widget-drafts/<new-name>` and is published as a new widget identity.
- The old widget and its canonical folder are not renamed or deleted automatically.
- Stable rename identity and migration may be added later if the product needs it.

## Widget and mount naming

Implement one small deterministic name-normalization function.

Requirements:

- Human-readable output
- Stable for an unchanged name
- Reject empty names, `.`/`..`, separators, traversal, reserved names, and control characters
- Detect case collisions on case-insensitive filesystems
- Reject collisions across `widget-cwd`, `widget-drafts`, and the chat's `widgets/` directory
- No hashes, fingerprints, random suffixes, entity IDs, session IDs, or timestamps

The backend alone creates and removes mounts. Before creating a mount it verifies that:

- The requested widget or draft exists.
- The link name is safe and unused.
- The target is a direct child of `widget-cwd` or `widget-drafts`.
- An existing filesystem entry is never silently replaced.

## Chat cwd and mount resolution

Replace current and legacy cwd shapes such as:

```text
conversation-cwd/<canvasId>/<chatWidgetId>/<sessionId>
widget-cwd/<widgetId><sessionId>
```

with:

```text
chat-cwd/<chat-id>/
```

On connection:

1. Ensure `chat-cwd/<chat-id>/widgets` exists.
2. Start or resume the independent transcript/provider session.
3. Pass `chat-cwd/<chat-id>` to the agent session as `cwd`.
4. Normalize current transcript cwd headers when required.
5. Preserve valid existing mounts for that chat across reconnect.

The generic file tools accept lexical paths inside the chat cwd. For paths beneath `widgets/<name>` they may resolve through a backend-created mount into `widget-cwd` or `widget-drafts`.

The path guard must not use the naïve rule “the resolved path must remain below chat cwd,” because valid widget mounts intentionally resolve outside it. Instead it verifies both:

1. The lexical path enters through a validated direct child of the chat's `widgets/` directory.
2. The resolved target remains inside the exact canonical widget or draft directory registered for that mount.

Direct absolute access to `widget-cwd` or `widget-drafts` without a chat mount is rejected. The agent cannot use a symlink it created itself to expand access.

Writes through `edit` and `patch` are serialized per real widget folder and committed with temporary-file plus atomic-rename behavior. Concurrent chats may edit the same real files; S83 does not add merge, undo, history, or conflict revisions.

## Exact phase-free AI tool registry

Register the following exact tools for every conversation from its first message through reconnect and continuation.

### Widgets and files

1. `vc_widget_create`
2. `vc_widget_load`
3. `vc_widget_validate`
4. `read`
5. `edit`
6. `patch`
7. `grep`

#### `vc_widget_create`

Creates one complete new widget in `widget-drafts` and mounts it into the invoking chat.

```ts
type TWidgetCreateInput = {
  name: string;
  kind: 'widget' | 'actor-widget';
  description?: string;
};
```

The backend scaffolds the manifest, widget source, actor files required by the selected kind, styles, package configuration, and validation baseline. Partial scaffolds are rolled back.

#### `vc_widget_load`

Loads an existing shared draft into the current chat. It never mounts a published folder.

```ts
type TWidgetLoadInput = {
  name: string;
  syncFromPublished?: boolean;
};
```

When `syncFromPublished` is true, the backend atomically overwrites or creates the shared draft from the canonical published snapshot before mounting it. Repeating a plain draft load is idempotent when the existing mount already points to that draft. A conflicting mount fails.

Mount removal is a backend chat-lifecycle operation, not another AI tool. It removes only the mount.

#### `vc_widget_validate`

```ts
type TWidgetValidateInput = {
  name: string;
};
```

Validation resolves only a widget currently mounted in the chat. It uses the trusted host compiler and SDK declarations and returns bounded diagnostics. It never publishes.

#### `read`, `edit`, `patch`, and `grep`

These generic tools operate from the isolated chat cwd. Widget access must go through `widgets/<mounted-name>/...`. Results and searches are bounded. `edit` and `patch` use serialized atomic writes to the real target folder.

There are no AI tools for widget publish, approval, rejection, deletion, unload, checkpoints, change sets, phases, or candidates.

### Resources

8. `vc_resource_list`
9. `vc_resource_inspect`
10. `vc_resource_create`
11. `vc_resource_update`
12. `vc_resource_delete`
13. `vc_resource_data_read`
14. `vc_resource_data_write`

The first five tools manage resource definitions and lifecycle. The two `data_*` tools operate on the contents of one specific `resourceId`.

Resource kinds in S83 are:

```ts
type TResourceKind = 'kv' | 'secretStore' | 'db';
```

All resource tools enforce visibility, authorization, kind matching, input bounds, and secret redaction. Resources remain host-global in S83; there is no resource-scope schema change. Resource IDs are backend identities; paths and database handles are never exposed.

#### `vc_resource_list`

```ts
type TResourceListInput = {
  kind?: TResourceKind;
  cursor?: string;
  limit?: number;
};
```

Returns a bounded stable page containing resource ID, kind, name, readiness, and safe summary metadata. It never returns KV values, secret values, database rows, database paths, or native configuration.

#### `vc_resource_inspect`

```ts
type TResourceInspectInput = {
  resourceId: string;
};
```

Returns kind-specific safe metadata:

- `kv`: limits, approximate entry count when available, and binding metadata; no values.
- `secretStore`: key names or key metadata only when policy allows; never plaintext values.
- `db`: SQLite schema metadata, tables, columns, indexes, views, triggers, and binding metadata; no table rows.

#### `vc_resource_create`

```ts
type TResourceCreateInput =
  | { kind: 'kv'; name: string }
  | { kind: 'secretStore'; name: string }
  | { kind: 'db'; name: string; engine?: 'sqlite' };
```

SQLite is the only database engine in S83. Name collisions fail clearly. The tool uses the in-memory approval boundary described below.

#### `vc_resource_update`

```ts
type TResourceUpdateInput = {
  resourceId: string;
  name?: string;
};
```

Only mutable resource metadata is updated. It cannot change a resource kind, expose storage paths, replace a database engine, or write resource data.

#### `vc_resource_delete`

```ts
type TResourceDeleteInput = {
  resourceId: string;
};
```

Deletion fails while live bindings reference the resource unless the existing user-controlled deletion flow explicitly resolves those bindings. The AI tool cannot force deletion or approve it.

#### `vc_resource_data_read`

`query` accepts either one kind-specific query or an array. The resource kind must match every query.

```ts
type TKvReadQuery =
  | { kind: 'kv'; operation: 'get'; key: string }
  | { kind: 'kv'; operation: 'has'; key: string }
  | { kind: 'kv'; operation: 'list'; prefix?: string; cursor?: string; limit?: number };

type TSecretStoreReadQuery =
  | { kind: 'secretStore'; operation: 'has'; key: string }
  | { kind: 'secretStore'; operation: 'list'; prefix?: string; cursor?: string; limit?: number };

type TDbParameter =
  | string
  | number
  | boolean
  | null
  | { type: 'integer'; value: string }
  | { type: 'blob'; base64: string };

type TDbReadQuery = {
  kind: 'db';
  sql: string;
  parameters?: TDbParameter[];
};

type TResourceDataReadQuery = TKvReadQuery | TSecretStoreReadQuery | TDbReadQuery;

type TResourceDataReadInput = {
  resourceId: string;
  query: TResourceDataReadQuery | TResourceDataReadQuery[];
};
```

Read behavior:

- Results are returned in input order in a `results` array, including for a singular query.
- Every result has its own success or structured error status so one failed query does not erase earlier results.
- KV `get` may return the stored value within response-size policy.
- Secret-store reads report only existence or key metadata; secret plaintext is never returned.
- DB queries use SQLite syntax, accept bound parameters, and must be read-only.
- Each DB query is one SQLite statement. Multiple statements are expressed as an array of queries.
- Database rows, bytes, execution time, and total batch size are bounded.
- An array is evaluated sequentially against the same resource; it does not imply a write transaction.

#### `vc_resource_data_write`

```ts
type TJson =
  | null
  | boolean
  | number
  | string
  | TJson[]
  | { [key: string]: TJson };

type TKvWriteOperation =
  | { kind: 'kv'; operation: 'set'; key: string; value: TJson }
  | { kind: 'kv'; operation: 'delete'; key: string };

type TSecretStoreWriteOperation =
  | { kind: 'secretStore'; operation: 'set'; key: string; value: string }
  | { kind: 'secretStore'; operation: 'delete'; key: string };

type TDbWriteOperation = {
  kind: 'db';
  sql: string;
  parameters?: TDbParameter[];
};

type TResourceDataWriteOperation = TKvWriteOperation | TSecretStoreWriteOperation | TDbWriteOperation;

type TResourceDataWriteInput = {
  resourceId: string;
  operation: TResourceDataWriteOperation | TResourceDataWriteOperation[];
};
```

Write behavior:

- The resource kind must match every operation.
- KV and secret-store key/value limits are enforced.
- DB writes use SQLite syntax and bound parameters.
- A DB operation is one SQLite statement; multiple statements use an array.
- Protected writes pause on the process-local approval coordinator; the agent cannot approve them.
- Secret values are accepted as write input but never echoed in results, logs, inspection, or approval summaries.
- Batched write atomicity follows the resource implementation and must be stated in the result; S83 does not invent a cross-resource transaction.

#### In-memory approval for protected resource tools

`vc_resource_create`, `vc_resource_update`, `vc_resource_delete`, and `vc_resource_data_write` require user approval before execution. Approval state is intentionally process-local and is not stored in the control database.

1. The tool stores an immutable in-memory copy of its exact arguments and emits a safe approval request.
2. The existing user-controlled approval API resolves only the approval ID and approve/reject decision; it cannot replace the stored arguments.
3. Approval rechecks the current user's authorization, claims the request once, and executes the stored operation.
4. Rejection, timeout, chat cancellation, disconnect, or server restart cancels the pending tool call without executing it.
5. Resolved and canceled requests are removed from memory. They are never resumed after restart.
6. Secret values remain only in the server-side pending payload and are omitted from approval details and logs.
7. Execution is never automatically retried after an ambiguous process failure. SQLite mutations continue using the existing durable DB draft/apply machinery for operation execution.

No approval hash, approval table, protected-execution ledger, or generic persisted tool-execution table is introduced.

## Validation and existing publish boundary

Validation operates directly on one mounted widget folder.

- Use the host-selected trusted compiler and SDK declarations.
- Do not resolve compilers or executables from model-authored widget files.
- Return bounded diagnostics to the requesting chat.
- A published widget whose declared name differs from its canonical directory name fails validation; the user must create a new widget draft for the new name.

S83 does not add or change publishing UI. The existing user-controlled publishing path must support:

### Existing published widget

1. Resolve the selected canonical folder in `widget-cwd`.
2. Validate it.
3. Install or reload it through the existing publication boundary.
4. Leave the same canonical folder and all chat mounts in place.

### New unpublished widget

1. Resolve the selected folder in `widget-drafts`.
2. Validate it.
3. Fail if `widget-cwd/<name>` already exists.
4. Atomically snapshot the folder into `widget-cwd/<name>` as part of publication while retaining the draft.
5. Register the new published widget.
6. Leave chat mounts on the shared draft target.
7. On failure, keep the draft and restore or remove the canonical snapshot as appropriate.

No fingerprint, checkpoint, or custom history record is created before or after publishing.

## Migration and removal

- Keep historical transcripts readable.
- Stop creating `conversation-cwd/<canvas>/<widget>/<session>` directories.
- Stop using legacy `<widgetId><sessionId>` directories as current write paths.
- Create persistent `chat-cwd/<chat-id>/widgets` directories for current chats.
- Reconcile each published widget into one missing canonical `widget-cwd/<name>` folder without overwriting an existing folder.
- Preserve old session workspaces outside the current write path for manual inspection; do not hash, fingerprint, or automatically merge them.
- Remove actor-candidate state, hidden phase prompts, and phase tool gates from the agent runtime.
- Do not delete historical user files during migration.
