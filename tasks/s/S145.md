# S145 - resources: enforce cloud-portable semantics in the OSS providers (order 6/8)
[Overview](../BASED.md)

Make the existing local Resource Store satisfy the portable SDK behavior,
including a Turso-Cloud-compatible SQL profile, while preserving every OSS
resource-management capability.

## Context

OSS resources are independent local KV, encrypted secret-store, and database
files. `DbResource` uses local Turso Database and currently accepts a broader
guest SQL surface than a remote Turso deployment can reproduce safely. The
private resource API also provides catalog CRUD, data editing, database row
editing, drafts, apply/backup/restore, inspection, and live SQL. The refactor
must not remove those OSS capabilities or replace local providers with a cloud
client.

## Plan

### 1. Route providers through the portable contract

- Adapt KV, secret-store, and DB providers to the SDK operation registry,
  codec, limits, and failures from [S144](./S144.md).
- Keep provider mechanics, encryption, files, local database handles, WAL,
  idle-handle eviction, write serialization, backups, and reconciliation in
  `apps/backend`.
- Remove duplicated portable operation declarations and conversion types where
  the SDK contract now owns them; retain backend domain and provider types that
  carry real local policy.

### 2. Define and enforce the portable SQL profile

- Validate named-operation SQL during offline check and host acceptance, and
  validate arbitrary SQL again at every call.
- Allow one bounded statement for a query or execute call. Express an
  execute-batch as a bounded array whose transaction is owned by the adapter,
  never as author-supplied transaction-control SQL.
- Reject `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT`, `RELEASE`,
  `ATTACH`, `DETACH`, `PRAGMA`, `VACUUM`, extension loading,
  host-file functions, temporary database objects, and writes to SQLite,
  libSQL, Turso, or Omnidraw internal namespaces.
- Verify that declared read operations cannot mutate and that declared write
  operations use the write path, including CTE, `RETURNING`, trigger, and
  multi-token edge cases. Fail closed on an unclassified statement.
- Keep local-only provider setup pragmas outside the portable profile.
  Cloud-specific journaling and concurrency behavior must never be authored
  widget SQL.
- Normalize parameters, rows, row counts, insert IDs, and database errors
  through the SDK codec so the same function observes the same result shape.

### 3. Preserve the OSS resource product

- Keep all current private API groups and behavior: resource list/get/create/
  rename/delete, KV/secret data list/set/delete/reveal, DB impact/inspection/
  live SQL, row list/get/create/update/delete/bulk, draft lifecycle and SQL,
  apply preview/confirm/history, and backup preview/restore/status/discard.
- Keep secrets redacted from general data/list responses and reveal them only
  through the existing explicit human-secret capability.
- Keep current local capacity, lifecycle, drain, recovery, and exact-resource
  authorization behavior. Do not introduce organization scope or managed
  billing into OSS.
- Record a user-visible resource capability matrix in the widget authority so
  the private managed implementation can provide equivalent behavior without
  sharing this private RPC or local storage schema.

### 4. Keep Turso Cloud out of OSS composition

- Continue using the current local embedded database provider in OSS.
- Do not add `@tursodatabase/serverless`, cloud database URLs/tokens,
  provisioning APIs, remote branches, or fallback network access to the OSS
  runtime.
- Treat Turso Cloud as the managed adapter selected in the private repository;
  OSS only owns the portable semantics and its local conformance target.
