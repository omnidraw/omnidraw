# S82 - replace the session-bound AI wizard with a shared multi-resource agent workspace
[Overview](../BASED.md)

Replace the widget-scoped AI wizard with a generalized AI workspace that can inspect, stage, validate, and coordinate changes across widgets, actors, databases, resource bindings, and related files while preserving shared draft identity, explicit user approval, compact context, and recoverable execution.

This is a large architectural and product migration. It changes the identity model, agent workflow, tool surface, event protocol, draft ownership, approval boundary, apply semantics, and chat UI. It must ship incrementally behind compatibility boundaries and must not leave two competing draft models active indefinitely.

## Outcome

When this task is complete:

- A chat is a conversation, not the owner of a widget draft.
- Multiple chats in the same workspace see and edit the same active draft for a published entity.
- A conversation can bring any supported entity into its working set without becoming permanently bound to it.
- The agent can discover affected widgets and resources without loading the complete dependency graph into model context.
- Database and widget changes can be staged in one coordinated change set.
- The user approves a frozen change set through deterministic UI and API commands.
- The model cannot approve or publish its own work.
- Normal assistant responses render as compact inline text.
- Tool activity renders as compact, stateful rows that can expand inline or open a focused dialog.
- Settings replace the chat body and provide a reliable Back to chat transition that restores chat state.
- Actor, tool, preview, schema, resource, diff, and validation views are contextual surfaces rather than permanent top-level tabs.
- Every staged and applied operation has an auditable identity, revision, lifecycle, and recovery state.

## Context

### Product problem

The current AI wizard assumes that one UI instance, one Pi session, one widget identifier, one draft filesystem, and one actor-candidate workflow are the same conceptual object. That assumption works for a narrow create-one-widget flow, but it breaks the desired product model:

- A user may rename a database table and then update every widget that references it in the same chat.
- The agent may discover affected entities that were not initially attached.
- The user may have multiple chats open against the same canvas or project.
- Those chats must not create conflicting draft directories for the same published widget merely because they have different session identifiers.
- A database change may be valid only if associated widget, binding, and actor changes are applied together.
- Tool output must expose enough semantic information for the agent and UI to continue the workflow without dumping a large dependency graph into context.
- The user needs detailed inspection on demand, but persistent Actor, Tool, and Preview tabs consume space and reinforce the one-widget mental model.

The current AgentService session map is effectively keyed by widget ID and session ID. The draft working directory is derived from both values. The canvas AI plugin persists a session identifier in the canvas element and passes the canvas AI element identifier through a widget-shaped API. This creates a draft filesystem per chat instead of a shared active draft per published entity.

The current tool workflow also uses global actor-candidate and implementation phases. Candidate approval changes the complete set of tools made available to the model. The UI sends hidden prompts that instruct the model to call approval and implementation tools, and the model can call the publish tool. This makes a model-generated tool call part of the authority boundary.

The database proposal flow records SQL, but approval can immediately create a database draft, execute it, preview it, and confirm a live apply independently from related widget changes. This cannot safely represent a coordinated rename that affects multiple widgets.

The current chat renderer treats tool results largely as generic messages and does not make the Pi tool execution start, update, and end lifecycle a first-class UI state. As a result, it cannot provide durable progress, compact rows, contextual actions, reliable reconnect behavior, or operation-specific dialogs.

### Product direction

The replacement is a generalized Vibecanvas AI workspace:

- The chat starts broad and can work with zero, one, or many resources.
- The working set is visible above the chat and can be changed with Add and @ mentions.
- An entity in the working set is context, not ownership.
- The agent searches and inspects progressively.
- The agent stages changes into a coordinated change set.
- The UI owns approval and apply commands.
- The assistant explains in plain inline text.
- Tool calls, approvals, warnings, plans, failures, and apply results get structured UI.
- Dense views open from the relevant message or tool row.
- Settings replace the chat body and retain a clear Back to chat action.

## Guiding principles

- Conversation identity, workspace identity, entity identity, draft identity, change-set identity, and approval identity are separate.
- A published entity has at most one active draft in a workspace.
- Different conversations may contribute to the same shared draft.
- A working set is conversation-local convenience state and never defines draft ownership.
- The model may propose, inspect, stage, and validate.
- The user must deterministically authorize sensitive or live mutations.
- Every write is revision-aware and either idempotent or explicitly non-retryable.
- Every model-callable tool returns typed semantic data.
- UI presentation is selected by the frontend, not encoded as service-agent component names or labels.
- Large results are referenced and paginated rather than copied wholesale into model context.
- Tool availability follows capabilities and workflow state, not one global actor phase.
- Partial apply is a first-class failure state and is never reported as complete.
- Secrets bypass the model and transcript.
- Resource discovery is broad; resource access and mutation remain authorization-scoped.
- The migration is additive first and destructive only after compatibility and recovery paths are proven.

## Scope

### In scope

- New identity model for surface, conversation, workspace, entity, draft, change set, and approval request.
- Shared draft filesystem and metadata ownership.
- Migration of AgentService from a widget-session coordinator to a composed conversation and workspace agent service.
- Generalized tool registry with conditional capability loading.
- Complete typed result contract for tool lifecycle and UI rendering.
- Search, inspection, dependency, working-set, widget, actor, resource, database, validation, preview, and change-set tools.
- Deterministic UI commands for approval, apply, discard, retry, cancel, secret entry, and destructive actions.
- Coordinated multi-resource change-set staging and apply.
- Compact chat tool rows with inline expansion, dialogs, and action menus.
- Working-set UI and @ mention behavior.
- Settings-as-page behavior with Back to chat state restoration.
- Contextual replacement of Actor, Tool, and Preview tabs.
- Compatibility migration for historical misspelled APIs, stored sessions, and existing active drafts.
- Security, observability, recovery, contract tests, UI tests, and end-to-end coverage.

### Explicit non-goals

- Do not replace the Pi provider SDK as part of this task unless a blocking incompatibility is proven.
- Do not give the model unrestricted shell, process, or arbitrary filesystem tools.
- Do not turn the chat into a full general-purpose IDE.
- Do not expose credential values, secret values, raw environment variables, or unrestricted KV contents to the model.
- Do not load every entity and every dependency into the initial prompt.
- Do not make provider credentials or model settings editable through model-callable tools.
- Do not promise a distributed atomic transaction across unsupported backends without an explicit coordinator and recovery design.
- Do not silently auto-apply live changes because validation passed.
- Do not preserve the old widget-session draft behavior as an undocumented fallback after migration.
- Do not require every resource type to support mutation in the first release; unsupported capabilities must be explicit.

## Terminology and identity model

### Surface ID

Identifies the canvas AI UI element or other visual surface from which a conversation is opened.

- Used for layout, placement, focus, and surface lifecycle.
- Must not own draft files.
- Must not be sent as a fake widget ID.
- May be absent for a standalone chat surface.

### Conversation ID

Identifies one model conversation and Pi history.

- Owns transcript, provider session, composer draft, scroll position, open tool-row state, and conversation-local working set.
- Does not own entity drafts.
- May be archived without deleting shared drafts.
- Must be addressable independently of a canvas AI surface.

### Workspace ID

Identifies the shared editing context in which published entities and active drafts live.

- All conversations in the same workspace resolve the same active draft for the same entity.
- Owns artifact draft registry, change sets, workspace revision, and shared operation state.
- Must have an explicit authorization boundary.
- Initially maps to the appropriate canvas or project identity; the mapping must be documented rather than inferred from a chat.

### Entity ID

Stable identity for a widget, actor definition, database resource, KV resource, binding, or other supported product entity.

- Must be paired with an entity type where IDs are not globally unique.
- Must remain stable across display-name changes.
- Must never use a filesystem path as public identity.

### Artifact draft ID

Identifies the active draft of a file-backed entity in a workspace.

- One published widget definition maps to at most one active artifact draft per workspace.
- Opening the same widget from two conversations returns the same artifact draft ID and working directory.
- Carries a base published revision and current draft revision.
- Is not deleted merely because a conversation closes.

### Change-set ID

Identifies a coordinated collection of proposed and staged operations across one or more entities.

- Owns operations, dependencies, validation results, revision preconditions, inclusion state, and apply state.
- Can include widget files, manifests, database structures, bindings, and KV metadata.
- Must be inspectable without loading all operation details into model context.
- Must be frozen before approval.

### Approval request ID

Identifies an immutable request for a user decision.

- References a frozen change-set revision.
- Becomes stale if the change set or relevant workspace revision changes.
- Cannot be generated and approved solely by model calls.
- Records user identity, decision, timestamp, and relevant policy context.

### Operation ID

Identifies one durable stage, validation, apply, verify, rollback, or recovery operation.

- Used for progress events, cancellation, retry policy, audit logs, and reconnect.
- Must make duplicate client delivery safe.

## Core invariants

- A conversation can exist without a working set.
- A conversation can inspect an entity without adding it to the working set.
- Adding an entity to a working set does not create a new draft.
- Opening an existing draft from any conversation resolves the workspace-level draft registry.
- The same entity cannot have two active workspace drafts unless a future explicit branching feature introduces named branches.
- A draft never becomes published through a model-callable approval or publish tool.
- An approval always references a frozen, validated revision.
- A stale approval cannot be applied.
- A resource rename uses stable entity identity and must not rely on display-name identity.
- A database structure draft remains separate from live state until coordinated apply.
- A change set with failed validation cannot enter ready-for-approval.
- A change set with excluded required dependencies cannot enter ready-for-approval.
- The UI can reconstruct operation state after reconnect.
- Tool results never reveal server filesystem paths.
- Secret values never enter tool arguments, tool results, model messages, telemetry, or persisted transcript.
- Every apply result distinguishes complete success, no-op, conflict, cancelled, partial apply, recovered, and recovery-required.

## Target user journeys

### Journey A - create a widget from a broad chat

1. User opens Vibecanvas AI with an empty working set.
2. User describes the widget and mentions or adds a data resource.
3. Agent inspects the resource shape and proposes a widget design.
4. A compact proposal tool row offers Review design.
5. User approves scaffolding through a direct UI command.
6. Agent stages files in the shared artifact draft.
7. Agent validates and builds a preview.
8. User opens preview from the validation or preview tool row.
9. Agent prepares a frozen change set.
10. User reviews and applies it.
11. UI reports publish and actor reload verification.

### Journey B - edit one published widget from two chats

1. Conversation A opens Widget X.
2. Conversation B later opens Widget X in the same workspace.
3. Both resolve the same artifact draft ID and current revision.
4. A write from Conversation A increments the draft revision.
5. A stale write from Conversation B returns a conflict with current revision and affected files.
6. Conversation B re-reads or rebases before staging another patch.
7. Both chats see shared draft and change-set status updates without sharing transcripts.
8. Closing either chat does not delete the draft.

### Journey C - rename a database table and update affected widgets

1. User asks to rename orders to purchases and update all consumers.
2. Agent inspects the database schema and direct dependency impact.
3. Tool result reports one database and affected widget references with a result reference for deeper pagination.
4. Agent suggests affected widgets for the working set.
5. User may accept all, accept selected, or leave the working set unchanged.
6. Agent stages the database structure operation.
7. Agent opens shared drafts for affected widgets and stages reference updates.
8. Agent validates database preview, widget files, manifests, bindings, and actor scenarios.
9. Agent prepares one coordinated change set.
10. User reviews included operations and approves the frozen revision.
11. Apply coordinator snapshots, stops affected actors, applies changes in the declared order, reloads definitions, restarts actors, and verifies.
12. UI shows per-operation results and an overall complete, partial, or recovery-required state.

### Journey D - inspect an unexpected dependency

1. Agent receives an impact summary that references an entity outside the working set.
2. Agent uses a targeted inspection tool with bounded depth.
3. UI shows the inspection as a compact tool row.
4. User can open the entity, add it to the working set, or inspect dependencies from the row menu.
5. Only the selected detail is added to model context.

### Journey E - enter a secret

1. Agent identifies that a resource needs a credential.
2. Agent calls the secret-input request tool with a purpose and destination reference but no value.
3. UI displays a secure input action.
4. User enters the value in a non-transcript form.
5. A direct API command stores the secret.
6. Agent receives only fulfilled, cancelled, expired, or failed status.

### Journey F - settings and contextual views

1. User clicks Settings.
2. Chat body is replaced with settings.
3. Header shows Back to chat.
4. Returning restores scroll position, composer content, working set, open tool rows, and any non-secret dialog state.
5. Actor, tool, preview, schema, diff, and resource detail views open contextually from chips or tool rows rather than permanent navigation tabs.

## Target workflow

Replace the global actor-candidate and implementation phases with an operation workflow:

1. Discover
2. Inspect
3. Plan
4. Stage
5. Validate
6. Await approval
7. Apply
8. Verify
9. Complete, recover, or discard

The workflow is not a single linear chat phase. Different entities in one change set may be at different internal states, while the change set derives an aggregate state.

### Capability-based tool selection

AgentService must derive a bounded tool set from:

- workspace permissions
- entity capabilities
- current user intent
- entities inspected in the turn
- active change-set state
- presence of supported drafts
- approval state
- server policy

The common model turn should expose approximately 8 to 14 relevant tools, not the complete catalog. Search and inspection tools remain broadly available; mutation tools appear only after the relevant capability and scope are known. The derivation function should be pure, testable, and independent of UI labels.

## Model-callable tool contract

Every model-callable tool must:

- Have a stable tool name and versioned argument schema.
- Validate workspace scope and entity scope on the server.
- Accept stable IDs rather than display names when mutating.
- Return compact model-facing content.
- Return typed semantic details for the UI.
- Declare whether it reads, stages, validates, or requests user input.
- Declare whether it is durable, cancellable, retryable, and idempotent.
- Include the current workspace or draft revision when relevant.
- Return conflicts as data rather than overwriting newer work.
- Return a result reference and cursor for large results.
- Exclude UI component names and presentation strings from service-agent contracts.
- Exclude raw paths, secret values, private connection strings, and unrestricted stack traces.

### Shared result envelope

Define one versioned result envelope with:

- schemaVersion
- kind
- status
- toolCallId
- operationId when durable
- conversationId
- workspaceId
- entityRefs
- artifactDraftId when relevant
- changeSetId when relevant
- workspaceRevision
- artifactRevision when relevant
- summary suitable for compact model context
- typed details discriminated by kind
- resultRef for deferred detail
- cursor and hasMore for pagination
- warnings
- recoverable error code and safe message
- retryability metadata
- cancellation metadata
- timestamps

Supported status values must include:

- running
- succeeded
- failed
- conflict
- cancelled
- awaiting-user
- partial
- recovery-required

### Frontend presentation registry

The frontend must map result kind to presentation behavior:

- row icon
- row title
- compact summary
- progress representation
- inline detail component
- dialog detail component
- generic menu actions
- result-specific menu actions
- error and recovery behavior

Service-agent must not return component names such as DatabaseImpactCard or PreviewDialog. It returns semantics such as database-impact or widget-preview.

## Coordinated apply semantics

The initial priority scenario is a database rename with dependent widget updates.

### Prepare

1. Freeze change-set ID and revision.
2. Verify workspace revision and every draft revision.
3. Reject stale validation.
4. Re-run required fast validations.
5. Resolve operation dependency order.
6. Verify every required operation is included.
7. Produce risk, downtime, backup, and recovery summary.
8. Create immutable approval request.

### Apply

1. Consume the valid user approval exactly once.
2. Acquire workspace and entity locks.
3. Recheck revisions after lock acquisition.
4. Snapshot published widget files and manifests.
5. Prepare database backup and confirm restore capability.
6. Stop affected actors when required.
7. Apply database draft in the declared order.
8. Publish widget artifact drafts.
9. Apply resource binding and non-secret KV operations.
10. Resolve fulfilled secret references without exposing values.
11. Reload actor and widget definitions.
12. Restart affected actors.
13. Persist per-operation results after every step.

### Verify

1. Verify live database schema revision.
2. Verify published artifact revisions.
3. Verify bindings.
4. Verify actor health.
5. Run declared smoke scenarios.
6. Check unresolved references.
7. Mark complete only when required verification passes.

### Failure and recovery

- If failure occurs before live mutation, release locks and mark failed without partial state.
- If failure occurs after any live mutation, mark partial immediately.
- Run only declared and tested compensation steps.
- Record which operations applied, failed, rolled back, or require manual recovery.
- Keep backups until recovery policy permits deletion.
- Never retry non-idempotent apply steps implicitly.
- Never publish a generic success message for a partial apply.
- Provide a recovery report and direct recovery commands.

## Risks and mitigations

### Draft identity migration

Risk:

- Existing users may have multiple divergent session drafts for one widget.

Mitigation:

- Inventory, hash, classify, back up, auto-adopt only unambiguous cases, and require explicit review for divergence.

### Cross-resource apply is not fully atomic

Risk:

- Database and filesystem publication may cross transaction boundaries.

Mitigation:

- Durable per-operation state, preflight, backups, locks, declared ordering, tested compensation, explicit partial state, and recovery UI.

### Too many tools reduce model reliability

Risk:

- A complete generalized catalog can overload tool selection.

Mitigation:

- Capability-based subsets, bounded schemas, prompt guidance, semantic summaries, and selection telemetry.

### Working set becomes another hidden binding

Risk:

- Users and code may treat chat context as persistent actor configuration.

Mitigation:

- Separate storage, contracts, labels, commands, and tests; never mutate bindings when working set changes.

### UI becomes card-heavy

Risk:

- Structured tool UI can consume more space than the existing chat.

Mitigation:

- Plain assistant text, compact one-line tool rows, progressive disclosure, and dialogs for dense information.

### Approval remains indirectly model-controlled

Risk:

- A hidden prompt or synthetic model message could continue to trigger authority.

Mitigation:

- Direct user commands, immutable approval requests, server authorization, audit identity, and removal of approval and publish tools.

### Reconnect shows incorrect operation state

Risk:

- Client transcript events alone may be incomplete.

Mitigation:

- Durable operation records, workspace subscriptions, revisioned events, explicit interrupted state, and server reconciliation.

### Secret leakage

Risk:

- Generic tool arguments, results, logs, or retries may capture secret values.

Mitigation:

- Separate secure-input API, status-only model contract, redaction tests, and no generic retry payload containing secret input.
