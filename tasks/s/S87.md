# S87 - simplify vc_widget_create to one runnable construction scaffold
[Overview](../BASED.md)

Make `vc_widget_create` create one predictable artifact: a complete unpublished widget with an actor, widget UI, valid manifest, and small working lifecycle. Remove the artificial `kind` choice and give the agent a readable starting point it can immediately turn into the requested product.

## Why this task exists

The public contract currently asks the model to choose `widget` or `actor-widget`, but [`tx.scaffold.ts`](../../packages/service-agent/src/tools/tx.scaffold.ts) creates both actor and widget folders in either case. The parameter suggests two outputs that do not exist.

The generated baseline also mixes infrastructure with fake product behavior:

- the manifest declares `in.update` and `tx.update` although no update behavior was requested;
- generated functions may throw `not implemented yet`;
- the UI dumps raw state/context instead of showing an intentional construction state;
- error recovery is declared, but the starter implementation must be a real working transition;
- the tool does not clearly tell the agent what exists after creation or what to edit next.

Creation should establish the boring infrastructure once. Product states, data, messages, functions, and resources should be added only when the agent understands the requested widget.

## Preflight findings and blockers

There is no architectural blocker. These compatibility and lifecycle constraints must be handled:

### Legacy manifest compatibility

[`vibecanvasjson.zod.ts`](../../packages/service-actor/src/core/vibecanvasjson.zod.ts) defines `kind` as optional. Existing manifests may contain either historical value. Remove `kind` only from the model-callable create input and new manifests. Keep old manifests readable and valid; no migration is needed.

### Booting is runtime-owned

The actor runtime begins in implicit `booting` and transitions to the manifest's `initialState`. A scaffold with no initialization work should not declare a synthetic booting state that can become stuck. Use manifest `initialState: "ready"`; make the UI handle `booting` and `booting.*` while startup occurs.

### Error recovery must be real

The manifest validator requires a recovery input for an error state. Keep one infrastructure input, `in.resetError`, targeting `ready` through `tx.resetError`. Its generated function must call `portal.next()` and must not throw.

### Creation remains transactional

Preserve the temporary scaffold, validation, atomic promotion, chat mount, and rollback sequence. Removing `kind` must not weaken path safety, duplicate checks, mount behavior, or cleanup ownership.

### Construction is a valid unpublished state

`Widget under construction...` is the deliberate default, not a validation failure. Whether an unchanged scaffold may be published is a separate policy and not part of S87.

## Outcome

When S87 is complete:

- `vc_widget_create` accepts only `name` and optional `description`;
- every call creates a complete actor-backed widget draft;
- new manifests omit `kind`, while legacy manifests remain compatible;
- the manifest has a minimal real `ready` and recoverable `error` lifecycle;
- the UI presents booting, construction/ready, and error states;
- the error view can reset the actor to `ready`;
- no generated source contains a generic `not implemented yet` failure;
- the result is valid, runnable, mounted, and ready for file tools;
- tool and prompt text explain what was created and how to continue.

## Fixed decisions

### Tool input

```ts
type TWidgetCreateInput = {
  name: string;
  description?: string;
};
```

- Keep existing widget-name normalization and validation.
- Reject unknown fields, including `kind`.
- Do not add a mode, template, lifecycle, or folder-shape option.
- Do not infer a scaffold variant from the name or description.

### Generated manifest

Generate the semantic equivalent of:

```ts
{
  schemaVersion: 1,
  name,
  description,
  actor: {
    initialState: 'ready',
    initialData: {},
    dataSchema: {
      type: 'object',
      properties: {},
      additionalProperties: false,
    },
    states: {
      ready: { on: {} },
      error: {
        on: {
          'in.resetError': {
            func: 'tx.resetError',
            targetState: 'ready',
          },
        },
      },
    },
    input: {
      'in.resetError': {
        schema: {
          type: 'object',
          properties: {},
          additionalProperties: false,
        },
      },
    },
    output: {},
    resources: {},
  },
  widget: {
    // Preserve the established complete entry/build contract.
  },
}
```

Follow the schema's exact names and canonical omission rules. The fixed semantics are:

- no `kind` in new manifests;
- `ready` is the initial state;
- actor data is an empty strict object;
- no sample counter, update input, output, or resource;
- `error` has exactly one real recovery path;
- field and file ordering remains deterministic.

### Generated actor function

Generate only the required reset transaction using repository SDK types and function-file conventions:

```ts
export async function txResetError(portal: TPortal, args: TArgs) {
  void args;
  await portal.next();
}
```

Do not generate unused update or sample function files. The generated `tx.*.ts` must follow the two-argument `portal`/`args` rule and permitted imports.

### Generated UI and CSS

- `booting` and `booting.*`: render `Starting widget...`.
- `error` and `error.*`: render `Widget encountered an error.` and a native `Reset` button.
- settled non-error states: render `Widget under construction...`.
- Reset sends `in.resetError` with `{}` through the actor API.
- Do not print raw context/state objects or invent product behavior.
- Use a minimal accessible layout, system typography, readable contrast, and visible keyboard focus.
- Avoid branding, animation, elaborate layouts, and sample-product styling.

State-family matching must follow runtime conventions rather than handling only one exact leaf.

### Tool description and result

Describe create as producing a complete runnable unpublished actor/widget draft and mounting it into the current chat. Tell the agent to continue with `read`, `edit` or `patch`, then `vc_widget_validate`; calling create again is not an update workflow.

Keep the successful model result compact:

```ts
{
  name: string;
  mountPath: string;
  source: 'draft';
  draft: true;
  files: string[];
}
```

Do not return `kind` or absolute host paths. Keep the relative path and deterministic bounded file inventory. Preserve visible stable errors for invalid names, conflicts, authorization, scaffold failure, and mount failure.

## Creation lifecycle

1. Authorize `vc_widget_create`.
2. Parse and validate `name` plus optional `description`.
3. Reject conflicting draft or published names using existing rules.
4. Build the minimal manifest without `kind`.
5. Scaffold all files into a temporary directory.
6. Validate the manifest and generated-file contract.
7. Atomically promote the complete directory to the draft store.
8. Mount the draft into the current chat workspace.
9. Return the safe relative mount path and file list.
10. On failure, remove only artifacts owned by this attempt and preserve existing files.

Never persist a manifest separately from its source tree or leave a durable half-scaffold.

## Agent workflow guidance

Update the prompt to recommend:

1. List widgets if the desired name may already exist.
2. Create once for a new widget.
3. Read the generated manifest and relevant actor/widget sources.
4. Replace the construction UI with the requested feature.
5. Add only the schema, states, messages, functions, and resources the feature needs.
6. Edit or patch source; use Bash only when build/test commands help.
7. Validate, inspect every diagnostic, and fix errors before presenting the draft.

Do not encourage editing published source directly or recreating a widget to update it.

## Implementation plan

### 1. Simplify the create contract

- Remove `kind` from the schema and description in [`tool.widget-workspace.ts`](../../packages/service-agent/src/tools/tool.widget-workspace.ts).
- Remove it from internal create arguments and [`fn.widget-create.ts`](../../packages/service-agent/src/tools/fn.widget-create.ts).
- Omit it from generated manifests.
- Keep legacy parsing support unchanged.

### 2. Replace sample behavior with the minimal lifecycle

- Remove fake update input, transition, schema, and function.
- Generate strict empty initial data.
- Keep `ready`, `error`, reset input, and reset transition only.
- Ensure the manifest passes current schema and lifecycle lint.

Keep manifest construction pure. Exported `fn.*.ts` functions must begin with `fn`, use only allowed runtime imports, and avoid globals and side effects.

### 3. Make scaffolded source runnable

- Update [`tx.scaffold.ts`](../../packages/service-agent/src/tools/tx.scaffold.ts) so files match the manifest exactly.
- Generate the working reset transaction.
- Remove throwing placeholders from the baseline file set.
- Generate the three UI presentations and neutral CSS.
- Keep package and TypeScript configuration aligned with the current runtime.

If source-string generation needs extraction, use small deterministic `fn.*.ts` siblings and retain filesystem writes in `tx.scaffold.ts`; do not introduce a second template system solely for S87.

### 4. Update guidance and result language

- Update [`prompt.tools.md`](../../packages/service-agent/src/prompts/prompt.tools.md) with the create-edit-validate workflow.
- Remove kind-selection guidance.
- Explain the generated baseline briefly.
- Keep usable relative paths/files in model-visible content and omit removed fields.

### 5. Preserve safety and compatibility

- Keep old manifests with `kind` valid.
- Preserve draft/published discovery and conflict rules.
- Preserve temporary creation, atomic promotion, mount, and rollback.
- Never modify an existing widget after a name conflict.
- Never expose absolute draft-store paths.

## Non-goals

- Do not rewrite existing manifests to remove `kind`.
- Do not add templates, presets, frameworks, or scaffold modes.
- Do not infer product state/data from the widget name.
- Do not add a publish gate for the construction placeholder.
- Do not change widget clone identity, chat identity, or chat storage.
- Do not redesign the actor runtime.
- Do not bind resources by default.
- Do not publish automatically.
