# S149 - AI Chat: simplify tool schemas for strict providers
[Overview](../BASED.md)

Make every AI Chat tool publish one object-shaped input contract. Remove the
top-level resource-create union that DeepSeek rejects before generation and
guard the provider-neutral shape at the complete tool registry boundary.

## Context

[`od_resource_create`](../../apps/backend/src/shell/agent/tools/tool.resources.ts)
currently declares `parameters` as a `Type.Union` of three objects. TypeBox
serializes that root as `anyOf` without `type`, so DeepSeek reports the schema
as `type: null` and rejects the complete model request:

```text
Invalid schema for function 'od_resource_create': schema must be a JSON Schema
of 'type: "object"', got 'type: null'.
```

The failure happens while the provider validates the advertised tools, before
the model can choose or execute one. GPT endpoints accept the same loose root,
which hid the portability defect.

The installed [`@earendil-works/pi-ai@0.80.10`](../../bun.lock) DeepSeek path
uses OpenAI-compatible chat completions and forwards each TypeBox
`tool.parameters` schema unchanged. Pi has open and historical reports for the
same general lack of OpenAI-compatible schema normalization:

- [Pi #7010: normalize optional object tool schemas](https://github.com/earendil-works/pi/issues/7010)
- [Pi #1964: OpenAI-compatible providers reject unsanitized schemas](https://github.com/earendil-works/pi/issues/1964)
- [DeepSeek tool-call schema guidance](https://api-docs.deepseek.com/guides/tool_calls/)

Omnidraw owns the tool definitions and should publish the portable contract
directly. Do not patch installed Pi output, fork Pi, add a DeepSeek-only branch,
or wait for a general upstream sanitizer. Nested unions may remain where they
describe a property or array item; the hard invariant here is that the
function-parameter root is an object.

The existing resource schema test in
[`resource-tools.test.ts`](../../apps/backend/src/shell/agent/tests/resource-tools.test.ts)
does not include `od_resource_create` in its provider-visible assertions, and
there is no complete-registry assertion for the root shape.

## Plan

### 1. Collapse resource creation to one object contract

- Replace the three-object top-level union with one closed `Type.Object` whose
  required fields are `kind` and `name`.
- Represent `kind` as a provider-friendly string enum for `kv`, `secretStore`,
  and `db`, rather than an `anyOf`/`const` literal union.
- Remove the optional provider-visible `engine` field. SQLite is the only local
  database engine, the description already fixes that choice, and execution
  freezes only `kind` and `name`; retaining `engine: "sqlite"` adds no
  capability.
- Preserve the existing approval, exact-argument freezing, resource service,
  safe result, and error behavior.

### 2. Enforce the contract at the registry boundary

- Add a focused assertion over every entry returned by
  [`createToolRegistry`](../../apps/backend/src/shell/agent/tools/ToolRegistry.ts)
  that its serialized `parameters` root has `type: "object"`.
- Assert `od_resource_create` exposes the three exact kind values, requires
  `kind` and `name`, rejects extra properties, and no longer advertises
  `engine` or a top-level composition keyword.
- Keep semantic execution tests for all three resource kinds and approval
  argument freezing so the schema simplification cannot widen host authority.
- Make the test provider-neutral and offline. It should inspect the exact tool
  definitions handed to Pi, not mock a DeepSeek response or require an API key.

### 3. Qualify the subtraction

- Run the focused resource-tool and prompt/session registry tests.
- Run backend typecheck and the complete backend agent test group.
- Confirm the emitted schema for `od_resource_create` is a closed root object
  with a string enum and contains no top-level `anyOf`, `oneOf`, or `allOf`.
- Confirm GPT behavior remains unchanged and record a manual DeepSeek smoke
  result when credentials are available; the offline schema assertion is the
  required acceptance gate.

## NOTES

- This is a subtraction because it removes a redundant schema branch and
  provider-visible field while narrowing the supported contract.
- Root-object portability belongs to Omnidraw's provider-neutral tool boundary;
  recursive provider-specific JSON Schema sanitization remains a Pi concern.
- No UI behavior changes, so no mockup or screen-atlas update is required.
- Do not enable DeepSeek strict mode as part of this task. The reported failure
  occurs during ordinary tool registration with Pi emitting `strict: false`.
