# S93 - secret stores: reveal values and encrypt Turso files at rest
[Overview](../BASED.md)

Let the human operator deliberately reveal secret values while encrypting every secret-store Turso database at the database-page level. Preserve the stronger rule that agents, generic resource tools, lists, mutations, logs, approvals, and events never receive secret plaintext.

## Context

[S91](S91.md) moved each secret store into its own Turso file under the actor-resource data root, but deliberately left plaintext at rest and made the management UI write-only. The current behavior is visible in [`GenericResourcePage.tsx`](../../apps/frontend/src/feature/resource/GenericResourcePage.tsx):

- the secret table returns names and revision metadata only;
- rows offer Rotate and Delete, but no Reveal action;
- the Add/Rotate dialog uses a password input with no visibility toggle;
- the dialog says that secret plaintext is write-only.

The screenshot attached to this task shows that current Add Secret dialog and its write-only copy. S93 must improve both operator workflows:

1. the operator can temporarily show/hide the value being typed into Add/Rotate;
2. the operator can explicitly reveal/hide one already-stored secret value from its table row.

The existing plaintext path is intentionally narrow:

- [`SecretStoreResource.ts`](../../packages/service-actor/src/resources/SecretStoreResource.ts) returns plaintext only to an authorized actor `get` call; management helpers return metadata.
- [`ActorService.ts`](../../packages/service-actor/src/ActorService.ts) intentionally strips plaintext from `getResourceDataEntry`, list, set, delete, and conflict responses.
- [`fn.resource-data.ts`](../../packages/service-actor/src/resources/fn.resource-data.ts) maps secret pages and mutations to metadata-only DTOs.
- [`tool.resources.ts`](../../packages/service-agent/src/tools/tool.resources.ts) rejects model-facing secret `get` operations with `SECRET_READ_UNSUPPORTED`.
- [`fn.redact-secret-resource-write.ts`](../../packages/service-agent/src/tools/fn.redact-secret-resource-write.ts) and the approval vault prevent set values from entering persisted AI messages.

Physical persistence is currently shared by KV and secret-store resources in [`ActorResourceKeyValueStore.ts`](../../packages/service-actor/src/resources/ActorResourceKeyValueStore.ts). Its Turso `Database` options do not include encryption, so `data.db` and its WAL contain readable secret plaintext. The native wrapper in [`turso-native.ts`](../../packages/service-db/src/DbServiceTurso/turso-native.ts) already forwards the Turso `encryption: { cipher, hexkey }` option to the native addon.

The Turso references indexed by [`docs/external/llm.turso.md`](../../docs/external/llm.turso.md) establish these constraints:

- encryption is native page-level authenticated encryption and covers database pages and WAL data;
- `aegis256` uses a 256-bit/32-byte key represented as 64 hexadecimal characters and is the recommended 256-bit default;
- the same cipher and key must be provided on every connection;
- the database header is not confidential, and filenames/directories are outside the database encryption boundary;
- Turso does not store the key in the database;
- passphrase derivation, in-place encryption of existing databases, and in-place key rotation are not currently available, so existing plaintext files require copy-and-swap conversion.

## Fixed decisions

### Encryption cipher

Use Turso native `aegis256` page encryption for secret-store databases only. Its 32-byte key matches the native wrapper and Turso's recommended 256-bit option. Do not encrypt ordinary KV or DbResource files as part of S93.

Pass encryption through the structured `Database` option:

```text
encryption: {
  cipher: "aegis256",
  hexkey: <64 lowercase hexadecimal characters>
}
```

Never append the key to a database URI, where it is more likely to leak through errors, diagnostics, process inspection, or logging. Never issue the key through SQL/PRAGMA text.

### Which key to use

Create one random installation-scoped secret-store master key and derive one distinct Turso key per resource.

The production master key is:

- 32 cryptographically random bytes generated once by the host on first secret-store use;
- stored outside the data directory under the Vibecanvas configuration root in a dedicated, versioned key file, not in `config.json`, the control database, a secret-store database, agent auth storage, or widget storage;
- created atomically with exclusive creation and owner-only access (`0600` on POSIX and an equivalent current-user-only ACL on Windows);
- loaded only by the host process, retained only as key material in memory, and never returned through an application API;
- injected in tests/headless composition so tests never read a developer key.

Derive each database's 32-byte key with HKDF-SHA-256:

```text
IKM  = installation master key
salt = UTF-8 resource ID
info = "vibecanvas/secret-store/turso/aegis256/v1"
L    = 32 bytes
```

Encode the result as 64 lowercase hexadecimal characters for Turso. The resource ID is immutable and host-generated, so the same resource receives the same key after restart while different resources do not share raw database keys.

Do not use or derive from:

- a model-provider API key, OAuth token, or `pi/agent/auth.json`;
- the Vibecanvas control database contents or hash;
- a user password that Vibecanvas cannot reliably recover at startup;
- resource names, paths, machine IDs, usernames, hostnames, or hard-coded repository constants;
- random per-resource keys stored beside `data.db`.

This key-file design is the minimum reliable cross-platform custody available to the current local CLI. It protects a copied secret database/WAL and data-directory-only backups. It does not protect against an attacker who can read both the user's config and data roots or control the running process. State that threat model plainly; database encryption is not a substitute for filesystem permissions, host security, API authorization, or redaction.

If the runtime cannot enforce current-user-only permissions on a platform, fail closed for secret-store provisioning/opening and report a non-sensitive configuration error. Do not silently create a weaker key file.

### Key loss, backup, and rotation

Losing or replacing the installation master key makes every encrypted secret store unreadable. Startup/reconciliation must report a stable `SECRET_STORE_KEY_UNAVAILABLE` or `SECRET_STORE_DECRYPTION_FAILED` condition without recreating the file, replacing the key, or exposing native error details.

Treat the versioned master key and encrypted secret-store directory as one backup unit. Document this before release and include both in uninstall consequences. Do not add a plaintext key export UI in S93.

Turso currently has no in-place rekey path. S93 does not expose key rotation. A future rotation task must copy every database through a verified encrypted temporary file and atomically swap it, just like the plaintext conversion defined here.

### Existing plaintext secret databases

Do not try to enable encryption while opening an existing plaintext file. Convert each existing secret store under a resource lifecycle lock:

1. Block new operations and drain in-flight reads/writes.
2. Close its cached database handle and checkpoint/close the WAL.
3. Open the old file without encryption and verify exact resource identity, kind, schema, and health.
4. Create a sibling temporary database with the derived AEGIS-256 key and the final secret schema.
5. Copy metadata and entries through parameterized statements while preserving key, value, revision, and timestamps exactly.
6. Close and reopen the temporary database with the key; run health, schema, identity, row-count, and content checks.
7. Prove that opening/querying it without encryption or with a wrong key fails.
8. Atomically rename the plaintext file to a recovery name, move the encrypted file to `data.db`, reopen it, and only then delete the recovery file.
9. Recover deterministically from every crash point without guessing which file is authoritative.

Never write the secret value to JSON, logs, migration reports, error details, or a plaintext temporary file. Temporary/recovery filenames contain only the resource ID and migration state.

Increment the physical secret-store format/encryption metadata so startup can distinguish plaintext-v1, encrypted-v2, incomplete conversion, wrong-key, swapped-kind, and corruption states. Ordinary KV format handling remains unchanged.

### Human reveal boundary

Add a dedicated operator-management reveal operation. Do not change the existing list DTO, generic data-entry metadata method, mutation DTOs, actor IPC contract, SDK portal, or model tool contract to include values.

The reveal request identifies exactly one secret by resource ID and name. The response contains only:

```text
{
  kind: "secretStore",
  name: string,
  value: string,
  revision: number
}
```

Use a mutation-style request rather than a cacheable list/read route, set no-store response behavior where transport semantics allow it, resolve only ready `secretStore` resources, and return stable not-found/kind/unavailable errors with no key, path, SQL, or plaintext details.

The current application is local and does not yet provide complete public-method authorization; [A43](../a/A43.md) tracks that larger boundary. In S93, expose reveal only through the human resource-management handler used by the frontend and keep it completely absent from service-agent tools and prompts. Do not claim this is multi-user authorization. When A43 lands, reveal requires an explicit secret-reveal permission and must deny service/model identities.

### Reveal user experience

Secret values remain masked by default.

- Add/Rotate dialog: provide an accessible Show/Hide control for the current password input. Hiding does not clear the draft; closing or successfully submitting clears it.
- Stored row: add Reveal beside Rotate/Delete. Reveal fetches only that row and renders the plaintext in a bounded masked/revealed control with Hide.
- Never reveal all rows, reveal on hover, prefetch values, or retain revealed plaintext in the list DTO.
- Clear revealed plaintext on Hide, row/page/filter/resource/tab changes, refresh, navigation, component cleanup, request failure, and after 30 seconds of inactivity.
- A stale reveal response must be discarded if the resource, row, request generation, or displayed revision changed while the request was in flight.
- Do not place plaintext in the URL, title attributes, DOM attributes, toast messages, browser storage, query caches, analytics, events, or console output.
- Copy-to-clipboard is out of scope unless added with an explicit action, success feedback that omits the value, and best-effort clipboard clearing semantics documented honestly.

### Redaction invariants

Authorized actor code may continue calling its bound secret-store `get` portal and receiving plaintext. S93 changes at-rest protection and adds a human reveal path; it does not broaden agent access.

The following remain metadata-only or fully redacted:

- secret list/count/has operations;
- management set/delete/CAS success and conflict responses;
- service-agent resource inspect/read/write results;
- approvals and persisted agent messages;
- tool-call summaries, chat history, events, notifications, telemetry, logs, and error causes;
- generic resource DTOs and frontend catalog/sidebar state.

## Plan

### 1. Freeze the security and compatibility baseline

- Record current secret creation, rotation, list, actor `get`, management metadata, agent-tool rejection, redaction, restart, and deletion behavior.
- Add sentinel-based tests proving where plaintext is intentionally present today and every boundary where it is absent.
- Verify the installed and compiled Turso native addons expose `EncryptionCipher.Aegis256` on every supported target before changing persisted files.
- Record Turso `0.6.1` encryption behavior for correct key, missing key, wrong key, plaintext open, WAL contents, health checks, and native error shapes.

### 2. Add host-owned key custody

- Define a narrow secret-store master-key provider at the host/service composition edge.
- Generate the installation key from injected cryptographic randomness and create the versioned key file atomically.
- Enforce exact length/hex validation, owner-only permissions/ACLs, symlink rejection, regular-file checks, and no overwrite on races.
- Derive per-resource keys with the fixed HKDF parameters and erase avoidable temporary buffers after constructing database options.
- Inject the provider through CLI composition into ActorService/SecretStore persistence; keep direct globals out of any new `fn/fx/tx` helpers.
- Add deterministic provider tests for first creation, concurrent creation, restart, wrong length, permission drift, symlink/path substitution, missing key with existing databases, and test injection.

### 3. Separate encrypted secret persistence from ordinary KV options

- Preserve the shared bounded lifecycle/store logic where useful, but make database-open options resource-kind specific.
- Ensure every secret provision, verification, cached handle open, standalone check, conversion, and recovery open receives `aegis256` plus the derived key.
- Ensure KV opens never receive secret encryption options.
- Prevent database options, native errors, and test diagnostics from serializing `hexkey`.
- Update secret physical format metadata without weakening exact resource-ID and kind verification.

### 4. Convert plaintext files safely

- Implement the lifecycle-locked copy-and-swap state machine defined above.
- Preserve all values, revisions, and timestamps exactly and verify full equality before swap.
- Handle plaintext file plus WAL, encrypted temporary file, recovery file, and interrupted rename combinations deterministically.
- Never delete the last verified copy until the encrypted replacement is open and authoritative.
- Treat wrong-key/corrupt/swapped databases as errors, never as candidates for automatic reprovisioning.
- Add fault-injection tests at create, copy, checkpoint, close, verify, rename, reopen, and cleanup boundaries.

### 5. Add the operator-only reveal contract

- Add a dedicated API contract and handler for one-secret reveal with bounded resource/name inputs and a strict response schema.
- Add an ActorService management method that resolves a ready secret-store resource and calls a purpose-named reveal method on `SecretStoreResource`.
- Keep `getResourceDataEntry` and list/mutation helpers metadata-only so generic callers cannot accidentally start receiving plaintext.
- Ensure the handler is not registered in service-agent tool definitions, prompt guidance, actor IPC, or public widget SDK resource portals.
- Add API and service tests for success, missing secret, wrong kind, unavailable/decryption error, stale revision behavior if revision is accepted, and sentinel-free errors.

### 6. Implement temporary reveal UI behavior

- Add Show/Hide to Add and Rotate password fields with accessible labels and predictable focus behavior.
- Replace the write-only dialog copy with precise language: values are encrypted at rest, masked by default, and can be intentionally revealed by the operator.
- Add per-row Reveal/Hide state without inserting values into the page list model.
- Apply request-generation and revision checks so late responses cannot reveal the wrong row/resource.
- Clear plaintext on every lifecycle boundary and timeout listed in the fixed decisions.
- Keep errors and success toasts value-free.

### 7. Preserve model and actor boundaries

- Retain actor-bound secret `get` semantics and read-scope enforcement.
- Retain `SECRET_READ_UNSUPPORTED` for service-agent tools and metadata-only resource inspection.
- Re-run approval-vault, transcript, tool-result, error, event, and frontend rendering sentinel tests.
- Update prompts only to remove the obsolete claim that secret values are stored as plaintext; do not tell the model that it can reveal secrets through management APIs.

### 8. Document operations and verify packaging

- Update service-actor architecture notes with AEGIS-256, key derivation, key location, threat model, backup coupling, key-loss behavior, and unsupported rotation.
- Update operator-facing help with reveal behavior and the warning that losing the configuration key loses secret access.
- Ensure uninstall removes the key only as part of the already-confirmed full config/data uninstall and explains that removal is irreversible.
- Verify source and compiled native-addon encryption support on macOS ARM64, Linux ARM64/x64, and Windows x64.
- Run focused service-actor/API/frontend/service-agent tests, functional-core lint, typechecks, full relevant builds, compiled binary tests, restart/conversion tests, and `bun run generate:files`.

## Acceptance criteria

- New secret-store databases use Turso AEGIS-256 page encryption from their first write.
- Existing plaintext secret-store databases convert through a verified crash-safe copy-and-swap path without changing values, revisions, or timestamps.
- Secret database and WAL contents do not expose a sentinel plaintext value through direct byte inspection.
- Opening an encrypted secret database without the key or with the wrong key fails; the application never replaces or resets it automatically.
- One installation master key is generated once outside the data root with current-user-only access, and each resource receives a deterministic distinct HKDF-derived key.
- No API key, OAuth token, password, database content, machine identifier, resource name, or hard-coded key is used as encryption material.
- The operator can show/hide a draft Add/Rotate value and explicitly reveal/hide one stored secret.
- Stored secrets remain masked and unfetched by default; reveal state clears on timeout and all relevant navigation/lifecycle changes.
- Generic resource pages, lists, mutations, actor IPC, SDK contracts, AI tools, prompts, approvals, transcripts, logs, events, errors, and browser storage do not gain plaintext.
- Authorized bound actor `get` continues to return plaintext under the existing read-scope rules.
- KV and DbResource persistence behavior remains unchanged.
- Key loss, backup requirements, unsupported rotation, and the local-host threat model are documented accurately.

## NOTES

- Turso database encryption protects database pages and WAL contents, not file names, directory structure, memory, UI rendering, or a compromised host process.
- The master-key file is deliberately outside the data root so copying only actor-resource data does not also copy its decryption key. A full-home-directory compromise still defeats this boundary.
- S92 changes the control-database migration tail. S93 changes independent actor-resource files and can use its own physical format conversion; do not add this conversion to control-database SQL migrations.
- A43 remains the place for comprehensive public API authorization. S93 must keep reveal operator-only by architecture and must not overstate the current local session as multi-user security.
