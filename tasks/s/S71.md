# S71 - image paste: render local preview while uploading to remote server
[Overview](../../BASED.md)

Image paste should feel instant when the server is remote: decode and render the clipboard `File` locally, upload in the background, then reconcile the same runtime image node with the persisted URL.

## Current flow
The blocking path is now known:

- Paste/drop/picker enters `insertImage()` in `packages/canvas/src/plugins/image/Image.plugin.ts`.
- `txInsertImage()` in `packages/canvas/src/plugins/image/tx.insert-image.ts` reads a base64 data URL, reads the file bytes, waits for `api.file.put`, and only then creates the Konva node and CRDT element.
- Therefore remote upload latency delays the first canvas render.
- `TImageData.url` and `TImageData.base64` are already nullable. No persisted image schema change is needed.

## Decided design
Use a browser object URL only as a short-lived decode source. Do **not** put the object URL, base64 payload, upload state, or other temporary data into Automerge/image data.

The pending preview is a local-only Konva image node with its final stable ID and geometry. It is not committed to CRDT until upload succeeds. On success, the same node receives normal persisted metadata/listeners and the element is committed with the server URL. Other clients only ever receive the valid persisted image.

### Why this design
- `URL.createObjectURL(file)` avoids base64's extra copy and roughly 33% size expansion.
- The object URL is revoked immediately after the local `HTMLImageElement` has loaded; it does not remain alive for the duration of a slow upload.
- The decoded image object remains usable by Konva after URL revocation.
- No browser storage, IndexedDB, cache file, or application temp file is created.
- Pending bytes consist only of the clipboard `File`, the decoded bitmap needed for display, and the transient upload byte buffer already required by the API.
- Keeping temporary state out of `TImageData` prevents invalid `blob:` URLs from being persisted or broadcast.

## Implementation plan
1. Refactor `txInsertImage()` into explicit prepare, preview, upload, and reconcile phases.
2. Validate format from `file.type`; remove the base64 data-URL read/parse from this insertion path.
3. Create one object URL and start image decode/dimension discovery from it. Start byte reading/upload concurrently so decode does not add to upload latency.
4. Once decoded:
   - calculate the existing viewport-fitted dimensions;
   - allocate the final image ID;
   - create a local element-shaped value with `url: null` only for constructing the runtime node;
   - create the Konva node without normal persistence listeners, install the already-decoded image object, add/select/draw it immediately;
   - revoke the object URL in `finally` as soon as decode has settled.
5. On upload success:
   - confirm the pending token/node is still active (it may have been deleted or the plugin destroyed);
   - build the final element from the node's current geometry using the returned server URL;
   - synchronize persisted image metadata onto the same node;
   - attach normal image listeners;
   - commit the final element to CRDT and record the existing `insert-image` undo/redo history entry.
6. Replace the displayed bitmap without flicker:
   - begin loading the server URL while retaining the decoded local image on the Konva node;
   - only replace `node.image()` after the server image fires `load`;
   - never clear the local image between sources.
7. On upload failure:
   - remove the still-pending local node;
   - clear selection/focus only when they reference that node;
   - redraw and show the existing error notification;
   - do not create CRDT or history records.
8. Track pending inserts by ID/token in the image plugin. On node deletion or plugin destroy, mark them cancelled so late upload completions cannot recreate/persist an image. Release all local references on every success, failure, cancellation, and destroy path.

## Interaction and race rules
- The preview uses the final node ID; reconciliation must not destroy/recreate it.
- A pending node is local-only and must not run normal drag/transform persistence listeners until upload succeeds. This prevents an interaction from accidentally creating a CRDT image with `url: null`.
- If global delete/teardown destroys a pending node, upload completion becomes a no-op.
- Multiple pasted images may upload independently; completion order must not affect z-order or IDs.
- The server URL is persisted as soon as upload succeeds. A slow second fetch of that URL affects only bitmap replacement, not persistence.
- If loading the returned server URL fails, keep the already-decoded local bitmap for the current session and report an image-load error; the persisted URL remains the source of truth for reload/share.

## Acceptance criteria
- [ ] Pasted/dropped/picked image appears after local decode without waiting for `api.file.put`.
- [ ] Upload can remain unresolved in a test while one correctly sized Konva image is already visible.
- [ ] The same runtime node and ID survive successful reconciliation.
- [ ] Local preview stays visible until the server-backed image has loaded; no blank frame/flicker occurs.
- [ ] CRDT receives no element before success and then receives exactly one image with the persisted server URL.
- [ ] No `blob:` URL or temporary/base64 payload enters CRDT, history, or collaboration traffic.
- [ ] Every object URL is revoked after decode, including decode failure.
- [ ] Upload failure removes the preview, reports an error, and leaves no CRDT/history entry.
- [ ] Delete/destroy during upload makes late completion a no-op and releases pending references.
- [ ] Undo/redo after successful reconciliation retains existing persisted image behavior.
- [ ] Local and simulated high-latency remote-server tests pass.

## Test plan
- Deferred upload promise: assert preview exists before resolving upload.
- Success: resolve upload, assert same node identity/ID, one CRDT commit, server URL metadata, and one history record.
- Flicker: hold server image load pending and assert the local bitmap remains installed; trigger load and assert atomic replacement.
- Failure: reject upload and assert node removal, notification, and zero CRDT/history writes.
- Cleanup: assert object URL revocation on decode success and failure.
- Cancellation: destroy/delete node or plugin before upload resolves and assert no late commit.
- Concurrency: paste two files and resolve uploads in reverse order.
- Existing paste-from-document and normal image reload/share tests remain green.
