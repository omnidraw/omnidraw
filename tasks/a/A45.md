# A45 - eslint functional-core rules plus Pi/Codex post-turn hooks
[Overview](../BASED.md)

Reimplement the current Pi functional-core extension as ESLint rules, then wire Pi and Codex hooks to run ESLint after an agent turn finishes and feed failures back into the agent flow.

## Context

Today functional-core checks live in the project-local Pi extension and block `write`/`edit` tool calls before invalid edits hit disk.

Current source surfaces:
- `.pi/extensions/functional-core/`
- `.pi/extensions/functional-core/core/checks.ts`
- `.pi/extensions/functional-core/pi-adapter.ts`
- `.codex/`

Target behavior:
- ESLint becomes the source of truth for functional-core checks.
- Rules apply only to relevant source files, for example `**/src/**/fn.*.ts`, `**/src/**/fx.*.ts`, and `**/src/**/tx.*.ts`.
- Test files and non-`src` helper folders do not receive these rules.
- Standard ESLint disable comments provide escape hatches for intentionally dirty code.
- Pi and Codex do not preflight/intercept edits anymore.
- After an agent turn finishes, run ESLint automatically.
- If ESLint fails, extend the message flow with the lint output so the agent sees the errors and fixes them.

Important product decision:
- Do not preserve current pre-edit blocking behavior.
- Prefer post-turn repair loop over interrupting tool calls.

## Plan

### Phase 1 - define ESLint architecture

Pick the package/location for the custom ESLint plugin and config.

Decisions to make:
- Where the local ESLint plugin lives.
- Whether it ships as a workspace package or repo-local config module.
- Whether ESLint runs with flat config only.
- Which command is canonical, for example `bun run lint:functional-core`.

Expected rule groups:
- `functional-core/import-boundary`
- `functional-core/no-runtime-globals`
- `functional-core/export-shape`
- `functional-core/fx-tx-params`

### Phase 2 - port functional-core checks to ESLint rules

Reimplement the existing behavior as AST-based ESLint rules instead of regex-based Pi validators.

Rules to preserve:
- `fn.*.ts` exported functions must start with `fn`.
- `fx.*.ts` exported functions must start with `fx`.
- `tx.*.ts` exported functions must start with `tx`.
- Runtime imports are restricted by file kind.
- `CONSTANTS` and `GUARDS` runtime imports stay allowed.
- UPPER_CASE runtime value imports stay allowed.
- Runtime globals like `window`, `fetch`, `Bun`, `process`, `console`, and `globalThis` stay blocked when used directly.
- `fx*` and `tx*` exported functions require `portal` as first param and optional `args` as second param.
- `portal` type must start with `TPortal`.
- `args` type must start with `TArgs`.
- Exported classes, enums, and non-function runtime values stay blocked in functional-core files.

### Phase 3 - scope rules to `src` and keep tests clean

Configure ESLint overrides so rules apply only to source paths.

Desired scope:
- include `**/src/**/fn.*.ts`
- include `**/src/**/fx.*.ts`
- include `**/src/**/tx.*.ts`
- ignore `**/*.test.ts`
- ignore `**/*.spec.ts`
- ignore non-`src` task, hook, fixture, test, and generated folders

This avoids accidental enforcement in test folders and utility scripts.

### Phase 4 - support escape hatches through ESLint disables

Use normal ESLint disable comments instead of inventing a custom suppression syntax.

Examples:

```ts
// eslint-disable-next-line functional-core/import-boundary -- temporary bridge to legacy runtime API
import { legacyRuntime } from "../legacy";
```

```ts
/* eslint-disable functional-core/no-runtime-globals -- browser adapter boundary */
const href = window.location.href;
/* eslint-enable functional-core/no-runtime-globals */
```

Configuration goals:
- Report unused disable directives as errors.
- Prefer requiring disable descriptions if the chosen ESLint comment tooling supports it cleanly.
- Keep rules granular so agents can disable only the dirty rule, not the whole functional-core policy.

### Phase 5 - add Pi post-turn ESLint hook

Replace or shrink `.pi/extensions/functional-core` so it no longer blocks `write` or `edit` tool calls.

New Pi behavior:
- Keep optional system-prompt guidance about functional-core rules.
- Listen for the end of an agent run/turn, not individual edit calls.
- Run the canonical ESLint command after the agent finishes.
- If ESLint passes, do nothing.
- If ESLint fails, append/send a follow-up message containing concise lint output and ask the agent to fix it.
- Avoid infinite loops by adding a retry limit or detecting repeated identical failures.

Pi files to consider:
- `.pi/extensions/functional-core/index.ts`
- `.pi/extensions/functional-core/pi-adapter.ts`
- `.pi/extensions/functional-core/README.md`

### Phase 6 - add Codex post-turn ESLint hook

Update `.codex` integration to run the same ESLint command after Codex finishes a turn or post-tool sequence, depending on available Codex hook semantics.

New Codex behavior:
- Do not preflight edits.
- Run ESLint after the agent has finished its current work unit.
- Return Codex-compatible feedback that becomes visible to the agent.
- Prefer the same canonical command and same output formatting used by Pi.

Codex files to consider:
- `.codex/`
- `.codex/hooks.json` or `.codex/config.toml`
- `.codex/hooks/`

### Phase 7 - output formatting and repair flow

Create a concise lint feedback format optimized for agents.

Output should include:
- command that failed
- file paths
- rule names
- line/column
- short messages
- instruction to fix without disabling rules unless there is an explicit reason

Avoid dumping huge logs. Cap output and tell the agent to run the lint command if more detail is needed.

### Phase 8 - migration and cleanup

Once ESLint is trusted:
- Stop using regex validators as the primary enforcement path.
- Keep old Pi core temporarily only if needed for compatibility while hooks migrate.
- Remove old pre-edit blocking behavior.
- Update docs to explain ESLint source of truth and escape hatches.

### Phase 9 - validation

Validate with representative files:
- clean `src/**/fn.*.ts` passes
- dirty runtime import fails
- dirty import with `eslint-disable-next-line functional-core/import-boundary -- reason` passes
- unused disable fails
- `tests/**/fn.*.ts` does not get functional-core rules
- `src/**/fn.*.test.ts` does not get functional-core rules
- Pi post-turn failure sends a follow-up message
- Codex post-turn failure feeds back to the agent
- successful lint run is silent

## NOTES

- This task intentionally changes enforcement timing from pre-edit blocking to post-turn repair.
- ESLint gives native escape hatches through `eslint-disable-next-line` and related comments.
- Granular rules are important because escape hatches should disable only one policy at a time.
- Path scoping belongs primarily in ESLint config, not inside every rule, unless direct rule-level protection is still useful.
- The existing `.pi/extensions/functional-core` implementation is still useful as a behavior reference during the port.
- The existing A42 Codex hook work may need replacement rather than incremental patching because it reused the Pi functional-core core directly.
