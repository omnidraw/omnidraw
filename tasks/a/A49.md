# A49 - ai wizard: cancel ongoing agent run
[Overview](../BASED.md)

Add cancel support for running AI wizard prompts so the composer send button becomes a stop action while the backend agent is streaming/running.

## Context

The AI wizard currently submits prompts from the chat composer and listens for Pi agent events, but there is no user-facing way to abort an ongoing run.

Relevant files:
- `packages/canvas/src/components/AiWizzard/index.tsx` - owns AI wizard session id, event stream handling, and `prompt()` call into backend.
- `packages/canvas/src/components/AiWizzard/tabs/ChatTab.tsx` - passes submit/new-chat handlers into `ChatComposer`.
- `packages/canvas/src/components/AiWizzard/ChatComposer/ChatComposer.tsx` - owns submit button UI; must eventually show a stop icon while running.
- `packages/canvas/src/components/AiWizzard/ChatComposer/interface.ts` - composer props will need running/cancel callback additions.
- Backend agent API contract files under `packages/core-contract` and server implementation under `apps/cli` / relevant agent service files must expose cancel.
- `docs/external/llm.pi.sdk.md` documents Pi SDK support for `AgentSession.isStreaming` and `AgentSession.abort(): Promise<void>`.

Important Pi SDK facts from `docs/external/llm.pi.sdk.md`:
- `AgentSession` has `isStreaming: boolean` for current streaming/running state.
- `AgentSession.abort(): Promise<void>` aborts the current operation.
- Prompting may still finish by emitting normal events/messages after an abort; UI state should be driven by lifecycle events and backend acknowledgement, not only by button click.

## Plan

### 1. Backend running state

Find where per-widget/per-session `AgentSession` instances are stored and where `agent.wizzard.prompt` is implemented.

Add a session lookup that can answer whether the current agent is running. Prefer using Pi SDK `session.isStreaming` if available from the stored runtime/session.

The backend should send enough state to the frontend so the UI can know:
- prompt accepted / run started
- run ended normally
- run aborted / ended after cancel
- run failed before acceptance

### 2. Backend cancel endpoint

Add an API endpoint/action for canceling the current wizard run, scoped by:
- `widgetId`
- `sessionId`

Endpoint behavior:
- If no matching active session exists, return a safe no-op response.
- If the session exists but is not running, return a safe no-op response.
- If running, call Pi SDK `AgentSession.abort()` and return success.
- Do not create a new session just to cancel.
- Do not clear message history on cancel.

### 3. Frontend event/state handling

In `packages/canvas/src/components/AiWizzard/index.tsx`, keep local running state for the current widget/session.

State transitions should cover at least:
- set running true when a prompt is accepted or agent emits start/message streaming events for this session
- keep running true across incremental `message_start` / `message_update`
- set running false on `agent_end`
- set running false on cancellation acknowledgement/error path if no terminal event arrives
- reset running false when `newChat()` changes session id

Do not replace message history on `agent_end`; append/upsert new messages only.

### 4. Composer stop button

Update composer props to receive:
- `isRunning` or equivalent
- `onCancel` or equivalent

When running:
- replace submit arrow icon with stop icon
- clicking the button calls cancel instead of submit
- prevent duplicate cancel calls while a cancel is already in flight if needed

When not running:
- keep current submit behavior.

Do not change prompt text clearing behavior unless the cancel flow requires it. Prefer preserving typed text when canceling a run.

### 5. UX edge cases

Handle:
- user clicks stop repeatedly
- agent ends while cancel request is in flight
- new chat while agent is running
- backend says nothing is running
- prompt rejected before start

- This is an addition because it adds a new user-facing control and backend capability.
- Keep the implementation session-scoped; cancel must not affect other widgets or sessions.
- Prefer idempotent cancel semantics: canceling when nothing is running should be safe.
- The frontend should not assume `agent_end.messages` is the complete transcript; it may contain only new messages.
