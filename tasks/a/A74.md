# A74 - actor resources: replace versioned DbResource migrations with coordinated drafts and applies
[Overview](../BASED.md)

Follow up [A72](A72.md) after implementing the first DbResource management UI. Remove schema IDs, schema versions, published migration lineages, and compatibility claims from DbResource. Keep Turso as a host-private engine while presenting guest code with a small SQLite-compatible query/execute contract. Replace versioned migrations with resource-local schema drafts, coordinated transactional applies, live table/data editing, affected-actor previews, and observed restart results.

## Context

A72 deliberately allowed trusted actor `tx` code with `arbitrarySql: true` and effective write permission to execute DDL. The host has no proven engine authorizer in the current Turso adapter and must not pretend a parser or SQL-prefix check can reliably prevent schema changes. Consequently:

- `_vibecanvas_migrations` proves only that host migration SQL once ran; it does not prove the physical schema still matches.
- Exact schema/version equality rejects harmless changes while still missing actor-created drift at the same version.
- A schema generation, revision, fingerprint, minimum version, or compatibility range cannot prove that dynamic actor SQL will work.
- Guest code must stay simple. Do not move schema coordination, migrations, engine selection, or compatibility bookkeeping into actors.
- AI validation may be added later as advice, but it is not a core safety boundary or part of this task.

A74 replaces false compatibility guarantees with operational guarantees the host can actually enforce: intentional UI changes are isolated for drafting, previewed, applied while affected actors are stopped, backed up, transactional where supported, health-checked, and followed by transparent restart outcomes.

## Decisions

| Question | Decision |
|---|---|
| Schema IDs or versions | Remove them from the public and runtime DbResource model. |
| Generation/revision/fingerprint | Do not add any replacement counter or schema identity. |
| Published migrations | Remove the global schema/migration catalog and physical migration history table. |
| Compatibility | Do not infer or persist actor/schema compatibility. Show references and observed runtime outcomes only. |
| Engine | Keep the existing local Turso implementation as a host detail. Do not expose Turso as the guest contract. |
| Guest SQL dialect | Document and generate ordinary SQLite-compatible SQL only. Turso-only syntax, custom types, MVCC, CDC, sync, remote access, and native handles are not guest APIs. |
| Arbitrary SQL | Retain the trusted `query`/`execute` portal and accept that write access may change schema. Do not parse DDL as an authorization boundary. |
| UI data editing | Edit live data through short host-generated transactions with optimistic conflict checks. |
| UI schema editing | Edit a temporary resource copy, record ordered changes, and explicitly apply those changes to live. |
| Apply result | Database success and actor restart results are separate. Actor failure does not retroactively mean the database transaction failed. |

## Public DbResource contract

### Manifest

The DB slot becomes schema-agnostic:

```ts
{
  kind: "db",
  required: true,
  scope: ["read", "write"],
  arbitrarySql: true,
  operations: {
    listNotes: {
      effect: "read",
      sql: "SELECT id, title FROM notes ORDER BY id",
      result: "rows",
    },
  },
}
```

Remove the required `schema: { id, version }` object from:

- runtime manifest types and Zod validation;
- `@vibecanvas/sdk` actor types and generated JSON schema;
- wizard candidates, approval, scaffolding, publishing, and registry normalization;
- actor binding status and start admission DTOs;
- implementation prompts, widget-system documentation, fixtures, and tests.

For one compatibility window, manifest ingestion may accept a legacy DB `schema` object, ignore it completely, and emit one actionable host warning. New scaffolded/published output must omit it. It must never affect binding, admission, or actor calls. Record a removal TODO rather than maintaining dual semantics indefinitely.

### Resource creation and binding

Creating a database resource becomes:

```ts
{ kind: "db", name: "CRM" }
```

No schema must be created or selected first. Provision an empty physical database containing only host-private metadata required for apply recovery.

Binding validates only:

- the definition and slot exist;
- resource kind is `db`;
- resource lifecycle is `ready`;
- binding permissions are a subset of manifest scope.

Remove schema/version mismatch states. Starts are blocked only by real lifecycle conditions such as provisioning, applying, deleting, or unrecovered error.

### Guest portal and dialect

Keep named operations and optional arbitrary `query`/`execute`, including ordered execute arrays and explicit transaction control. Preserve function-class and effective-scope enforcement.

The SDK and AI prompts describe a SQLite-compatible contract:

- use ordinary SQLite tables, indexes, views, triggers, parameters, and transactions;
- do not use Turso-only SQL or PRAGMAs;
- do not assume remote synchronization, MVCC, CDC, custom types, materialized views, extensions, or multiple processes;
- the host may change its internal SQLite-compatible engine without changing guest APIs.

This is a supported-language contract, not a hostile-code sandbox. Retain current host-file and extension restrictions, bounds, timeouts, result limits, serialized writes, and trusted-actor documentation. Do not add SQL parsing to classify DDL.

## Control database replacement

Add the next control migration after `011-add-db-resources.sql`.

Drop A72 persistence in dependency order:

- `db_resource_migration_blocks`;
- `db_resource_configurations`;
- `db_resource_schema_migrations`;
- `db_resource_schemas`;
- their domains, triggers, indexes, models, and persistence methods where the engine supports dropping them safely.

Replace them with resource-local draft/apply state. Exact names may follow repository conventions, but preserve this model.

### Drafts

```sql
CREATE DOMAIN DB_RESOURCE_DRAFT_STATUS AS TEXT
  CHECK (value IN ('editing', 'applying', 'applied', 'discarded', 'error'));

CREATE TABLE db_resource_drafts (
  id TEXT PRIMARY KEY NOT NULL,
  resource_id TEXT NOT NULL REFERENCES actor_resources(id) ON DELETE CASCADE,
  name TEXT NOT NULL,
  status DB_RESOURCE_DRAFT_STATUS,
  last_error JSON,
  created_at TIMESTAMP NOT NULL DEFAULT (datetime('now')),
  updated_at TIMESTAMP NOT NULL DEFAULT (datetime('now')),
  applied_at TIMESTAMP
) STRICT;
```

Permit at most one `editing` or `applying` draft per resource through service validation and a database constraint/index if supported cleanly. Draft IDs are host-generated and determine the physical path; user names never determine paths.

Draft changes are ordered operations, not migrations or revisions:

```sql
CREATE DOMAIN DB_RESOURCE_DRAFT_CHANGE_KIND AS TEXT
  CHECK (value IN ('structure', 'sql'));

CREATE TABLE db_resource_draft_changes (
  draft_id TEXT NOT NULL REFERENCES db_resource_drafts(id) ON DELETE CASCADE,
  sequence INTEGER NOT NULL CHECK (sequence >= 1),
  kind DB_RESOURCE_DRAFT_CHANGE_KIND,
  operation JSON,
  sql TEXT NOT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT (datetime('now')),
  PRIMARY KEY (draft_id, sequence)
) STRICT;
```

- `operation` stores the structured table-editor intent when available, such as add column or create index.
- `sql` stores the exact bounded SQL applied to the draft and later submitted to live.
- Advanced raw SQL is allowed for the local user but is marked `sql`; no structured safety explanation is claimed.
- Sequence is execution order only. It is not a schema generation or compatibility version.

### Apply runs and actor outcomes

Persist each coordinated apply independently of the draft UI session:

```sql
CREATE DOMAIN DB_RESOURCE_APPLY_STATUS AS TEXT
  CHECK (value IN (
    'preparing', 'stopping', 'applying', 'restarting',
    'succeeded', 'failed', 'recovered'
  ));

CREATE TABLE db_resource_apply_runs (
  id TEXT PRIMARY KEY NOT NULL,
  resource_id TEXT NOT NULL REFERENCES actor_resources(id) ON DELETE CASCADE,
  draft_id TEXT REFERENCES db_resource_drafts(id) ON DELETE SET NULL,
  status DB_RESOURCE_APPLY_STATUS,
  last_error JSON,
  backup_retained BOOLEAN NOT NULL DEFAULT false,
  created_at TIMESTAMP NOT NULL DEFAULT (datetime('now')),
  completed_at TIMESTAMP
) STRICT;
```

Persist one result for each affected instance so process restart does not erase the report:

```sql
CREATE DOMAIN DB_RESOURCE_APPLY_INSTANCE_STATUS AS TEXT
  CHECK (value IN (
    'notRunning', 'pendingStop', 'stopped', 'stopFailed',
    'pendingRestart', 'restarted', 'startFailed', 'crashed'
  ));

CREATE TABLE db_resource_apply_instance_results (
  apply_id TEXT NOT NULL REFERENCES db_resource_apply_runs(id) ON DELETE CASCADE,
  actor_instance_id TEXT NOT NULL REFERENCES actor_instances(id) ON DELETE CASCADE,
  actor_definition_name TEXT NOT NULL,
  was_running BOOLEAN NOT NULL,
  status DB_RESOURCE_APPLY_INSTANCE_STATUS,
  error JSON,
  updated_at TIMESTAMP NOT NULL DEFAULT (datetime('now')),
  PRIMARY KEY (apply_id, actor_instance_id)
) STRICT;
```

Index drafts and apply runs by `resource_id`; index apply-instance results by `actor_instance_id`. Add updated-at triggers and JSON validity checks following current Turso conventions.

## Physical storage and migration of existing resources

Keep one host-derived Turso database per resource:

```text
<dataRoot>/actor-resources/db/<resource-id>/data.db
```

Keep schema drafts separately:

```text
<dataRoot>/actor-resources/db-drafts/<draft-id>/data.db
```

Draft names, table names, SQL, actors, and UI requests never provide filesystem paths.

Existing A72 resources must retain all user tables and data. During startup reconciliation after the control migration:

- stop requiring `db_resource_configurations`;
- remove the host-created `_vibecanvas_migrations` table from physical resources;
- remove/quarantine stale `.pre-migration` files only after verifying the active database opens and passes health checks;
- clear obsolete migration-block admission state;
- clear only schema/version-specific actor errors; do not clear unrelated actor failures;
- preserve resource IDs, names, bindings, and physical data.

No old schema/migration rows are converted into revisions or change history. They are obsolete control metadata. Existing applied SQL remains reflected in the physical database itself.

Create a small host-private physical apply marker table, keyed by opaque apply ID, solely for crash recovery. It is not exposed to actors as a revision and is not used for compatibility. The marker is inserted in the same live transaction as an apply so startup can distinguish a committed apply from an interrupted pre-commit apply.

## Database inspection and live data editing

Add resource-management APIs for schema introspection and table data. These are local installation-management APIs, not actor portals.

### Introspection

Return bounded structured DTOs for:

- user tables and views;
- columns, declared SQLite types, nullability, defaults, and primary-key order;
- indexes and indexed columns;
- foreign keys;
- views/triggers where the adapter exposes them safely;
- whether a table has a stable editable identity.

Exclude `_vibecanvas_*`, `sqlite_*`, Turso internal objects, and host metadata from ordinary UI lists.

### Row browsing

- Require explicit table selection and bounded page size.
- Use primary-key tuples when available; otherwise use `rowid` for ordinary rowid tables.
- Treat views and tables without a safe stable identity as read-only.
- Quote host-validated identifiers and bind all values; never interpolate user values.
- Return SQLite-compatible values deliberately, including null, integer/bigint, real, text, and bytes.
- Do not load full tables or use offset pagination as the only large-table strategy.

### Row writes

Create/update/delete rows directly on live through the existing per-resource serialized write lane. Each UI action is a short transaction.

- Require the stable row identity returned by the read API.
- Accept expected original values for edited/deleted fields and use them as optimistic predicates.
- Return a typed conflict when the row changed or disappeared instead of silently overwriting actor changes.
- Validate required/null/default behavior against engine results; the database remains authoritative.
- Bulk edits are bounded and transactional. No cross-resource transaction.
- UI row writes do not create schema drafts or apply runs.

## Schema draft workflow

Drafts are for structure changes, not long-lived data merging.

### Create

1. Require a `ready` DB resource and no open draft/apply for it.
2. Briefly block new resource calls, drain in-flight operations, checkpoint/close the host handle, and create a verified physical copy.
3. Reopen live immediately; do not stop actor processes merely to retain a long-lived draft.
4. Initialize the draft catalog row as `editing`.

The draft is a preview snapshot. Live data may continue changing afterward.

### Edit

The table-structure editor issues host-generated SQLite SQL against the draft and appends the exact successful operation to `db_resource_draft_changes` atomically with draft state where possible.

Support a first complete structure surface:

- create, rename, and drop table;
- add, rename, and drop column where supported;
- edit declared type, nullability, default, and primary-key shape through a safe table-rebuild workflow when required;
- create/drop indexes;
- create/drop foreign keys through table rebuild when required;
- advanced bounded raw SQL.

Every destructive operation requires explicit confirmation and displays affected objects/data. The host validates the resulting draft with `quick_check` and `foreign_key_check`. Do not claim that structured UI operations make arbitrary actor SQL safe.

### Discard

Close the draft handle, delete only its host-derived directory, and mark it `discarded`. A failed cleanup remains visible and retryable.

## Coordinated apply workflow

### Preview

Before confirmation, return:

- resource identity and current lifecycle state;
- ordered structured/raw changes;
- destructive-change warnings known from structured operations;
- every bound definition and slot;
- every persisted instance for those definitions;
- which instances are currently running and would be restarted;
- an explicit statement that actor compatibility cannot be guaranteed.

Do not return `compatible`, expected/actual version, schema match, or revision fields.

### Apply

1. Revalidate the resource/draft and create an apply-run row.
2. Transition the resource to `migrating` (UI wording: `applying`) to block new starts, binds, calls, deletion, other drafts, and row edits.
3. Recompute all bindings and persisted instances after acquiring the lifecycle lock.
4. Persist instance-result rows, recording which instances are running.
5. Stop every running affected instance and wait for child/in-flight closure. If any cannot stop, abort before live mutation, return the resource to `ready`, restart instances already stopped by this attempt, and report the stop failure.
6. Drain resource calls, checkpoint, close the handle, and create a verified backup including required sidecars.
7. Apply all draft changes to the live resource in order inside one engine transaction where supported, inserting the opaque physical apply marker in that same transaction.
8. Reopen and run bounded `quick_check`, compare `foreign_key_check` with the pre-apply baseline so pre-existing violations are not misreported as new, and verify the apply marker.
9. On SQL/health failure, restore the verified backup and mark the run `recovered`; if restore verification fails, leave the resource `error` and actors stopped.
10. On database success, mark the resource `ready` before restart attempts.
11. Restart every instance that was running before apply, regardless of definition metadata. Previously stopped instances remain stopped.
12. Persist `restarted`, `startFailed`, or observed immediate `crashed` outcomes with safe actor errors.
13. Mark the database apply `succeeded` even when some actors fail; present database and actor results separately.

Restart success is observational only. It does not prove future dynamic SQL will work. Do not auto-edit definitions, auto-run AI, or auto-rollback a healthy database solely because an actor fails.

Retain the latest verified pre-apply backup and expose explicit discard/restore management actions. Restore is destructive after post-apply writes: it requires the same stop/drain coordination and a confirmation that newer data will be lost. Do not silently restore after actors resume.

### Crash reconciliation

On startup, reconcile transitional resource/draft/apply states using the control rows, physical apply marker, active file, and retained backup:

- before committed live apply: verify live, mark failed, and restore actors that were stopped by the run;
- committed and healthy apply: finish control state and pending restart reporting;
- uncertain/invalid live with verified backup: restore and report `recovered`;
- neither active nor backup verifiable: leave resource `error` and actors stopped.

Do not infer compatibility or manufacture a revision during reconciliation.

## UI replacement

Replace the current DB resource page's schema/version/migration UI.

### Resource overview

- resource status, identity, rename/delete;
- bound definitions/slots and all affected instance statuses;
- clear trusted-SQL notice: actors with write access may change data and schema;
- recent apply runs with separate database and actor results.

### Data tab

- table/view navigator;
- paginated grid with SQLite value rendering;
- add, edit, delete, and bounded bulk actions for safely identifiable tables;
- read-only explanation for views/unsupported identity;
- optimistic-conflict UI with reload/retry rather than silent overwrite.

### Structure tab

- current live table/column/index/foreign-key inspector;
- create/open/discard draft;
- draft-only structure editor and advanced SQL panel;
- ordered change summary and destructive warnings;
- apply preview listing definitions and instances;
- explicit apply confirmation.

### Apply result

Render a table with definition, instance, prior state, stop result, restart result, and actionable actor error. Say `restart succeeded` rather than `compatible`. Link to the widget update flow where available, but do not require or invoke AI.

## Service and API replacement

Remove:

- schema CRUD/publish/deprecate APIs;
- migration draft/publish/list APIs;
- version-target configuration APIs;
- migration preview/apply DTOs based on versions;
- schema context injection based on published migrations;
- migration compatibility blocks and restart-when-compatible behavior;
- schema/version mismatch error codes and remediation copy.

Add grouped control APIs for:

- resource schema introspection;
- table row list/create/update/delete;
- draft create/get/list/discard;
- draft structure operations and advanced SQL;
- apply preview/confirm/status/history;
- retained-backup discard and explicit coordinated restore.

Keep API payloads bounded and typed. Never return physical paths, native handles, unrestricted control-database access, or raw native errors.

When the agent creates or edits a widget already bound to a DB resource, it may receive current bounded schema introspection as point-in-time implementation context. It must be described as current structure, not a versioned contract. An unbound/new widget receives no invented tables and can create required tables through simple guest SQLite code if the product flow permits it.

## Stable errors

Retain generic resource and query/execute errors. Remove schema/version mismatch and migration-history errors from public contracts after legacy parsing is handled.

Add safe management codes such as:

- `DB_RESOURCE_DRAFT_EXISTS`
- `DB_RESOURCE_DRAFT_NOT_FOUND`
- `DB_RESOURCE_DRAFT_INVALID`
- `DB_RESOURCE_APPLY_IN_PROGRESS`
- `DB_RESOURCE_APPLY_FAILED`
- `DB_RESOURCE_APPLY_RECOVERED`
- `DB_RESOURCE_RESTORE_FAILED`
- `DB_RESOURCE_ROW_IDENTITY_REQUIRED`
- `DB_RESOURCE_ROW_CONFLICT`
- `DB_RESOURCE_TABLE_READ_ONLY`
- `DB_RESOURCE_SCHEMA_OPERATION_INVALID`

Do not expose SQL bodies, bound row values, paths, or native diagnostics in actor-facing errors. Local management DTOs may identify table/column/change names needed for remediation but still omit sensitive row values by default.

## Tests

### Contract removal and compatibility migration

- New DB manifests contain no schema ID/version and create resources without DB configuration args.
- Legacy schema fields parse as ignored compatibility input with one warning and never affect binding/admission.
- New scaffolds, SDK schema, prompts, fixtures, and published output omit schema/version.
- Binding checks only kind, lifecycle, and permission subset.
- Actor starts are never blocked by obsolete schema/version metadata.
- Migration 012 removes old control metadata while preserving resources, bindings, actor instances, physical user tables, and rows.
- Physical `_vibecanvas_migrations` cleanup preserves all non-host tables.

### Guest runtime

- Named and arbitrary SQLite-compatible query/execute behavior remains source-compatible apart from manifest schema removal.
- `fn` has no portal, `fx` remains read-only, and `tx` follows effective scope.
- Actor DDL remains possible and is documented as trusted behavior.
- Guest examples avoid Turso-only SQL even though the host still uses Turso internally.
- Serialized writes, transaction arrays, limits, cancellation, and resource lifecycle blocking remain intact.

### Introspection and rows

- Internal objects are excluded from table lists.
- Columns/indexes/foreign keys/views are represented accurately.
- Primary-key, composite-key, rowid, WITHOUT ROWID, view, and no-safe-identity cases.
- Cursor pagination, bigint/blob/null values, bounded results, and identifier quoting.
- Live create/update/delete and transactional bulk operations.
- Expected-value conflicts detect concurrent actor edits without overwriting them.
- Invalid constraints return safe management errors.

### Drafts

- Consistent physical draft copy under concurrent actor reads/writes.
- Only one active draft per resource.
- Structured create/rename/drop table and column operations.
- Table rebuild preserves data or fails without modifying live.
- Index and foreign-key operations.
- Advanced SQL bounds and draft health failures.
- Discard cleanup and recoverable cleanup failure.
- Draft changes never affect live before apply.

### Apply lifecycle

- Preview lists every bound definition, slot, persisted instance, and running state without compatibility claims.
- Lifecycle lock closes races with starts, binds, calls, row edits, and deletion.
- Stop failure aborts before live mutation and restarts already-stopped instances.
- Ordered draft changes apply atomically and record the physical apply marker.
- SQL failure leaves live unchanged or restores the verified backup.
- Health failure restores backup; failed restore leaves resource `error`.
- Previously running instances restart; previously stopped instances remain stopped.
- Start/crash failures are persisted and rendered without marking the database apply failed.
- Unrelated actors/resources continue running.
- Explicit backup restore warns about and demonstrably loses newer writes only after confirmation.
- Crash reconciliation covers pre-commit, committed, restored, and unrecoverable states.

### Build and lifecycle

- Source and embedded control migrations stay synchronized.
- Compiled binary continues locating the host-private Turso native addon.
- Resource close/delete includes live, draft, and retained-backup handles/files safely.
- No resource file receives Vibecanvas application/control migrations.
- Frontend tests cover empty/loading/error, narrow viewport, keyboard, and all built-in themes.

## Acceptance criteria

- DbResource has no public or runtime schema ID, schema version, generation, revision, fingerprint, or compatibility range.
- Turso remains host-private; guest types, docs, prompts, and examples promise only the supported SQLite-compatible portal.
- Arbitrary write remains trusted and may perform DDL without parser-based claims.
- Existing physical resource data survives removal of A72 migration metadata.
- Database resources are created empty without a schema catalog prerequisite.
- Live table data can be inspected and edited safely with bounded pagination and optimistic conflicts.
- Schema changes are drafted on a temporary copy and never affect live before explicit apply.
- Apply stops all affected running actors, drains calls, creates a verified backup, applies changes transactionally, health-checks, and restarts exactly the actors that were running.
- The UI identifies all affected definitions/instances before apply and reports observed stop/restart failures afterward without claiming compatibility.
- Failed/uncertain applies recover from backup when verifiable or leave the resource blocked in an honest error state.
- No CDC, AI verification, SQL authorization parser, remote Turso, MVCC, sync, or multi-process guest database access is introduced.

## NOTES

A74 intentionally does less semantic inference than A72. The host guarantees operational coordination and recovery for its own apply workflow; it does not guarantee that arbitrary guest SQL is compatible with any current or future physical schema.

The latest retained backup is a recovery tool, not a reverse migration. Restoring it after actors or users write against the changed database is explicitly destructive.
