# A67 - actor runtime: state lifecycle hooks and single state activity
[Overview](../BASED.md)

Add first-class actor state lifecycle behavior: one optional activity per state, plus explicit enter/exit/error semantics. This is for actors that must do backend work while a state is active, without abusing timeout messages or long-running transition functions.

## Context
- Design context: [llm.widget-system.md](../../docs/internal/llm.widget-system.md)
- Service facade: [ActorService.ts](../../packages/service-actor/src/ActorService.ts)
- Per-instance runtime: [Actor.ts](../../packages/service-actor/src/Actor.ts)
- Supervisor/persistence/routing: [ActorSupervisor.ts](../../packages/service-actor/src/ActorSupervisor.ts)
- Child-process function runner: [icp-client.ts](../../packages/service-actor/src/icp-client.ts)
- Actor manifest/types: [types.ts](../../packages/service-actor/src/core/types.ts)

Current actor runtime is message-triggered. `ActorService.sendMessage()` finds an in-memory actor and calls `actor.inbox(msgName, msgPayload)`. `Actor.inbox()` validates the input schema, verifies there is a transition for the current state, enqueues the inbox item, and returns a message id immediately.

Functions execute later in `Actor.#processQueue()` when the child process is ready. Queue processing is serialized with `#isProcessing`. The transition function pipeline runs through `#runTransition()` before `#applyTransitionTargetState()`. The child process receives `{ func, payload, data }`, resolves function names from the `fn`/`fx`/`tx` registry, and runs the pipeline. `portal.setData()` updates parent in-memory data and emits `data.changed`; after child `done`, the parent applies the target state and emits `ack`.

The supervisor persists actor machine snapshots only on `ack` events via `persistActorMachineSnapshot(actor)`. Actor output messages are routed to connected target actors. Error events currently do not obviously trigger the same persistence path.

`Actor.ts` already has timeout-message support: on start or state change, it scans current state transitions for message names like `timeout:1000ms` or `timout:1000ms`, schedules the earliest one, and enqueues that message. This should remain a dead-state / timeout mechanism, not the solution for state activities.

## Problem
We want a state like `busy.counting` to have backend work that runs while the actor remains in that state:

```text
enter busy.counting -> start counting activity
while busy.counting -> run activity every second
stop message -> leave busy.counting -> activity stops
```

A long-running transition function is the wrong primitive. If a transition function loops forever and sleeps every second, `Actor.#processQueue()` remains inside `await #runTransition(...)`, `#isProcessing` stays true, and later messages such as `stop` wait behind the loop. The actor cannot cleanly leave the state.

Timeout messages are also the wrong abstraction because they are named transitions and are meant as catch/dead-state behavior. They are one-shot state timers, not state-scoped activities.

## Proposed Type Shape
Start with one optional activity per state, not a record of named activities.

```ts
export type TActorErrorHandler = {
  func: TFunctionName[];
  recover?: "stay" | {
    targetState: TActorNonErrorState;
  };
}

export type TActorActivity = {
  everyMs: number;
  func: TFunctionName[];
  runImmediately?: boolean;
  onError?: TActorErrorHandler;
}

export type TTransition = {
  func: TFunctionName[];
  targetState: TActorState;
  onError?: TActorErrorHandler;
}

export type TActorStateConfig = {
  on: Partial<Record<TInputMessage, TTransition>>;
  activity?: TActorActivity;
  onEnter?: TFunctionName[];
  onExit?: TFunctionName[];
  onError?: TActorErrorHandler;
}
```

Open compatibility question: current manifests use `allowedTargetStates: TActorState[]`. Lifecycle semantics are simpler with a single `targetState`. Either migrate to `targetState`, support both during transition, or define how a function selects among multiple allowed target states before enter/exit semantics are implemented.

## Semantics
### Message transition order
For a normal message that changes state:

```text
message accepted
-> if target state differs and current state exit should run: run current state's onExit
-> run transition func pipeline
-> apply target state
-> run target state's onEnter
-> start target state's activity
-> ack + persist snapshot
```

User preference captured here: `onExit` runs before transition functions.

If target state equals current state, do not run `onExit`/`onEnter`; treat it as an internal/self transition unless later design says otherwise.

### onEnter
- Runs whenever a state is entered.
- Runs on actor startup/restore for the restored/current state.
- Cannot change the transition target state.
- If it fails, actor moves to implicit error state.
- Activity should start only after `onEnter` succeeds.

### onExit
- Runs before transition functions when leaving the current state.
- Does not run for implicit error transitions.
- If `onExit` fails, the transition fails and error handling applies.

### Activity
- At most one activity per state: `activity?: TActorActivity`.
- Runtime starts it after successful `onEnter` / state activation.
- Runtime cancels it when leaving the state.
- Activity functions must be short-running jobs, not loops.
- Repetition is owned by the actor runtime, not guest code.
- Activity ticks should enter the same serialized actor queue as messages to avoid races with `stop` or other inputs.
- Activity tick should check state generation/current state before running so stale scheduled ticks are dropped.

### Error handling
Need a first-class error handler concept that can recover and prevent implicit transition to `error`.

Priority suggestion:
1. Activity-level `activity.onError` for activity failures.
2. Transition-level `transition.onError` for message transition failures.
3. State-level `state.onError` as fallback.
4. If no handler recovers, apply implicit error state.

Recovery shape:
- `recover: "stay"` means handler success prevents error state and leaves actor in current state.
- `recover: { targetState }` means handler success prevents error state and moves actor to a non-error recovery state.
- If the error handler itself fails, actor goes to implicit error state.

Need decide what error payload is passed to handler functions. Likely include failed message/activity metadata, current data, and serialized error details.

## Essential Complexity
### 1. Queue model
Actor already serializes message processing. Activities should reuse that serialized path instead of running concurrently. This keeps data updates deterministic and prevents races between activity ticks and user messages.

### 2. Lifecycle generation
State activities need a generation/token. Each state activation increments a generation. Timers/jobs capture the generation. If the state or generation no longer matches when the tick fires, drop the stale tick.

### 3. Cancellation
Leaving a state cancels future ticks. Already-running activity jobs probably finish unless explicit cancellation is added later. This is simpler and matches the existing child-process run model.

### 4. Persistence
Current persistence happens on `ack`. Lifecycle hooks and activity ticks may not correspond to external input acks. The runtime/supervisor needs a persistence trigger after successful activity jobs, onEnter, onExit, recovery transitions, and errors/recoveries.

### 5. Startup/restore
On service startup, `ActorSupervisor.loadActorInstance()` creates actors from DB state/data and calls `actor.start()`. Start currently emits running/status/state events and schedules timeouts. New behavior should run `onEnter` for restored state and start that state's activity.

### 6. Browser closed vs server closed
If browser is closed but server keeps running, backend activities can continue. If server is stopped, no every-second work actually runs. On restart, runtime can resume activities for the persisted state, but must decide whether to catch up missed activity ticks. For a pure elapsed-time counter, storing `createdAt` and deriving elapsed seconds is still more durable and cheaper than writing once per second.

### 7. Scale/backpressure
One actor ticking every second is easy. Many actors ticking every second means many child-process runs and DB writes. Plan should consider minimum interval, dropped/coalesced ticks when prior tick is still queued/running, and future backpressure.

### 8. IPC/function runner
`icp-client.ts` already runs arbitrary function pipelines from names and supports `setData`, `emitMessage`, and `next`. Lifecycle hooks and activities can likely reuse `#runTransition`-like IPC, but the parent must pass a distinct job type/message id and persistence/event semantics.

## Plan
### 1. Finalize manifest contract
- Decide whether to migrate `TTransition` from `allowedTargetStates` to `targetState`.
- Decide compatibility behavior for existing manifests.
- Add `activity`, `onEnter`, `onExit`, and error handler types to manifest validation.
- Define whether `onEnter/onExit` may call `setData` and `emitMessage` through the same portal. Initial answer: yes, reuse existing function pipeline semantics.

### 2. Model actor jobs internally
- Split queue item type from only inbox messages into a discriminated job queue:
  - external input message job
  - activity tick job
  - lifecycle enter/exit job if needed, or inline lifecycle runs in transition flow
- Preserve one serialized processing lane.
- Ensure `sendMessage()` still returns immediately after validation/enqueue.

### 3. Implement state lifecycle runtime
- Add state activation method that runs `onEnter`, starts activity, and schedules timeout only where timeout support remains valid.
- Add state deactivation method that cancels activity and runs `onExit` for normal state exits.
- Ensure implicit error transitions bypass `onExit` per desired semantics.
- Ensure startup/restore runs `onEnter` for current state.

### 4. Implement single activity scheduler
- Store current activity timer and state generation.
- Support `runImmediately`.
- On each tick, enqueue an activity job tagged with state + generation.
- Drop stale activity jobs if state/generation no longer matches.
- Decide tick overlap policy: likely skip scheduling a new tick if previous activity job for same generation is still queued/running.

### 5. Implement error recovery
- Add transition/activity/state error handler lookup.
- Run handler in the same serialized path.
- If handler succeeds and has recovery policy, prevent implicit error state.
- Persist recovered state/data.
- If handler fails or no recovery exists, transition to error.

### 6. Persistence and events
- Define system events for lifecycle/activity jobs, or reuse existing events carefully.
- Persist machine snapshots after successful lifecycle/activity jobs, not only input `ack`.
- Persist implicit error state and recovery state.
- Keep widget snapshot updates flowing through actor events.

### 7. Tests and examples
- Create a fixture actor with `busy.counting` activity and `stop` transition.
- Verify activity ticks while in state and stops after `stop`.
- Verify `stop` is not blocked by activity because activity functions are short jobs.
- Verify startup/restore runs `onEnter` and resumes activity.
- Verify activity `onError` can recover and prevent error state.
- Verify `onEnter` failure moves to error.
- Verify `onExit` does not run for implicit error transitions.

## NOTES
- Do not solve this with timeout messages. Timeout messages are for dead-state/catch behavior.
- Do not solve this with a long-running actor function loop. It blocks the serialized queue and prevents `stop` from running.
- Prefer one `activity?: TActorActivity` per state for now. Multiple named activities can be added later only if needed.
- Pure elapsed counters should still prefer `createdAt`/derived time when possible; activities are for real backend work while a state is active.
- Current timeout scheduling has same-state limitations because `#applyTransitionTargetState()` returns early when next state equals current state. That is separate from this task.
