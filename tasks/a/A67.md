# A67 - actor runtime: state lifecycle hooks and single state activity
[Overview](../BASED.md)

Add first-class actor state lifecycle behavior: one optional activity per state, plus explicit enter/exit/error semantics. This is for actors that must do backend work while a state is active, without abusing timeout messages or long-running transition functions.

## Context
- Design context: [llm.widget-system.md](../../docs/internal/llm.widget-system.md)
- Service facade: [ActorService.ts](../../packages/service-actor/src/ActorService.ts)
- Per-instance runtime: [Actor.ts](../../packages/service-actor/src/Actor.ts)
- Supervisor/persistence/routing: [ActorSupervisor.ts](../../packages/service-actor/src/ActorSupervisor.ts)
- Child-process function runner: [icp-client.ts](../../packages/service-actor/src/icp-client.ts)
- Actor manifest/types: [types.ts](../../packages/service-actor/src/core/types.ts)

Current actor runtime is message-triggered. `ActorService.sendMessage()` finds an in-memory actor and calls `actor.inbox(msgName, msgPayload)`. `Actor.inbox()` validates the input schema, verifies there is a transition for the current state, enqueues the inbox item, and returns a message id immediately.

Functions execute later in `Actor.#processQueue()` when the child process is ready. Queue processing is serialized with `#isProcessing`. The transition function pipeline runs through `#runTransition()` before `#applyTransitionTargetState()`. The child process receives `{ func, payload, data }`, resolves function names from the `fn`/`fx`/`tx` registry, and runs the pipeline. `portal.setData()` updates parent in-memory data and emits `data.changed`; after child `done`, the parent applies the target state and emits `ack`.

The supervisor persists actor machine snapshots only on `ack` events via `persistActorMachineSnapshot(actor)`. Actor output messages are routed to connected target actors. Error events currently do not obviously trigger the same persistence path.

`Actor.ts` already has timeout-message support: on start or state change, it scans current state transitions for message names like `timeout:1000ms` or `timout:1000ms`, schedules the earliest one, and enqueues that message. This should remain a dead-state / timeout mechanism, not the solution for state activities.

## Problem
We want a state like `busy.counting` to have backend work that runs while the actor remains in that state:

```text
enter busy.counting -> start counting activity
while busy.counting -> run activity every second
stop message -> leave busy.counting -> activity stops
```

A long-running transition function is the wrong primitive. If a transition function loops forever and sleeps every second, `Actor.#processQueue()` remains inside `await #runTransition(...)`, `#isProcessing` stays true, and later messages such as `stop` wait behind the loop. The actor cannot cleanly leave the state.

Timeout messages are also the wrong abstraction because they are named transitions and are meant as catch/dead-state behavior. They are one-shot state timers, not state-scoped activities.

## Resolved Manifest Contract
Start with one optional activity per state, not a record of named activities. New manifests use `targetState`; old manifests using `allowedTargetStates` remain valid and do not require migration.

```ts
export type TActorErrorHandler = {
  func: TFunctionName[];
  recover: "stay" | {
    targetState: TActorNonErrorState;
  };
}

export type TActorActivity = {
  everyMs: number;
  func: TFunctionName[];
  runImmediately?: boolean;
  onError?: TActorErrorHandler;
}

export type TTransition = {
  func: TFunctionName[];
  targetState: TActorState;
  onError?: TActorErrorHandler;
}

export type TLegacyTransition = {
  func: TFunctionName[];
  allowedTargetStates: TActorState[];
  onError?: TActorErrorHandler;
}

export type TActorStateConfig = {
  on: Partial<Record<TInputMessage, TTransition | TLegacyTransition>>;
  activity?: TActorActivity;
  onEnter?: TFunctionName[];
  onExit?: TFunctionName[];
  onError?: TActorErrorHandler;
}
```

### Backward compatibility rules
- Treat the filesystem manifest as an input format and normalize it once when loaded. The `Actor` runtime and downstream UI should consume a canonical transition with one `targetState`.
- New and AI-generated manifests emit only `targetState`.
- Existing `allowedTargetStates` with exactly one item normalizes to that item.
- Existing `allowedTargetStates` with zero or multiple items preserves current behavior: transition functions run, the actor remains in the source state, and a definition warning is emitted. This avoids changing old widgets that are currently acknowledged without a state change.
- If both `targetState` and `allowedTargetStates` are present, reject the manifest as ambiguous.
- Keep accepting explicit error targets from old filesystem manifests because the current core schema permits them. New-manifest linting should warn and continue to prefer implicit error transitions.
- Do not remove `allowedTargetStates` support without a future versioned manifest migration.
- Manifests without lifecycle/activity/error fields retain their current message, event, timeout, and state behavior.
- Keep the existing `timeout:` and misspelled `timout:` message forms working.

## Resolved Runtime Semantics
### Serialized jobs
Use one discriminated queue and one processing lane:

```text
startup activation job
external input job
activity tick job
```

`onExit`, transition functions, `onEnter`, and recovery run inline inside the owning job. They are not independent queue items, so another message cannot interleave halfway through a transition.

Each queued job has a job id. Activity and timeout jobs also capture the state name and activation generation. External messages capture the state/generation in which they were accepted.

Messages accepted while initial activation is still pending are tagged for that pending initial state and bound to the first activation generation after `onEnter` succeeds. They are not treated as stale merely because startup created the first generation.

If an external message becomes stale before execution, drop it with `DROP_MESSAGE` / `STALE_STATE_MESSAGE`; do not move the actor to `error`. Activity/timeout jobs that become stale are discarded silently. Self-transitions do not increment the generation, so queued work for the same active state remains valid.

`ActorService.sendMessage()` continues returning a message id immediately after schema/state validation and enqueue.

### Startup and readiness
Startup/restore is an activation job and is the first job processed after the child reports IPC readiness.

```text
spawn child
-> child ready
-> apply restored/initial state
-> run state onEnter
-> start timeout/activity scheduling
-> emit snapshot-ready state
-> actor is ready/running
```

Messages received after `start()` but before activation completes may queue, but cannot execute before activation. `waitUntilReady()` must mean child ready plus initial activation finished, not only IPC ready. `ActorSupervisor` marks instance health as running only after this barrier.

An initial `onEnter` failure follows normal error handling. If unrecovered, enter the implicit base `error` state, run `error.onEnter` once, persist the error snapshot, and still allow manual recovery messages. A failure from `error.onEnter` emits an error and stops lifecycle recursion; it does not try to enter `error` again.

Startup/restore does not catch up ticks missed while the server was offline. After activation, `runImmediately: true` queues one tick; otherwise the first tick waits `everyMs`. Startup `onEnter` and immediate activities therefore have at-least-once side-effect semantics and should be idempotent.

### Normal message transition order
For a message whose canonical target differs from the source state:

```text
message accepted
-> cancel source timeout/activity and invalidate its generation
-> run source onExit
-> run transition func pipeline
-> apply target state and emit state.changed
-> run target onEnter
-> start target timeout/activity scheduling
-> emit ack
-> emit final snapshot event
```

User preference is preserved: `onExit` runs before transition functions. The target is considered entered before `onEnter` runs, so an `onEnter` failure may produce `source -> target -> error` state events, but only the final outcome is persisted.

If target state equals the current state, treat it as an internal/self transition: run only the transition pipeline, do not run `onExit`/`onEnter`, do not cancel/restart timeout or activity, and do not increment the activation generation.

### Lifecycle hooks and portal behavior
- `onEnter` runs after every real entry, including startup/restore, normal transitions, implicit error entry, and recovery re-entry.
- `onExit` runs only for a normal message transition or an explicit recovery target leaving a successfully active state.
- Implicit transitions to `error` bypass `onExit`.
- Runtime close/reload cancels work but does not run `onExit`, because the persisted machine remains in the same state and will be restored later.
- Lifecycle, activity, and error pipelines reuse the existing child-process function runner and may call `next`, `setData`, and `emitMessage`.
- Existing transition functions continue receiving the original input payload unchanged.
- Internal pipelines receive structured JSON payloads:
  - enter: `{ kind: "lifecycle.enter", state, fromState, cause, messageId? }`
  - exit: `{ kind: "lifecycle.exit", state, toState, cause, messageId? }`
  - activity: `{ kind: "activity.tick", state, generation, tick, scheduledAt }`
  - error handler: `{ kind: "actor.error", phase, job, sourceState, targetState?, currentState, error }`
- `args.data` remains the current actor data. Serialized error data contains `name`, `message`, optional `stack`, and optional `code`.
- Preserve current non-transactional portal behavior for compatibility: `setData` and emitted messages take effect immediately. If a later function fails, those effects are not rolled back; the final error/recovery snapshot persists the resulting data.
- Update IPC payload typing/validation from object-only to JSON/unknown so valid primitive input payloads continue to work and internal payloads share one runner.

### Activity scheduler and backpressure
- Validate `everyMs` as an integer from `1_000` through `2_147_483_647`. Activities are backend work, not animation timers.
- Use recursive `setTimeout`, not `setInterval`.
- Keep at most one queued or running activity job for an activation generation.
- Schedule the next delayed tick only after the prior tick reaches a terminal success/recovery outcome. This provides fixed-delay behavior and prevents backlog.
- `runImmediately: true` queues one tick after successful activation; it does not also start a parallel interval.
- A queued tick before a `stop` message may finish first by FIFO order. If `stop` executes first, generation invalidation drops the stale tick.
- A currently running activity is not preempted. `stop` waits for that short job to finish, but repeated future ticks cannot keep it blocked.
- Leaving state, implicit error, actor close, service stop, reload, and child exit clear activity timers. Close also clears queued jobs and rejects pending/waiting runs so no work is left hanging.
- Apply the same generation token to state timeout jobs so recovery/re-entry into the same named state cannot execute an old timer.

### Error lookup and recovery
Error handlers are selected by failure phase:

1. Activity failure: `activity.onError`, then active `state.onError`.
2. `onExit` or transition pipeline failure: `transition.onError`, then source `state.onError`.
3. `onEnter` failure caused by a transition: `transition.onError`, then target `state.onError`.
4. Startup/recovery `onEnter` failure: entered state's `state.onError`.
5. No applicable handler: implicit base `error` state.

Only the first declared handler runs. If it fails, go directly to implicit `error`; do not fall through to another handler. `recover` is required so a successful handler always has an unambiguous outcome.

Recovery behavior:
- `recover: "stay"` reactivates the state current at the point of failure. If deactivation had started, or `onEnter` failed, run `onEnter` once again with recovery cause before restarting timeout/activity. Failure of this recovery entry goes directly to implicit `error` without invoking another handler.
- `recover: { targetState }` moves to that non-error state. If the failed state was fully active, cancel its scheduling and run its `onExit`; if exit/deactivation already started or its `onEnter` never succeeded, do not run `onExit` again. Then apply the recovery target, run its `onEnter`, and start scheduling.
- A recovered external input emits its normal `ack` after recovery activation completes. An unrecovered input emits an error but no `ack`.
- Implicit error entry cancels scheduling, changes to base `error`, runs `error.onEnter` once, and schedules the error state's timeout/activity only if entry succeeds.

### Persistence and events
Keep existing `ack`, `state.changed`, `data.changed`, actor output, and error events compatible. `ack` continues to mean that an external message finished successfully or recovered; it does not promise durable storage.

Add a system snapshot event containing `{ revision, state, data, cause, jobId? }`. Emit exactly one final snapshot after:
- successful startup activation;
- a successful or recovered external input;
- a successful or recovered activity tick that may have changed data;
- an unrecovered failure after the implicit error state is applied.

Do not persist intermediate `onExit`, transition, or `onEnter` states separately. `ActorSupervisor` should persist from the event's captured state/data rather than reading mutable actor getters later. Serialize writes per actor by monotonic revision, optionally coalescing pending revisions, so frequent ticks cannot overwrite newer state with an older DB completion.

Once snapshot events are in place, stop using `ack` itself as the supervisor persistence trigger so one input does not schedule duplicate writes.

Semantic actor errors keep instance health `running` because the actor can receive recovery input; child-process/runtime failure still marks instance health `error` as today.

### 1. Add raw-manifest compatibility and canonical normalization
- Add lifecycle/activity/error handler types plus raw legacy/new transition types.
- Add one pure normalizer that resolves transitions with their source state and returns a canonical actor definition plus warnings.
- Update the Zod manifest schema to accept either transition form exclusively.
- Update the agent TypeBox candidate schema to generate only `targetState`.
- Update manifest linting to validate canonical targets, recovery targets, activity interval bounds, and all lifecycle/activity/error function names.
- Update function discovery/scaffolding so registries include functions referenced by transitions, hooks, activities, and every error handler.
- Update prompts, examples, fixtures, tests, and Actor UI graph mapping to use canonical targets while retaining legacy fixtures as compatibility tests.
- Bring `packages/sdk/vibecanvas.schema.json` in sync with the actual manifest contract instead of leaving a second stale format.

### 2. Generalize the actor queue and child runs
- Replace inbox-only queue items with startup, input, and activity jobs.
- Add job metadata to pending IPC runs so emitted messages/data/errors retain the correct message/job context.
- Keep lifecycle phases inline within their owning serialized job.
- Add accepted state/generation to external inputs and drop stale inputs without entering error.
- Bind inputs accepted during startup to the first successful activation generation.
- Generalize `#runTransition()` into a pipeline runner accepting function list, structured payload, job metadata, and failure phase.

### 3. Implement activation/deactivation and readiness
- Centralize state activation: apply state when needed, emit state change, run `onEnter`, then schedule timeout/activity.
- Centralize deactivation: invalidate generation, clear scheduling, and run `onExit` only when semantics require it.
- Queue startup activation after child ready and make `waitUntilReady()` await the whole activation result.
- Guard implicit error entry and recovery entry against recursive lifecycle failures.
- Make `ActorService.stop()` close supervisor actors.

### 4. Implement the activity/timeout scheduler
- Store activation generation, activity timer, timeout timer, activity queued/running flag, and tick sequence.
- Queue immediate/delayed activity ticks with fixed-delay scheduling and no overlap.
- Tag timeout jobs with the same generation and preserve both timeout spellings.
- Cancel timers/jobs and reject pending work on close, reload, and child failure.

### 5. Implement phase-aware error recovery
- Build the structured, clone-safe error context.
- Resolve handlers using the defined phase priority.
- Implement stay reactivation, target recovery, handler failure, and guarded implicit error entry.
- Preserve immediate `setData`/output effects and persist the final resulting snapshot.

### 6. Add ordered snapshot persistence
- Add monotonic snapshot events without changing existing ack semantics.
- Make the supervisor serialize/coalesce per-actor machine snapshot writes from captured event data.
- Persist startup, activity, recovery, and implicit error outcomes.
- Keep runtime-health persistence separate from recoverable machine error state.

### 7. Tests and compatibility fixtures
- Keep an unchanged legacy widget fixture using single-item `allowedTargetStates` and verify identical behavior/events.
- Verify zero/multi-item legacy targets preserve current self-state behavior and emit warnings.
- Verify new `targetState` manifests and reject manifests containing both target forms.
- Verify startup readiness, restored `onEnter`, no missed-tick catch-up, and startup failure/error entry.
- Verify normal order: exit -> transition -> state change -> enter -> activity -> ack/snapshot.
- Verify self-transitions do not restart lifecycle, activity, timeout, or generation.
- Verify immediate and delayed ticks, no overlap/backlog, FIFO stop behavior, stale tick dropping, and cleanup on close/reload/child exit.
- Verify activity, exit, transition, and enter error priority; stay/target recovery; handler failure; and recursion guards.
- Verify `onExit` is skipped for implicit error and is not double-run during recovery.
- Verify snapshots are final-only, revisions persist in order, and error/recovery state/data survive restart.
- Verify lifecycle/activity/error functions are discovered, linted, and scaffolded.
- Verify primitive transition payloads still execute through IPC.

## NOTES
- Do not solve this with timeout messages. Timeout messages are for dead-state/catch behavior.
- Do not solve this with a long-running actor function loop. It blocks the serialized queue and prevents `stop` from running.
- Prefer one `activity?: TActorActivity` per state for now. Multiple named activities can be added later only if needed.
- Pure elapsed counters should still prefer `createdAt`/derived time when possible; activities are for real backend work while a state is active.
- Self-transitions intentionally do not restart timeout or activity scheduling; stale timeout/activity jobs are generation-guarded across real exits and recovery re-entry.
