# A69 - actor resources: prepare shared resource control plane and IPC
[Overview](../BASED.md)

Prepare the definition-level resource system used by actor functions. Add resource catalog/binding persistence to Vibecanvas's existing `DbServiceTurso`, make resource ownership an `ActorService` responsibility, declare named resource slots in widget manifests, and establish the generic actor IPC/resource gateway required by `KvResource`, `SecretStoreResource`, and `DbResource`.

This task is preparation only. It must leave a complete control plane and transport extension that the three concrete resource tasks can implement without redesigning actor identity, bindings, manifest validation, service ownership, or IPC correlation.

## Context

### Product requirement

A user can create multiple resource instances and bind a widget definition to one resource instance per declared slot. Every actor instance created from that widget definition resolves the same binding and therefore shares the same resource.

Examples:

```text
Widget definition "GitHub Profile"
  slot "credentials" -> SecretStoreResource "Personal GitHub"

Widget definition "CRM Contacts"
  slot "crm" -> DbResource "Acme CRM"
  slot "preferences" -> KvResource "Acme CRM Settings"
```

The binding belongs to the actor/widget definition, not to one actor instance or one canvas element.

### Required terminology

Use the `Resource` suffix consistently for user-defined actor resources:

- `KvResource`
- `SecretStoreResource`
- `DbResource`

`DbServiceTurso` remains the Vibecanvas application/control database service. A `DbResource` is user-defined actor data storage with a different, schema-agnostic interface. Do not call a `DbResource` a `DbServiceTurso`, do not run Vibecanvas application migrations against it, and do not expose the application database through actor portals.

Recommended persisted kind values:

- `kv`
- `secretStore`
- `db`

Recommended public TypeScript discriminants may use the same exact values. Avoid introducing parallel spellings such as `key-value`, `database`, `secret_store`, or `turso` in different layers.

### Explicitly accepted limitations and out-of-scope work

The following are intentionally not part of A69-A72:

- Durable actor inbox/outbox.
- Hard security isolation between `fn`, `fx`, and `tx` code.
- Sandboxing the actor IPC process.
- Preventing guest code from retaining portals or using direct Bun APIs.
- Actor child environment/network/filesystem hardening.
- Secret encryption at rest or envelope encryption.
- Turso Cloud, remote Turso, embedded replicas, or cloud synchronization.
- Hardcoded or generated `DbResource` table schemas.
- ORM integration.
- A generic resource system outside `ActorService`.

The current actor-process trust model is accepted. Function-class capabilities are an SDK/runtime correctness boundary for now, not protection against malicious guest code. Future IPC sandboxing may enforce the same contract more strongly without changing the public resource APIs.

## Target model

### Resource slot declaration

A widget manifest declares requirements under the actor definition. It never contains a concrete resource ID or local database path.

Conceptual shape:

```json
{
  "actor": {
    "resources": {
      "preferences": {
        "kind": "kv",
        "required": false,
        "access": "readWrite"
      },
      "credentials": {
        "kind": "secretStore",
        "required": true,
        "access": "readWrite"
      },
      "crm": {
        "kind": "db",
        "required": true,
        "access": "readWrite"
      }
    }
  }
}
```

Exact field names may be refined during implementation, but preserve these semantics:

- Slot names are definition-local stable identifiers.
- Slot names are non-empty, bounded strings suitable for map keys.
- `kind` is mandatory and discriminated.
- `required` is explicit or has one documented default.
- Access is no broader than `read` or `readWrite` in the first version.
- No `DbResource` schema appears in the manifest.
- No resource instance ID appears in the manifest.
- Existing manifests with no `resources` field remain valid.
- Unknown fields are handled consistently with the existing Zod manifest policy.

The definition can declare multiple slots of the same kind even if the first UI/API consumer usually binds one of each kind.

### Resource catalog row

Add a Vibecanvas application DB migration for a generic actor-owned resource catalog. Recommended table semantics:

```text
actor_resources
  id                 immutable text primary key
  kind               kv | secretStore | db
  name               user-facing non-empty name
  status             created | ready | error | deleting, or the smallest useful equivalent
  metadata            JSON object for non-secret provider metadata; default {}
  last_error          nullable JSON-compatible structured error, if lifecycle needs it
  created_at
  updated_at
```

Decisions:

- Do not overload the existing global `kv` table.
- Do not put resource values in `actor_resources`.
- Do not put `DbResource` table schemas in `metadata`.
- Do not store arbitrary guest-controlled file paths.
- The first version is installation/single-user scoped because current actor APIs are not fully authorized by account. Keep the model capable of adding an owner/scope later without changing slot semantics.
- Decide and test whether names are unique globally, unique per kind, or not unique. Prefer allowing duplicate display names and identifying resources by immutable ID.

### Definition binding row

Add a binding table with semantics equivalent to:

```text
actor_resource_bindings
  actor_definition_name    FK -> actor_definitions(name)
  slot_name                manifest slot name
  resource_id              FK -> actor_resources(id)
  created_at
  updated_at

  primary key (actor_definition_name, slot_name)
```

Required behavior:

- One binding per definition slot.
- One resource can be bound to multiple definitions intentionally.
- All actor instances of a definition resolve the same row.
- Binding validation verifies that the slot exists and kinds match.
- Rebinding replaces the mapping atomically.
- Removing an actor instance does not remove bindings or resources.
- Deleting an actor definition removes its bindings but does not delete shared resources.
- Deleting a resource that is still bound is rejected with a useful conflict unless an explicit future force workflow is added.
- Foreign keys and indexes support listing bindings by definition and references by resource.

Use the current definition name FK for compatibility with the existing model. Record a note that an immutable definition ID is a future model improvement; do not expand this task into a definition identity migration unless implementation proves it necessary.

## Database changes required

A69 changes only Vibecanvas's application/control database. It does **not** create the concrete KV entries, secret values, or user database tables owned by A70-A72.

### New migration

Add `008-add-actor-resources.sql`. Migration `007-add-actor-instance-error.sql` already exists in the source registry, so it must not be renumbered or replaced. The generated `embedded-migrations.ts` currently stops at `006`; regenerate/fix it so both `007` and `008` are present in packaged builds.

The migration adds two tables:

```sql
CREATE DOMAIN IF NOT EXISTS ACTOR_RESOURCE_KIND AS TEXT
  NOT NULL
  CONSTRAINT actor_resource_kind_allowed
    CHECK (value IN ('kv', 'secretStore', 'db'));

CREATE DOMAIN IF NOT EXISTS ACTOR_RESOURCE_STATUS AS TEXT
  DEFAULT 'created'
  NOT NULL
  CONSTRAINT actor_resource_status_allowed
    CHECK (value IN ('created', 'ready', 'error', 'deleting'));

actor_resources (
  id          TEXT PRIMARY KEY NOT NULL,
  kind        ACTOR_RESOURCE_KIND,
  name        TEXT NOT NULL CHECK (length(trim(name)) > 0),
  status      ACTOR_RESOURCE_STATUS,
  metadata    JSON NOT NULL DEFAULT '{}',
  last_error  JSON,
  created_at  TIMESTAMP NOT NULL DEFAULT (datetime('now')),
  updated_at  TIMESTAMP NOT NULL DEFAULT (datetime('now'))
) STRICT

actor_resource_bindings (
  actor_definition_name TEXT NOT NULL
    REFERENCES actor_definitions(name) ON DELETE CASCADE,
  slot_name             TEXT NOT NULL,
  resource_id           TEXT NOT NULL
    REFERENCES actor_resources(id) ON DELETE RESTRICT,
  created_at            TIMESTAMP NOT NULL DEFAULT (datetime('now')),
  updated_at            TIMESTAMP NOT NULL DEFAULT (datetime('now')),
  PRIMARY KEY (actor_definition_name, slot_name)
) STRICT
```

Use Turso `CREATE DOMAIN` declarations for the closed resource kind and lifecycle status sets, following the existing `ACTOR_SYSTEM_STATUS` pattern in migration `005`; do not duplicate these invariants as per-column `CHECK` clauses. Use the repository's actual migration syntax and statement separators. Add JSON validity/object checks where supported by the existing migration conventions. Add updated-at triggers consistent with the actor tables.

### Constraints and indexes

- Resource IDs are immutable and are the only stable resource identity.
- Display names are deliberately **not unique**; duplicate names are allowed across and within kinds.
- The binding primary key enforces one resource per definition slot.
- Do not add uniqueness on `resource_id`: one resource may be shared by many slots/definitions.
- Index `actor_resources(kind)` for filtered catalog lists.
- Index `actor_resource_bindings(resource_id)` for reference checks and delete-conflict reporting. The binding primary key already supports listing by definition.
- Definition deletion cascades only its bindings. It never deletes catalog resources.
- Resource deletion is restricted while bindings exist. The persistence method should detect references first and return a domain conflict; the FK remains the race-safe backstop.
- Slot existence, slot kind compatibility, and read/write access are manifest/business rules and cannot be enforced by these tables; `ActorService` validates them before writing a binding.

### Persistence/model changes

Add validated persistence row types in `packages/service-db/src/model.ts` and an `actorResource` namespace on `DbServiceTurso`. It must provide catalog create/get/list/update/delete and binding list/reference/upsert/remove operations. Keep this namespace persistence-only: it stores metadata and mappings, not provider objects or resource contents.

Rebinding is a transaction/upsert of `(actor_definition_name, slot_name)` that replaces only `resource_id` and updates `updated_at`. Catalog updates and rebinding should avoid native `UPDATE ... RETURNING`; perform the write and then select the resulting row. All DB methods must return parsed DTOs rather than raw JSON strings.

No existing data needs backfilling: existing definitions simply have no binding rows. Do not alter `actor_instances`, copy bindings into actor instance context, reuse the global `kv` table from migration `006`, or store local provider paths in catalog metadata.

### Database verification

Tests must run the migration from an empty database and verify catalog CRUD, duplicate display names, kind filtering, rebind behavior, shared resources, same-kind multiple slots, unbinding, definition-delete cascade, bound-resource delete rejection, and unbound-resource deletion. Also assert that both source and embedded migration lists include `007` and `008` in order.

### 3. Add Vibecanvas DB migration and persistence methods

Add the next numbered migration for `actor_resources` and `actor_resource_bindings`.

Update every migration registry/build path, including compiled embedded migration assets. Verify the current source/embedded mismatch around migration 007 while doing this; do not silently ship a migration that source mode applies but compiled mode omits.

Add low-level `DbServiceTurso.actorResource` or equivalently clear namespace methods for:

- Create catalog row.
- Get by ID.
- List catalog rows, optionally by kind.
- Rename/update metadata/status.
- Delete unbound resource row.
- Get bindings for a definition.
- Get definitions referencing a resource.
- Upsert/rebind a definition slot atomically.
- Remove one binding.
- Remove all bindings for a definition through FK cascade or explicit transaction.

The namespace is persistence only. It must not own runtime `KvResource`, `SecretStoreResource`, or `DbResource` objects.

Avoid risky native `UPDATE ... RETURNING` patterns identified elsewhere in the repository. Prefer write followed by select when necessary and cover it with service-db tests.

### 4. Add ActorService-owned resource control plane

Create an actor-package component such as `ActorResourceManager`/`ActorResourceRegistry`; choose one clear name and keep it internal to `ActorService` unless a public service method is required.

Responsibilities:

- Own concrete provider registration.
- Create resource IDs using host `crypto`.
- Validate resource kind/name.
- Coordinate catalog persistence with provider provisioning/cleanup.
- Validate definition slot existence and kind on binding.
- Resolve `(definitionName, slotName)` into a resource descriptor.
- Refuse deletion while bindings exist.
- Close provider handles when `ActorService.stop()` runs.
- Keep failures local to the requested resource; one bad resource must not prevent unrelated actor definitions from starting.

`ActorService` remains the only runtime service registered in `setup-services.ts`; do not introduce a top-level `ResourceService` in the runtime registry.

Extend `ActorService` configuration with the resource data root needed by A72, derived from the existing XDG data directory. Ensure tests can inject a temporary root. Creation of DB files is deferred to A72.

Also fix/define actor shutdown ownership as needed so resource providers and actor children are actually closed by `ActorService.stop()`.

### 5. Add resource management service/API methods

Expose boring actor-service methods needed by management callers:

- List/get/create/rename/delete resource metadata.
- List resource bindings for a definition.
- Bind/rebind a slot.
- Unbind a slot.
- Return definition resource requirements and binding status.

Extend `packages/api-actors` with typed ORPC routes for the same control-plane operations. Responses must contain metadata and binding state only; concrete KV values, secrets, SQL rows, file paths, and provider handles are not resource-management DTOs.

Required error mapping:

- Definition not found.
- Slot not declared.
- Resource not found.
- Kind mismatch.
- Resource still bound.
- Required binding missing.
- Provider unavailable.

No dedicated frontend management UI is required by this preparation task. The service/API must nevertheless be complete enough for a later UI or tests to create resources and assign them to definitions without touching DB internals.

### 6. Define the generic actor resource gateway

Keep `Actor.ts` generic. Add an injected gateway/callback interface rather than giving it `DbServiceTurso` or `ActorResourceManager` directly.

The trusted parent must derive:

- Actor instance ID.
- Actor definition name.
- Current run/message ID.
- Requested slot.
- Function class/read-write ceiling.

The child supplies only slot, operation, and operation arguments. It must never supply a concrete resource ID, application DB handle, local path, or provider credential.

At actor creation, `ActorSupervisor` injects a gateway bound to that actor's definition. Resolve bindings at operation time or cache them with explicit invalidation; do not permanently copy a resource ID into actor machine context.

### 7. Extend IPC with correlated resource calls

Add explicit child-to-parent and parent-to-child resource messages. Do not overload the current `next`, `setData`, or `emitMessage` acknowledgment keys.

Protocol requirements:

- Resource call ID unique within the child process/run.
- Actor run ID remains present for cancellation and diagnostics.
- Slot name, resource kind, operation name, and serializable arguments.
- Success response with serializable result.
- Failure response with stable code, safe message, and optional safe details.
- Pending call cleanup on actor close, child exit, run failure, or parent send failure.
- No unresolved promise if the actor child dies.
- Multiple resource calls in one function can be correlated correctly.
- Calls from concurrent asynchronous work cannot consume each other's responses.

Refactor `icp-client.ts` portal construction so each function class receives the intended resource capability shape:

- `fn.*`: no resource portal.
- `fx.*`: read-only resource operations.
- `tx.*`: read and write resource operations.

The existing trusted-process limitation is accepted. Tests should validate normal portal shape and operation routing, not claim malicious child isolation.

### 8. Add SDK preparation types

Extend `@vibecanvas/sdk/actor` with shared resource slot and error types, while leaving concrete operation interfaces to A70-A72 where practical.

Public API rules:

- Actor authors refer to manifest slot names.
- No `DbServiceTurso` types leak into the SDK.
- No concrete DB schema is required.
- Results remain call-site typable by actor authors later.
- Existing `defineFn`, `defineFx`, `defineTx`, and registries remain source compatible.
- `fn` portal remains resource-free.

Update SDK build/tests and package exports only if necessary; keep the existing `@vibecanvas/sdk/actor` subpath.

### 9. Define missing-binding behavior

Do not prevent an actor process from starting merely because an optional resource is unbound.

For a resource call:

- Missing required or optional binding returns a stable `RESOURCE_NOT_BOUND` operation error containing the slot but no internal DB information.
- Kind mismatch returns `RESOURCE_KIND_MISMATCH`.
- Deleted/unavailable resource returns `RESOURCE_UNAVAILABLE`.
- Read-only slot write attempt returns `RESOURCE_WRITE_NOT_ALLOWED`.
- Unknown slot returns `RESOURCE_SLOT_UNKNOWN`.

Expose binding status through the control API so the host can eventually render setup UI. Do not write infrastructure binding errors into actor business context automatically.
