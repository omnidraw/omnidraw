# A69 - shared resource control plane, manifest contract, and actor IPC
[Overview](../BASED.md)

Prepare the shared resource control plane used by actor functions. Add resource catalog/binding persistence to Vibecanvas's `DbServiceTurso`, make `ActorService` responsible for host runtime lifecycle, declare named resource slots in widget manifests, and establish the generic correlated IPC gateway required by A70–A72.

This task is preparation. Concrete KV, secret, and database operations remain in A70–A72.

## Resource model

A resource is neutral shared infrastructure. It is not owned by one widget or actor instance.

- `DbServiceTurso` persists the application/control-plane catalog and bindings.
- `ActorService` owns runtime provider registration, provisioning coordination, resolution, operation dispatch, and shutdown.
- Widget definitions declare requirements and permissions for named slots.
- Users bind definition slots to concrete resources.
- Every actor instance of a definition resolves the same binding.
- One resource may intentionally be shared by multiple definitions.
- Actor children never receive control-database handles, resource paths, provider handles, or authority to choose resource IDs.

Examples:

```text
Widget definition "GitHub Profile"
  slot "credentials" -> SecretStoreResource "Personal GitHub"

Widget definition "CRM Contacts"
  slot "crm" -> DbResource "Acme CRM"
  slot "preferences" -> KvResource "Acme CRM Settings"
```

Current resources are shared. Future isolation must use explicit forks/physical partitions and is not part of A69–A72.

## Terminology

Use these public names and discriminants consistently:

- `KvResource` / `kv`
- `SecretStoreResource` / `secretStore`
- `DbResource` / `db`

`DbServiceTurso` remains Vibecanvas's application/control database. A `DbResource` is a separate local database implemented by A72. Never expose `DbServiceTurso` through actor portals or run application migrations against a `DbResource`.

`scope` means actor resource **permission scope** in these tasks. It contains `read`, `write`, or both. It does not mean account, row, actor-instance, or physical isolation scope. Future isolation should use terms such as fork/partition/isolation.

## Accepted limitations and exclusions

- Installation/single-user control-plane authorization.
- Current trusted actor-child process model.
- No durable inbox/outbox.
- No hard `fn`/`fx`/`tx` sandbox.
- No actor process environment/network/filesystem hardening.
- No secret encryption at rest.
- No cloud/remote Turso or synchronization.
- No resource forks or security-grade instance isolation.
- No dedicated resource-management frontend in A69–A72. Typed control APIs and actionable status DTOs are required; UI work is postponed.

## Manifest contract

Existing manifests with no `resources` field remain valid. Resources are a definition-level map with stable bounded slot names.

### KV and secret slots

```ts
{
  kind: "kv" | "secretStore",
  required: boolean,
  scope: Array<"read" | "write">,
}
```

### Database slots

```ts
{
  kind: "db",
  required: boolean,
  scope: Array<"read" | "write">,
  schema: {
    id: string,
    version: number, // integer >= 0
  },
  arbitrarySql?: boolean, // default false
  operations?: Record<string, {
    effect: "read" | "write",
    sql: string,
    parameters?: Record<string, {
      type: "string" | "number" | "boolean" | "bigint" | "bytes" | "json",
      required?: boolean, // default true
      nullable?: boolean, // default false
    }>,
    result: "rows" | "execute",
  }>,
}
```

A DB schema version of `0` explicitly means no host migrations have been applied. The schema itself must still exist/publish through A72 before a resource can be configured or bound.

### Validation rules

- Slot names are non-empty bounded strings and are not normalized.
- Supported kinds are exactly `kv | secretStore | db`.
- `required` is explicit; use `true` as the documented scaffold default.
- Scope is a non-empty duplicate-free subset of `read | write`.
- Scope is permission, not isolation.
- `fn` receives no resource portal regardless of scope.
- `fx` has a read ceiling.
- `tx` may receive declared read/write permissions.
- DB schema IDs and operation names are non-empty bounded stable identifiers.
- DB version is an integer `>= 0`.
- `arbitrarySql` defaults to false.
- Named operation SQL is one non-empty bounded statement. Reject multi-statement declarations during publication using a proven parser/adapter facility where possible; do not claim naive splitting is a security boundary.
- Named SQL parameters are declared, named, bounded, and validated at invocation. Missing required and unknown extra parameters are rejected.
- `effect: write` requires definition write scope. A read operation requires read scope.
- A write named operation can only execute from `tx` at runtime.
- Named effect classification is trusted declaration under the accepted process model, not engine-level SQL security.
- Unknown fields follow the existing Zod manifest policy.

No concrete resource ID or local path appears in a manifest. KV/secret slots contain no value schema. DB slots declare compatibility, named operations, and permissions but do not own the resource or migration lifecycle.

Update `TVibecanvasActor`, Zod schemas, SDK preparation types, wizard candidate schemas, approval/scaffold output, implementation prompt, registry validation, complete draft validation, and publish preservation tests.

When the agent authors/updates a DB widget, A72 supplies all published migration SQL through the expected version so the agent can derive local actor row types. A69 only prepares the manifest shape and transport types.

## Control database migration

Add `008-add-actor-resources.sql`. Migration `007-add-actor-instance-error.sql` already exists in the source registry. Regenerate/fix `embedded-migrations.ts`, which currently stops at `006`, so packaged builds include `007` and `008` in order.

Use Turso domains following the existing migration style:

```sql
CREATE DOMAIN IF NOT EXISTS ACTOR_RESOURCE_KIND AS TEXT
  NOT NULL
  CONSTRAINT actor_resource_kind_allowed
    CHECK (value IN ('kv', 'secretStore', 'db'));

CREATE DOMAIN IF NOT EXISTS ACTOR_RESOURCE_STATUS AS TEXT
  DEFAULT 'created'
  NOT NULL
  CONSTRAINT actor_resource_status_allowed
    CHECK (value IN (
      'created',
      'provisioning',
      'ready',
      'migrating',
      'error',
      'deleting'
    ));
```

Add the catalog:

```sql
CREATE TABLE IF NOT EXISTS `actor_resources` (
  `id` TEXT PRIMARY KEY NOT NULL,
  `kind` ACTOR_RESOURCE_KIND,
  `name` TEXT NOT NULL CHECK (length(trim(`name`)) > 0),
  `status` ACTOR_RESOURCE_STATUS,
  `last_error` JSON,
  `created_at` TIMESTAMP NOT NULL DEFAULT (datetime('now')),
  `updated_at` TIMESTAMP NOT NULL DEFAULT (datetime('now'))
) STRICT;
```

Add definition bindings with permission reduction:

```sql
CREATE TABLE IF NOT EXISTS `actor_resource_bindings` (
  `actor_definition_name` TEXT NOT NULL
    REFERENCES `actor_definitions` (`name`)
    ON UPDATE NO ACTION
    ON DELETE CASCADE,
  `slot_name` TEXT NOT NULL CHECK (length(trim(`slot_name`)) > 0),
  `resource_id` TEXT NOT NULL
    REFERENCES `actor_resources` (`id`)
    ON UPDATE NO ACTION
    ON DELETE RESTRICT,
  `allow_read` BOOLEAN NOT NULL,
  `allow_write` BOOLEAN NOT NULL,
  `created_at` TIMESTAMP NOT NULL DEFAULT (datetime('now')),
  `updated_at` TIMESTAMP NOT NULL DEFAULT (datetime('now')),
  CHECK (`allow_read` OR `allow_write`),
  PRIMARY KEY (`actor_definition_name`, `slot_name`)
) STRICT;
```

Use actual repository statement separators and updated-at triggers. Add JSON validity checks for JSON columns where supported by current Turso conventions.

### Catalog/binding invariants

- IDs are immutable and are the only stable resource identity.
- Display names are not unique; duplicate names are allowed.
- The generic catalog stores identity and lifecycle state only; provider-owned configuration belongs in dedicated provider tables.
- One binding exists per definition slot.
- One resource may be bound by many definitions/slots.
- Binding permission booleans may reduce but never broaden manifest scope.
- Slot existence, kind, DB schema/version, and permission-subset validation occur in ActorService before persistence.
- Deleting a definition cascades its bindings only.
- Deleting a resource while bound is rejected. FK `RESTRICT` is the race-safe backstop.
- Index `actor_resources(kind)` and `actor_resource_bindings(resource_id)`.
- The binding primary key already supports listing by definition.
- Use the current definition name FK for compatibility; immutable definition ID remains future work.

No existing data needs backfilling. Existing definitions simply have no binding rows. Do not reuse migration `006`'s global `kv` table or copy resource IDs/bindings into actor instance context.

## Service-db persistence namespace

Add validated persistence models in `packages/service-db/src/model.ts` and an `actorResource` namespace on `DbServiceTurso`.

Required methods:

- Create/get/list catalog rows, optionally filtered by kind/status.
- Rename a resource.
- Provider-controlled status/last-error update.
- Delete an unbound catalog row.
- Get bindings for a definition.
- Get definitions referencing a resource.
- Atomically upsert/rebind a slot with permission restriction.
- Remove one binding.
- Remove all bindings through definition cascade.
- Begin deletion transactionally: verify no bindings and transition to `deleting` so new bindings are rejected.

The namespace is persistence-only. It does not own provider instances or physical resource contents.

Avoid risky native `UPDATE ... RETURNING`; write then select. Rebinding updates `(resource_id, allow_read, allow_write, updated_at)` atomically. Parse JSON strings into validated DTOs.

## ActorService resource control plane

Create one internal component such as `ActorResourceManager`, owned by `ActorService`.

Responsibilities:

- Register providers by exact kind.
- Generate IDs through injected host crypto.
- Validate names, kinds, lifecycle transitions, and provider-specific creation inputs.
- Coordinate persistence with provider provisioning/deletion sagas.
- Validate slot existence, kind, schema/version compatibility, and binding permission subset.
- Resolve `(definitionName, slotName)` at operation start.
- Calculate effective permissions.
- Refuse new binding/calls while provisioning, migrating, error, or deleting.
- Refuse deletion while bound.
- Track/drain in-flight calls for provider migration/deletion.
- Close all providers/handles during `ActorService.stop()`, continuing if one close fails.
- Isolate provider failure to the requested resource.

ActorService remains the only top-level runtime service. Do not register a separate generic `ResourceService`.

Extend ActorService configuration with an injected resource data root derived from CLI XDG data. Tests inject a temporary root. A69 does not create concrete provider files.

### Lifecycle transitions

Use explicit guarded transitions, including:

```text
created -> provisioning -> ready
provisioning -> error
ready -> migrating -> ready | error
ready -> deleting -> removed | error
error -> provider-specific recovery/migration/deletion path
```

Control DB, filesystem, and provider databases cannot share one transaction. Provider tasks must use recoverable sagas and startup reconciliation for transitional states. A69 establishes status/types/hooks; A72 implements DB-specific backup and recovery.

### Binding/rebinding call semantics

- A resource call resolves one binding at call start.
- That call finishes against the resolved resource even if a rebind occurs concurrently.
- Calls starting after commit resolve the new resource.
- Migration/deletion waits for already resolved calls to drain.
- Resource deletion starts with a control-DB transaction that verifies no references and marks deleting.

## Management service/API

Expose typed ActorService methods and actor ORPC routes for:

- List/get/create/rename/delete resource catalog rows.
- List definition requirements and binding compatibility/status.
- List definitions referencing a resource.
- Bind/rebind with optional reducing scope.
- Unbind.
- Provider-specific status/action extension points used by A72 schema/migration routes.

Responses contain generic lifecycle state only. They never include KV values, secrets, SQL rows, migration SQL unless using A72's explicit schema-management API, local paths, handles, provider credentials, or provider-specific configuration except through its dedicated API.

## Binding status DTO

Return at least:

```text
slot
requirement
bound
resource catalog row (when bound)
requested scope
binding scope
scope valid
kind matches
ready
compatible
blocked code/message
```

For DB slots also return:

```text
expected schema ID/version
actual schema ID/applied version
target version
schema matches
version matches
```

Missing required or optional bindings do not by themselves prevent the generic actor process from starting; resource calls fail safely and required status is exposed to control clients. Binding creation rejects known kind/schema/version incompatibility. A72 may deliberately keep actors stopped after a disruptive resource migration when their published DB version no longer matches.

Do not write infrastructure binding/version errors into actor business context automatically.

## Generic actor resource gateway

Keep `Actor.ts` generic. Inject a gateway callback/interface rather than `DbServiceTurso` or ActorResourceManager.

The trusted parent derives:

- Actor instance ID.
- Definition identity.
- Current run/message ID.
- Slot requirement and current binding.
- Resolved resource ID internally.
- Function class.
- Manifest scope.
- Binding restriction.
- Effective permissions.
- Resource lifecycle and compatibility.

The child supplies only slot, operation/named-operation name, and serializable arguments. It never supplies resource ID, path, effective scope, function class, account/instance authority, provider credential, or application DB handle.

Resolve at operation start; do not permanently copy bindings into machine context. Cache only with explicit invalidation.

## Correlated IPC protocol

Add explicit child-to-parent resource request and parent-to-child response messages. Do not overload `next`, `setData`, or `emitMessage` acknowledgements.

Request contains:

- Unique call ID within child process/run.
- Actor run ID.
- Slot.
- Resource kind expected by typed proxy.
- Operation or named-operation name.
- Serializable arguments.

Response contains either:

- Success with serializable result; or
- Stable safe code, message, and optional safe details.

Requirements:

- Correlate multiple concurrent calls correctly.
- Pending calls reject on actor close, child exit, run failure/cancel, parent send failure, provider drain, or gateway close.
- No unresolved promises after child death.
- Parent rejects unknown/forged operations even if typings normally prevent them.
- Logging excludes secret values, complete DB parameters, paths, and raw native errors.

Portal construction by function class:

- `fn.*`: no resource portal.
- `fx.*`: only read-capable proxies.
- `tx.*`: read/write proxies according to effective permissions.

This is a correctness capability boundary under the accepted trusted-process model, not a hostile-code sandbox.
