# A75 - actor resources: build DbResource management workbench
[Overview](../BASED.md)

Replace the first versioned-migration DbResource page with a complete A74 management workbench for live data, structure drafts, coordinated applies, actor restart outcomes, and retained-backup recovery.

## Dependency

Blocked by [A74](A74.md). Implement against A74's final schema-agnostic DbResource contract. Do not preserve or rebuild A72 schema IDs, versions, published migrations, compatibility checks, or version-target UI.

Parallel A74 edits may be present while this task is prepared. Treat A74's accepted behavior as the source of truth rather than adapting this task to temporary intermediate symbols.

Correct the mocks where they conflict with A74:

## Product model

The database page has four top-level tabs:

1. `OVERVIEW`
2. `SCHEMA`
3. `DATA`
4. `SQL`

Keep the active tab and selected object in the URL:

```text
/resources/:resourceId?tab=overview
/resources/:resourceId?tab=schema&object=notes
/resources/:resourceId?tab=data&object=notes
/resources/:resourceId?tab=sql
```

Only one active editing/applying draft exists per resource, so draft ID does not need to be user-managed in the URL.

### Persistent header

- Show `DATABASE RESOURCE`, resource name, lifecycle status, sidebar toggle, and destructive resource action.
- Render Kobalte tabs directly below the title bar.
- Preserve the existing square, flat, monospace styling and semantic theme tokens.

### Overview

- Resource status, ID, timestamps, rename, and guarded delete.
- Do not add a standalone trusted-SQL or read-only-connection notice; keep mutation approval at the point of action.
- Bindings grouped by definition, slot, and effective access.
- All affected persisted instances with observed current status/running state.
- Recent apply runs with database outcome and actor restart outcome shown separately.
- Latest retained backup with explicit discard and coordinated restore actions.
- Never render `compatible`, schema version, target version, or migration version.

### Schema

With no active draft:

- Inspect live tables read-only.
- Show columns, declared types, nullability, defaults, primary-key order, indexes, foreign keys, triggers, editable identity, and CREATE SQL.
- Primary action is `CREATE SCHEMA DRAFT`.

With an active draft:

- Inspect and edit the physical draft, not live.
- Show `DRAFT ACTIVE`, pending-change count, and `Live database unchanged`.
- Use a narrow object navigator, central structure table, and right inspector.
- Support create/rename/drop table; add/rename/edit/drop column; create/drop indexes; create/drop foreign keys.
- Show ordered structured/raw changes and the exact server-generated SQL.
- Require explicit confirmation for destructive changes and identify affected objects/data.
- Provide `DISCARD DRAFT` and `REVIEW & APPLY` actions.

Do not implement column drag reordering in this task. The mock's grip must not imply unsupported reorder behavior.

### Data

- Select an explicit table or view before loading rows.
- Render bounded cursor-paginated rows in a compact grid.
- Deliberately render SQLite null, integer/bigint, real, text, and bytes.
- Row pages return only bounded BLOB previews and byte lengths. Hydrate one identified row on demand for edit/delete so large BLOBs never inflate normal pagination responses.
- Add/edit/delete rows only for tables with a safe primary-key or rowid identity.
- Explain why views, WITHOUT ROWID tables without a PK, and other unsupported identities are read-only.
- Send stable identity and expected original values for update/delete.
- On optimistic conflict, preserve the proposed edit and offer `RELOAD ROW` or `CANCEL`; never silently overwrite actor changes.
- Support bounded transactional bulk delete.
- Data editing always targets live and never becomes part of a structure draft.

### SQL

- SQL runs against the live database and displays bounded typed result sets.
- Read-only statements run immediately on a physically read-only connection.
- A statement that can mutate live data or schema must fail closed until the user reviews the exact SQL and checks a prominent approval control.
- Approved mutations run on the serialized live write lane and report rows affected/last inserted identity separately from row-producing results.
- Result grids and row pages stay bounded so many rows and large BLOBs do not make the frontend unresponsive.

### Apply and restore

`REVIEW & APPLY` must fetch a fresh preview immediately before confirmation:

- ordered changes and known destructive warnings;
- bound definitions and slots;
- all persisted instances and which are currently running;
- explicit wording that compatibility cannot be guaranteed.

After confirmation, poll the persisted apply run by ID and show preparing, stopping, applying, health-check/recovery, and restarting phases. Database success and actor restart failures are separate results. Use `restart succeeded`, `start failed`, and `actor crashed`; never `compatible`.

Restore must preview affected actors and explicitly warn that writes made after the retained backup will be lost. It uses the same coordinated stop/drain/restart model as apply.

## Control API replacement

Remove the A72-facing ORPC groups and all frontend use of:

- `dbSchemas.*`;
- `dbMigrations.*`;
- version-target `dbResources.configuration`, `previewMigration`, and `migrate`;
- schema/version compatibility DTO fields.

Update database creation to accept only:

```ts
{ kind: "db", name: string }
```

### Resource inspection and impact

Add:

```text
dbResources.impact({ resourceId })
dbResources.inspect({ resourceId, target: "live" })
dbResources.executeSql({ resourceId, sql, parameters?, approved })
```

`impact` returns definitions, slots, persisted instances, and observed status/running state. Existing generic resource references are insufficient because they omit affected instances.

`inspect` returns bounded user tables/views while excluding `_vibecanvas_*`, `sqlite_*`, and Turso-internal objects. Each object includes columns, indexes, foreign keys, triggers, CREATE SQL, stable identity, editability, and a read-only reason.

### Lossless row values

Use an explicit wire representation so bigint and bytes survive transport:

```ts
type TDbCellValue =
  | { type: "null" }
  | { type: "integer"; value: string }
  | { type: "real"; value: number }
  | { type: "text"; value: string }
  | { type: "blob"; base64: string }
```

Add:

```text
dbRows.list
dbRows.get
dbRows.create
dbRows.update
dbRows.delete
dbRows.bulk
```

- List uses stable primary-key tuple/rowid cursor pagination, never offset-only as the final contract.
- List returns bounded BLOB preview metadata; `get` hydrates one stable-identity row under a strict payload limit.
- Update/delete require identity and expected original values.
- Bulk accepts a bounded operation array and is transactional within one resource.
- Return typed identity-required, read-only, and conflict errors.

### Draft APIs

Add:

```text
dbDrafts.create
dbDrafts.list
dbDrafts.get
dbDrafts.inspect
dbDrafts.change
dbDrafts.executeSql
dbDrafts.discard
```

`dbDrafts.change` accepts a typed discriminated structured-operation union. The host validates identifiers, generates SQLite-compatible SQL, performs required table rebuilds, health-checks the draft, and stores the exact successful SQL. Do not make browser-generated SQL authoritative.

Required operation discriminants:

- `createTable`, `renameTable`, `dropTable`;
- `addColumn`, `renameColumn`, `alterColumn`, `dropColumn`;
- `createIndex`, `dropIndex`;
- `createForeignKey`, `dropForeignKey`.

### Apply APIs

Add:

```text
dbApplies.preview({ draftId })
dbApplies.confirm({ draftId })
dbApplies.get({ applyId })
dbApplies.list({ resourceId, cursor?, limit? })
```

Polling `get` is sufficient for the first UI. A streamed apply-event API is optional.

### Backup APIs

Add:

```text
dbBackups.get({ resourceId })
dbBackups.discard({ resourceId, applyId })
dbBackups.previewRestore({ resourceId, applyId })
dbBackups.restore({ resourceId, applyId })
dbBackups.restoreStatus({ restoreId })
```

Return metadata and outcomes only. Never return physical paths, native handles, bound row values in errors, or raw native diagnostics.

## Frontend architecture

Move DbResource management out of the monolithic route into a feature-local module such as:

```text
apps/frontend/src/feature/db-resource/
  DbResourcePage.tsx
  DbResourcePage.module.css
  components/
  fn.*.ts
  fx.*.ts
  tx.*.ts
```

Keep the route page as a thin resource-kind dispatcher.

Follow the repository function-file rules:

- pure conversion, validation, grid formatting, and change summaries in `fn.*.ts`;
- API reads in two-parameter `fx.*.ts` portal functions;
- API writes in two-parameter `tx.*.ts` portal functions;
- no direct runtime globals inside function files;
- Solid components retain UI state and orchestration.

Use Kobalte subpath imports and explicit composition:

- `Tabs` for page navigation;
- `DropdownMenu` for object actions;
- `TextField`, `Select`, `Switch`, and `Checkbox` for editors;
- `AlertDialog` for destructive confirmation;
- `Dialog` for apply/restore previews and result windows;
- existing Toast for operation outcomes.

Use local CSS modules, semantic theme variables, visible focus, square corners, restrained overlay shadows, compact spacing, and `data-*` state styling. Verify light, dark, sepia, and graphite.

At narrow desktop widths, move the right inspector into a dialog/overlay while retaining the object navigator and primary grid. This task does not introduce a mobile dashboard redesign.

## Acceptance criteria

- Database resources are created with name only and no schema/version prerequisite.
- The page contains Overview, Schema, Data, and live SQL tabs.
- No UI or API claims schema compatibility or exposes migration versions.
- Live schema introspection excludes internal objects and accurately represents editability.
- Live table rows support bounded cursor browsing and conflict-safe CRUD with lossless SQLite values.
- Live SQL reads return bounded typed result sets; mutations cannot execute before exact-SQL acknowledgement and approval.
- Structure changes modify only the physical draft until explicit coordinated apply.
- Structured operations are server-generated and recorded with exact SQL.
- Apply preview lists every affected definition/slot/instance and does not claim compatibility.
- Apply results distinguish database outcome from actor restart outcome.
- Retained backup discard and destructive coordinated restore are usable from Overview.
- The UI follows Vibecanvas's square, compact, theme-aware workstation style and is fully keyboard operable.
- KV and secret-store resources provide Overview/Data tabs with 50-row prefix-filtered cursor pages.
- Secret-store Data exposes names, revisions, and timestamps only; plaintext values never cross the management API.
- KV and secret-store Data tabs support conflict-safe CRUD; secret updates are rotations with an empty replacement field.
- The Data workbench keeps its pagination footer visible while large result pages scroll inside the table.
