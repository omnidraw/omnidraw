# A48 - chat-render-output: assistant markdown without boxes
[Overview](../BASED.md)

Render AI wizard chat history like a real chat transcript: user prompts may stay framed, assistant output renders as document content without a message box, and assistant Markdown is supported including ```md fenced output.

## Context

Requested target area:
- `packages/canvas/src/components/AiWizzard/ChatComposer/ChatComposer.tsx`
- `packages/canvas/src/components/AiWizzard/tabs/ChatTab.tsx`
- `packages/canvas/src/components/AiWizzard/index.css`

Current implementation notes:
- `ChatTab.tsx` renders each history item as `<article class="ai-chat-history__message"><span>role</span><p>content</p></article>`.
- `index.css` styles every `.ai-chat-history__message` with dashed border, card-like background, and padding.
- This makes assistant responses look like simple boxes; requested UX says assistant responses should not be boxed.
- User messages may remain framed and should have a tilted/tinted background treatment.
- Reference screenshot was provided at `/var/folders/pf/mzkxrfrj2zbcv5wfsln5h0rw0000gn/T/pi-clipboard-8d48b5e5-2e24-4580-a490-153dfbca6c33.png`.

Requested behavior:
- User messages: okay to be framed; add/keep a distinct tilted/tinted background style.
- Assistant messages: no surrounding box/chrome; render the content directly in the chat stream.
- Assistant Markdown must render as Markdown.
- If assistant output is wrapped in a Markdown code fence like ```md ... ```, treat the inner content as Markdown, not as a literal code block.
- Do not implement in this task; this leaf is planning/context only.

## Research notes

Brave search query:
- `parse LLM output markdown code fences structured output best practices`

Useful findings:
- LLMs often wrap structured or markup output in Markdown fences and/or add prose around it. Rendering code should defensively detect wrappers rather than assuming perfect output.
- For structured data, modern APIs prefer schema/JSON modes; for chat display, we still need tolerant content rendering because assistant text is intentionally human-facing Markdown.
- Chrome Developers guidance for streamed LLM rendering warns against naive `innerHTML` updates for Markdown because of security and performance. Markdown output should be parsed/sanitized through a safe renderer, not injected directly.
- Streaming Markdown can be reparsed from accumulated text, but avoid unsafe HTML passthrough and avoid repeated full DOM churn where possible.

Research/source links:
- Chrome streamed LLM rendering notes: `https://developer.chrome.com/docs/ai/render-llm-responses`
- LLM structured output parsing overview: `https://tetrate.io/learn/ai/llm-output-parsing-structured-generation`
- Solid Markdown renderer option found: `https://github.com/andi23rosca/solid-markdown`
- Safe marked + DOMPurify option found: `https://github.com/azu/safe-marked`

Existing dependency scan:
- `packages/canvas/package.json` already has `dompurify`.
- `packages/canvas/package.json` has `@codemirror/lang-markdown`, but that is editor language support, not a chat Markdown renderer.
- No obvious existing `marked`, `remark`, `rehype`, `micromark`, or `solid-markdown` dependency was found in root/canvas package manifests.

Implications for this task:
- Add a small normalization step before rendering assistant content:
  - trim only wrapper noise, not meaningful Markdown indentation
  - recognize full-content fences with language aliases like `md` and `markdown`
  - unwrap only when the whole assistant response is one Markdown fence
  - keep normal code fences inside Markdown intact
- Use a Markdown renderer with unsafe raw HTML disabled or sanitized.
- Avoid styling assistant Markdown as a card/box; style headings/lists/code blocks as document content.

## Plan

### 1. Split chat history rendering by role
- Add role-aware classes or a small local renderer component for chat messages.
- Preserve a framed user-message style.
- Remove border/background/padding for assistant-message container.
- Keep assistant role label subtle or omit if visual hierarchy is clear.

### 2. Add assistant Markdown rendering
- Choose the existing project-preferred Markdown rendering path if one exists.
- If adding a dependency is needed, prefer a safe Markdown pipeline with raw HTML disabled/sanitized.
- Support standard Markdown: paragraphs, headings, lists, links, inline code, fenced code, blockquotes.
- Add special handling for full-response ```md / ```markdown fences.

### 3. Keep user text simple
- User messages can render as escaped plain text with preserved whitespace.
- Do not parse user prompt text as trusted HTML.
- Keep the tilted/tinted background limited to the user bubble visual style.

### 4. Add tests or focused checks
- Cover role branching: user bubble vs assistant document rendering.
- Cover assistant plain Markdown.
- Cover assistant wrapped Markdown fence: ```md\n# Title\n...\n``` renders as Markdown content.
- Cover nested/non-wrapper code fences remain code blocks.
