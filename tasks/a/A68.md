# A68 - widgets: isolate loading failures and render in-frame error states
[Overview](../BASED.md)

Make widget and actor failures visible, local, and survivable. One broken actor instance, widget definition, actor event stream, snapshot request, or sandbox render must not abort server/canvas startup or make a persisted widget silently disappear. The minimum visible outcome is an error inside the existing widget frame:

```text
[Error loading Widget: <useful message>]
```

## Context

This task follows the investigation in [B41](../b/B41.md). B41 exposed a production restart crash while actor startup updated an actor row using Turso `UPDATE ... RETURNING`. The exact native pager panic/segmentation fault cannot be caught in JavaScript because the process terminates before a promise can reject. B41's SQL/runtime mitigation is therefore a prerequisite. This task covers the recoverable failures around that path and ensures they reach the canvas as explicit widget error states.

## Current Failure Path

### B41 startup path

```text
runCliMain()
-> runtime.boot()
-> services start sequentially
-> ActorService.start()
-> ActorSupervisor.init()
-> ActorSupervisor.reload()
-> loadMissingActorInstances()
-> loadActorInstance(actor row)
-> actor.start()
-> db.actor.updateInstanceStatus(...)
-> Turso native pager panic / segmentation fault
```

`createRuntime.boot()` starts all registered services before applying plugins. The actor service starts before the server plugin is applied. A normal rejected actor-start promise can therefore reject the complete runtime boot before HTTP/WebSocket serving becomes available. A native segmentation fault terminates the process outright and is not catchable.

Required distinction:
- Native abort/panic: prevent the invalid native SQL shape; no JS error UI is possible after process death.
- Ordinary exception/rejection: isolate it at the smallest actor/widget boundary, persist/query it, transport it, and render it.

## Findings: Missing Error Boundaries

### 1. Persisted actor startup is all-or-nothing

`ActorSupervisor.loadMissingActorInstances()` loops through actor rows and directly awaits `loadActorInstance()`. One recoverable failure aborts the remainder of the loop and bubbles through `ActorService.start()` into the complete server runtime boot.

Missing behavior:
- Catch per actor instance.
- Clean up partially inserted `actorMap` entries/processes.
- Continue loading later instances.
- Mark the failed instance as errored.
- Publish structured diagnostics.

### 2. Actor construction/start/status update is not transactional as a lifecycle

`loadActorInstance()` currently:
1. Resolves the definition.
2. Constructs the actor.
3. Adds it to `actorMap`.
4. attaches listeners.
5. starts its child process.
6. updates DB status to `running`.

Failures between these steps can leave an inconsistent map, running child process, or stale DB status. A missing definition currently returns silently and can leave the row appearing healthy.

### 3. Definition synchronization can fail as one batch

`txSyncDbActorDefinitions()` builds a `Promise.all()` over all inserts/updates. A single invalid/conflicting definition rejects the batch and can prevent actor startup. Definition parsing errors are currently published as global notifications, but invalid definitions are discarded from the in-memory map and do not become a queryable catalog state.

### 4. Async Automerge callbacks are invoked as `void`

`setup-services.ts` supplies async `onElementCreate`/`onElementDelete` callbacks. `AutomergeService` invokes them without awaiting or attaching a rejection handler. Actor creation failure can therefore become an unhandled rejection.

If actor creation returns `null` or rejects, the persisted widget never receives `actorInstanceId`. The canvas-side sandbox performs a bounded wait and then remains on a booting/null snapshot rather than showing a host error.

### 5. Definition API errors are reduced to `console.error`

`Widget.plugin.ts` logs and returns when definition list/get calls fail. No error reaches `WidgetManagerService`.

If a persisted widget kind is not registered, `ElementService.createNodeFromElement()` returns `null`. `SceneHydrator` silently skips that element. The CRDT element still exists, but the widget disappears visually. This is the most important frontend fallback gap.

### 6. Widget registration and scene hydration run in parallel

Canvas `initAsync` is an `AsyncParallelHook`. Published-widget registration and initial scene hydration can race. Even healthy widgets can initially be unregistered when hydration examines them. Later `widgetRegister` can repair a successfully loaded kind, but there is no generic node/error frame during the missing interval or for permanent registration failure.

### 7. DOM render and sandbox mount are unprotected

`txAttachDomPortal()` directly invokes:
- `widgetConfig.renderDom(...)`
- `mountArrowSandbox(...)`

A synchronous renderer, source transformation, sandbox compile, or sandbox mount exception can interrupt element creation/scene hydration or reject canvas boot. There is no local error replacement.

### 8. Actor error information reaches the SDK, not the host frame

`mountArrowSandbox()` converts snapshot failures and actor `system.error` events into `{ state: "error", context: ... }` snapshots. This assumes every generated widget implements an error UI. A widget may render nothing, throw while processing the snapshot, or ignore error state entirely.

The canvas host needs an independent last-resort error surface.

### 9. Actor events are transient and not replayed

`EventPublisherService` publishes actor events to current subscribers only. Startup failures can occur before the frontend connects, so event-only error transport loses the failure. Notifications are global and unsuitable as the authoritative state for one persisted widget.

### 10. Actor event stream failure permanently disables updates

`WidgetManagerService.#listenToActorEvents()` logs an initial endpoint error and returns. It does not retry. Errors thrown while iterating the stream are not caught. Widgets can silently stop receiving state/error events.

### 11. Canvas runtime boot rejection is discarded

`Canvas.tsx` calls `void runtime.boot()` without a rejection handler. Canvas-wide initialization errors can become unhandled and leave a partially constructed canvas without an error shell.

## Design Goals

1. A native/process-fatal error is prevented before it occurs; do not claim JS catches can recover a segfault.
2. One bad actor instance must not prevent server startup or later actor instances from starting.
3. One bad widget definition must not remove unrelated tools/widgets.
4. Every persisted widget element must have a visible runtime node, even when its definition is unavailable.
5. The host must render a safe fallback without relying on widget-authored code.
6. Errors that happen before frontend subscription must remain queryable.
7. Errors should be structured, phase-specific, and safe to display.
8. Do not overwrite actor business data (`machine_context`) with infrastructure diagnostics.
9. Recovery should replace the error view with the real widget without duplicating DOM portals.
10. Global toast notifications supplement the in-frame state; they do not replace it.

## Proposed Error Model

Define a shared JSON-compatible shape, preferably in an API/service-owned types module rather than inside a UI file:

```ts
type TWidgetErrorPhase =
  | "definition-discovery"
  | "definition-sync"
  | "definition-fetch"
  | "instance-create"
  | "instance-start"
  | "instance-persist"
  | "snapshot"
  | "event-stream"
  | "dom-render"
  | "sandbox-compile"
  | "sandbox-runtime";

type TWidgetError = {
  phase: TWidgetErrorPhase;
  code: string;
  message: string;
  details?: unknown;
  retryable: boolean;
  occurredAt?: string;
};
```

Rules:
- `message` is a human-usable summary, not a serialized raw exception object.
- `details` must satisfy the existing JSON contract before crossing ORPC.
- Never expose secrets, environment variables, full local paths, request credentials, or uncontrolled stack traces to the browser.
- Preserve full internal diagnostics in server logs where appropriate.
- Error rendering must use `textContent`, not `innerHTML`.
- Codes must be stable enough for tests and retry decisions.

Example codes:
- `WIDGET_DEFINITION_INVALID`
- `WIDGET_DEFINITION_UNAVAILABLE`
- `ACTOR_INSTANCE_CREATE_FAILED`
- `ACTOR_INSTANCE_START_FAILED`
- `ACTOR_INSTANCE_NOT_READY`
- `ACTOR_SNAPSHOT_FAILED`
- `ACTOR_EVENT_STREAM_DISCONNECTED`
- `WIDGET_RENDER_FAILED`
- `WIDGET_SANDBOX_MOUNT_FAILED`
- `WIDGET_SANDBOX_RUNTIME_FAILED`

## Persistence and Queryability

### Actor instance errors

Add dedicated persisted error state to `actor_instances`, for example nullable `last_error JSON`. Keep `status = "error"` as the coarse lifecycle state and `last_error` as the detailed explanation.

Do not store infrastructure errors in `machine_context`; that field is actor-owned business state and may contain data needed for recovery.

Update semantics:
- On recoverable instance start/create/persist failure: set `status = "error"`, set `last_error`.
- On successful restart/recovery: set the appropriate healthy status and clear `last_error`.
- If DB error persistence itself fails, log/publish the original and persistence errors without recursively retrying forever.
- Avoid dangerous `UPDATE ... RETURNING` shapes identified in B41.

Migration considerations:
- Add a new migration rather than rewriting an applied migration.
- Use a nullable JSON/TEXT-compatible column supported by Turso custom types.
- Update Zod model/types, insert/update/select parsing, fixtures, and migration tests.
- Confirm old databases migrate without touching large `machine_context` values unnecessarily.

### Definition errors

Retain a definition health/error catalog in `ActorSupervisor` instead of discarding every failed definition after a toast. The catalog must distinguish:
- Valid definition with widget code available.
- Invalid manifest/definition.
- DB synchronization failure.
- Widget source read failure.
- Removed definition.

When a manifest is too invalid to yield a definition name, retain path/folder diagnostics for global reporting. When a DB row or persisted canvas widget provides a known name, expose an error keyed by that widget kind.

## API Contract Plan

### Instance snapshot

Expand the snapshot response from:

```ts
{ state, context }
```

to:

```ts
{
  status,
  state,
  context,
  error: TWidgetError | null
}
```

Questions to resolve during implementation:
- Snapshot currently finds instances by `instanceId`. A newly persisted widget may not yet have one. Either allow lookup by `elementId`, add an instance-health endpoint by element id, or persist a creation error on the canvas element.
- Prefer a server lookup by `elementId` if it avoids putting transient backend diagnostics into the collaborative canvas document.
- A true missing instance must return a structured `ACTOR_INSTANCE_NOT_READY`/`NOT_FOUND` outcome that the host can render after the bounded creation window.

### Definition catalog

Definition list/get must expose known broken states instead of forcing the frontend to infer them from a generic ORPC error. Possible response shape:

```ts
type TWidgetDefinitionCatalogItem =
  | { kind: "ready"; name: string; definition: ... }
  | { kind: "error"; name: string; error: TWidgetError };
```

If keeping the current list/get split:
- List returns every known definition name and its health.
- Get returns source only for ready definitions.
- Widget plugin registers an error fallback for error items and for per-definition get failures.

### Event stream

Keep actor `system.error` events for live updates. Add host handling rather than relying only on widget SDK snapshots.

Events remain an optimization for immediacy; snapshot/catalog APIs remain authoritative for reconnect and startup.

## Canvas Architecture Plan

### Generic fallback widget definition

Register one low-priority fallback element definition from `WidgetManagerService.start()` that matches every persisted `widget` element.

Behavior:
- Specific widget definitions must have higher precedence and remain the base creator when available.
- When no specific definition exists, fallback creates the normal Konva widget frame using `fnCreateWidgetNode()`.
- Fallback attaches the same host listeners/menu/transform behavior required to move, resize, minimize, fullscreen, or delete the broken widget.
- Fallback mounts an error DOM body rather than returning `null`.
- Avoid duplicate listener attachment when both fallback and specific definitions match. The fallback may need only the base creation hook, with shared widget behavior extracted into a separate modifier definition, or an explicit ownership/priority design.

This is required because fixing only `txAttachDomPortal` is insufficient: without a registered definition, no node or DOM portal is created at all.

### Error state ownership in WidgetManagerService

Maintain runtime error state keyed at the correct scope:
- Global catalog error: definition service unavailable.
- Widget kind error: definition/source unavailable for all instances of one kind.
- Element error: one persisted canvas widget cannot initialize.
- Actor instance error: one runtime actor failed.

Suggested precedence when choosing what to render:
1. Element/instance-specific error.
2. Kind/definition error.
3. Global catalog error.
4. Generic `WIDGET_DEFINITION_UNAVAILABLE` fallback.

Expose service methods such as:

```ts
setDefinitionError(kind: string, error: TWidgetError): void
clearDefinitionError(kind: string): void
setElementError(elementId: string, error: TWidgetError): void
clearElementError(elementId: string): void
```

Each change should trigger re-render/rehydration only for the affected widget kind/element. Do not reload the entire canvas unnecessarily.

### Host-owned error DOM

Create a small local renderer in the widget service folder. It should produce an accessible, theme-aware message inside the existing widget body.

Minimum content:

```text
[Error loading Widget: <message>]
```

Recommended DOM behavior:
- `role="alert"` or `role="status"` depending on severity/update behavior.
- Wrap long messages.
- Preserve selection and pointer behavior.
- Use canvas theme variables/colors, not hardcoded white-only styling.
- Optionally show a short stable code.
- Do not expose raw stack traces.
- Optional retry button only when a real retry action exists.

### DOM portal boundary

Wrap separately so the phase remains accurate:
1. `renderDom()` call.
2. `mountArrowSandbox()` call.
3. Any sandbox-reported compile/runtime failure.
4. Cleanup callbacks, so a failing cleanup cannot prevent portal removal.

On failure:
- Dispose partial renderer/sandbox resources where possible.
- Clear partial content.
- Render host error state.
- Log via `LoggingService` with widget kind and element id.
- Keep the Konva frame alive and selectable.

### Sandbox bridge

Extend `mountArrowSandbox()` with host callbacks such as:

```ts
onError(error: TWidgetError): void
onRecovered?(): void
```

Report:
- Snapshot request failure.
- Missing actor instance after bounded wait.
- Actor `system.error` events.
- Actor status becoming `error`/unexpectedly stopped.
- Sandbox compiler/mount/runtime output that represents failure.
- Actor event subscription disconnect.

Do not remove the existing SDK error snapshot. Widget-authored error UI and host fallback can coexist; the host fallback is the guaranteed minimum.

Define recovery behavior explicitly. For example, a later healthy snapshot/status may clear actor infrastructure errors, while a sandbox compile error remains until new widget code is registered.

### Registration recovery

When a previously broken definition loads successfully:
1. Clear the kind error.
2. Register/replace the specific widget definition.
3. Fire the existing `widgetRegister` hook.
4. Scene hydrator destroys the fallback node/portal.
5. Recreate the real node/portal once.
6. Restore selection/focus and persisted position/order.

Existing scene-hydrator cleanup tests provide a base for verifying there is exactly one portal after reload.

## Server Isolation Plan

### Per-instance startup boundary

Refactor persisted instance loading around a per-instance result:

```ts
type TLoadActorInstanceResult =
  | { ok: true; actor: Actor }
  | { ok: false; error: TWidgetError };
```

For each instance:
- Resolve definition; missing definition is an explicit failure, not silent return.
- Construct actor.
- Attach listener.
- Start child process.
- Confirm the desired readiness semantics before declaring `running` if feasible.
- Persist healthy status/clear error.
- On catch, close partial actor, remove map entry, persist error, publish notification/event, continue loop.

Do not catch `unknown` and discard it. Normalize it once into the structured error shape.

### Actor child readiness

`Actor.start()` currently emits `running` immediately after spawning, before the child sends `ready`. Decide whether instance startup success should mean:
- Process spawn succeeded, or
- Child sent `ready` within a timeout.

For reliable widget loading status, prefer a readiness promise/timeout. A child that exits before ready should produce `ACTOR_INSTANCE_START_FAILED`, persist error, and become visible through snapshot.

### Runtime actor failures

Actor child exit already emits `state.changed`, `error`, and `status.changed`, but supervisor persistence currently focuses on `ack` snapshots. Persist status/error transitions too, so reconnecting clients see the failure.

Avoid treating every domain-level actor error identically to infrastructure failure without a decision. Distinguish:
- Widget/actor business state deliberately entering `error`.
- Actor child/process/runtime infrastructure failure.
- Invalid widget message/output validation error.

The host fallback should at least cover infrastructure/load failures. Product design may allow widget-authored UI to own expected domain errors.

### Service availability

The actor service should finish `start()` after collecting/reporting per-instance failures. It should reject only when the service itself is unusable globally, such as database connection/migration failure or inability to enumerate any required state.

This permits the server/API/frontend to remain available and show diagnostics.

## Canvas-Wide Boot Error

Handle `runtime.boot()` rejection in `Canvas.tsx` with Solid state:
- Log structured context.
- Stop/shutdown partially started runtime where safe.
- Show a canvas-level error shell.
- Do not confuse a canvas-wide failure with one widget's in-frame failure.

Suggested distinction:

```text
Canvas document failure -> canvas shell error
Canvas runtime composition failure -> canvas shell error
One widget definition/actor/sandbox failure -> widget frame error
```

## Acceptance Criteria

- Server remains available when one actor instance or widget definition fails recoverably.
- Later actor instances continue starting after one failure.
- No persisted widget silently disappears solely because its definition/runtime failed to load.
- Every failed widget displays a safe in-frame message containing a useful reason.
- Startup errors remain visible after frontend connection or page refresh.
- Global notifications identify failures, but widget frames remain the authoritative local UX.
- Healthy widgets are unaffected by unrelated failures.
- Recovery replaces the error view cleanly and leaves one DOM portal/subscription.
- Canvas-wide boot failures are caught separately.
- Tests cover server isolation, transport, fallback hydration, DOM/sandbox errors, reconnect, and the B41-sized-state scenario.

## Non-Goals / Guardrails

- Do not attempt to catch or recover from native segmentation faults inside JavaScript. Prevent the unsafe query/runtime path.
- Do not store infrastructure diagnostics inside actor `machine_context`.
- Do not require every widget author/generated widget to implement error rendering.
- Do not delete broken persisted widget elements during hydration.
- Do not use only transient events for startup error state.
- Do not display raw stack traces, secrets, or arbitrary HTML in the frame.
- Do not make one definition error unregister healthy unrelated widget kinds.
- Do not introduce automatic infinite retry loops without cancellation/backoff.

- [ ] Exact child readiness definition and timeout.
