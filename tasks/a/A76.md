# A76 - sidebar: replace Tool Groups with a version-aware Widgets catalog
[Overview](../BASED.md)

Replace the standalone `TOOL GROUPS` sidebar section with a `WIDGETS` section that presents published widgets, meaningful draft differences, and expandable tool-group folders. Selecting a widget opens a management page for inspecting its manifest and files and editing draft-owned presentation metadata such as its icon and group.

## Context

The requested navigation has one product concept—widgets—but the current implementation obtains its data from three disconnected sources:

- [`apps/frontend/src/feature/sidebar/components/Sidebar.tsx`](../../apps/frontend/src/feature/sidebar/components/Sidebar.tsx) renders `CANVASES`, `RESOURCES`, and `TOOL GROUPS`. It lists persisted tool groups directly, then performs `actors.definitions.list()` followed by one `actors.definitions.get()` call per definition only to discover `widget.tool.group`.
- [`packages/api-actors/src/contract.ts`](../../packages/api-actors/src/contract.ts) exposes installed published definitions. `definitions.list` does not include manifest tool metadata, while `definitions.get` returns one merged definition plus files only from `widget.relWidgetDir`.
- [`packages/api-agent/src/contract.ts`](../../packages/api-agent/src/contract.ts) exposes `widgetDraft.list/get`, Preview, and Publish. A draft summary says only `new` or `modified`; it cannot distinguish an unchanged post-publication draft from a genuinely divergent draft.
- [`packages/service-agent/src/workspace/fx.widget-catalog.ts`](../../packages/service-agent/src/workspace/fx.widget-catalog.ts) already discovers logical widget names and `hasDraft`/`hasPublished`, but it is shaped for the model tool and does not return manifests, icons, grouping, version equality, or detail/file data.
- [`packages/orpc-client/src/index.ts`](../../packages/orpc-client/src/index.ts) composes the API package contracts into one typed WebSocket client. It should not grow handwritten widget request wrappers. Extending an already-composed contract automatically exposes the new typed safe-client methods.
- [`apps/frontend/src/pages/resource.tsx`](../../apps/frontend/src/pages/resource.tsx), [`apps/frontend/src/feature/resource/GenericResourcePage.tsx`](../../apps/frontend/src/feature/resource/GenericResourcePage.tsx), and [`apps/frontend/src/feature/db-resource/DbResourcePage.tsx`](../../apps/frontend/src/feature/db-resource/DbResourcePage.tsx) establish the current route/detail-page pattern: persistent header, route-owned loading, compact tabs, flat panels, bounded inspection, and sidebar selection.
- [`apps/frontend/src/feature/sidebar/components/ToolGroupDialog.tsx`](../../apps/frontend/src/feature/sidebar/components/ToolGroupDialog.tsx) already edits tool-group name/icon and lists linked widgets, but opening a group row currently opens the dialog instead of expanding a hierarchy.
- [`packages/service-actor/src/core/vibecanvasjson.zod.ts`](../../packages/service-actor/src/core/vibecanvasjson.zod.ts) makes `widget.tool.icon` and `widget.tool.group` authoritative manifest fields. [`packages/api-tool/src/contract.ts`](../../packages/api-tool/src/contract.ts) stores group presentation independently in `tool_groups`.
- A66 deliberately treats a manifest group reference with no matching persisted tool group as an ungrouped standalone widget. A76 must preserve a safe, visible version of that behavior rather than hiding the widget.

The current APIs are insufficient for the requested screen:

1. Published and draft data cannot be loaded as one coherent catalog without frontend joins and N+1 calls.
2. `state: "modified"` currently means only that a published copy exists; it does not prove the draft content differs.
3. No management endpoint returns a safe complete file tree for either source variant.
4. The chat-scoped manifest patch API requires a connected AI widget/session and is not an appropriate general widget-management API.
5. Tool-group rename/delete currently changes only the group registry row. Because membership lives in manifests by group name, silently treating that as a folder rename would orphan references.

## Product contract

### Logical widgets and visible variants

- The logical widget identity remains its validated manifest/directory `name`. Do not introduce a second public widget ID in this task.
- A widget can have two source variants: `published` and `draft`.
- Always render the published row when a published variant exists.
- Render a separate draft row only when:
  - no published variant exists; or
  - the managed draft source tree differs from the canonical published source tree; or
  - either variant is invalid/ambiguous and equality cannot be proven safely.
- If draft and published are content-identical, render only the published row. The detail response may still report that an identical draft exists so editing can reuse it.
- A draft-only widget is rendered once and clearly marked `DRAFT`.
- When both rows are visible, the draft row must include both an icon badge and accessible text indicating `Draft`; color alone is insufficient.
- Invalid manifests and catalog problems remain visible with a fallback widget icon and an actionable problem marker. Never drop a widget because its icon or manifest cannot be parsed.

### Equality contract

“Draft equals published” means deterministic managed-source equality, not matching timestamps and not merely matching `name`, `slug`, or manifest JSON.

- Compare the shared draft folder with the canonical published folder, never with the installed runtime copy.
- Compare normalized relative paths and file bytes.
- Exclude backend/transient content consistently: `node_modules`, `.git`, `.vibecanvas-wizard`, validation temp files, Preview snapshots, and publish/reconcile staging directories.
- Symlinks, unreadable entries, limit overruns, or ambiguous directories fail closed to `different/unknown`; they must never collapse a draft row.
- Return a stable content fingerprint/relation from the backend so the browser does not read files or invent equality.
- Keep the existing draft revision for optimistic edits. A content fingerprint answers equality; the draft revision answers “did this mutable draft change since I loaded it?” They are separate contracts.
- Bound file count and total bytes during fingerprinting and return a typed catalog problem if a widget exceeds those limits.

### Hierarchy and sorting

The expanded section is projected as:

```text
WIDGETS                                      …
  ▸ Productivity                            …
  ▾ Media                                   …
      Camera
      Camera                                DRAFT  ✎
  Standalone widget
  New widget                                DRAFT  ✎
```

- Render every persisted tool group, including empty groups, so it can still be edited or deleted.
- A group row has a dedicated expand/collapse control and a separate three-dot action button. Do not nest interactive buttons.
- Group rows render the persisted group icon with a safe fallback.
- Widget rows render the selected source variant’s `widget.tool.icon`, sanitized through a shared icon renderer; do not duplicate raw `innerHTML` logic in `Sidebar.tsx`.
- A variant belongs to the group named by that variant’s manifest. A divergent published/draft pair may therefore appear in different groups.
- A missing group reference renders the widget at top level with a warning indicator; the widget remains navigable.
- Sort groups by display name, group members by widget name with `published` before `draft`, and ungrouped rows by widget name with the same source ordering. Do not reuse toolbar priority as sidebar ordering.
- Keep section and group expansion local UI state for the first version. Persisting expansion is optional and must not block the feature.

### Navigation and detail page

Use source-explicit routes because published and draft rows for the same widget can coexist:

```text
/widgets/published/:encodedName?tab=overview
/widgets/published/:encodedName?tab=config
/widgets/published/:encodedName?tab=files&path=widget/main.ts
/widgets/draft/:encodedName?tab=overview
/widgets/draft/:encodedName?tab=config
/widgets/draft/:encodedName?tab=files&path=actor/functions.ts
```

- Encode and decode the widget name as one route segment; reject malformed or unsafe names at the API boundary.
- Sidebar selection includes both name and source, so selecting a draft does not also select the published row.
- The page header shows source (`PUBLISHED WIDGET` or `WIDGET DRAFT`), icon, name, kind, slug, revision/fingerprint, health/problem state, and sidebar toggle.
- `OVERVIEW` shows description, tool label/behavior/group, published/draft relationship, validation status for drafts, and timestamps where available.
- `CONFIG` renders the full validated `vibecanvas.json` in a structured read-only inspector and provides a focused editor for tool icon and group. Do not build a general arbitrary-manifest form in A76.
- `FILES` renders a lazy file tree and a bounded text preview. Binary files show metadata only. Do not download an entire widget source tree in the list response.
- Keep the active tab and selected file in the URL, following the Resource workbench pattern.
- A missing/deleted variant shows a route-level not-found state and refreshes the sidebar catalog instead of redirecting to an unrelated canvas.

### Editing ownership

- Published canonical/installed files remain immutable from the detail page.
- Editing icon/group always targets a shared draft and uses optimistic `expectedRevision`.
- If the user starts from a published-only widget, `Edit as draft` copies/synchronizes the canonical publication into the shared draft through `WidgetWorkspace`; it must not require an AI chat mount.
- If an identical hidden draft already exists, reuse it rather than creating another copy.
- Saving icon/group returns the new draft revision and immediately makes the draft row visible when it diverges.
- Publishing remains explicit through the existing `widgetPublish.publish` lifecycle. Icon edits do not silently mutate the running published toolbar.
- If a draft edit conflicts, preserve the user’s selection, reload the current revision, and offer retry; never overwrite a concurrent AI/Bash edit silently.
- Name/slug editing, arbitrary file editing, widget creation/deletion, and general manifest editing are out of scope.

### Tool-group mutation semantics

Tool-group membership is stored in each source variant’s manifest by group name. A group row therefore cannot truthfully rename/delete a folder by changing only `tool_groups`.

- Keep group creation in the `WIDGETS` section-header three-dot menu. Remove the old section-level plus button.
- Keep group icon edits as direct group-registry metadata updates.
- A group rename must either update every linked draft/published manifest through a coordinated backend operation with rollback, or fail before mutation. The implementation must not silently orphan members.
- A group delete moves members to the ungrouped level by clearing their group references through the same coordinated operation. It never deletes widgets.
- For published variants, coordinated group mutation must update canonical and installed copies together, reload definitions/toolbars, and restore files plus the group registry if any step fails. Reuse the B48 publication-compensation model rather than open-coding best-effort loops.
- The confirmation dialog lists affected published and draft variants. If safe compensation cannot be implemented in the first delivery, rename/delete of non-empty groups must be blocked with a typed `GROUP_IN_USE` error; do not fall back to partial behavior.
- Group creation and successful mutations dispatch one catalog-change signal and the existing toolbar group-change signal.

## ORPC/API plan

### Placement

Add a management-oriented router to the existing agent contract, for example:

```text
api.agent.widgets.catalog
api.agent.widgets.detail
api.agent.widgets.files
api.agent.widgets.file
api.agent.widgets.ensureDraft
api.agent.widgets.patchDraftTool
api.agent.widgets.groups.create
api.agent.widgets.groups.update
api.agent.widgets.groups.remove
```

The exact leaf names may be adjusted to repository conventions, but keep one cohesive widget-management namespace. Do not make the frontend join `api.actors.definitions`, `api.agent.widgetDraft`, and `api.tool.groups` itself.

`api-agent` is the appropriate coordination boundary because its request context already has the database, event publisher, and `AgentService`/`WidgetWorkspace`. Published runtime reads may delegate to `ActorService`; tool-group persistence may delegate to the existing database service. Keep low-level `api.tool.groups.list` for the runtime toolbar until consumers migrate.

No handwritten change is expected in [`packages/orpc-client/src/index.ts`](../../packages/orpc-client/src/index.ts) beyond normal contract composition tests because `agentContract` is already included. The new router should appear automatically in `TOrpcClient` and `TOrpcSafeClient`.

### Catalog DTO

Return one request with tool groups and logical widget entries, not one request per widget:

```ts
type TWidgetCatalog = {
  generation: string;
  groups: Array<{
    name: string;
    icon: TVibecanvasToolIcon | null;
  }>;
  widgets: Array<{
    name: string;
    relation: "published-only" | "draft-only" | "same" | "different" | "unknown";
    published: TWidgetVariantSummary | null;
    draft: TWidgetVariantSummary | null;
    problem: { code: string; message: string } | null;
  }>;
};

type TWidgetVariantSummary = {
  source: "published" | "draft";
  displayName: string;
  kind: "widget" | "actor-widget" | null;
  slug: string | null;
  description: string | null;
  revision: string;
  contentFingerprint: string | null;
  updatedAt: string | null;
  tool: {
    label: string | null;
    icon: TVibecanvasToolIcon | null;
    group: string | null;
    priority: number | null;
    behaviorType: "mode" | "action" | "modal" | null;
  };
  validation: TWidgetDraftValidation | null;
};
```

- `generation` fingerprints the catalog projection and supports stale-response/event coalescing; it is not a filesystem path or secret.
- Do not return absolute draft, canonical, installed, or snapshot paths.
- Return bounded safe problem messages; do not expose native filesystem diagnostics.
- The backend returns both variants even when relation is `same`; the frontend projection decides to hide the redundant draft row while detail/edit flows can still reuse it.

### Detail and files

```text
detail({ name, source })
files({ name, source })
file({ name, source, path })
```

- `detail` returns the selected variant summary, full validated manifest when valid, sibling-variant summary, and equality relation.
- `files` returns a flat sorted safe tree model such as `{ path, kind, size, children? }` or a flat parent-derived list. Paths are widget-relative POSIX display paths only.
- `file` accepts one validated relative path and returns bounded UTF-8 text plus truncation/size metadata. Reject traversal, absolute paths, symlinks, directories, and files beyond the read limit.
- Exclude backend-private/transient folders from both fingerprinting and file inspection.
- Published inspection reads canonical published source so it matches the version model; runtime installed files are implementation output, not the management source of truth.

### Mutations

```text
ensureDraft({ name, expectedPublishedFingerprint? })
patchDraftTool({
  name,
  expectedRevision,
  patch: {
    icon?: TVibecanvasToolIcon | null;
    group?: string | null;
  }
})
```

- `ensureDraft` is idempotent and returns the existing/synchronized draft summary.
- `patchDraftTool` reuses the manifest validation logic currently embedded in the chat-scoped patch flow; extract shared pure validation instead of duplicating it.
- Validate a non-null group against the persisted group registry. Return a typed not-found error rather than persisting a new dangling reference from the management UI.
- Mutations use the per-widget workspace write lane, recheck `expectedRevision` inside it, write atomically, invalidate validation/Preview state as required, and emit `widget-draft: changed`.
- Define typed errors for not found, stale revision, invalid manifest/icon/group, unsafe path, payload limit, group in use, and compensated group-mutation failure.

## Frontend architecture

Do not continue growing [`Sidebar.tsx`](../../apps/frontend/src/feature/sidebar/components/Sidebar.tsx) into a catalog controller. Introduce a feature-local widgets module, for example:

```text
apps/frontend/src/feature/widgets/
  WidgetCatalogProvider.tsx
  WidgetDetailPage.tsx
  WidgetDetailPage.module.css
  components/
    WidgetsSidebarSection.tsx
    WidgetSidebarRow.tsx
    WidgetGroupRow.tsx
    WidgetIcon.tsx
    WidgetConfigPanel.tsx
    WidgetFileTree.tsx
    WidgetFilePreview.tsx
    ToolGroupDialog.tsx
  fn.widget-catalog.ts
  fn.widget-route.ts
  fx.widget-catalog.ts
  fx.widget-detail.ts
  tx.widget-draft.ts
  types.ts
```

- `Sidebar.tsx` keeps top-level composition and supplies the new section.
- Move/generalize the current Tool Group dialog rather than maintaining two versions.
- Pure functions project API catalog entries into group/row view models, decide whether the draft row is visible, sort rows, and resolve route selection.
- `fx.*` functions perform typed catalog/detail/file reads with exactly the repository-required portal/args shape.
- `tx.*` functions perform ensure-draft, icon/group patch, and group mutations.
- Solid components own loading, expansion, menus, dialogs, and orchestration.
- Use Kobalte `DropdownMenu` for section/group three-dot actions, `Collapsible` or explicit accessible disclosure buttons for group expansion, `Tabs` for detail navigation, and existing icon-picker composition for icon edits.
- Avoid nested buttons: group disclosure, group name/select target, and ellipsis menu trigger must be sibling controls.

### Refresh model

- Load the catalog once when the application shell mounts.
- Subscribe to `api.agent.events` at the catalog-provider level and refetch on `widget-draft`, `widget-published`, and `widgetupdate` events.
- Refetch after local group CRUD and draft-tool mutations.
- Coalesce bursts and guard responses with request IDs/generation so a slow old request cannot replace a newer catalog.
- Keep the existing `TOOL_GROUPS_CHANGED_EVENT` only for runtime-toolbar compatibility during migration; the Widgets UI should use its provider state rather than window events as its source of truth.
- Closing or reconnecting the WebSocket must not leave an unhandled async iterator. Clean up subscriptions with the application shell lifecycle.

## Implementation plan

### 1. Build the backend catalog model

- Extract shared widget-name/source discovery from `fx.widget-catalog.ts` without changing the model-facing `vc_widget_list` response.
- Add deterministic managed-tree comparison and bounded fingerprints.
- Parse each source manifest independently and preserve per-variant problems.
- Join tool-group definitions in one backend operation.
- Add catalog unit tests for published-only, draft-only, identical, divergent, invalid, ambiguous, missing-group, and limit cases.

### 2. Add typed management ORPC endpoints

- Add catalog/detail/files/file schemas and handlers under the existing agent API.
- Add ensure-draft and optimistic tool-patch handlers.
- Return source-relative data only.
- Verify the composed `@vibecanvas/orpc-client` safe-client type exposes the new router without a custom wrapper.
- Remove the sidebar’s definitions list/get N+1 path only after the new catalog is available.

### 3. Make group management hierarchy-safe

- Move group create to the Widgets header overflow menu.
- Make group rows independently expandable and actionable.
- Implement coordinated rename/delete with affected-variant discovery and rollback, or block non-empty mutations with `GROUP_IN_USE` until that compensation is complete.
- Preserve icon-only updates and existing toolbar refresh behavior.
- Test empty groups, missing group references, rename, delete-to-ungroup, rollback, and concurrent publish/draft edits.

### 4. Replace the sidebar section

- Remove the standalone Tool Groups section and its `loadWidgetGroups()` N+1 fetch.
- Add the catalog provider and `WidgetsSidebarSection`.
- Render source-specific icons, draft markers, selected states, empty/loading/error states, and expandable groups.
- Ensure all widgets remain reachable when a group is collapsed, missing, invalid, or empty through predictable disclosure and top-level fallback behavior.

### 5. Add widget detail routing

- Register `/widgets/:source/:name` beneath the existing app shell.
- Add stale-request-safe route loading similar to `fn.resource-route.ts`.
- Implement Overview, Config, and Files tabs with URL state.
- Lazy-load file metadata/content and enforce text/binary/truncation states.
- Add route, tab, file selection, and deleted-variant tests.

### 6. Implement icon/group editing through drafts

- Reuse the existing `ToolIconPicker` and central safe icon renderer.
- For published-only selection, require/perform `Edit as draft` before mutation.
- Patch only icon/group against `expectedRevision` and return the new catalog state.
- Show that published behavior is unchanged until Publish succeeds.
- Test identical hidden draft reuse, draft appearance after edit, optimistic conflict, invalid group, clear icon/group, and Publish refresh.

### 7. Verify accessibility and integration

- Keyboard-test section disclosure, group disclosure, ellipsis menus, widget links, tabs, file tree, icon picker, dialogs, and focus return.
- Verify draft state has textual/ARIA meaning in addition to its icon.
- Verify custom SVG is sanitized and invalid icons fall back safely.
- Verify the sidebar stays dense and scrollable with many groups/widgets at narrow viewport heights.
- Verify toolbar grouping refreshes after group/icon changes and published widget refreshes.

## Acceptance criteria

- `TOOL GROUPS` no longer appears as a standalone sidebar section; `WIDGETS` replaces it.
- Every discoverable published or draft widget remains reachable.
- An identical draft/published pair renders one published row.
- A divergent pair renders published and explicitly marked draft rows.
- Widget and group rows render safe configured icons with fallbacks.
- Group rows expand/collapse independently and expose a separate three-dot edit/delete menu.
- Group creation lives in the Widgets section overflow menu.
- Clicking a widget opens the correct source-specific detail route.
- Detail config and files originate from the selected source variant and expose no host paths.
- Icon/group edits are optimistic draft mutations and never silently change published runtime files.
- The file tree is lazy, bounded, traversal-safe, and read-only.
- Sidebar data loads without one API request per widget.
- Widget/group events refresh the catalog without a page reload or stale-response regression.
- Group rename/delete cannot silently strand or partially rewrite member variants.
- Runtime toolbar grouping/icons remain consistent after successful management changes.
- Config exposes supported manifest metadata without duplicating the raw file view.
- Messages explains the widget/actor boundary and lists accepted inputs, emitted outputs, schemas, and accepted states.
- States renders the actor state-machine definition.
- Draft deletion removes only the draft; published deletion also removes its draft, definition, and every canvas actor instance after explicit confirmation.
- A missing or failing runtime definition does not prevent removable published or draft source from being cleaned up, and partial cleanup is reported accurately.
- The tab strip remains a fixed-height navigation row while the selected tab owns content scrolling.
- Overview shows slug and health; the redundant Kind/fingerprint/revision metadata strip is absent.

## Non-goals

- General widget source editing in the management page.
- Editing widget slug.
- Creating widgets from the sidebar.
- Replacing the AI widget creation/editing flow.
- Showing Preview actor runtime state in this detail page.
- Version history, source control, arbitrary diffs, or rollback UI.
- Changing the manifest ownership of `widget.tool.group`.
- Exposing installed/canonical/draft filesystem paths.

## NOTES

- Keep the sidebar projection separate from `vc_widget_list`; a model-facing paginated tool result and a local management catalog have different density/security needs.
- Published definitions are runtime records, while canonical published source and shared drafts are management records. The detail page must not confuse installed runtime files with the canonical source variant.
- The existing Tool Group dialog’s linked-widget list is useful, but it must become variant-aware: `Camera (published)` and `Camera (draft)` can have different memberships.
- If equality cannot be proven, rendering an extra draft row is safer than hiding user work.
- The new endpoint should live in an API contract already composed by `@vibecanvas/orpc-client`; creating a second WebSocket service or frontend-only client abstraction is unnecessary.
- The first delivery uses the explicitly permitted safe fallback for group membership mutations: rename/delete succeeds for empty groups, icon-only updates remain available, and non-empty rename/delete fails before database mutation with `GROUP_IN_USE`.
