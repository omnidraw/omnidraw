# A71 - actor resources: implement SecretStoreResource
[Overview](../BASED.md)

Implement neutral shared `SecretStoreResource` instances with host runtime lifecycle managed by `ActorService`. Build persistence on A70's resource-scoped key-value foundation, keep a distinct actor-facing interface and resource kind, enforce A69 definition/binding permission scope, and share one bound store across every actor instance of a definition.

## Dependencies

Blocked by:

- [A69](A69.md) — resource catalog, bindings, ActorService ownership, IPC gateway, and manifest slots.
- [A70](A70.md) — resource-scoped key-value persistence primitives.

Do not create a second secrets table merely to bypass A70 unless implementation discovers a concrete storage requirement that the shared key-value table cannot satisfy.

## Context

### Required use case

```text
Widget definition declares slot "credentials": secretStore
User binds SecretStoreResource "GitHub Account"

Any actor instance:
  has("accessToken")
    false -> actor tells widget to prompt user
    true  -> actor gets token, makes request, displays user data

User provides token through the current trusted actor/widget flow
Actor tx stores token in the bound SecretStoreResource
All new and existing actor instances resolve the same stored token
```

The current actor process security limitations are accepted. Actor code may retrieve the plaintext token and use direct `fetch`. A future sandbox/network capability can harden this without changing the resource binding model.

### Naming and separation

Use `SecretStoreResource` consistently.

Although it is built on the A70 key-value persistence layer, it is not a `KvResource` in the public SDK:

- Catalog kind is `secretStore`.
- Binding requires a `secretStore` manifest slot.
- Values are strings in the first version.
- Read/write methods have secret-oriented names and return shapes.
- Listing returns names/metadata, not values.
- `KvResource` bindings cannot access `SecretStoreResource` rows and vice versa.

`DbServiceTurso` remains the Vibecanvas database service. `ActorService` owns `SecretStoreResource` behavior.

### Explicit accepted limitations and non-goals

- No encryption at rest.
- No envelope encryption.
- No OS keychain integration.
- No secret-use-only HTTP capability.
- No actor IPC sandboxing.
- No prevention of plaintext secret access by trusted guest actor code.
- No secret rotation scheduler or automatic expiry.
- No cloud secret manager provider.
- No durable inbox/outbox.
- No dedicated trusted host secret-entry modal unless separately requested.
- No attempt to infer which strings are secrets in ordinary actor messages/context.

Even without encryption, avoid accidental disclosure through API DTOs, logs, events, error details, and list operations.

## Persistence model

Use `actor_resource_key_values` from A70:

```text
resource_id = SecretStoreResource catalog ID
key         = secret name
value       = JSON string containing plaintext secret
revision    = write revision
```

Required storage behavior:

- ActorService verifies the catalog row kind is `secretStore` before every operation.
- A `KvResource` provider verifies kind `kv` and therefore cannot access the same row through a differently typed binding.
- Secret value must be a non-empty or empty string according to one explicit rule. Prefer allowing empty strings only if they have a meaningful use; otherwise reject and document.
- Secret names use the same safe key storage mechanics as KV keys but can have separate length/character validation.
- Revisions come from the shared KV persistence and support replacement awareness.
- Deleting the `SecretStoreResource` after it is unbound cascades its entries.

No encryption columns or key metadata are added in this task. Document plainly that values are stored as plaintext JSON strings in the Vibecanvas database.

## Actor-facing interface

### Read interface available to `fx` and `tx` when effective scope includes read

```text
has(slot, name) -> boolean
get(slot, name) -> { value: string, revision: number } | null
list(slot, { prefix?, cursor?, limit? })
  -> page of { name, revision, createdAt?, updatedAt? }
```

`list` must never return values.

### Write interface available only to `tx` when effective scope includes write

```text
set(slot, { name, value }) -> { name, revision }
delete(slot, { name }) -> { deleted: boolean }
compareAndSet(slot, { name, expectedRevision, value }) -> result/conflict
```

CAS is useful for replacement/rotation races and should reuse A70 semantics. If A70 omits a public batch, do not introduce a secret-only transaction API.

### Return-shape rules

- `set` should not echo the plaintext value back. The caller already has it; returning it increases accidental propagation.
- `delete` should not return the removed value.
- Error details should contain slot/name/revision where useful, never the plaintext value.
- Management APIs list resource metadata and binding state, not secret names or values unless a future explicit secrets-management endpoint is designed.

## Plan

### 1. Add SecretStoreResource service types

Define actor-service types for:

- Secret name.
- Secret metadata entry.
- Secret read result.
- Secret write/delete/CAS arguments/results.
- Stable operation errors.

Use `string` for values. Do not generalize to JSON objects in the first version; callers can serialize structured credentials themselves only if product intentionally permits that later.

Keep local `TPortal*`/`TArgs*` types with function helpers according to repository rules during implementation.

### 2. Implement SecretStoreResource over A70 persistence

Add `SecretStoreResource` under `packages/service-actor`.

Responsibilities:

- Verify resource kind `secretStore`.
- Resolve definition binding through A69.
- Validate secret name and string value.
- Delegate exact storage/CAS/list mechanics to A70's low-level key-value persistence.
- Strip values from list/write/delete results.
- Map lower-level KV conflict/storage errors to secret-specific public errors.
- Avoid caching plaintext values in the resource object.
- Avoid publishing values in notifications or resource metadata.

Composition rule:

- Reuse persistence functions or an injected storage port.
- Do not instantiate a public `KvResource` and bypass its kind check.
- Do not duplicate SQL.

### 3. Register secretStore provider lifecycle

Register catalog kind `secretStore` in the A69 ActorService resource manager.

Creation:

- Creates catalog metadata only.
- Requires a name and kind.
- Starts ready when application DB persistence is available.
- Does not create encryption keys or files.

Deletion:

- Reject while any definition binding references it.
- Once unbound, delete catalog row and cascade stored entries.
- Do not delete an actor definition or actor instances.

Binding:

- Slot must declare `kind: secretStore`.
- Resource row must have kind `secretStore`.
- Effective permission scope is enforced as definition scope ∩ binding restriction ∩ function-class ceiling.

### 4. Add IPC dispatch and class-specific portals

Add resource operations to the generic protocol from A69.

Host dispatch matrix:

| Function | Allowed SecretStoreResource operations |
|---|---|
| `fn.*` | none |
| `fx.*` | `has`, `get`, `list` when effective scope includes read |
| `tx.*` | reads when effective scope includes read; `set`, `delete`, `compareAndSet` when it includes write |

The current trusted child could theoretically retain a broader portal; this is accepted and should be documented, not solved in this task.

IPC tests must assert that request/result/error logging fixtures do not snapshot plaintext values unnecessarily. If debug logging exists, log operation, slot, name and call ID but not `value`.

### 5. Extend @vibecanvas/sdk/actor

Expose `SecretStoreResource` read/write interfaces from `@vibecanvas/sdk/actor`.

Requirements:

- Named slot access.
- Promise-based methods.
- `get` returns plaintext only for explicitly called secret read.
- `list` has metadata-only typing.
- `set` result omits plaintext value.
- No encryption claims in docs/types.
- No browser/widget SDK exposure; actor side only.
- Existing actors remain compatible.

Use resource-specific type names rather than aliasing all public secret types to KV types. Internal implementation can share mechanics.

### 6. Update manifest/wizard guidance

Update actor implementation prompt and any generated comments to teach the intended flow:

1. Declare a `secretStore` slot.
2. Use `fx` `has/get` for read/check operations.
3. Use `tx` `set/delete` for mutation.
4. Keep token out of actor context and output messages where possible.
5. Retrieve only when making the external request.
6. Never log or emit the token.

Do not claim the token is encrypted. Add a clear current limitation note in internal documentation, not necessarily generated UI copy.

### 7. Build an end-to-end fixture

Add a deterministic service-actor fixture representing an access-token widget.

Suggested transitions:

```text
in.checkToken -> fx.checkToken
in.saveToken  -> tx.saveToken
in.loadProfile -> fx/tx function that gets token and uses a mocked injected request in tests
```

Test flow:

1. Create SecretStoreResource A and B.
2. Bind widget definition slot to A.
3. Start actor instances A1 and A2.
4. A1 checks and gets missing.
5. A1 stores token through tx.
6. A2 checks and gets present/same value.
7. Rebind definition to B.
8. Subsequent operation sees missing in B.
9. Rebind to A and value is still present.
10. Delete token and both instances observe missing on their next read.

Do not call a real external API in automated tests. Mock/fake the request layer or limit the integration test to secret retrieval.

### 8. Stable errors and redaction

Recommended codes:

- `SECRET_STORE_NOT_BOUND`
- `SECRET_STORE_UNAVAILABLE`
- `SECRET_NAME_INVALID`
- `SECRET_VALUE_INVALID`
- `SECRET_NOT_FOUND` only where an operation requires existence; ordinary `get` returns null.
- `SECRET_CONFLICT`
- `SECRET_WRITE_NOT_ALLOWED`
- `SECRET_OPERATION_FAILED`

Redaction requirements despite accepted plaintext storage:

- Never include secret `value` in error messages/details.
- Never include all IPC arguments in actor system errors for a failed secret operation.
- Never include values in event publisher notifications.
- Never include values in control-plane resource DTOs.
- Never include values in `toString`/inspection output of `SecretStoreResource`.
- Tests should use a recognizable sentinel token and assert it is absent from serialized errors/events/list results.

This is accidental-disclosure hygiene, not a hard security boundary.

### 9. Concurrency behavior

- Plain `set` replaces the current value and increments revision.
- Concurrent `set` is last-write-wins.
- CAS supports expected revision replacement.
- A stale CAS does not overwrite a newer secret.
- No plaintext value is returned in a conflict response.
- Per-actor queues do not serialize separate actor instances.

### 10. Tests

Persistence reuse tests:

- String secret round-trip through resource-key-value persistence.
- Same secret name in two stores remains isolated.
- Revisions increment.
- CAS conflict preserves newer value.
- Cascade deletion after unbind.

Actor service tests:

- Catalog kind mismatch rejects binding/access.
- `SecretStoreResource` cannot be accessed through a `kv` slot.
- `KvResource` cannot be accessed through a `secretStore` slot.
- Two instances of one definition share one store.
- Two definitions bound to the same store intentionally share it.
- Rebinding switches stores on subsequent calls.
- A binding with `allow_write = false` rejects `set/delete/CAS` even when the definition declares write scope.
- A binding cannot broaden the definition's read/write scope.

IPC/SDK tests:

- `fx` exposes only reads.
- `tx` exposes reads/writes.
- `fn` exposes nothing.
- `get` value survives normal IPC.
- `list/set/delete/error` payloads omit value.
- Pending call rejects on child exit.
- Type fixtures compile with named secret slot calls.

Redaction tests:

- Sentinel absent from actor error event serialization.
- Sentinel absent from management resource response.
- Sentinel absent from list metadata.
- Sentinel absent from write result.
- Sentinel absent from expected conflict details.

API tests:

- Create/list/rename/delete secret store metadata through generic resource routes.
- Bind/unbind secretStore slot.
- Delete blocked while bound.
- No data-plane secret get/set route is accidentally added to general frontend API.

## Acceptance criteria

- Multiple plaintext `SecretStoreResource` instances can be created and bound independently.
- A definition binding is shared by every actor instance of that definition.
- `fx` functions can check/get/list; `tx` can also set/delete/CAS.
- Secret storage reuses A70 resource-key-value persistence rather than duplicating SQL.
- Public/list/write/delete/error surfaces avoid echoing secret values.
- Actor code can retrieve a token and use current direct network access under the accepted trust model.
- No encryption, cloud provider, sandbox, durable inbox/outbox, or use-only HTTP capability is added.

## NOTES

No encryption is intentional for this iteration. Keep persistence and APIs structured so encrypted storage can later replace the storage adapter without changing manifest slots or actor-facing methods.

The widget can currently prompt for a token and send it through its actor message flow. A trusted host secret-entry UI is not part of this task.

Shared storage does not automatically rerun every actor. Other instances observe the new token on their next secret read unless a generic resource invalidation mechanism exists from A69.
