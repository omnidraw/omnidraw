# A60 - actor IPC: spawn same compiled binary
[Overview](../../BASED.md)

Make actor subprocess IPC work in both source/dev/test mode and compiled-binary mode by spawning the correct Vibecanvas runtime entrypoint instead of `bun run icp-client.ts`.

## Context

Actor runtime currently isolates guest actor functions in a Bun child process:

- Host actor process: [`packages/service-actor/src/Actor.ts`](../../packages/service-actor/src/Actor.ts)
- Child IPC bootstrap: [`packages/service-actor/src/icp-client.ts`](../../packages/service-actor/src/icp-client.ts)
- Compiled CLI entrypoint: [`apps/cli/src/main.ts`](../../apps/cli/src/main.ts)
- Build target: [`scripts/build.ts`](../../scripts/build.ts)
- Binary smoke test: [`scripts/test-binary.ts`](../../scripts/test-binary.ts)

The current implementation in `Actor.ts` starts the child with:

```ts
const icpClientPath = new URL('icp-client.ts', import.meta.url).pathname
Bun.spawn(["bun", "run", icpClientPath, "--functionPath", this.#functionPath], { ipc })
```

This is acceptable only when the host machine has Bun installed and the source file exists on the normal filesystem. It is not acceptable for compiled production binaries.

Compiled mode problem:

- `bun build --compile` embeds source files into Bun's virtual filesystem.
- `new URL('icp-client.ts', import.meta.url).pathname` can become a virtual path like `/$bunfs/root/icp-client.ts`.
- A separately spawned `bun run /$bunfs/root/icp-client.ts` cannot access that virtual module path.
- Published/compiled Vibecanvas packages should not require the host to have Bun installed.

Observed current compiled failure in a minimal actor runner:

```txt
error: Module not found "/$bunfs/root/icp-client.ts"
idle false data {"balance":0}
```

There is also a lifecycle bug exposed by this failure: when the child process dies before completing a pending run, `Actor.isIdle()` can stay false because pending runs are not rejected on child exit.

## Investigation findings

### Source/dev/test mode process shape

When running source files under Bun:

```txt
process.execPath = /Users/.../.bun/bin/bun
Bun.argv = [bun, /path/to/script.ts, ...]
Bun.main = /path/to/script.ts
```

Important consequence:

```ts
Bun.spawn([process.execPath, "--icp-client"])
```

is wrong in source mode because `process.execPath` is only the Bun executable. It will print Bun CLI help instead of running Vibecanvas code.

Source mode must pass a script path after `process.execPath`, for example:

```ts
[process.execPath, icpClientPath, "--icp-client", "--functionPath", functionPath]
```

or, if the CLI entrypoint is intentionally used:

```ts
[process.execPath, cliMainPath, "--icp-client", "--functionPath", functionPath]
```

Do not rely exclusively on `Bun.main` inside `service-actor`: under `bun test`, `Bun.main` is the test file, not the CLI app entrypoint.

### Compiled mode process shape

When running a compiled Bun executable:

```txt
process.execPath = /real/path/to/vibecanvas
Bun.argv = ["bun", "/$bunfs/root/vibecanvas", ...]
Bun.main = "/$bunfs/root/vibecanvas"
```

Important consequences:

- `process.execPath` is the real executable to spawn.
- `Bun.argv[0]` is not useful; it can be the string `bun`.
- The child command should be:

```ts
[process.execPath, "--icp-client", "--functionPath", functionPath]
```

### Bun IPC behavior

Validated with a compiled proof:

- A compiled Bun binary can spawn itself using `Bun.spawn(..., { ipc })`.
- The child receives `process.send` when the parent supplies an `ipc` handler.
- The child can receive parent messages through `process.on("message")`.
- The parent can receive child messages through the `ipc(message)` callback.

### External actor function files in compiled mode

Validated with a compiled proof:

- A compiled Bun binary can `require("/path/to/widget/actor/functions.ts")` at runtime.
- Relative TypeScript imports from that external file can work, for example:

```ts
import { txAddFunds } from "./tx_add-funds"
```

Production constraints still apply:

- Actor files must exist on disk.
- Runtime imports from npm packages must be available to the child process, usually through the widget folder's `node_modules` or by using self-contained/bundled actor code.
- Type-only imports erase and are safe.
- For long-term reliability, consider a production authoring rule that actor registries are either self-contained TS/JS files or pre-bundled JS modules.

## Plan

### 1. Refactor the child IPC module into an importable runner

Update [`packages/service-actor/src/icp-client.ts`](../../packages/service-actor/src/icp-client.ts) so it no longer relies entirely on top-level execution.

Recommended shape:

```ts
export async function runActorIpcClient(rawArgs = Bun.argv.slice(2)) {
  // parse args
  // validate IPC availability
  // validate functionPath
  // load registry
  // send ready/error
  // attach process.on("message")
  // process.stdin.resume()
}

if (import.meta.main) {
  await runActorIpcClient()
}
```

The exported runner lets the compiled CLI entrypoint dispatch into child mode without starting the normal app/server/runtime.

Parsing should use `Bun.argv.slice(2)` semantics for normal calls. Current code parses all of `Bun.argv`, which includes executable/script positionals and makes future entrypoint switching more fragile.

Suggested options:

```ts
parseArgs({
  args: rawArgs,
  strict: true,
  allowPositionals: true,
  options: {
    "icp-client": { type: "boolean", default: false },
    debug: { type: "boolean", short: "d", default: false },
    functionPath: { type: "string" },
  },
})
```

Startup contract:

- If `process.send` is missing:
  - print a clear stderr message
  - exit non-zero
- If `--functionPath` is missing:
  - send an IPC error if possible
  - exit non-zero
- If registry loading fails:
  - send an IPC error with useful details
  - exit non-zero
- After registry loads successfully:
  - send `{ type: "ready" }`

Registry loading should tolerate either default exports or direct module exports:

```ts
const mod = require(values.functionPath)
const funcMap = mod.default ?? mod
```

Also consider validating the registry shape before accepting it:

- `funcMap` is an object
- `funcMap.fn`, `funcMap.fx`, `funcMap.tx` are objects or default to `{}`

### 2. Add an early CLI mode switch for compiled binary child mode

The compiled binary currently starts at [`apps/cli/src/main.ts`](../../apps/cli/src/main.ts), configured in [`scripts/build.ts`](../../scripts/build.ts).

The CLI entrypoint should check for `--icp-client` before importing or booting normal CLI/server services.

Recommended implementation:

1. Move the current `apps/cli/src/main.ts` body into a new file, for example:
   - `apps/cli/src/main-app.ts`
   - export `runCliMain()`
2. Replace `main.ts` with a tiny bootstrap:

```ts
#!/usr/bin/env bun

const args = Bun.argv.slice(2)

if (args.includes("--icp-client")) {
  const { runActorIpcClient } = await import("@vibecanvas/service-actor/icp-client")
  await runActorIpcClient(args)
  process.exit(process.exitCode ?? 0)
}

const { runCliMain } = await import("./main-app")
await runCliMain()
```

Why this must be early:

- The child process should not create DB services.
- The child process should not bind HTTP/WebSocket servers.
- The child process should not start Automerge, PTY, filesystem, auth, or agent services.
- The child process should only be the actor guest-function runner.

Dynamic imports are preferred here because static imports would load the normal application graph before the flag check.

### 3. Replace hard-coded `bun run icp-client.ts` in Actor

Update [`packages/service-actor/src/Actor.ts`](../../packages/service-actor/src/Actor.ts).

Current method name has a typo:

```ts
private actorFuncions()
```

This can be renamed while changing spawn behavior, for example:

```ts
private spawnActorFunctionsProcess()
```

Recommended command construction:

```ts
function isCompiledRuntime(): boolean {
  return (
    (typeof VIBECANVAS_COMPILED !== "undefined" && VIBECANVAS_COMPILED) ||
    process.env.VIBECANVAS_COMPILED === "true" ||
    Bun.argv[1]?.startsWith("/$bunfs/") === true
  )
}

function buildActorIpcCommand(functionPath: string): string[] {
  const childArgs = ["--icp-client", "--functionPath", functionPath]

  if (isCompiledRuntime()) {
    return [process.execPath, ...childArgs]
  }

  const icpClientPath = new URL("icp-client.ts", import.meta.url).pathname
  return [process.execPath, icpClientPath, ...childArgs]
}
```

Then spawn with:

```ts
const proc = Bun.spawn(buildActorIpcCommand(this.#functionPath), {
  cwd: this.#rootDir,
  env: { ...process.env },
  stdout: "pipe",
  stderr: "pipe",
  ipc: (message) => this.#handleChildMessage(message as TActorChildMessage),
})
```

Notes:

- Source/test mode still uses `icp-client.ts` directly, preserving existing package tests without needing the CLI app entrypoint.
- Compiled mode uses the same executable, which avoids requiring host Bun and avoids virtual BunFS path issues.
- The `cwd` should remain the actor root directory so guest relative filesystem assumptions keep working.

### 4. Add child ready/failure state to Actor

`Actor` should not process queued messages until the child announces readiness.

Add fields similar to:

```ts
#isChildReady = false
#isClosing = false
#childFailure: Error | null = null
```

Lifecycle expectations:

- `start()` spawns the child.
- Child sends `{ type: "ready" }` after loading actor function registry.
- Parent sets `#isChildReady = true` and calls `#processQueue()`.
- `#processQueue()` returns early when the child is not ready.
- If child sends an unrecoverable startup error, reject pending work and emit a system error.
- If child exits unexpectedly, reject pending work and emit a system error.

Extend child message union:

```ts
type TActorChildMessage =
  | { type: "ready" }
  | { type: "next"; id: number }
  | { type: "setData"; id: number; data: TActorData }
  | { type: "emitMessage"; id: number; msg: any }
  | { type: "done"; id: number }
  | { type: "error"; id?: number; msg: any }
  | { error: boolean; id?: number; msg: any }
```

When receiving ready:

```ts
if (message.type === "ready") {
  this.#isChildReady = true
  this.#processQueue()
  return
}
```

### 5. Handle child exit and startup failure robustly

Current behavior can leave the actor permanently busy if the child exits before a pending run resolves.

After spawning:

```ts
void proc.exited.then((exitCode) => {
  this.#handleChildExit(exitCode)
})
```

Suggested behavior:

```ts
#handleChildExit(exitCode: number | null) {
  if (this.#isClosing) return

  this.#isChildReady = false
  this.#proc = null

  const error = new Error(`Actor child process exited with code ${exitCode}`)
  this.#rejectPending(undefined, error)

  if (this.#isProcessing) {
    this.#isProcessing = false
  }

  this.#applyImplicitErrorState()
  this.#emitError({
    code: "ACTOR_CHILD_EXITED",
    message: error.message,
    details: { exitCode },
  })

  this.#emitSystemEvent({ type: "status.changed", from: "running", to: "stopped" })
}
```

Be careful to avoid duplicate status events during intentional `close()`.

### 6. Improve error serialization across IPC

Currently `buildError(error)` can send raw `Error` objects. IPC serialization may drop useful fields.

Use a serializer:

```ts
function serializeError(value: unknown) {
  if (value instanceof Error) {
    return {
      name: value.name,
      message: value.message,
      stack: value.stack,
    }
  }
  return value
}
```

Then `buildError` should use `serializeError(msg)`.

Parent-side `#rejectPending` should turn serialized child errors into useful `Error` messages.

### 7. Keep API surface internal

The `--icp-client` flag should be treated as an internal implementation detail, not a user-facing CLI command.

Do not add it to general `--help` output unless there is a separate debug/developer help section.

Suggested behavior if a user runs it manually without IPC:

```txt
vibecanvas --icp-client must be launched by Vibecanvas via Bun.spawn({ ipc }).
```

Exit code should be non-zero.

## NOTES

- Do not spawn `bun run ...` in compiled mode. Production installs should not need Bun on the host.
- In source mode, spawning `process.execPath` alone is not enough because it points at the Bun runtime, not the app.
- In compiled mode, `process.execPath` is the correct real executable path.
- In compiled mode, `Bun.argv[0]` can be the literal string `bun`; do not use it to find the executable.
- `process.send` exists in the child only when the parent uses `Bun.spawn(..., { ipc })`.
- Dynamic loading of external `.ts` actor functions works in compiled Bun proofs, including relative `.ts` imports.
- Actor files still need any runtime npm dependencies available on disk, unless actor code is self-contained or bundled.
- The `--icp-client` flag should remain internal and should not be advertised as a normal user command.
- Existing actor test fixtures import type-only paths from source packages; type-only imports erase, but binary smoke tests should prefer minimal temporary fixtures to avoid workspace dependency coupling.
- The current actor child process has no ready handshake. Adding one will make startup errors clearer and prevent queue hangs.
- Child exit handling is necessary regardless of compiled support because any guest crash can otherwise leave pending runs unresolved.
