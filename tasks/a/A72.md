# A72 - system-owned DbResource schemas, migrations, and scoped actor access
[Overview](../BASED.md)

Implement system-owned local Turso `DbResource` instances. The system owns each resource, its schema, migration history, physical database, lifecycle, and access policy. Actors only use a bound resource through a host-derived scoped capability.

## Dependencies

Blocked by [A69](A69.md) for the resource catalog, definition bindings, ActorService ownership, and generic IPC gateway.

A70 and A71 are not architectural prerequisites. When choosing the migration number, use the next number present at implementation time and keep source and embedded migration registries ordered; do not collide with A70's planned migration.

## Ownership model

- `DbServiceTurso` is Vibecanvas's application/control database. It persists the resource catalog, schema definitions, immutable migration definitions, bindings, and scope policy.
- `ActorService` provisions physical databases, applies trusted migrations, owns connections, resolves bindings/scopes, and dispatches actor operations.
- A `DbResource` is an independent local Turso database owned by the system.
- An actor definition declares a `db` slot requirement. It does not own the resource, schema, migration SQL, path, or lifecycle.
- An actor child supplies only slot, operation, and operation arguments. Resource ID, definition/instance identity, and effective scope are derived by the trusted parent.

Never instantiate `DbServiceTurso` over a resource database, expose the application DB to actors, or run Vibecanvas application migrations against a `DbResource`.

## Explicit non-goals

- Turso Cloud, remote URLs, auth tokens, replicas, or synchronization.
- ORM integration.
- Widget-owned or actor-submitted migration SQL.
- Migration execution through actor IPC.
- Arbitrary guest-controlled database paths.
- Durable actor inbox/outbox or hard actor sandboxing.
- Pretending that SQL prefix inspection provides read-only or row-scope security.

## Control database changes

A69's `actor_resources` row remains the generic resource catalog. For `kind = 'db'`, `metadata` may contain a small validated summary such as provider, schema ID, desired schema version, and migration bundle checksum. Do **not** store SQL migration bodies in `metadata`.

Add dedicated system-owned schema tables in the next available application migration.

```sql
CREATE TABLE IF NOT EXISTS `db_resource_schemas` (
  `id` TEXT PRIMARY KEY NOT NULL,
  `name` TEXT NOT NULL CHECK (length(trim(`name`)) > 0),
  `description` TEXT,
  `created_at` TIMESTAMP NOT NULL DEFAULT (datetime('now')),
  `updated_at` TIMESTAMP NOT NULL DEFAULT (datetime('now'))
) STRICT;
--> statement-breakpoint
CREATE TABLE IF NOT EXISTS `db_resource_schema_migrations` (
  `schema_id` TEXT NOT NULL
    REFERENCES `db_resource_schemas` (`id`)
    ON UPDATE NO ACTION
    ON DELETE CASCADE,
  `version` INTEGER NOT NULL CHECK (`version` >= 1),
  `name` TEXT NOT NULL CHECK (length(trim(`name`)) > 0),
  `sql` TEXT NOT NULL CHECK (length(trim(`sql`)) > 0),
  `checksum` TEXT NOT NULL CHECK (length(trim(`checksum`)) > 0),
  `created_at` TIMESTAMP NOT NULL DEFAULT (datetime('now')),
  PRIMARY KEY (`schema_id`, `version`),
  UNIQUE (`schema_id`, `name`)
) STRICT;
--> statement-breakpoint
CREATE TABLE IF NOT EXISTS `db_resource_configurations` (
  `resource_id` TEXT PRIMARY KEY NOT NULL
    REFERENCES `actor_resources` (`id`)
    ON UPDATE NO ACTION
    ON DELETE CASCADE,
  `schema_id` TEXT NOT NULL
    REFERENCES `db_resource_schemas` (`id`)
    ON UPDATE NO ACTION
    ON DELETE RESTRICT,
  `target_version` INTEGER NOT NULL CHECK (`target_version` >= 1),
  `created_at` TIMESTAMP NOT NULL DEFAULT (datetime('now')),
  `updated_at` TIMESTAMP NOT NULL DEFAULT (datetime('now'))
) STRICT;
```

Use repository migration syntax, statement separators, and updated-at triggers. Add indexes only for demonstrated access paths; the declared primary/unique keys cover migration ordering and configuration lookup.

### Migration definition invariants

- Schema IDs are immutable system identities.
- Versions are positive, unique, ordered integers per schema.
- Published migration SQL is append-only and immutable.
- Compute and persist a canonical SHA-256 checksum when importing/publishing SQL.
- Reject changing SQL/checksum for an existing `(schema_id, version)`.
- Reject gaps unless an explicit import policy permits them and is tested.
- A schema cannot be deleted while a resource configuration references it.
- A resource has exactly one schema configuration in the first version.

Add validated row types and persistence methods to `service-db`. The namespace stores definitions/configuration only; it never opens a user resource database.

## SQL source and publishing

SQL files are an administrative authoring/import format, not actor-owned runtime files. A system-managed source layout may be:

```text
resources/db-schemas/<schema-id>/migrations/
  001-initial.sql
  002-add-email.sql
```

A trusted management operation reads the file, validates identity/version/size, computes its checksum, and inserts the immutable SQL into `db_resource_schema_migrations`. Runtime migration application reads the published SQL from `DbServiceTurso`; it does not depend on widget files or accept SQL from actor IPC.

Expose typed management methods/API routes to:

- Create/list/get/rename schema definitions.
- Publish/list migration definitions.
- Reject mutation of an already published migration.
- Create a `DbResource` using a schema and target version.
- Inspect desired/applied version and safe migration failure state.
- Explicitly upgrade a resource to a newer published target version.

Do not expose physical paths or unrestricted metadata mutation.

## Physical storage

Use one host-owned database per resource:

```text
<dataDir>/actor-resources/db/<resource-id>/data.db
```

The resource ID is generated and validated by the host. The path is derived, never persisted as an editable guest value. Actor children never open files.

Each physical resource database tracks applied migrations:

```sql
CREATE TABLE IF NOT EXISTS `_vibecanvas_migrations` (
  `schema_id` TEXT NOT NULL,
  `version` INTEGER NOT NULL CHECK (`version` >= 1),
  `name` TEXT NOT NULL,
  `checksum` TEXT NOT NULL,
  `applied_at` TIMESTAMP NOT NULL DEFAULT (datetime('now')),
  PRIMARY KEY (`schema_id`, `version`)
) STRICT;
```

This table is authoritative for what was applied to that physical database. Control metadata may cache applied version for listing/health, but it must be reconciled against the resource database.

## Safe migration runner

Migration execution is an `ActorService`/provider control-plane operation, never an actor data-plane operation.

For creation:

1. Validate catalog kind, schema, target version, and published migration sequence.
2. Allocate the host resource ID and derive its safe directory.
3. Create/open the physical database and apply resource pragmas.
4. Create `_vibecanvas_migrations`.
5. Apply migrations in ascending version order through the target.
6. For each migration, execute its SQL and insert its history row in the same transaction.
7. Verify checksums and health.
8. Mark the catalog resource `ready` only after success.
9. On failure, roll back the current migration, close handles, and persist a safe structured error/cleanup state.

For upgrades:

- Serialize migration execution with writes for that resource.
- Compare every already-applied checksum with the published checksum.
- Skip exact matches; reject changed history with `DB_RESOURCE_MIGRATION_CHANGED`.
- Apply only forward migrations; no automatic down migrations.
- Never silently recreate a missing or corrupt database.
- Snapshot/backup before upgrade if rollback across already committed migrations is required; otherwise document forward-repair behavior.

Safety requirements:

- Disable/reject `ATTACH`, `DETACH`, and extension loading.
- Do not permit caller-provided paths.
- Bound migration SQL size, statement count, and execution time.
- Verify installed Turso support for multi-statement execution and transactional DDL with adapter tests.
- Do not use a naive SQL parser as a security boundary. Use engine authorization/configuration where available; otherwise constrain the trusted schema-publishing surface and document the limitation.
- Keep internal diagnostics separate from actor-safe errors; never leak full paths or native objects.

## Scope model

Bindings may carry a system-controlled scope policy. The actor may request/use a declared scope mode, but it cannot provide the effective identity or broaden policy. The parent derives scope from actor definition, actor instance, account/installation context, and binding configuration.

Before implementation, lock the supported first-version modes and their enforcement. Candidate semantics are:

- `shared`: every actor using the binding accesses the same resource data.
- `definition`: access is limited to the bound definition identity.
- `instance`: access is limited to one actor instance identity.

Do not claim row-level isolation while exposing unrestricted arbitrary SQL. Choose and test an enforceable implementation:

1. Separate physical databases per isolated scope; or
2. A structured host query API that owns table access and injects scope predicates; or
3. Proven engine-level authorization/views that actors cannot bypass.

If A72 retains arbitrary schema SQL (`query`/`execute`), use physical separation for security-grade instance isolation, or explicitly classify logical scope as a trusted correctness convention. Never rely on asking actor SQL to include `WHERE actor_instance_id = ?`.

Scope is resolved by the parent and never copied permanently into actor machine context. Management responses may expose policy and binding status but not sensitive scope internals.

## Runtime and connection ownership

ActorService owns a DbResource provider/connection manager that:

- Provisions and migrates resources.
- Opens lazily after creation or eagerly by one documented policy.
- Caches at most one intended handle per physical resource/scope.
- Serializes migrations and writes per resource initially.
- Applies resource-specific pragmas once per connection.
- Closes handles on delete and `ActorService.stop()`.
- Drains/rejects operations during migration/deletion.
- Isolates failures so one bad resource does not prevent unrelated actors from running.

Reuse the repository's source/compiled Turso native-loading capability through an injected low-level connection factory. Do not instantiate `DbServiceTurso` for user databases.

Deletion order:

1. Reject while bindings reference the resource.
2. Mark deleting and block new operations.
3. Drain in-flight work.
4. Close handles.
5. Remove only the host-derived resource directory.
6. Delete catalog/configuration rows after successful cleanup, or retain recoverable error state.

## Actor-facing data plane

Actors operate on a bound slot only. They cannot create schemas, publish/apply migrations, select target versions, or inspect migration SQL/history.

Read operations for `fx` and `tx`:

```text
query<TRow>(slot, { sql, parameters? }) -> TRow[]
first<TRow>(slot, { sql, parameters? }) -> TRow | null
```

Write operations for `tx` only:

```text
execute(slot, { sql, parameters? })
  -> { rowsAffected, lastInsertRowId? }
batch(slot, { statements, mode? })
  -> ordered documented results
```

If unrestricted DDL must be reserved for system migrations, reject actor DDL and document the supported SQL subset. Parameters must be bound. Do not expose raw Turso clients/results or transaction callbacks over IPC.

Do not determine read-only behavior by checking whether SQL starts with `SELECT`. Use engine-level enforcement if available. The current trusted-process limitation may remain documented, but public `fx` portals still omit writes and the host rejects known write operations.

Define an IPC-safe value contract after testing the installed adapter, preferably:

```text
null | string | number | bigint | Uint8Array
```

Normalize deliberately if IPC cannot preserve a type. Bound row counts, result bytes, batch size, statement size, and execution time.

## IPC and SDK

The A69 gateway must derive:

- Resource and binding from definition plus slot.
- Actor instance and definition identity.
- Current run/message ID.
- Effective scope.
- Function-class and manifest access ceiling.

Operation matrix:

| Function | DbResource operations |
|---|---|
| `fn.*` | none |
| `fx.*` | `query`, `first` |
| `tx.*` | `query`, `first`, `execute`, `batch` |

Add schema-agnostic SDK row/value and operation types without exposing Turso or control-DB types. Query generics are compile-time assertions, not runtime validation. Do not expose schema-management methods to actor portals.

## Stable errors

Include stable safe codes such as:

- `DB_RESOURCE_NOT_BOUND`
- `DB_RESOURCE_UNAVAILABLE`
- `DB_RESOURCE_SCOPE_DENIED`
- `DB_RESOURCE_FILE_MISSING`
- `DB_RESOURCE_OPEN_FAILED`
- `DB_RESOURCE_SCHEMA_MISMATCH`
- `DB_RESOURCE_MIGRATION_CHANGED`
- `DB_RESOURCE_MIGRATION_FAILED`
- `DB_RESOURCE_UPGRADE_REQUIRED`
- `DB_QUERY_INVALID`
- `DB_QUERY_FAILED`
- `DB_WRITE_NOT_ALLOWED`
- `DB_BATCH_LIMIT_EXCEEDED`
- `DB_RESULT_LIMIT_EXCEEDED`
- `DB_BUSY`
- `DB_CONFLICT`
- `DB_RESOURCE_DELETE_FAILED`

Guest-facing errors may include slot, operation, and safe codes. Do not include migration SQL, complete parameters, paths, raw native errors, or unrelated process details.

## Tests

### Service DB

- New control migration applies from empty DB.
- Schema CRUD and resource configuration.
- Ordered migration publication.
- Duplicate version/name rejection.
- Published migration mutation/checksum rejection.
- Schema deletion restricted while referenced.
- Source and embedded migration lists remain synchronized.

### Migration runner

- Create and migrate a new resource to target version.
- Restart/reopen and skip matching history.
- Forward upgrade applies only missing migrations.
- Changed historical checksum is rejected.
- Failed migration rolls back its SQL and history insert.
- Migration/write serialization.
- Missing/corrupt files do not silently recreate data.
- `ATTACH`/extensions and unsafe paths are unavailable.
- SQL/statement/time limits.

### Scope and actor integration

- Parent derives scope; child cannot forge instance/definition/resource identity.
- Shared mode is visible to intended actors.
- Definition/instance modes satisfy the selected enforcement strategy.
- Cross-scope reads and writes fail in security-grade modes.
- Two actor instances using a shared binding see committed data.
- Rebinding changes subsequent resolution.
- `fn` gets no DB portal, `fx` gets reads, and `tx` gets writes.
- Actor IPC cannot invoke schema or migration management.

### Lifecycle/build

- Safe deterministic host path.
- Bound delete rejected before file removal.
- Stop closes all handles even if one close fails.
- One broken resource does not stop unrelated resources.
- Compiled binary locates the native Turso addon.
- Resource DB never receives Vibecanvas application migrations.

## Acceptance criteria

- DbResources, schemas, migration SQL, files, and lifecycle are system-owned.
- Migration SQL is stored in dedicated immutable control tables, not generic metadata or widget files at runtime.
- Every physical resource records and verifies applied migration checksums.
- Resource creation and explicit upgrade apply safe ordered forward migrations.
- Actors cannot publish/apply migrations or provide resource IDs, paths, or effective scope identity.
- Scope behavior is explicit and enforced without naive SQL-prefix or caller-supplied-filter claims.
- Each DbResource remains physically separate from the Vibecanvas application database.
- ActorService owns provisioning, migration, connection, operation, shutdown, and deletion lifecycle.
- `fx` receives reads; `tx` receives reads/writes; `fn` receives no resource portal.
- Source and compiled runtimes can open and migrate local resource databases.
- No cloud sync, remote Turso, ORM, durable inbox/outbox, or false sandbox guarantee is introduced.

## NOTES

`actor_resources.metadata` may cache validated provider/schema/version summaries, but migration SQL belongs in `db_resource_schema_migrations`.

System ownership does not by itself make arbitrary SQL safely row-scoped. Physical isolation or a constrained host-owned query layer is required for a meaningful instance security boundary.

Prefer serialized writes and migrations per physical resource initially because this repository has prior Turso native/concurrency failures.
