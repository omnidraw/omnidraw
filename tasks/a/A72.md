# A72 - host-managed DbResource schemas, migrations, and hybrid actor access
[Overview](../BASED.md)

Implement local Turso `DbResource` instances with host-managed physical lifecycle, versioned schemas/migrations, shared widget bindings, and hybrid named-operation/arbitrary-SQL actor access.

A `DbResource` is neutral shared infrastructure. It is not owned by one widget definition and is not described as application-system data. The host manages its file, connection, migration lifecycle, bindings, and limits. Actor definitions declare the schema version and access contract they expect from a bound resource.

## Dependencies

Blocked by [A69](A69.md) for the generic resource catalog, definition bindings, ActorService ownership, and correlated resource IPC gateway.

A70 and A71 are not architectural prerequisites. Use the next available control-database migration number at implementation time and keep source/embedded registries ordered. A70 follows the same next-available rule, so implementation order cannot create a numbering collision.

## Core model

- `DbServiceTurso` is Vibecanvas's application/control database.
- A `DbResource` is a separate local Turso database.
- `ActorService` owns physical provisioning, connections, migration coordination, operation routing, stop/restart coordination, and deletion.
- A resource may be bound to multiple widget definitions.
- A widget definition does not own the resource. It declares the schema ID/version and access it was authored against.
- Resources are shared in this version. Future isolation will use explicit resource forks/physical databases, not pretend that caller-provided row filters are a security boundary.
- Actor children never provide resource IDs, paths, function class, binding restrictions, or effective access.

Never point `DbServiceTurso` at a `DbResource`, run Vibecanvas application migrations against it, put user tables in the control database, or open a resource file in an actor child.

## Explicit non-goals

- Turso Cloud, remote URLs, tokens, replicas, or synchronization.
- ORM integration.
- Durable actor inbox/outbox or hard guest sandboxing.
- Security-grade row/instance isolation in the shared-resource version.
- SQL-string inspection presented as an engine authorization boundary.
- A required `batch` actor API.
- Automatic schema/type generation from migrations. The agent receives migration files and derives local actor row types itself.
- Frontend resource management, migration confirmation, and live-instance error rendering. This task returns complete preview/status/action DTOs; UI implementation is postponed.

## Widget DbResource declaration

A `db` slot declares its expected schema contract and permissions. Exact field names may be refined, but preserve this model:

```ts
{
  resources: {
    notes: {
      kind: "db",
      schema: {
        id: "notes",
        version: 2,
      },
      scope: ["read", "write"],
      arbitrarySql: true,
      operations: {
        listNotes: {
          effect: "read",
          sql: `
            SELECT id, title, checked
            FROM notes
            ORDER BY title
          `,
        },
        toggleBox: {
          effect: "write",
          sql: `
            UPDATE notes
            SET checked = NOT checked
            WHERE id = :id
          `,
          parameters: {
            id: "string",
          },
        },
      },
    },
  },
}
```

Rules:

- `schema.id` and `schema.version` identify the exact contract the definition expects.
- Version `0` is valid and means an empty/unmigrated schema.
- `scope` contains `read`, `write`, or both.
- `fn` receives no database access.
- `fx` is capped at read.
- `tx` may receive read and/or write according to the declaration and binding restriction.
- The binding may reduce scope but cannot broaden the definition declaration.
- `arbitrarySql` is explicit and defaults to false. When enabled, arbitrary reads/writes are still limited by effective read/write scope and function class.
- Named operations are optional and available even when arbitrary SQL is disabled.
- A named operation's declared effect must match how it can be invoked: read operations require effective read; write operations require effective write and `tx`.
- Named parameters are validated before dispatch.
- Existing non-DB slots keep A69's simpler kind/access model.

Use A69's persisted binding permission restriction and its kind/schema/version compatibility status contract.

## Version compatibility and shared resources

Binding a definition to a `DbResource` requires:

- Resource kind `db`.
- Matching schema ID.
- Exact schema version match in the first version.
- Resource lifecycle status `ready`.
- Binding scope no broader than the definition scope.

A shared resource migration may intentionally make currently bound definitions incompatible. The host must show affected definitions/instances before confirmation. After migration, any definition whose declared version does not exactly match remains linked but blocked with a visible resource-version error, for example:

```text
DbResource "Shared Notes" is at schema notes@3.
Widget definition "Notes Board" expects notes@2.
Update and republish the widget definition before its actors can restart.
```

This is preferable to silently running old actor SQL against a new schema. Binding status/control API responses must expose expected version, resource version, compatibility, and safe remediation text. Do not write the mismatch into actor business context.

When an incompatible widget definition is updated/published to the resource's exact version, revalidate all of that definition's bindings. Clear the compatibility block on success. Instances that were recorded as running before the resource migration may restart automatically after successful revalidation; instances that were already stopped remain stopped. Persist or otherwise durably associate this restart intent so a process restart does not incorrectly start unrelated actors.

Use the Turso domains shown above, following the repository's existing domain convention. Add updated-at triggers. Index `db_resource_migration_blocks(actor_instance_id)` for definition-update/restart lookup; its primary key supports resource migration/recovery lookup. Avoid other redundant indexes.

`db_resource_migration_blocks` durably records actor-instance stop/restart intent and schema compatibility blocks caused by DbResource migration workflows. Remove a row only after restart succeeds, the actor is intentionally left stopped, or the block is otherwise explicitly resolved. This is migration lifecycle state, not a generic actor blocking system or durable actor inbox/outbox.

Version `0` has no migration row, so composite FKs to migration rows cannot represent it. Persistence/service validation must ensure every positive applied/target version exists for the configured schema. The physical migration table is authoritative; `applied_version` is its last reconciled control-plane projection. Normally applied equals target. During an upgrade, applied remains old while target records the requested version. On restored failure, target returns to applied. Add tests for invalid positive versions and reconciliation drift.

### Schema and migration invariants

- Schema IDs are immutable.
- Draft schema metadata and draft migration rows may be edited/deleted through explicit draft APIs.
- Publishing a schema validates and atomically publishes its initial contiguous migration sequence.
- A published schema may receive a new draft migration only at the next version; publishing that migration makes it available as a target.
- Published schemas/migrations are immutable; deprecate schemas rather than delete them.
- Published migration SQL is append-only. Deprecated schemas accept no new migrations.
- Versions are contiguous positive integers beginning at 1; version 0 means none applied.
- The schema definition must be published before creating/binding a resource, including a resource at version 0.
- Compute `sha256:<hex>` over exact UTF-8 SQL file bytes.
- Reject changed SQL/checksum for an existing `(schema_id, version)`.
- A referenced schema cannot be deleted.
- Provider-owned schema/version configuration cannot be changed through generic resource APIs.
- A resource has exactly one schema configuration in the first version.
- Existing resources migrate forward only: target must be greater than applied version. Downgrade requires a future explicit fork/restore workflow, not reverse migration execution.

Anyone with access to the local management API may currently create/publish schemas and migrations. This is an accepted local/single-user limitation; do not claim stronger authorization.

## SQL files and agent context

SQL files are an authoring/import representation, for example:

```text
resources/db-schemas/<schema-id>/migrations/
  001-initial.sql
  002-add-email.sql
```

A local management operation imports exact file bytes, validates version/name/size, computes the checksum, and stores a draft migration row. An explicit publish operation freezes it. Runtime migration application reads only published rows from `DbServiceTurso`, not widget paths or actor IPC.

When generating or updating a widget for a schema version, provide the AI all published migration SQL from version 1 through that version. The AI derives local query/result types and named operations itself. Generics remain compile-time assertions; Vibecanvas does not infer or enforce table types.

Expose management methods/routes to:

- Create/list/get/rename/publish/deprecate schema definitions.
- Publish and list immutable migrations.
- Create a DbResource at schema version 0 or a positive published version.
- Preview affected definitions/instances for an upgrade.
- Confirm an explicit resource migration.
- Inspect configured/applied version, compatibility, and safe failure state.

## Physical storage

Use one host-derived database per resource:

```text
<dataDir>/actor-resources/db/<resource-id>/data.db
```

Resource ID is host-generated and validated. Names, actor arguments, and SQL cannot provide the path.

Each physical resource database tracks applied migrations:

```sql
CREATE TABLE IF NOT EXISTS `_vibecanvas_migrations` (
  `schema_id` TEXT NOT NULL,
  `version` INTEGER NOT NULL CHECK (`version` >= 1),
  `name` TEXT NOT NULL,
  `checksum` TEXT NOT NULL,
  `applied_at` TIMESTAMP NOT NULL DEFAULT (datetime('now')),
  PRIMARY KEY (`schema_id`, `version`)
) STRICT;
```

The physical table is authoritative for applied migrations. `db_resource_configurations.applied_version` is a reconciled control-plane projection used by status/compatibility APIs; `target_version` records desired migration state.

Actor arbitrary-write access is trusted with the complete resource schema and data because the current Turso adapter has no proven authorizer. It may perform DDL. Protection of `_vibecanvas_migrations`, strict read-only SQL classification, and hard sandbox enforcement are explicitly deferred under the accepted trust model.

Resource version records host migration history, not proof that physical schema still matches it after arbitrary actor DDL. Arbitrary-write actors can make named operations or later migrations fail. Reconciliation verifies migration history/checksums and health but does not attempt full schema diffing. Surface resulting failures honestly rather than silently changing resource version.

## Migration coordination and actor lifecycle

A resource migration is an explicit disruptive control-plane operation:

1. Resolve every definition bound to the resource and all persisted actor instances of those definitions, including instances not currently loaded by ActorSupervisor. Add/reuse service-db queries needed for this complete reference set.
2. Return a compatibility-impact preview DTO listing affected definitions/instances before confirmation. Frontend rendering is postponed.
3. Record which linked instances are currently running, stop those instances, and wait for their child processes/in-flight resource calls to close. Already stopped instances remain stopped.
4. Block new starts, bindings, calls, and deletion for the resource by marking it `migrating`.
5. Close/drain the resource connection.
6. Create a recoverable local backup/snapshot of the database file.
7. Apply migrations in ascending order.
8. For each migration, execute SQL and insert its history row in the same transaction.
9. Reopen and health-check the resource.
10. Persist the new configured version/status.
11. Restart only instances that were running before migration and whose definitions now exactly match the resource version.
12. Leave incompatible instances blocked and expose an actionable version-mismatch state through control/status APIs. Frontend rendering is postponed.

A69's lifecycle domain supplies `provisioning` and `migrating`. One resource migration must not stop unrelated actors/resources. If any previously running linked actor cannot stop cleanly, abort before backup/mutation, return the resource to its prior ready state, and report which instances blocked migration.

### Failure and recovery policy

Define concrete whole-upgrade recovery:

- Hash exact UTF-8 migration bytes and verify all previously applied rows before mutation.
- Verify adapter support for transactional DDL/multi-statement execution with focused tests; do not use a homemade SQL splitter as a security mechanism.
- If any migration fails, roll back its transaction, close the failed handle, and atomically restore the pre-upgrade backup.
- Reopen and verify the restored database and migration history.
- Restore the previous configured/applied version.
- Persist a safe structured migration error and return the resource to `ready` only if restoration is verified; otherwise leave it `error`.
- Restart previously compatible linked actors only after successful restoration.
- Keep internal SQL/native/path diagnostics out of actor-facing errors.
- Do not copy only `data.db` while WAL state may exist. Close the handle, perform a verified checkpoint or use a supported Turso backup/snapshot API, and test reopening the backup before migration. Snapshot/restore the complete database state including required sidecars.
- Remove the backup only after the upgraded database and control state are durably verified; retain or quarantine it on uncertain recovery.
- On process restart, reconcile resources left in `provisioning`, `migrating`, `deleting`, or `error` rather than silently recreating data.

Apply bounded SQL size, statement count, execution time, and migration count. Disable extension loading and reject host-path control. `ATTACH`/`DETACH` should be disabled where the adapter supports it; current trusted arbitrary-write limitations must be documented if engine enforcement is unavailable.

## Creation and deletion sagas

The control DB, filesystem, and physical resource DB cannot share one transaction. Treat provisioning/deletion as recoverable sagas.

Creation:

1. Persist catalog/configuration as `provisioning`.
2. Create the host-derived directory/database.
3. Apply migrations through target version, including version 0 behavior.
4. Health-check and mark `ready`.
5. On failure, clean up or retain an explicit recoverable `error` state.

Deletion:

1. In a control-DB transaction, verify no bindings, transition to `deleting`, and thereby block new bindings.
2. Drain calls and close handles.
3. Remove only the host-derived resource directory.
4. Delete catalog/configuration rows after successful cleanup.
5. If filesystem cleanup fails, retain the row in recoverable error/deleting state.

The FK restriction is the race-safe backstop. A resource cannot be deleted while any definition uses it.

## Host-managed runtime

ActorService owns a provider/connection manager that:

- Provisions and migrates resources.
- Keeps at most one intended handle per active shared resource.
- Serializes writes and migrations per resource initially.
- Applies resource-specific pragmas once per connection.
- Tracks in-flight operations for migration/delete draining.
- Closes handles on delete and `ActorService.stop()`.
- Isolates failures to the affected resource.

Reuse source/compiled Turso native loading through an injected low-level connection factory. Do not instantiate `DbServiceTurso` for resource files.

Rebinding semantics:

- A call resolves its binding once and finishes against that resource.
- Calls beginning after a rebind resolve the new resource.
- Deletion/migration waits for already resolved in-flight calls.

## Hybrid actor access

The actor definition determines allowed use through named operations and optional arbitrary SQL.

### Named operations

Named operations provide parameter validation, explicit read/write classification, auditing, and a smaller surface where arbitrary SQL is unnecessary.

- Validate operation names and parameter schemas at definition publication.
- Bind parameters; never interpolate actor values.
- A read operation requires effective read access.
- A write operation requires effective write access and `tx`.
- Log operation name/call ID, not sensitive parameter values.
- Different widget definitions may declare different named operations against the same compatible schema version.

### Arbitrary SQL

When `arbitrarySql` is enabled:

- Effective read permits arbitrary query/read calls.
- Effective write permits arbitrary mutation and DDL from `tx`.
- `fn` receives nothing.
- `fx` receives the read portal only.
- `tx` receives capabilities permitted by effective scope.
- No `batch` operation is required for the first version.

Because no proven engine authorizer exists, arbitrary-write actors are trusted with the entire resource schema/data. Do not classify DML versus DDL using SQL-prefix checks. The host still enforces function class, declared scope, binding restrictions, known portal operation, statement/result limits, resource state, and binding identity.

Effective access is:

```text
definition scope
∩ binding restriction
∩ function-class ceiling
= effective access
```

The child cannot broaden any component.

## Future isolation and forks

This version uses shared resources. Future definition/instance isolation must use explicit resource forks or separate physical databases when arbitrary SQL is enabled.

Do not add a `scope = instance` flag that still points unrestricted SQL at the same physical database. A future fork design must define parent resource/version, fork identity, migration behavior, retention, deletion, quotas, and whether changes merge. Keep current IDs/bindings capable of referencing a fork later without implementing it now.

## IPC and SDK

The parent gateway derives definition, instance, run ID, binding, resource, resource state, expected/actual schema version, binding restriction, function class, and effective access.

The portal may expose:

- Invocation of declared named operations.
- Arbitrary query when enabled with read access.
- Arbitrary execute when enabled with write access in `tx`.

Final ergonomic method names may be refined, but no schema management or migration method is exposed to actors.

Define an IPC-safe Turso value contract after adapter tests, preferably:

```text
null | string | number | bigint | Uint8Array
```

Normalize deliberately if IPC cannot preserve a type. Bound result rows/bytes, SQL size, parameters, and execution time. Do not expose raw Turso handles/results.

### Migration lifecycle

- Create at version 0 and at a positive version.
- Exact-byte checksum verification.
- Explicit upgrade preview lists all linked definitions/instances.
- All linked actors stop before migration begins.
- Matching previously-running actors restart after success; previously-stopped actors remain stopped.
- Mismatched actors remain blocked with expected/actual versions in status DTOs.
- Publishing a matching widget definition clears compatibility blocks and honors durable restart intent.
- A linked actor stop failure aborts before database mutation.
- Failed migration restores backup and previous version.
- Failed restoration leaves resource `error` and actors stopped.
- Crash reconciliation for transitional states.
- Unrelated actors continue running.

### Binding and hybrid access

- Kind, schema ID, exact version, and scope restriction validation.
- Two compatible definitions intentionally share one resource.
- Resource migration makes old definitions visibly incompatible.
- Named read/write operation routing and parameter validation.
- Binding cannot broaden scope.
- `fn` has no DB portal; `fx` cannot invoke writes; `tx` follows effective scope.
- Arbitrary SQL is absent by default and available only when declared.
- Arbitrary write supports DDL under the accepted trust model.
- Actor IPC cannot invoke schema publication/migration.
- Rebinding affects only calls started after rebind.

### Lifecycle/build

- Bound deletion is rejected transactionally before filesystem removal.
- Safe deterministic path and no traversal.
- Stop closes all handles even when one close fails.
- Missing/corrupt DB does not silently create an empty replacement.
- Compiled binary locates native Turso addon.
- Resource DB never receives Vibecanvas application migrations.

## NOTES

The current arbitrary-write mode deliberately trusts actor code with complete resource schema/data. Named operations reduce exposure but do not change that fact when arbitrary SQL is enabled.

A resource version change is an operational event affecting every linked definition. Compatibility is explicit and visible rather than silently assumed.

Arbitrary `execute` now also accepts a bounded ordered operation array in one IPC call and serialized write lane. Each item remains one parameterized statement; callers explicitly provide transaction and savepoint control statements. This is not a separate `batch` API and does not change the single-statement named-operation contract.

Prefer serialized writes/migrations per resource because this repository has prior Turso native/concurrency failures.
