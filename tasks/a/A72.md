# A72 - actor resources: implement schema-agnostic local Turso DbResource
[Overview](../BASED.md)

Implement user-defined `DbResource` instances owned by `ActorService`. Each resource is an independent local Turso database with a schema-agnostic actor interface, bound at widget-definition scope and shared by every actor instance of that definition.

## Dependency

Blocked by [A69](A69.md). A70 and A71 are not architectural prerequisites, though shared test utilities and completed control-plane work may make sequencing easier.

## Context

### Required distinction

`DbServiceTurso` is the Vibecanvas application/control database service. It stores canvases, actor definitions/instances, resource metadata/bindings, and KV/secret resource entries.

`DbResource` is user-defined actor data storage:

- Different lifecycle.
- Different interface.
- Independent physical database.
- No Vibecanvas application migrations.
- No hardcoded schema.
- No compile-time knowledge of CRM/contact/user tables.
- Owned and resolved by `ActorService`.

Never expose `DbServiceTurso.db` as the implementation of a `DbResource` actor portal.

### Product behavior

```text
DbResource "Acme CRM"
  local file owned by Vibecanvas resource runtime
  schema created by actor tx SQL or user-provided SQL

Widget definition "CRM Contacts"
  slot "crm" -> DbResource "Acme CRM"

Actor instance A inserts contact
Actor instance B queries contacts
Both use the same physical DbResource
```

The user can also create `DbResource "Demo CRM"` and rebind the widget definition without changing actor code.

### Schema-agnostic requirement

The SDK must not hardcode, infer, generate, or validate a database schema globally.

Actor authors own local types at each query boundary:

```text
query<TContact>(...)
first<TContact>(...)
```

Those generics are compile-time assertions/convenience only. Runtime rows come from Turso and are not schema-validated by Vibecanvas unless the actor author validates them.

Do not add table definitions to `vibecanvas.json`. Do not make the wizard enumerate CRM tables as part of the base resource contract.

### Turso scope

Use local embedded Turso only.

Current documentation points to `@tursodatabase/database` for local/embedded use. The repository already uses that package behind `DbServiceTurso` and has special native-addon resolution for compiled Vibecanvas binaries.

Explicitly out of scope:

- Turso Cloud.
- Remote database URLs.
- Auth tokens.
- Embedded replicas.
- `@tursodatabase/sync`.
- Push/pull/conflict sync.
- ORM support.
- Database branching.
- Automatic widget schema migrations.
- Durable actor inbox/outbox.
- Hard actor sandboxing.

## Storage layout

### One physical database per DbResource

Use a deterministic host-owned location under A69's actor resource data root, conceptually:

```text
<dataDir>/actor-resources/db/<resource-id>/data.db
```

Requirements:

- Resource ID is host-generated and validated before path construction.
- Database path is derived by the host, not stored/provided by guest actor code.
- No user path traversal.
- Parent directories are created atomically/recursively as needed.
- Resource metadata may record provider/version information, but not an arbitrary editable local path.
- File is not opened by actor children.
- Deleting an unbound DbResource closes its handle before removing its directory.
- Failed deletion reports error and does not falsely remove catalog metadata first.
- A partially created resource is reconciled or cleaned up on failure.

Do not place user tables inside the Vibecanvas application DB. SQLite/Turso lacks a safe schema namespace for arbitrary untrusted SQL in one shared physical DB.

### Catalog metadata

Use A69's `actor_resources` row with kind `db`.

Possible non-secret metadata:

- Provider: local Turso.
- Format/provider version.
- Created/last-opened information only if used.

Do not store table schemas, migration SQL, query history, or database contents in catalog metadata.

## Runtime ownership and connection model

### ActorService owns DbResource

Implement `DbResource` and a small ActorService-owned connection manager/provider.

Responsibilities:

- Provision an empty local database on resource creation.
- Open lazily on first operation or validate eagerly at creation; choose and test one behavior.
- Cache at most one intended database handle per resource within the process unless Turso API requires another shape.
- Share that handle safely among actor instances.
- Apply resource-specific pragmas once per opened database.
- Close one handle on resource delete.
- Close all handles on `ActorService.stop()`.
- Evict/close idle handles only if needed; avoid premature complexity for the first version.
- Surface resource health without preventing unrelated resources or actors from running.

Do not instantiate `DbServiceTurso` for each user database because that would run Vibecanvas migrations and expose the wrong public interface.

### Turso connection factory

The repository's `turso-native.ts` handles source versus compiled addon resolution. Reuse that capability without moving `DbResource` ownership out of actor service.

Acceptable directions:

- Export a neutral low-level Turso `Database`/connection factory from service-db infrastructure and inject it into ActorService.
- Move native-loading logic into a small lower-level package shared by service-db and service-actor if ownership remains clear.
- Inject a `connectLocalTurso(path, options)` portal from CLI setup for tests/build compatibility.

Unacceptable direction:

- Import `DbServiceTurso` and point it at the resource file.

Whichever approach is chosen must work in:

- Source development.
- Unit tests with temporary directories/in-memory substitutes.
- Compiled Vibecanvas binaries with bundled native addon.
- Supported platform/architecture matrix already handled by the CLI.

## Database value and row contract

Turso SQL values may include values outside actor JSON context, especially blobs and large integers. Define an explicit IPC-safe database value contract after inspecting the exact installed Turso API/types.

Preferred first-version contract:

```text
input parameter:
  null | string | number | bigint | Uint8Array

output cell:
  null | string | number | bigint | Uint8Array
```

If Bun IPC or SDK packaging makes `bigint`/`Uint8Array` unreliable, normalize deliberately and document it rather than silently coercing arbitrary values. Actor machine context remains JSON-compatible; actor authors must transform DB-only values before `setData` or output messages.

Rows are schema-agnostic records:

```text
Record<string, TDbResourceValue>
```

Do not use `any` at public boundaries where an `unknown`/generic row type is more honest.

## Actor-facing interface

The exact slot-access syntax follows A69. Preserve the operation semantics below.

### Read interface available to `fx` and `tx`

```text
query<TRow>(slot, { sql, parameters? }) -> TRow[]
first<TRow>(slot, { sql, parameters? }) -> TRow | null
```

Optional useful metadata:

- Column names if Turso result API makes them available.
- Row count.

Keep the first public shape small. Do not expose a raw Turso result/client object.

### Write interface available only to `tx`

```text
execute(slot, { sql, parameters? })
  -> { rowsAffected, lastInsertRowId? }

batch(slot, { statements, mode? })
  -> ordered statement results, all-or-nothing when documented as transactional
```

Required semantics:

- Parameters are bound; examples never interpolate user values into SQL.
- `execute` may run DDL and DML because the schema belongs to the user resource.
- Multi-statement string behavior is explicit. Prefer one statement per `execute` and a structured batch for multiple statements.
- No callback transaction over IPC.
- If the installed Turso API cannot guarantee transactional batch behavior, expose separate non-transactional/transactional names rather than making a false guarantee.
- A batch cannot span two resource slots.

### Read-only enforcement

Do not classify read-only SQL by checking whether the string starts with `SELECT`.

Inspect local Turso capabilities for engine-level read-only preparation/connection/statement metadata. Choose one of:

1. Reliable engine-level read-only enforcement for `fx` query/first.
2. A constrained read API proven not to permit mutation.
3. If the current local API cannot enforce it, document that the trusted-process limitation also applies to SQL classification and still omit write methods from the `fx` portal.

The current project accepts trusted guest code, but the implementation should not add a known-naive SQL parser that future developers may mistake for a security boundary.

- Prepared statement parameter types.
- Row/result shape.
- `bigint` and blob behavior.
- DDL/DML result metadata.
- Transaction/batch APIs and atomicity.
- Concurrent use of one handle.
- Read-only capability, if any.
- Conflict/busy error signatures.
- Pragmas supported by the installed engine.

Commit these as adapter tests where useful, not a separate exploration task.

Do not use documentation examples alone when repository package/native behavior can differ.

### 2. Add/adjust low-level connection factory

Provide ActorService a local Turso connection constructor compatible with source and compiled runtime.

Requirements:

- No Vibecanvas migrations.
- No application `DbServiceTurso` public namespaces.
- Explicit close method.
- Test injection.
- Compiled native addon resolution reuse.
- Errors identify resource operation without leaking unnecessary full local paths to guest code.

Update package dependencies/catalog entries and binary asset configuration only as needed.

### 3. Implement DbResource filesystem lifecycle

Creation order must avoid orphaned/false-ready resources:

1. Validate requested name/kind through A69 manager.
2. Allocate resource ID.
3. Derive safe directory/path.
4. Create directory and database.
5. Open and apply pragmas.
6. Perform a minimal health query.
7. Persist/mark catalog resource ready.
8. Close immediately or retain handle according to chosen connection model.

Define rollback for failure at each step.

Deletion order:

1. Verify no bindings.
2. Block new operations/mark deleting if lifecycle supports it.
3. Drain or reject in-flight operations.
4. Close cached handle.
5. Remove resource directory only, never a caller-supplied path.
6. Delete catalog metadata after successful file removal, or persist recoverable error state if cleanup fails.

Restart/reconciliation:

- Existing catalog row + file present: open normally.
- Catalog row + file missing: `DB_RESOURCE_UNAVAILABLE`, no replacement empty DB silently created.
- Orphan directory without catalog row: leave/log for explicit cleanup; do not attach it to a random resource.
- Corrupt/open failure: mark/error locally; other resources continue.

### 4. Choose and apply DbResource pragmas

Start from current application DB reliability settings but decide independently for user DBs:

- `foreign_keys = ON`.
- `busy_timeout` bounded.
- `synchronous = FULL` unless product accepts weaker durability.
- Journal mode deliberately chosen.
- Temp/cache settings only when justified.

Turso documentation distinguishes default serialized writes and MVCC/concurrent writes with conflict retries. For first implementation, choose one explicit strategy:

#### Simpler option: serialized writes per DbResource

- Maintain a per-resource write tail/mutex in the parent provider.
- Use proven journal settings.
- Read operations may proceed according to engine behavior.
- Lower throughput but deterministic behavior and fewer native conflict paths.

#### Concurrent option: MVCC plus retry

- Enable the verified MVCC pragma/mode.
- Use concurrent transactions.
- Retry only known conflict/busy failures with bounded exponential backoff/jitter.
- Never retry syntax, constraint, or arbitrary operation errors.
- Ensure transaction rollback before retry.

Given B37/B41 history, prefer the simpler serialized-write baseline unless benchmarks demonstrate a need for MVCC. Turso still provides local asynchronous reads and the resource can evolve later.

### 5. Implement DbResource provider

Add `DbResource` in service-actor.

Responsibilities:

- Verify catalog kind `db`.
- Resolve slot binding.
- Obtain/open connection from ActorService-owned manager.
- Validate operation arguments and bounded statement counts.
- Prepare and bind parameters.
- Normalize rows/results to the SDK contract.
- Apply time/row/result-size limits where practical.
- Serialize writes if that strategy is selected.
- Map native errors to stable resource errors.
- Never expose connection, prepared statement, physical path, application DB, or provider internals.

Do not hardcode tables or run widget migrations. A new database is empty; actor tx code may execute `CREATE TABLE IF NOT EXISTS ...` as part of its own behavior.

### 6. Register provider with ActorService

- Register kind `db` in A69 manager.
- Hook creation/deletion into provider lifecycle rather than generic metadata-only creation.
- Pass A69 resource data root from `setup-services.ts`.
- Close all DB resource handles in `ActorService.stop()` even if one close fails.
- Ensure one broken DB resource does not abort ActorService startup.
- Expose metadata/health through resource management routes without exposing file paths.

### 7. Add IPC operation dispatch

Host checks:

- Declared slot exists and is kind `db`.
- Binding exists and points to `db` resource.
- Requested operation is known.
- Function/access mode permits operation.
- Statement/batch/parameter/result limits.

Operation matrix:

| Function | DbResource operations |
|---|---|
| `fn.*` | none |
| `fx.*` | `query`, `first` |
| `tx.*` | `query`, `first`, `execute`, `batch` |

IPC requirements:

- Preserve parameter value types according to finalized contract.
- Preserve row column names.
- Correlate multiple queries in one function.
- Reject pending query on child/actor/resource close.
- Avoid unbounded row serialization.
- Do not log complete SQL parameters by default because they may contain private CRM data or credentials.

### 8. Extend @vibecanvas/sdk/actor

Add schema-agnostic public types:

- `TDbResourceValue`.
- `TDbResourceRow`.
- Query/execute/batch argument/result types.
- Read portal.
- Write portal.

Typing requirements:

- Query/first accept call-site row generic.
- No central table/schema generic required on resource creation.
- No imported Turso client/result types.
- Parameter types are explicit.
- Results are plain serializable objects/arrays.
- Actor authors are reminded that generics do not perform runtime validation.

Update actor implementation prompt with parameterized SQL examples and rules:

- Never interpolate actor message values into SQL.
- Create tables explicitly if the widget owns an empty database.
- Keep initialization idempotent with `IF NOT EXISTS` where suitable.
- Handle missing tables/rows deliberately.
- Use tx for DDL/DML.
- Use fx for read-only query.

### 9. Define initialization behavior

Because Vibecanvas does not hardcode schemas, decide how a widget initializes an empty DB.

Recommended first version:

- `DbResource` creates an empty database only.
- Widget definition does not provide host-run migrations.
- Actor tx function runs idempotent DDL before first use, or exposes an explicit `in.initialize` transition.
- Multiple actor instances may race initialization; SQL must use idempotent DDL and provider write serialization/DB transaction semantics.
- Initialization state may be stored in the user database itself, not in actor resource metadata.

Do not add an implicit schema because a CRM example needs contacts.

### 10. Stable errors

Recommended codes:

- `DB_RESOURCE_NOT_BOUND`
- `DB_RESOURCE_UNAVAILABLE`
- `DB_RESOURCE_FILE_MISSING`
- `DB_RESOURCE_OPEN_FAILED`
- `DB_QUERY_INVALID`
- `DB_QUERY_FAILED`
- `DB_WRITE_NOT_ALLOWED`
- `DB_BATCH_LIMIT_EXCEEDED`
- `DB_RESULT_LIMIT_EXCEEDED`
- `DB_BUSY`
- `DB_CONFLICT`
- `DB_RESOURCE_DELETE_FAILED`

Guest-facing errors may include slot, operation, and safe database error code/message. Avoid full local paths, raw native objects, complete parameter values, or unrelated process details.

Constraint/syntax errors should remain useful enough for generated actor debugging, but separate internal diagnostics from safe actor event details.

### 12. Performance and reliability baseline

- Keep one connection/handle per active resource, not per actor instance.
- Do not open a DB in the child process.
- Use prepared/bound parameters.
- Bound query rows and batch statements.
- Prefer bulk/batch over one IPC call per row.
- Serialize writes per resource initially if chosen.
- Apply timeout/cancellation at gateway level where available.
- Do not cache arbitrary query results in ActorService.
- Actor context remains a UI projection; DB is source of shared truth.

Automatic cross-instance UI invalidation is not required unless A69 established it. Two instances share committed data and observe it when they next query.

## Acceptance criteria

- `DbServiceTurso` remains the Vibecanvas DB service and is never exposed as a user `DbResource`.
- Each `DbResource` has an independent local Turso database file.
- `ActorService` owns provisioning, connection caching, operation routing, close, and delete lifecycle.
- Widget manifests declare only a `db` slot/access requirement, never a schema or path.
- Query results are call-site generic/schema-agnostic.
- Two actor instances of one definition share committed data from one bound resource.
- Rebinding switches subsequent operations without copying/moving databases.
- `fx` receives query operations; `tx` receives query plus execute/batch.
- Actor children never receive file paths or database handles.
- Source and compiled Vibecanvas runtimes can open DbResource files using bundled native Turso support.
- No cloud sync, remote Turso, ORM, automatic migrations, durable inbox/outbox, or sandbox work is added.

## NOTES

Prefer per-resource serialized writes for the first version because this repository has prior Turso native/concurrency failures. This is a baseline choice, not a permanent claim that Turso cannot support MVCC.

`DbResource` should create an empty database. Actor code owns its SQL schema and can initialize it with idempotent DDL through tx operations.

A database row generic is not runtime validation. Generated actors should define local row types and validate external/untrusted data when correctness requires it.
