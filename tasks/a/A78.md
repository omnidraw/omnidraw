# A78 - startup: warn when Node.js or npm is unavailable for widgets
[Overview](../BASED.md)

Add a non-blocking startup prerequisite check for the external Node.js and npm toolchain used by the widget system. Vibecanvas itself remains a standalone Bun-built executable.

## Context

Widget creation, dependency installation, and TypeScript validation will rely on executables provided by the user's Node.js/npm installation. The CLI runtime starts in [`apps/cli/src/main-app.ts`](../../apps/cli/src/main-app.ts), while [`apps/cli/src/setup-services.ts`](../../apps/cli/src/setup-services.ts) creates the shared event publisher used by the notification API.

Server notifications are defined in [`packages/api-notification/src/contract.ts`](../../packages/api-notification/src/contract.ts), retained and published by [`packages/service-event-publisher/src/EventPublisherService.ts`](../../packages/service-event-publisher/src/EventPublisherService.ts), and consumed by the frontend notification bridge in [`apps/frontend/src/services/orpc-websocket.ts`](../../apps/frontend/src/services/orpc-websocket.ts). The notification contract currently has no warning severity, so this task must carry warning semantics through to the canvas UI instead of reporting a missing prerequisite as an error or generic info message.

## Plan

1. Add a small, independently testable CLI startup check that probes `node --version` and `npm --version` without a shell and reports each executable as available, missing, or unusable.
2. Run the check once for the `serve` command after the event publisher exists. Skip it for help, version, upgrade, uninstall, and other non-server command paths.
3. Keep startup non-blocking: missing or unusable tools must not stop the server, change the exit code, or prevent the canvas from loading.
4. When either executable is unavailable, emit one concise CLI warning that names the missing tools, explains that widget creation/build/validation requires Node.js and npm, and gives an actionable installation instruction. Do not warn when both probes succeed.
5. Extend the notification event contract with a warning severity and carry it through the ORPC notification stream and frontend/canvas toast presentation with warning-specific styling.
6. Publish the same consolidated warning through `IEventPublisherService.publishNotification`. Preserve late-client delivery through the notification API's existing latest-event replay behavior so the canvas can display a warning emitted during server startup.
7. Add focused tests for both tools available, Node.js missing, npm missing, both missing, an executable returning a non-zero result, non-serve command exclusion, one-warning-per-startup behavior, CLI warning text, notification payload, late subscriber replay, and warning toast routing.
8. Exercise the check in source/dev mode and in a compiled-binary smoke test with controlled `PATH` fixtures to ensure it checks the user's external Node.js/npm installation rather than Bun or repository-local tooling.

## NOTES

- Node.js and npm are requirements of the widget system only; do not change Vibecanvas's Bun-based build or standalone runtime architecture.
- Check `node` and `npm` independently because one may be installed or reachable without the other.
- Availability is the scope of this task. Do not introduce minimum-version policy unless a separate widget compatibility requirement defines one.
- Avoid shell-based checks so paths and arguments remain portable and do not introduce command-injection behavior.
- Warning delivery must be best-effort and must never become a startup failure.
