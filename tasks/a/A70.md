# A70 - actor resources: implement KvResource
[Overview](../BASED.md)

Implement neutral shared `KvResource` instances with host runtime lifecycle managed by `ActorService`, entries persisted through Vibecanvas's `DbServiceTurso`, definition-level bindings, binding permission reduction, and actor `fx`/`tx` access through the A69 resource gateway.

## Dependency

Blocked by [A69](A69.md). Do not implement a parallel binding model or direct child-process database access to work around missing A69 pieces.

## Context

### Required behavior

- A user can create multiple `KvResource` instances.
- A widget definition declares one or more named `kv` slots.
- A user binds each slot to a concrete `KvResource`.
- Every actor instance of that definition reads/writes the same entries.
- Different resource instances remain isolated even when keys are identical.
- A slot declares A69 permission scope using `read`, `write`, or both.
- `fx.*` functions receive KV reads only when effective scope includes read.
- `tx.*` functions receive reads/writes allowed by definition scope ∩ binding restriction.
- `fn.*` functions receive no resource operations.

Example:

```text
KvResource "CRM Preferences"
  key "selectedPipeline" = "enterprise"
  key "pageSize" = 50

CRM widget definition
  slot "preferences" -> KvResource "CRM Preferences"

CRM actor instance A and B
  preferences.get("pageSize") -> 50
```

### Naming and ownership

Use `KvResource` in actor-service/runtime/SDK naming. Do not call it `DbServiceTurso.keyValue`, `KVService`, `Store`, or a generic `Resource` in public actor code.

`DbServiceTurso` owns the physical Vibecanvas application database connection and low-level persistence methods. `ActorService` owns the runtime `KvResource` abstraction, binding resolution, and actor-facing behavior.

### Explicit non-goals

- Do not reuse the global application `kv` table as-is.
- Do not expose the application `DbServiceTurso` to actors.
- No TTL/expiration in the first version unless it falls out with negligible complexity.
- No distributed cache, cloud KV, or Turso sync.
- No watch/subscription API unless A69 introduced a generic resource invalidation mechanism.
- No durable actor inbox/outbox.
- No hard sandbox guarantees.
- No cross-resource transaction.
- No secret semantics; A71 wraps the shared key-value persistence for `SecretStoreResource`.

## Data model

### Shared resource key-value entry table

Add a resource-scoped key-value table. It should be generic enough for A71's `SecretStoreResource` to reuse at the persistence layer while preserving kind checks in actor service.

Build this table in the next available migration after A69's `008-add-actor-resources.sql` (suggested suffix `add-actor-resource-key-values.sql`). Do not hardcode a number that can collide with A72 if tasks land in a different order:

```sql
CREATE TABLE IF NOT EXISTS `actor_resource_key_values` (
  `resource_id` TEXT NOT NULL
    REFERENCES `actor_resources` (`id`)
    ON UPDATE NO ACTION
    ON DELETE CASCADE,
  `key` TEXT NOT NULL
    CHECK (length(trim(`key`)) > 0),
  `value` JSON NOT NULL,
  `revision` INTEGER NOT NULL DEFAULT 1
    CHECK (`revision` >= 1),
  `created_at` TIMESTAMP NOT NULL DEFAULT (datetime('now')),
  `updated_at` TIMESTAMP NOT NULL DEFAULT (datetime('now')),
  PRIMARY KEY (`resource_id`, `key`)
) STRICT;
--> statement-breakpoint
CREATE TRIGGER IF NOT EXISTS `actor_resource_key_values_updated_at_after_update`
AFTER UPDATE ON `actor_resource_key_values`
FOR EACH ROW
WHEN NEW.`updated_at` = OLD.`updated_at`
BEGIN
  UPDATE `actor_resource_key_values`
  SET `updated_at` = datetime('now')
  WHERE `resource_id` = OLD.`resource_id`
    AND `key` = OLD.`key`;
END;
```

Do not add a separate index: the composite primary key supports exact access and ordered scans beginning with `resource_id`. Do not add a duplicated `kind` column; the referenced catalog row owns kind, and `ActorService` verifies it before accessing entries. The application must validate that `value` is a supported JSON-compatible value before persistence; stored JSON `null` remains valid because it is a JSON value rather than SQL `NULL`.

Important decisions:

- The composite key is mandatory. A key from resource A must never collide with resource B.
- Values use the repository's JSON-compatible model for the first version.
- `undefined`, functions, symbols, `bigint`, cyclic values, database handles, and class instances are rejected before persistence.
- `null` is a valid value and must be distinguishable from a missing key.
- Revision starts at one and increments exactly once for each successful content-changing write.
- Decide whether setting an identical JSON value increments revision. Prefer incrementing for every successful explicit set because deep equality is expensive/ambiguous; document the behavior.
- Deletion removes the row. A returned delete result can report whether an entry existed and its final revision if useful, but do not add tombstones unless required.
- The table may hold rows for `kv` and `secretStore` catalog resources. ActorService validates the resource kind before reaching persistence.

Add indexes only for actual access patterns:

- Composite primary key handles exact get/set/delete.
- `(resource_id, key)` also supports ordered prefix listing.
- Avoid redundant indexes.

Update source and embedded migration registration and compiled binary tests as required.

## Actor-facing interface

The exact call style should align with A69's portal design. Preserve these semantics even if method names differ slightly.

### Read interface available to `fx` and `tx` when effective scope includes read

```text
get(slot, key) -> { value, revision } | null
has(slot, key) -> boolean
list(slot, { prefix?, cursor?, limit? }) -> page of { key, value, revision }
```

### Write interface available only to `tx` when effective scope includes write

```text
set(slot, { key, value }) -> { value, revision }
delete(slot, { key }) -> { deleted: boolean }
compareAndSet(slot, { key, expectedRevision, value })
  -> success with next revision
  -> typed conflict with current revision or missing state
```

Consider an atomic batch only if the Turso database API can implement and test it cleanly in this task. If included, define all-or-nothing behavior and reject cross-resource batches. Do not expose a transaction callback over IPC.

### Why reads return revisions

Multiple actors of one definition run independent queues. Shared storage introduces concurrent read/modify/write behavior that per-actor serialization does not prevent. Revisions and CAS provide explicit lost-update protection without forcing every write through one global actor lock.

Simple `set` remains last-write-wins. Actor authors choose CAS when coordination matters.

### Generic typing

KV values are JSON-compatible but should be call-site typable:

```text
get<TValue>(...)
set<TValue extends TVibecanvasJsonValue>(...)
```

Runtime validation still treats the value as untrusted. TypeScript generics do not validate persisted data.

Do not require schemas in the widget manifest for KV keys or values.

## Plan

### 1. Add persistence schema and models

- Allocate the next available migration number after A69's `008-add-actor-resources.sql`; do not collide with A72 if implementation order differs.
- The entry table has no duplicated resource-kind column: kind remains constrained by A69's `ACTOR_RESOURCE_KIND` domain on `actor_resources`, and `ActorService` enforces `kv` versus `secretStore` before entry access.
- Add model schemas/types for persisted entry rows and actor-service DTOs.
- Add parsing that handles Turso JSON values consistently whether returned as parsed values or strings.
- Add timestamps/revision validation.
- Register the chosen migration in source and embedded/compiled lists and assert all discovered migrations are ordered and synchronized.

### 2. Add low-level DbServiceTurso resource-KV operations

Create focused `fx.*`/`tx.*` persistence helpers under `packages/service-db/src/DbServiceTurso` and expose them through the A69 actor-resource persistence namespace.

Required operations:

- Get exact key by `(resourceId, key)`.
- Has exact key without loading/parsing a large value where practical.
- Bounded ordered list by resource and optional prefix/cursor.
- Upsert value and increment revision atomically.
- Delete key scoped by resource.
- CAS create/update with expected revision semantics.
- Optional count for quotas/diagnostics only if used.

Implementation constraints:

- Always parameterize values and identifiers that can be parameters.
- Never concatenate user key/prefix into SQL.
- Escape prefix wildcard semantics correctly or use range/cursor logic with tests.
- Avoid `UPDATE ... RETURNING` if it risks known native Turso problems in this project.
- CAS must be one conditional write, not read-then-unconditional-write.
- Distinguish not-found from stored `null`.
- Use bounded list defaults and a hard maximum.

### 3. Implement the ActorService-managed KvResource provider

Add `KvResource` in `packages/service-actor`, with dependencies injected through a small persistence portal rather than reaching through unrelated services.

Responsibilities:

- Hold immutable resource metadata/ID or receive it per call.
- Verify catalog kind is exactly `kv`.
- Validate slot binding through A69 manager.
- Validate key length/non-empty rules.
- Validate JSON-compatible values.
- Apply list limit/cursor bounds.
- Map persistence failures to stable resource errors.
- Return serializable DTOs only.
- Never expose `DbServiceTurso`, prepared statements, or raw database rows.

Decide whether one `KvResource` runtime object is cached per resource ID or constructed cheaply per resolved call. Prefer no stateful cache until measurements justify it; the backing DB service already owns the connection.

### 4. Register the provider with ActorService

- Register the `kv` provider in the A69 resource manager.
- Generic resource creation with kind `kv` should require no backing-file provisioning.
- Resource deletion must delete catalog/binding-protected metadata and cascade entry rows only after unbound validation succeeds.
- Actor service stop should not need special KV cleanup beyond existing DB lifecycle.
- Provider health can be `ready` when persistence is available.

### 5. Add IPC operation dispatch

Map operation names to the correct provider methods.

Parent checks before dispatch:

- Slot exists in manifest.
- Slot kind is `kv`.
- Binding exists.
- Bound resource still exists and is kind `kv`.
- Function class permits the operation.
- Effective permission scope permits the operation: definition scope ∩ binding restriction ∩ function-class ceiling.

Child SDK proxy:

- `fx` portal exposes `get`, `has`, `list` only.
- `tx` portal exposes reads plus `set`, `delete`, `compareAndSet` and optional batch.
- `fn` portal contains no KV accessor.

Reject unknown operation names at the host even if child typing normally prevents them.

- Missing keys return `null`, not `undefined`.

### 8. Error contract

Use stable codes at the actor resource boundary:

- `KV_RESOURCE_NOT_BOUND`
- `KV_RESOURCE_UNAVAILABLE`
- `KV_KEY_INVALID`
- `KV_VALUE_INVALID`
- `KV_ENTRY_CONFLICT`
- `KV_LIST_LIMIT_EXCEEDED`
- `KV_WRITE_NOT_ALLOWED`
- `KV_OPERATION_FAILED`

Error details may include slot, key, expected revision, and current revision when safe. Do not include SQL, full DB rows, local paths, or uncontrolled native error objects in guest-facing details.

### 9. Concurrency semantics

Document and test:

- Exact reads observe committed values from the shared application DB connection.
- `set` is last-write-wins.
- CAS with matching revision succeeds once.
- Concurrent CAS requests using the same expected revision produce one success and one conflict.
- Actor-instance queue serialization does not serialize other actor instances.
- Resource deletion cannot race through a valid binding; deletion is blocked while bound.

Do not add global in-memory locks as the primary correctness mechanism. The DB condition is authoritative.

## Acceptance criteria

- Multiple `KvResource` instances can exist with identical keys and isolated values.
- Binding is definition-level and shared by all actor instances of that definition.
- `fx` can read but cannot write through its public/runtime portal.
- `tx` can read, set, delete, and perform CAS.
- Values are JSON-compatible and schema-free.
- Revisions prevent silent read-modify-write races when actor authors use CAS.
- The existing global `DbServiceTurso.keyValue` API/table is not exposed as the actor resource.
- A71 can reuse the resource-scoped key-value persistence without duplicating its table.
- No cloud sync, durable inbox/outbox, sandboxing, or secret encryption is introduced.

## NOTES

A `KvResource` is user actor data even though its entries are physically stored in the Vibecanvas application database. `DbServiceTurso` remains an infrastructure detail.

A71 must reuse the resource-key-value persistence layer but present a separate `SecretStoreResource` interface and enforce `secretStore` resource kind. Do not add secret-specific methods to the public `KvResource` API.

Automatic cross-actor UI refresh is not implied by a successful KV write unless A69 defines a resource invalidation event. Shared persistence correctness is required; reactive invalidation may remain a separately declared transition/refresh behavior.
