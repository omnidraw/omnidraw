# A63 - widgets: split instance delete from definition delete
[Overview](../../BASED.md)

For actor-backed widgets, the header overflow menu now distinguishes deleting one canvas instance from deleting the whole published widget definition.

## Context

Current widget header menu is created in `packages/canvas/src/services/widget/WidgetManagerService.ts` and has minimize/restore, fullscreen/exit fullscreen, and a single `Delete widget` action. For `element.data.type === "widget"`, that label is ambiguous because there is both a canvas instance and a published actor/widget definition registered into the toolbar.

Requested behavior:
- If the selected element is a published actor-backed widget (`element.data.type === "widget"`), the header three-dot menu should show: minimize, fullscreen, delete instance, delete widget.
- `Delete instance` removes only this canvas element/instance. Existing Automerge element delete handling in `apps/cli/src/setup-services.ts` already removes the actor instance when a widget element is deleted.
- `Delete widget` opens a confirmation dialog, then deletes all canvas instances for that widget kind and deletes/unregisters the widget definition so it disappears from the toolbar.

## Plan

### 1. Clarify header menu actions
- In `WidgetManagerService`, branch the menu by `widgetData.type`.
- Keep existing behavior for `ui-widget` unless product decides otherwise.
- For `widget`, rename the current remove-selected-node action to `Delete instance`.
- Keep minimize/restore and fullscreen/exit fullscreen actions first.

### 2. Add definition delete confirmation UI
- Add a canvas-level confirm dialog or reuse the existing Solid/Kobalte dialog pattern.
- Trigger it from the widget header menu `Delete widget` action.
- Dialog copy must make clear that all instances of this widget kind and the toolbar definition will be deleted.

### 3. Add server/API support for definition deletion
- `packages/api-actors/src/contract.ts` currently exposes `definitions.list` and `definitions.get`, but no delete endpoint.
- Add an ORPC definition delete route and handler.
- Actor service/supervisor likely needs a method that removes a definition cleanly, including active actor instances/connections and the DB definition row.
- Decide whether deleting the definition should also remove widget files under the configured widgets folder, or only DB/runtime registration.

### 4. Remove all canvas instances for the widget kind
- Delete all elements where `element.data.type === "widget"` and `element.data.kind === definitionName` from the current canvas document.
- Ensure actor instances are removed. Existing `onElementDelete` path removes each widget actor instance by element id.
- Record history only if this can be modeled safely; otherwise treat definition deletion as non-undoable and document it in the dialog.

### 5. Unregister deleted widget from canvas runtime and toolbar
- Add a `WidgetManagerService` path to unregister a widget kind from `ToolService` and `ElementService`.
- Update `Widget.plugin.ts` because `registerPublishedWidgets()` only registers/updates current definitions; it does not unregister definitions missing after a later list call.
- Ensure toolbar refreshes after `ToolService.unregisterTool`.

## NOTES

Current `Delete widget` in `WidgetManagerService` calls `#removeWidgetNode`, which removes only one canvas node/element and records undo history. That behavior should become `Delete instance` for actor-backed widgets.

`DbServiceTurso` already has `actor.deleteDefinition(name)`, but the actors ORPC contract does not expose a definition delete route yet. `ActorService`/`ActorSupervisor` also do not currently expose a delete-definition method.

Implementation deletes published widget files from the configured widget folder through `ActorSupervisor.deleteDefinition()`. Deleting only the DB row is not enough because actor reload would rediscover the definition from disk.
