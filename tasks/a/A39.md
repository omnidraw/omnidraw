# A39 - canvas: non-sandboxed filesystem IDE plugin
[Overview](../../BASED.md)

Create a first-party canvas plugin named `filesystem` that renders a trusted DOM widget with ArrowJS and CodeMirror, not Arrow sandbox.

## Context
- Target plugin folder: `packages/canvas/src/plugins/filesystem/`.
- Runtime plugin list to update: `packages/canvas/src/runtime.ts`.
- Plugin barrel to update: `packages/canvas/src/plugins/index.ts`.
- Existing canvas plugin examples live in `packages/canvas/src/plugins/*/*.plugin.ts`.
- Existing hosted widget/DOM portal behavior lives in `packages/canvas/src/services/widget/`.
- Current legacy filetree/editor references are under canvas, not frontend:
  - `packages/canvas/src/components/filetree/FiletreeWidget.tsx`
  - `packages/canvas/src/components/filetree/createFiletreeContextLogic.ts`
  - `packages/canvas/src/components/file/viewers/CodeEditor.tsx`
  - `packages/canvas/src/components/file/FileWidget.tsx`
- Requested legacy path `apps/frontend/src/components/` currently only has generic UI/path picker files; no filetree/codeeditor implementation was found there.
- Keep `packages/widget-filesystem` as a sandbox-package reference for later, but do not base this plugin on it now.

Problem:
- Arrow sandbox cannot host full browser APIs like CodeMirror `EditorView` because it has no real DOM refs, `document`, layout, focus, or mutation APIs.
- A filesystem IDE widget needs real browser DOM APIs, so it must be trusted/non-sandboxed.

Goal:
- Add a `filesystem` canvas plugin with its own tool.
- Tool creates one IDE-like canvas widget.
- Widget layout mimics an IDE:
  - left: file tree
  - right: CodeMirror editor
- Editor pane is always visible, even when no file is selected.
- When no file is selected, editor is empty but mounted.
- Filetree supports folder open/close.
- Double click opens files.
- Multiple opened files appear as tabs like VS Code.
- There is always a root/cwd path.
- New filesystem widget must select a root path/cwd through a small dialog or similar root selection UX.

## Plan

### 1. Plugin shell
- Create `packages/canvas/src/plugins/filesystem/Filesystem.plugin.ts`.
- Export it from `packages/canvas/src/plugins/index.ts`.
- Include `createFilesystemPlugin()` in `packages/canvas/src/runtime.ts` plugin list.
- Register a tool named `filesystem` through `ToolService`.
- Tool should create the filesystem IDE widget as one canvas element/window.

### 2. Trusted DOM rendering
- Do not use `@arrow-js/sandbox` for this plugin.
- Use normal host-side `@arrow-js/core` templates/components mounted into a real DOM portal.
- Use CodeMirror `EditorView` in the editor pane because it requires a real `HTMLElement` parent.
- Ensure cleanup destroys CodeMirror views and unmounts Arrow DOM when widget is removed.

### 3. Widget model
- Persist enough widget data to restore:
  - root path/cwd
  - widget geometry
  - selected file path if desired
  - open tab paths if desired
- Keep initial version simple: root path and geometry are required; tabs may be local state first if persistence is too much.
- Avoid changing `packages/widget-filesystem`; it remains a reference for sandboxable widgets later.

### 4. Root path selection
- On creating a new filesystem widget, prompt/select root path/cwd.
- Reuse ideas from `PathPickerDialog` if practical, but avoid pulling Solid component internals into Arrow directly without thought.
- If dialog reuse is awkward, create a small plugin-local path picker shell first.
- Root path must exist before first filetree load.

### 5. Filetree behavior
- Load root children with filesystem API.
- Keep folder open/closed state locally.
- Single click selects tree row and toggles folder open/closed for folders.
- Double click file opens or focuses a tab.
- Support lazy loading folders like `createFiletreeContextLogic.ts`.
- Later: add watch/refresh/move/drag-drop after first working IDE widget.

### 6. Editor behavior
- Use CodeMirror setup from `CodeEditor.tsx` as reference:
  - `EditorState`
  - `EditorView`
  - keymaps/history/search/autocomplete where needed
  - theme aligned with canvas theme tokens
  - cleanup via `view.destroy()`
- Empty editor exists before file selection.
- Opening a file loads content into an editor tab.
- Multiple file tabs can be opened.
- Clicking a tab focuses the corresponding editor document.
- Saving can be deferred to a later lane if read-only first version is faster.

### 7. Event routing with canvas
- Because this is non-sandboxed DOM content, pointer events must follow the active-widget rules learned from widget portal work.
- Default should not block canvas pan/zoom unless the filesystem widget is active/focused.
- When active, filetree/editor should receive pointer/keyboard events.
- Selection/transform state must remain distinct from active DOM interaction.

### 8. Tests/checks
- Add focused tests if the plugin has pure helpers.
- Manual test path:
  - select filesystem tool
  - choose root/cwd
  - widget appears on canvas
  - pan/zoom still works when inactive
  - activate widget and scroll filetree/editor
  - open/close folders
  - double click file opens tab
  - editor remains visible when no tab/file selected
  - plugin is loaded from `runtime.ts`

## NOTES
- Important learning: Arrow sandbox is still useful for safe widgets that only need declarative DOM/SVG, state, timers, fetch, and host-bridge calls.
- Important learning: CodeMirror `EditorView`, Canvas API, WebGPU, and similar browser APIs need real DOM/browser globals; they should use trusted/non-sandboxed widget mode.
- `packages/widget-filesystem` should remain a reference for the later sandboxed external package shape: `dist/main.js` + `dist/main.css` bundled by esbuild.
- This task is for first-party trusted canvas plugin work, not the external sandbox package lane.
- Avoid implementing an iframe. The stated direction is non-sandboxed ArrowJS in the canvas plugin.
- Keep implementation local to `plugins/filesystem/` where possible. Use sibling `fn.*.ts`, `fx.*.ts`, `tx.*.ts`, `typed.ts`, and CSS only when they clarify the plugin.
