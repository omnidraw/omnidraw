# E32 - Capsule migration: compiled, actor-native widget sandbox

[Overview](../BASED.md)

Investigate whether the Capsule prototype can replace the current ArrowJS widget runtime, identify the gaps between the prototype and the repository, and define the build, actor, resource, type, lifecycle, security, and migration requirements.

This exploration is complete. Capsule implementation remains future work and is split into explicit gates below.

## Executive conclusion

Capsule is not a drop-in replacement for `@arrow-js/sandbox`. It is a greenfield runtime design, and no Capsule implementation or package currently exists in this repository. The difficult part is not framework bundling by itself; it is proving that a synchronous QuickJS-to-real-DOM membrane can preserve browser semantics, remain interruptible, and stay inside a defensible security boundary.

The migration is still a reasonable direction because the current Arrow architecture cannot support React, CodeMirror, or WebGPU without replacing its compiler, module system, DOM protocol, event bridge, and lifecycle model. That is already most of a new runtime.

The recommended direction is:

1. Treat Capsule's synchronous DOM/event model as a falsifiable architecture hypothesis. Do not begin the broad WebIDL surface until the Phase 0 browser experiments pass.
2. Add a trusted build service. A widget definition must produce separate, immutable UI and actor artifacts from one pinned draft revision; neither browser mounts nor actor processes should execute raw TypeScript source.
3. Make the widget's owning actor a built-in, versioned Capsule capability with schema-derived types, revision-aware synchronization, bounded queues, explicit acknowledgement semantics, and host-controlled authority.
4. Keep actor KV, database, and secret resources behind the backend actor by default. "Typed actor resources" should mean generated resource contracts and actor-side operations, not automatic browser authority.
5. Integrate through a runtime-neutral widget handle so the existing canvas portal placement code can survive. Run Arrow and Capsule side by side until published definitions have been rebuilt and rollback is proven.
6. Do not claim hostile-code isolation until both the UI runtime and the backend actor trust model are resolved. The existing actor process can bypass its resource portals through ordinary Bun/process/fs/network access.

## Current end-to-end widget path

The repository currently has no widget build artifact boundary:

1. `tx.scaffold.ts` creates an Arrow `widget/main.ts`, a CSS file, an actor, a `package.json`, and a TypeScript configuration. The package declares Arrow and the Vibecanvas SDK, but the configuration is authoring support rather than an emitting widget build.
2. `tx.validate-widget-files.ts` creates a temporary `tsc --noEmit` configuration whose include covers `actor/**/*.ts`. Widget TypeScript is neither semantically checked nor bundled by this validation step.
3. Preview validation reads the draft widget files into a source map. A draft can become preview-ready without proving that it has a valid, runnable Arrow entry.
4. `tx.publish-widget-draft.ts` recursively copies the draft source tree into the published definition directory. It does not produce a revisioned UI or actor artifact.
5. `tx.actor-definitions.ts` recursively reads every widget file as UTF-8 text. `api.def-get.ts` returns the files as `{ path, content }[]` under `widgetCode`.
6. `Widget.plugin.ts` refetches definitions, reconstructs a source map, assumes `main.ts`/`main.css`, and registers an `arrowjs` sandbox config. The entry contract is currently hidden behind a TypeScript suppression.
7. `attach-dom-portal.ts` creates and positions the canvas-owned DOM overlay. `mount-arrow-sandbox.ts` rewrites SDK import strings, injects an actor bridge, and asks Arrow to compile and start a new QuickJS runtime for every mounted element.
8. The guest polls a custom actor event queue. Collapsing the widget changes CSS display, but the VM, timers, fetches, and actor polling remain alive.
9. The backend actor child writes an SDK shim into the definition and loads the actor function path from raw TypeScript with `require()`. Actor execution also lacks an immutable build target.

Consequences:

- identical source is repeatedly read, transported, compiled, and instantiated;
- non-text assets are not a supported delivery primitive;
- there is no artifact integrity, runtime ABI, dependency lock, source map, framework metadata, capability declaration, or cache key;
- preview and publication can validate different things from what the browser eventually executes;
- the UI and actor can execute mutable source rather than a coherent, pinned definition revision;
- a widget definition update causes the plugin to list and refetch every definition, producing an N+1 reload path;
- an installed or compiled Vibecanvas binary still depends on runtime behavior such as `bun x tsc`, rather than carrying a defined widget-builder toolchain.

## What can survive the migration

The following current pieces are useful boundaries rather than throwaway code:

- the canvas-owned overlay root and geometry/focus/fullscreen handling in `attach-dom-portal.ts`;
- the definition manifest and runtime JSON-schema validation, after adding a versioned `ui`/artifact section;
- the actor supervisor and resource manager's host-side lookup of requirements, bindings, and scopes, subject to the actor trust fixes below;
- the draft preview and publish workflow as orchestration points for the new builder;
- the canvas plugin as definition discovery and registration, once it receives compact artifact descriptors;
- actor creation tied to a canvas element and the host's knowledge of the owning actor instance.

The following pieces should be replaced or retained only as a legacy path:

- browser-side TypeScript transpilation and virtual source-file maps;
- raw `widgetCode` transport;
- string-based rewriting of `@vibecanvas/sdk/widget` imports;
- Arrow's serialized template/event renderer for Capsule widgets;
- the injected, duplicate actor bootstrap and long-poll queue;
- the global unscoped event fan-out followed by client-side actor routing;
- hard-coded `sandbox.arrowjs` and `main.ts`/`main.css` assumptions.

## P0 blockers and stop conditions

### 1. Synchronous real-DOM architecture is unproven

Arrow's asynchronous serialized renderer cannot become Capsule's synchronous DOM membrane by filling in missing methods. Capsule must first prove all of these together in a real browser:

- a real event enters QuickJS synchronously and guest `preventDefault()` changes the native event before the listener returns;
- propagation and `stopImmediatePropagation()` behave correctly across host and guest listeners;
- nested events caused by `focus()`, `click()`, selection changes, or custom host behavior are safe under QuickJS/WASM reentrancy;
- stable guest wrappers preserve host node identity without allowing cross-root access or stale-handle reuse;
- native contenteditable changes reach a guest `MutationObserver` in the expected microtask order;
- selection/range geometry and hit testing remain correct under canvas transforms;
- an infinite loop is interrupted during boot, an event, a timer, a microtask, an observer delivery, and a capability completion;
- teardown returns all nodes, handles, listeners, observers, timers, promise jobs, and host callbacks to zero.

Failure to achieve safe reentrancy, native cancellation, or bounded interruption latency is a stop condition. A deliberately constrained browser document/iframe could be investigated as an alternate runtime, but that would reverse Capsule's explicit no-iframe constraint rather than qualify as the same Capsule architecture.

QuickJS interruption only counts guest instructions. Every synchronous host bridge operation must also be bounded; an unbounded host function cannot be preempted by the guest interrupt handler.

### 2. There is no build, artifact, or definition revision model

Capsule cannot mount source trees. It needs an immutable artifact identity and the server/database currently has nowhere to record it. A safe publication must build from one pinned draft revision, validate resource bindings, and atomically move the published pointer only after every output succeeds.

The database needs definition revisions that separately identify at least:

- UI artifact hash;
- actor artifact/source hash;
- actor contract hash;
- normalized manifest hash;
- builder/toolchain version;
- compatibility range and activation status.

Every actor instance must pin the actor-definition revision it is running. UI-only publication must not restart or reset backend actors. The current supervisor publication path can reset actor state to initial values; compatible upgrades must preserve data, and incompatible changes must provide an explicit migration while retaining the last good revision for rollback.

Mounted widget instances also need an explicit UI-artifact pin. Current definition refresh replaces registry/tool metadata but does not remount existing portals, which retain their captured source/config. Capsule publication must define whether a live instance stays pinned, performs a state-preserving remount, or waits for user action; a failed upgrade returns to the previous artifact without changing actor state.

### 3. Capsule has no actor protocol

The prototype contains no definition of actor ownership, snapshot revisions, actor status, output messages, acknowledgements, reconnect, resource authority, or UI/actor lifecycle interaction. A generic capability hook is not enough because these semantics determine data loss and security behavior.

The owning actor handle must be minted by the host from the mounted canvas element. Guest code must never select an arbitrary definition, instance, element, resource ID, provider, path, or account scope.

The current snapshot/send contracts accept caller-supplied instance or element identifiers, and the event endpoint is globally fanned out before the client routes events. Those APIs must not be exposed unchanged as a guest capability; the server transport must scope the handle and stream to the authorized canvas/instance.

### 4. Actor resource safety is not the same as UI sandbox safety

Current actor resources are authorized by the intersection of manifest scope, concrete host binding, and the `fn`/`fx`/`tx` function-class ceiling. That is a valuable server-side model, but it is not a browser-Capsule authority model.

The default rule should be:

- browser Capsule -> typed actor message;
- backend actor `fn`/`fx`/`tx` -> bound actor resource;
- resource result -> runtime-validated actor state/output -> browser Capsule.

In particular, the browser Capsule receives no direct secret capability. This alone is not a non-egress guarantee: current actor code receives plaintext and can copy it into state or output. Preventing that requires trusted actors, non-revealing secret operations, or a separate information-flow/egress policy.

If direct UI resource access is a hard product requirement, it is blocked on a separate design that introduces a `ui` authority class, instance-bound opaque handles, operation allowlists, redaction, quotas, revocation, audit, server authorization, and an explicit secret policy. Reusing actor management APIs or exposing resource IDs is not acceptable.

### 5. Backend actors are not an untrusted-code sandbox

Actor functions run as raw TypeScript in a Bun child process. The child inherits ordinary process capabilities, including environment, filesystem, and network access, and actor execution has no general CPU deadline. Resource portals therefore constrain cooperative code but do not prevent malicious code from bypassing them.

There is also an authority-sequencing concern: the host advances the current function class after a child-authored `next` IPC message. Because raw actor code can access `process.send`, the child can attempt to forge phase/control messages. Security-relevant execution phase must be held as unforgeable host state, not accepted from guest-authored IPC.

Before calling actor resources a security boundary, choose and document one model:

- actors are trusted application code, and resource scopes are correctness/least-privilege conventions; or
- actors are untrusted, in which case they need OS sandboxing or an interruptible headless capability runtime with CPU, memory, env, filesystem, network, and IPC restrictions.

This decision is independent from the browser Capsule but mandatory for an end-to-end untrusted widget claim.

### 6. Current message and event semantics cannot support freeze/park

Current snapshot events include an in-memory revision, but the widget-side snapshot reducer discards it, ignores non-system output events, and has no replay cursor. The counter restarts with each `Actor` and is not persisted. `sendMessage` returns the same opaque message-ID shape when an input is queued and when it is synchronously rejected/dropped, so the caller cannot distinguish acceptance and receives no processing result. Host and guest queues are unbounded.

A frozen or parked UI can therefore miss changes without detecting the gap. The new protocol needs either a persisted monotonic revision or a compound `(actorEpoch, revision)` cursor, gap detection, bounded/coalesced delivery, and distinct `accepted`, `rejected`, and optionally `processed` results. Resume must use an atomic snapshot-plus-cursor subscription or subscribe-first buffering with revision deduplication so events cannot be lost between snapshot and subscription. The server must validate input payloads and every actor data update against the canonical schemas at runtime, not rely on generated TypeScript types; current `setData` does not enforce `dataSchema`.

### 7. Main-thread security and performance remain hypotheses

QuickJS protects the browser's JavaScript realm only if the bridge is correct; it is not a process, renderer, or OS security boundary. Capsule's root containment, handle ownership/generation checks, URL/CSS/tag/attribute policy, custom-element denial, network policy, message limits, and WebGPU capability all require independent adversarial review.

The one-runtime-per-Capsule memory and startup costs, synchronous membrane call overhead, freeze/park retention, and editor/GPU frame budgets have not been measured. Do not lock a product scale target or 1.0 timeline before those numbers exist.

## Required widget build and artifact system

### Build inputs

A build must consume an immutable snapshot containing:

- normalized widget/actor manifest and schema files;
- widget and actor source, CSS, static/binary assets, and shaders within an allowed root;
- exact dependency lock and approved registry/source policy;
- selected Capsule ABI, DOM profile, framework plugins, and browser target;
- requested capabilities and budgets;
- generated actor contract input.

Reject absolute paths, `..` escapes, all symlinks, undeclared files, Node built-ins, native modules, unresolved dynamic imports, and dependencies outside the allowed graph. Snapshot reads and hashing must use no-follow, race-safe semantics so a mutable symlink target cannot change between revision hashing and copying. Guest workers and WebAssembly execution are initially rejected unless later profiles define their APIs, isolation, budgets, and lifecycle explicitly.

### Build execution

The builder is trusted infrastructure processing hostile input. It must:

- run outside the browser and outside the canvas package;
- execute in an OS-enforced sandbox/container or equivalent security boundary with read-only inputs, an isolated output directory, no network, and CPU, memory, process, file-count, byte, and time limits;
- disable lifecycle/install scripts and arbitrary guest bundler plugins/config execution;
- use a pinned TypeScript/bundler/plugin toolchain with no implicit network during a reproducible build;
- type-check widget and actor code against generated declarations;
- support an explicit matrix for TS/JS/JSX, React, Vue SFCs, CSS, assets, and shaders;
- produce deterministic bytes and diagnostics from identical inputs;
- preserve useful source maps without exposing server filesystem paths.

The installed Vibecanvas binary must have a defined way to perform this work. Either embed/ship the builder toolchain, run a managed builder sidecar, or explicitly declare an external prerequisite. Runtime `bun x` downloads and assumptions about a system Bun/npm installation are not a production artifact strategy.

### Artifact outputs

The backend-neutral artifact envelope should contain or reference:

- a versioned execution-target payload, such as content-addressed QuickJS-compatible ESM only after Gate 0A accepts that backend;
- extracted/parsed CSS and a binary asset table;
- source maps and build diagnostics;
- artifact ID, byte hash, integrity hash, optional signature, and builder version;
- dependency graph/lock digest;
- requested/required capabilities and CPU/memory/DOM/message/frame/lifecycle budget defaults or maxima;
- Capsule ABI/protocol version plus execution-backend and DOM/framework profile;
- actor contract hash and generated declaration version;
- entry module and supported parkability/serialization metadata.

The artifact declares requests and maxima; it never grants authority. Effective capabilities and budgets are computed at mount/deployment time from the artifact request, tenant/user decision, and host policy, then recorded as instance/session policy rather than immutable artifact metadata.

Source may be retained separately for authoring and debugging, but the browser execution API should receive an artifact descriptor/bytes rather than recursive source text.

### Preview and publish semantics

- Preview and publish use the same builder and artifact verifier.
- A build is keyed by the complete draft revision and cached by content hash.
- Preview executes the exact artifact bytes that publication would activate.
- Publication durably stages source, UI artifact, actor artifact, contract, and resource-binding plan, then changes one transactional database published-revision pointer/binding set.
- Actor/resource/process reconciliation after pointer activation is idempotent and resumable; failures use durable transition state and compensating rollback because filesystem/object storage, database rows, and live processes cannot share one transaction.
- Build, binding, schema, or migration failure leaves the previous definition active.
- UI and actor hashes are independent so a UI-only change preserves actor processes and state.
- Running instances lease referenced artifacts/revisions so cleanup cannot remove active rollback material.
- The definitions list returns runtime/profile/hash/tool metadata, avoiding a full definition refetch after every update.

The builder must emit both an ahead-of-time UI artifact and a separate headless actor artifact. They remain distinct targets because the UI and actor run under different authorities, and their hashes allow UI-only updates without actor restart. Actor startup must load the verified artifact instead of raw TypeScript and must not write runtime SDK shims into the published definition.

## First-class actor integration

### Normative ownership and lifecycle

Capsule should provide a versioned Vibecanvas actor module/capability rather than inject global functions or rewrite import strings. The public import can remain `@vibecanvas/sdk/widget` for migration compatibility, but the builder must resolve it module-aware to the generated Capsule adapter. It is first class when:

- the builder resolves it as an official virtual module;
- the host binds it to exactly the mounted element's owning actor;
- its wire protocol, errors, compatibility, and teardown are versioned;
- its types are generated from the same schemas used for runtime validation;
- its queues and payloads are budgeted;
- its behavior under active, frozen, parked, resumed, and destroyed UI states is specified.

Freezing or parking a Capsule detaches/coalesces its UI subscription; it does not silently stop, restart, or delete the backend actor. Resume uses an atomic snapshot-plus-cursor subscription or subscribe-first buffer/deduplicate sequence; a snapshot followed by a separate subscription is racy. Destroy cancels guest waits and subscriptions but only an explicit canvas/actor operation may destroy the actor.

If the actor instance is created after the UI mounts, the host performs one atomic late-bind transition that obtains the authoritative snapshot/cursor and establishes the subscription. Guest polling and a snapshot-only fallback are not sufficient.

### Guest-facing contract

The exact syntax can change, but the semantic surface needs:

- reactive `{ actorEpoch, revision, status, state, context, error }` snapshot data;
- schema-typed input messages;
- schema-typed actor outputs with a stated durable or ephemeral delivery policy;
- `send` results that distinguish transport acceptance, validation rejection, and optional processing completion;
- cursor/revision-aware subscribe and resync;
- cancellation and disposal;
- bounded payload depth/bytes, message rate, in-flight sends, and queued events;
- structured actor, schema, resource, transport, and lifecycle errors.

The current event reducer must no longer drop actor outputs or revisions, and actor transport failures must not be mislabeled as guest runtime failures.

### Generated type contract

One canonical normalized manifest/schema model should generate both `.d.ts` authoring support and runtime validators for:

- actor state-name union;
- actor data derived from `dataSchema` and the corresponding typed widget `context` shape;
- input message name-to-payload map from `inputMsgSchema`;
- output message name-to-payload map from `outputMsgSchema`;
- resource slot name, kind, requiredness, and permitted-scope map;
- named database operation parameter and result types;
- actor protocol and artifact compatibility versions.

New Capsule definitions require canonical data, input-message, and output-message schemas. Only legacy definitions may fall back to `unknown`, never `any`. The build fails when generated declarations, runtime schemas, actor artifact, and UI artifact disagree. The actor-contract digest is embedded in both artifacts and checked when the host binds them.

The current SDK duplicates actor/resource types across the SDK, service, IPC client, and injected widget bridge. It also declares an optional actor-function `args.context` while the runtime calls functions with only `{ msg, data }`. Move the wire contract into one versioned shared package, keep environment-specific adapters at the edges, and add runtime/type conformance fixtures so the declaration cannot outrun the actual call shape.

### Actor resource contract

Resource contracts and generated resource types are actor-side by default; they do not grant browser access. Resource readiness reaches the UI only through deliberately modeled actor state/output. Concrete resource IDs, provider handles, secrets, paths, and account scopes remain host-only.

Actor-side generated types should remove plain string slots and unsafe caller-selected result types. For example, a DB named operation needs declared parameter and result schemas; a KV slot needs an explicit value codec/schema if stronger than `unknown`; a secret slot exposes an actor-side secret operation but no direct browser API. Actor state/output still requires an explicit anti-egress policy if actors are not trusted.

## State ownership

Capsule's proposed durable store overlaps with two existing persistence systems. Use one owner per category:

- Automerge owns canvas document/layout data and deliberately shared widget UI properties;
- the backend actor owns durable business state and resource-backed state;
- Capsule local state owns ephemeral view state, caches, and explicitly scoped user preferences.

Do not silently journal actor context into Capsule storage. Cross-owner data must move through typed commands/events and have an explicit conflict/migration rule.

## Runtime integration boundary

Keep the low-level Capsule library framework-neutral. It should not import canvas, actor services, Automerge, or Vibecanvas APIs. Extend the prototype package layout with a Vibecanvas-owned adapter for actor capability/type generation and a canvas integration layer.

Suggested dependency direction:

1. Capsule protocol/VM/DOM host/DOM guest/policy/build/testkit remain generic.
2. A Vibecanvas Capsule adapter depends on the generic protocol plus the versioned actor contract.
3. The trusted draft/publish builder depends on Capsule build packages and generated actor declarations.
4. Canvas consumes only verified artifact descriptors, a host capability adapter, and a runtime-neutral handle.
5. Service-actor continues to own actor execution and concrete resources.

The canvas-facing handle should support at least:

- mount and destroy;
- size/rect/scale changes;
- focus and pointer-capture transitions;
- active/hidden/offscreen/collapsed visibility;
- freeze, park, resume, and authoritative actor resync;
- structured build/load/policy/actor/guest/host error reporting;
- budget and leak counters for diagnostics.

`WidgetManagerService` should become registry, artifact-cache, actor-transport, and lifecycle orchestration. `Widget.plugin.ts` should remain discovery/registration. `attach-dom-portal.ts` should continue to own canvas positioning while forwarding state to the runtime handle.

## Bottlenecks and required improvements

| Current bottleneck | Required improvement |
| --- | --- |
| Every definition update lists and refetches every definition. | Publish revisioned summaries and invalidate/fetch only the changed artifact hash. |
| Definition refresh replaces registry metadata but leaves mounted portals on captured old source/config without an explicit pin. | Pin every instance to an artifact hash and define stay/remount/rollback behavior. |
| Every fetch recursively reads and transports raw source. | Store binary-safe, content-addressed artifacts with size/file limits and cache headers. |
| Every element recompiles identical TypeScript. | Build once per revision and cache verified modules per artifact hash. |
| One QuickJS runtime is immediately mounted per created/hydrated widget element, even when offscreen or collapsed. | Central scheduler with admission, freeze, park, distance/visibility priority, and measured memory budgets. |
| Collapse only hides DOM. | Freeze timers/jobs/subscriptions or park serialized local UI state; resnapshot the actor on resume. |
| Global actor event stream fans out all actors. | Authorized per-canvas/per-instance multiplexing with cursors, gap detection, and bounded queues. |
| Actor/widget inbox and polling queues are unbounded. | Enforce bytes, depth, rates, concurrency, queue caps, coalescing, cancellation, and backpressure. |
| Actor binding uses short retries and can miss a late instance/subscription. | Mount with a host-provided owning-actor handle or support a cancellable late-bind transition followed by an authoritative snapshot. |
| Actor snapshot persistence queues every update. | Coalesce latest revision safely and persist definition revision plus a restart-safe epoch/revision cursor. |
| One Bun process is spawned per actor and bulk reload/startup is serial. | Define a process/memory budget, bounded-concurrency bulk startup, or an isolated worker/VM pool. |
| Resource lookup rereads bindings/resources on calls. | Add revision-aware caches with explicit invalidation without weakening authorization. |
| Synchronous DOM membrane crosses WASM on fine-grained operations. | Benchmark representative React/CodeMirror traces; batch only operations whose observable browser semantics permit it. |

## Security requirements before framework compatibility

The security kernel comes before React/Vue convenience layers:

- owner, generation, type, and lifetime checks for every opaque handle;
- root-containment verification after every topology mutation;
- deny scripts, frames, navigation, custom-element construction, top-layer APIs, fullscreen, pointer lock, and uncontrolled portals unless explicitly modeled;
- parse and policy-check CSS, selectors, URL-bearing properties/attributes, fonts, cursors, overlays, and `:host` behavior;
- deny network unless artifact declaration, user/host grant, and server policy all agree;
- cap DOM nodes, listeners, observers, handles, timers, jobs, payload size/depth, call rate, in-flight calls, assets, memory, CPU, and frames;
- generation-check WebGPU and other host objects; handle device loss, visibility throttling, cleanup, and buffer-copy costs;
- never expose raw host-realm objects or host prototype chains, custom-element constructors, resource-management APIs, or ambient browser globals; retain only reviewed guest-side prototype facades required by the DOM API;
- audit build-time code execution separately from runtime code execution;
- fuzz malformed handles, bridge messages, DOM topology, CSS/URLs, lifecycle transitions, and teardown.

Current Arrow behavior must not become the compatibility baseline: broad HTTPS fetch, arbitrary renderer tags/attributes, verbatim CSS, an open shadow root, unbounded bridge calls, and absent CPU interruption are migration risks to remove.

## Migration gates

### Gate 0A - architecture falsification

Build the smallest standalone real-browser Capsule spike. It must pass synchronous cancellation, nested-event reentrancy, node identity/root containment, contenteditable/MutationObserver order, selection/range geometry, comprehensive interruption, and zero-leak teardown. Finish with a pinned CodeMirror fixture that accepts one character with correct selection and `beforeinput` behavior.

Exit: every invariant has an automated Chromium test and recorded latency/memory measurements. Reentrancy or interruption failure stops the current architecture.

### Gate 0B - artifact skeleton

In parallel, define the normalized definition manifest, backend-neutral artifact envelope, UI/actor target payloads, builder protocol, content hash, dependency lock, capability/budget requests, actor-contract hash, diagnostics, and storage/revision rows. Build a static TypeScript widget plus actor in an OS-enforced build sandbox and prove preview/publish byte identity.

Exit: no raw TypeScript execution in either browser or actor process, reproducible hashes, tamper rejection, rollback-safe activation, and a builder path that works in the distributed Vibecanvas product.

### Gate 1 - security and DOM kernel

Implement the handle table, topology policy, scheduler/interrupt coverage, structured clone limits, lifecycle cleanup, closed shadow root, CSS/URL policy, and the minimal DOM needed by the default widget/store.

Exit: conformance, adversarial, fuzz, and leak suites pass before adding broad WebIDL.

### Gate 2 - actor-native vertical slice

Add the official actor virtual module, contract generation, host-minted owning-instance handle, typed input/output, epoch/revision-aware snapshot/subscription, bounded delivery, atomic late binding, race-free freeze/resume resync, and safe structured resource errors. Use a fixture actor with KV and DB slots; keep direct UI resource calls denied.

Exit: owner auto-binding, cross-instance denial, type fixtures, ack/reject behavior, reconnect/gap recovery, UI teardown, actor survival during UI park, and resource migration/restart tests pass.

### Gate 3 - compatibility profiles

Advance in small profiles: static DOM, default UI/store, Vue, React, editing primitives, CodeMirror, then WebGPU. Each profile declares its WebIDL/capability surface and exact dependency versions. Do not enable a broad browser namespace merely to make a framework test pass.

Exit: differential native-vs-Capsule behavior, accessibility, IME/composition, selection/clipboard/focus, performance, device-loss, and cleanup tests pass for the profile.

### Gate 4 - canvas dual runtime

Replace the hard-coded Arrow config with a discriminated artifact/runtime descriptor. Add a shared Capsule host/scheduler and one handle per element. Forward geometry, scale, focus, composition, visibility, collapse, distance, and lifecycle signals. Route draft previews and published widgets through the same artifact contract.

Exit: Capsule is feature-flagged per definition, Arrow remains a rollback path, and a failed Capsule mount does not corrupt actor or canvas state.

### Gate 5 - published-definition migration

Rebuild Capsule-capable definitions, retain a deliberate `arrow-v1` compatibility target for legacy definitions, and record the chosen runtime in each immutable revision. Pin every mounted instance to an artifact hash and apply an explicit stay/remount/rollback policy for live upgrades. Do not silently interpret old Arrow templates as ordinary DOM apps.

Exit: all supported published definitions have artifacts, rollback material is retained, UI-only updates preserve actor state, and telemetry shows stable error/performance budgets.

### Gate 6 - cutover and subtraction

Only after the migration gate succeeds, remove raw `widgetCode`, browser compiler paths, SDK string rewriting, duplicate actor bootstrap, global unscoped event routing, and Arrow dependencies. Keep an explicit export/upgrade story for definitions that cannot migrate.

## NOTES

Proceed with Capsule as a gated research and implementation program, not as a committed 1.0 replacement timeline. The immediate investment should be Gate 0A and Gate 0B. Both create reusable evidence: the artifact system remains useful if the execution model changes, while the browser spike can reject the riskiest architectural assumption before broad DOM work.

The repository boundary is resolved: Capsule is a separate consumer-neutral repository. Omnidraw owns the host adapter, SDK business surface, actor/resource authority, build orchestration, artifact publication, and canvas integration. See `docs/internal/llm.capsule.md` and `docs/internal/llm.widget-system.md`.

The strongest reusable boundary is the existing canvas DOM portal. The largest required changes are before it (build/publication/distribution) and inside it (runtime/DOM/security/actor bridge), not in canvas geometry itself.

The term `resource` must stay qualified in future work:

- Capsule capabilities are browser-host permissions such as DOM, network, clipboard, timers, and WebGPU.
- Actor resources are server-bound KV, database, secret, and future resource slots governed by actor function class and manifest scope.

Conflating these two models would either leak server authority into an untrusted browser or make the generated type surface promise access the runtime must deny.
