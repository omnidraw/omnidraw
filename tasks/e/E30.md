# E30 - actor resources: evaluate independent files for KV and secret stores
[Overview](../BASED.md)

Decision: move both `KvResource` and `SecretStoreResource` to independent host-managed database files, with the control database retaining only catalog and binding state.

## Context

The current resource model provides logical isolation through `actor_resource_key_values` keyed by `(resource_id, key)`. `KvResource` and `SecretStoreResource` share this table in `DbServiceTurso`. A `DbResource` instead owns a separate physical Turso database at `<dataRoot>/actor-resources/db/<resource-id>/data.db`.

Independent files could improve failure isolation, per-resource backup/restore/export, deletion, future forks, and storage-specific encryption. They also add provisioning/deletion sagas, per-resource schema migration, connection lifecycle and eviction, startup reconciliation, many-small-file overhead, and loss of atomicity with the control catalog.

A separate plaintext secret database does not materially improve confidentiality by itself. Secret-store separation is most valuable when paired with encryption and host key management. KV separation should be driven by concrete requirements such as large datasets, resource export/forking, independent retention, or failure isolation.

Relevant files:
- `packages/service-actor/src/resources/KvResource.ts`
- `packages/service-actor/src/resources/SecretStoreResource.ts`
- `packages/service-actor/src/resources/DbResource.ts`
- `packages/service-actor/src/resources/ActorResourceManager.ts`
- `packages/service-db/src/DbServiceTurso/DbServiceTurso.ts`

## Decision

Use one host-derived physical file per resource:

```text
<dataRoot>/actor-resources/kv/<resource-id>/data.db
<dataRoot>/actor-resources/secret-store/<resource-id>/data.db
```

Keep resource catalog rows, lifecycle status, and definition bindings in `DbServiceTurso`. Move entry contents, revisions, listing, and CAS behavior behind an actor-local persistence port. Preserve manifests, bindings, actor IPC, SDK methods, API DTOs, AI resource tools, and frontend behavior.

There is no data migration/backfill because actor KV and secret resources have not been deployed. Fresh control databases should stop creating `actor_resource_key_values`; existing local development databases may be reset or retain an unused table.

Independent secret files are plaintext at rest in this implementation. Physical separation improves operational isolation and future replaceability but is not an encryption claim. Encryption and host key management require a separate deliberate task.

## Implementation tasks

1. [S89](../s/S89.md) adds the shared physical key-value file adapter, format verification, per-resource write lanes, bounded lazy handles, deletion, reconciliation, and focused tests.
2. [S90](../s/S90.md) moves `KvResource` and KV management operations to physical files while preserving all public contracts.
3. [S91](../s/S91.md) moves `SecretStoreResource`, preserves redaction, and removes the obsolete control-database entry namespace/table from fresh migrations.
