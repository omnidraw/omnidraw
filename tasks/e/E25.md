# E25 - spawn actor IPC with same compiled binary
[Overview](../../BASED.md)

Explore making actor subprocess IPC work in dev and compiled-binary mode by spawning the same executable.

## Context

Current actor process code lives in [`packages/service-actor/src/Actor.ts`](../../packages/service-actor/src/Actor.ts) and child IPC bootstrap lives in [`packages/service-actor/src/icp-client.ts`](../../packages/service-actor/src/icp-client.ts).

The target model is Bun IPC using `Bun.spawn(..., { ipc })`, where the child can use `process.send()` / `process.on("message")`. For compiled binaries, avoid spawning `bun run ...` because the host may not have Bun installed. Instead explore spawning `process.execPath` with a mode flag like `--icp-client` so the compiled binary starts another copy of itself as the actor IPC child.

## Plan

### Validate runtime modes

Confirm behavior for:
- dev mode: running under `bun test` / `bun run`
- compiled mode: running from a `bun compile` binary

### Design entrypoint switch

Find the package/app entrypoint that should dispatch between normal app mode and `--icp-client` mode.

### Actor spawn contract

Define the command and args for the child process:
- executable: `process.execPath`
- mode flag: `--icp-client`
- actor function path: `--functionPath <path>`
- IPC enabled through `Bun.spawn(..., { ipc })`

### Child contract

Update or wrap `icp-client.ts` so it:
- parses `Bun.argv.slice(2)`
- safely sends ready/error messages over IPC
- handles missing IPC with a useful error during development
- supports messages from parent via `process.on("message")`

## NOTES

- `Bun.spawn(["bun", "run", icpClientPath])` requires Bun on the host and is not suitable as the compiled-binary production path.
- `process.send` exists in the child only when the parent supplies an `ipc` handler to `Bun.spawn`.
- Dynamic loading of external `.ts` actor function files may still require a runtime strategy in compiled mode.
