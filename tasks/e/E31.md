# E31 - Turso schema to TypeScript type generation
[Overview](../BASED.md)

Explore a reliable way to compile TypeScript database types from Turso schemas without assuming Turso is fully interchangeable with SQLite.

## Context

Vibecanvas now uses raw Turso SQL and manually maintained TypeScript row/input types. We need to determine whether types should be generated from migration SQL, an initialized database, Turso's schema metadata, or another canonical schema representation.

Turso is SQLite-compatible but is a superset with its own parser, runtime, supported features, metadata behavior, and client value mappings. A generator that only understands generic SQLite may accept invalid assumptions, reject valid Turso schema, or produce incorrect TypeScript types. The exploration must test actual Turso behavior rather than choosing a tool from its SQLite claim alone.

Relevant files:
- `packages/service-db/src/DbServiceTurso/DbServiceTurso.ts`
- `packages/service-db/src/DbServiceTurso/migration-files/`
- `packages/service-db/src/DbServiceTurso/fx.*.ts`

## Plan

### 1. Define the desired generated contract

Inventory current query result, insert, update, and nullable field types. Decide which artifacts are needed: table rows, insert payloads, update payloads, query result inference, or only a schema type map. Record expected mappings for integers, real values, text, blobs, nullability, defaults, JSON stored as text, primary keys, and values returned by the Turso client.

### 2. Establish Turso's actual schema surface

Create a representative schema fixture from current migrations plus Turso-specific edge cases. Compare migration SQL with metadata returned by an initialized Turso database, including `sqlite_schema`, pragma/table-valued schema introspection, views, indexes, foreign keys, generated columns, strict tables, altered tables, and any Turso-only syntax or behavior relevant to the project.

Determine whether local embedded Turso and remote Turso expose equivalent metadata and runtime value types. Document every meaningful difference from stock SQLite that affects parsing, introspection, or TypeScript output.

### 3. Compare generation strategies

Evaluate at least these approaches:
- parse migration SQL directly;
- apply migrations to a temporary Turso database and introspect the final schema;
- maintain a separate typed schema definition and generate SQL from it;
- use a Turso-native API/tool if one exists.

For each approach, assess Turso compatibility, migration-history handling, determinism, query-level inference, custom type overrides, dependency weight, maintenance activity, TypeScript 7 support, Bun support, offline generation, and license.

Shortlist existing SQLite type generators only after testing them against the Turso fixture. Do not treat successful parsing of simple SQLite DDL as sufficient compatibility.

### 4. Validate generated types against runtime behavior

Build a type-mapping matrix from declared SQL type and nullability to the values actually returned by the Turso client. Check ambiguous cases such as integer width, blobs, booleans represented as integers, date/time text, JSON text, expressions, joins, aliases, aggregates, and `RETURNING` results.

Compare generated output with representative queries in `fx.*.ts` and `tx.*.ts`. Identify where schema-derived types are sound, where query parsing is required, and where explicit validation or manual result types must remain.

### 5. Design drift and CI workflow

Determine the source of truth and when generation runs. Explore a reproducible command that starts from a clean database, applies migrations with the same Turso engine used by the app, generates stable output, and fails CI on drift.

Specify ownership and review rules for generated files, custom overrides, migration changes, unsupported constructs, and tool/version upgrades. Include a failure mode that prevents silently emitting broad `any`, `unknown`, or incorrect nullable types.

### 6. Recommend a bounded adoption path

Score the candidates and recommend one of: adopt a generator, build a thin Turso introspection adapter around an existing generator, retain manual types with automated schema checks, or postpone generation. Propose a small follow-up implementation scope on a few representative tables before any repository-wide migration.

## NOTES

The default hypothesis is that introspecting a temporary database after applying real migrations will be safer than parsing migration files independently, because it observes the final schema through the Turso engine. This still needs validation: schema introspection alone may not infer query result shapes or application-level encodings such as JSON and booleans.

The exploration should optimize for correctness and visible failure over maximum type coverage. A smaller generated table contract with explicit query types is preferable to a generator that silently models Turso as generic SQLite.
