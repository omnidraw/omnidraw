# E29 - validate actor/widget clone DB concurrency in minimal repo at .tmp/turso-actor-write-race
[Overview](../BASED.md)

Create a minimal reproducible repo under `.tmp/turso-actor-write-race` to validate whether actor/widget cloning in dev can cause Turso pager panics under concurrent writes.

## Context
Current crash signatures in monorepo point to Turso storage pager panics during CLI startup or actor write activity:
- `thread '<unnamed>' panicked at core/storage/pager.rs:380:9: cell_get: idx out of bounds | idx=0, ncells=0`
- backtrace through `turso_core::storage::pager::PageInner::cell_get` and SQL statement stepping
- also observed lock errors: `experimental multiprocess WAL ... already open with another process`

Recent repro observations indicate panics can be triggered by concurrent actor DB writes (insert/update/delete bursts) and may be hidden behind shared DB contention during copy/clone workflows.

Relevant code hotspots already inspected:
- `packages/service-actor/src/ActorSupervisor.ts`
- `packages/service-db/src/DbServiceTurso/tx.actor.ts`
- clone path touched by `packages/canvas/src/services/widget/tx.create-widget-clone-drag.ts`
- startup path in `apps/cli/src/setup-services.ts` and `apps/cli/src/main.ts`

## Plan
### 1) Scaffold minimal workspace
Create `/Users/omarezzat/Workspace/vibecanvas/vibecanvas/.tmp/turso-actor-write-race` with:
- package manifest for Bun runtime script
- simple Turso-backed schema bootstrap script
- one service/module that can open a DB and write actor rows in bursts
- minimal migration setup matching required tables (`canvas`, `actor_definitions`, `actor_instances` columns used in writes)

### 2) Reproduce crash path
Implement runner modes in `scripts/repro.ts`:
- `repro:concurrent`:
  - create canvas + definition row
  - run high-volume concurrent `insertInstance` + `updateInstanceMachine` + `updateInstanceStatus` operations
  - include occasional deletes
- `repro:serialized`:
  - same operations executed serially
  - compare behavior to concurrent baseline
- `repro:insert-only`:
  - compare against insert-only pressure without follow-up updates

### 3) Capture environment behaviors
Document:
- OS + Bun + Turso package versions
- DB path handling (`.turso`, `-wal`, `-tshm`)
- lock behavior with stale process (`lsof`, `kill`) and recovery command sequence

### 4) Record findings + handoff
Collect exact failing commands, iteration counts, logs, and any preconditions to decide whether minimal fix should stay in actor layer, db adapter, or caller serialization.
