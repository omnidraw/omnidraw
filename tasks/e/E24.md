# E24 - canvas services/plugins rendering responsibility split
[Overview](../../BASED.md)

Explore current `packages/canvas` services and plugins to prepare a refactor where services own backend talk and persistent/shared state, while plugins own canvas rendering and ephemeral UI state.

## Context
Target architecture:

- services stay useful for persistent state, backend APIs, CRDT/history, registries, and shared semantic state.
- plugins use services and render the current canvas engine.
- plugins may keep ephemeral UI state such as hover, disabled states, transient handles, drag previews, and button state.
- changing render engine should mostly mean replacing plugins, not rewriting backend/persistent services.

Relevant folders:

- [packages/canvas/src/services](/Users/omarezzat/.codex/worktrees/f51c/vibecanvas/packages/canvas/src/services)
- [packages/canvas/src/plugins](/Users/omarezzat/.codex/worktrees/f51c/vibecanvas/packages/canvas/src/plugins)
- [packages/canvas/src/runtime.ts](/Users/omarezzat/.codex/worktrees/f51c/vibecanvas/packages/canvas/src/runtime.ts)

## Plan
1. Inventory all canvas services and plugins.
2. Mark which services are state/backend/registry only and which directly render through Konva/DOM.
3. Mark which plugins are already mostly render-engine adapters and which contain persistent/backend behavior.
4. Capture likely refactor seams for future work.

### Refactor Direction

High priority service splits:

- `SceneService`: move Konva stage/layers/preview into a `KonvaScenePlugin` or renderer adapter.
- `WidgetManagerService`: split registry/backend widget definition concerns from host chrome/DOM portal rendering.
- `ElementService`: keep semantic registry, move Konva node lifecycle callbacks to renderer-specific registrations.
- `GroupService`: move boundary UI, node creation, drag listeners, and shortcuts into a group plugin.
- `ActorConnectionService`: keep backend connection state/API, move line/handle rendering into a connection plugin.
- `CameraService`: keep viewport state/math, move layer transform application to renderer plugin.
- `SelectionService`: store IDs/semantic selection, not Konva nodes.
- `RenderOrderService`: calculate/persist order by IDs; renderer plugin applies node ordering.
- `ToolService`: keep tool registry/active state; plugins own draft rendering and commit flows.

Likely migration order:

1. Introduce renderer-neutral IDs in `SelectionService` while keeping compatibility helpers for current Konva nodes.
2. Extract `SceneService` behind a narrow renderer portal used by plugins.
3. Move actor connection rendering from service to plugin; this is isolated and proves the pattern.
4. Split widget manager into registry/service plus Konva widget host plugin.
5. Split element/group registries into semantic service contracts and Konva renderer registrations.

### Focus: ElementService and GroupService Render Inversion

Yes, render functions can move to plugins without services calling plugins directly.

The important inversion is: plugins already call services during `apply(ctx)`, so plugins can register renderer implementations into a registry. The service does not need to import or call a plugin. It only exposes a neutral registry/hook surface.

Current problem:

- `ElementService` stores `createNode`, `afterCreateNode`, `toElement(node)`, `attachListeners(node)`, `updateElement(element)`, clone hooks, and transform hooks. These are Konva-renderer behaviors registered by plugins but executed through a service.
- `GroupService` registers the default group renderer inside `start()`, creates `Konva.Group`, syncs boundary overlays, attaches drag listeners, handles group clone previews, and calls context menu/keyboard UI. This makes it more renderer-owned than service-owned.
- `SceneHydratorPlugin` already behaves like the renderer orchestrator, but it currently asks `element.createNodeFromElement()` and `group.createNodeFromGroup()` to manufacture Konva nodes.

Better shape:

- Keep `ElementService` for semantic element metadata and service-owned behaviors: element type ids, selection-style config by persisted element type, delete/restore hooks that affect backend/persistent state, and maybe transform capability metadata if expressed without Konva nodes.
- Move element render lifecycle to a plugin-owned renderer registry, for example `ElementRenderRegistryService` or `KonvaRendererService`, registered by render plugins.
- Keep `GroupService` for semantic group commands and persisted grouping rules. Move group node creation, group boundary UI, drag listeners, clone previews, and shortcut/context-menu UI into `GroupPlugin`.
- Let renderer plugins consume services, not the reverse. Example: `Shape2dPlugin` registers `rect/diamond/ellipse` render adapters; `SceneHydratorPlugin` consumes those adapters to mount/update the scene.

Possible dependency direction:

```txt
Shape2dPlugin -> registers Konva element renderer
TextPlugin    -> registers Konva element renderer
GroupPlugin   -> registers Konva group renderer

SceneHydratorPlugin -> reads CrdtService doc
SceneHydratorPlugin -> asks renderer registry to create/update/destroy nodes

ElementService -> owns semantic element registry/state only
GroupService   -> owns semantic group operations only
```

Minimal API sketch:

```ts
type TElementRenderer<TNode> = {
  id: string;
  matchesElement(element: TElement): boolean;
  create(element: TElement): TNode | null;
  update(node: TNode, element: TElement): boolean;
  serialize(node: TNode): TElement | null;
  attach?(node: TNode): void;
  destroy?(node: TNode, element: TElement): void;
};
```

Then `SceneHydratorPlugin` calls the renderer registry:

```ts
const renderer = elementRenderers.findByElement(element);
const node = renderer.create(element);
renderer.attach?.(node);
```

This keeps service-to-plugin calls out of the system. The registry is the boundary object. Plugins register into it; other plugins use it.

Suggested first move:

1. Extract a Konva-specific `ElementRenderRegistryService` from the render parts of `ElementService`.
2. Change `SceneHydratorPlugin` to use that registry for `create/update/serialize/attach`.
3. Move the built-in group registration currently inside `GroupService.start()` into a new or existing `GroupPlugin`.
4. Leave compatibility wrappers on `ElementService`/`GroupService` temporarily if needed, but make them delegate to the renderer registry so callers can migrate gradually.
