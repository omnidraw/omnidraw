# E23 - actor output log pruning compatibility
[Overview](../BASED.md)

Explore whether future hourly server cleanup of committed actor output logs can be added without backwards-compatibility problems, and identify any schema/runtime changes that must happen before log pruning is safe.

## Context

Relevant files:

- `packages/service-actor/AGENTS.md` — actor service boundaries and DB model notes.
- `packages/service-actor/src/ActorSupervisor.ts` — commits actor outputs, publishes events, and routes connected outputs into inbox messages.
- `packages/service-actor/src/core/fx.actor-db.ts` — computes next actor output seq from existing `actor_outputs` rows today.
- `packages/service-actor/src/core/tx.actor-db.ts` — inserts actor output rows.
- `packages/service-db/src/schema.ts` — defines `actor_outputs`, `actor_inbox`, workflow tables, and actor instance state.
- `packages/api-actors/src/contract.ts` — exposes `outputs.list({ actorInstanceId, afterSeq })`.
- `packages/api-actors/src/api.list-actor-outputs.ts` and `packages/api-actors/src/fx.actor-db.ts` — current output list implementation.

Future direction: add a server cron/hourly job that deletes old committed actor output logs for chatty actors. This task is only exploration for now. The main question is whether future pruning will be backwards-safe, or whether we need to fix blockers now before more code depends on unbounded `actor_outputs` history.

## Plan

### 1. Map replay dependencies

Confirm what server-side actor replay actually requires after restart:

- actor instance `machine_state` / `machine_context`
- queued/claimed/processed inbox rows
- workflow runs/steps for in-flight reconciliation
- actor outputs only if they are part of replay, routing recovery, API recovery, or debug history

### 2. Identify pruning blockers

Check for assumptions that old `actor_outputs` rows always exist. Initial suspected blocker:

- `fxNextActorOutputSeq` calculates next seq by scanning existing output rows. Deleting old rows may reuse seq numbers unless a monotonic counter is stored elsewhere.

Also inspect whether `outputs.list(afterSeq)` must support infinite history or can become recent-log-only.

### 3. Define safe cleanup conditions

Draft the future cron deletion rule. Candidate constraints:

- only `commit_status = 'committed'`
- do not delete outputs tied to unfinished workflow/inbox reconciliation
- keep recent tail per actor
- preserve monotonic seq semantics after deletion

### 4. Decide if pre-work is needed now

Produce a recommendation:

- safe to add cron later without changes now, or
- must first add durable `last_output_seq` / checkpoint fields, pagination limits, or API behavior changes before any pruning lands.

## TODOS

## NOTES

Initial concern: future pruning is likely unsafe unless output sequence generation stops deriving `max(seq)` from the prunable table. A durable per-actor counter/checkpoint may be needed before deletion is introduced.
