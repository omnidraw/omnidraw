# E40 - AI widget live Preview: architecture and product decision ledger
[Overview](../BASED.md)

Resolve the product, security, Capsule, build, diagnostic, and publication
questions that must be answered before implementing [`A96`](../a/A96.md).
This exploration began question-first and now records both the traced context
and the normative answer to every decision.

## Why this exploration exists

The intended experience is:

1. AI Chat edits a widget.
2. The user sees fast live updates in a Preview window.
3. Widget build, host, and guest failures reach the AI with enough safe context
   to repair the source.
4. The user explicitly publishes when confident.

The current product cannot perform step 2. The Cangine cutover removed the
frontend Draft Preview build/mount path, while the backend stateless Preview API
remains. Restoring the deleted UI unchanged would still be too slow and would
not provide browser-runtime diagnostics to the AI.

The architectural direction proposed in A96 is a latest-wins build coordinator,
last-known-good Preview swapping, structured diagnostics, bounded AI repair,
and exact promotion of a frame-owned Preview revision. That direction
supersedes the UI-only, stateless decisions in [`S108`](../s/S108.md); the
decision record below resolves the conflict before implementation.

### Confirmed implementation facts

- `onOpenWidgetPreview` in the current Cangine AI Chat extension only shows
  “Publish the widget to place it on the authoritative canvas.”
- Direct Cangine placement accepts published references and rejects Draft
  references.
- No current frontend caller consumes the stateless Preview response's
  `bytesBase64`.
- The earlier `DraftPreviewFrameService`, mount path, and integration tests were
  removed in checkpoint commit `3db71817`.
- The backend Preview API still builds and returns signed Capsule UI bytes.
- `buildPreview()` first performs a complete validation build and then performs
  another complete Preview build.
- Publish similarly validates with a complete build and then performs a
  separate release build.
- Every build currently creates a fresh temporary npm project, probes
  Node/npm, installs dependencies, runs the widget build script, ingests the
  distribution with Capsule, signs it, and discards the scratch directory.
- Successful Preview diagnostics are discarded, mapped Capsule error objects
  lose their safe message in `WidgetUiRuntime`, and browser failures have no
  route to the originating AI session.
- Existing focused service, API, component, and published-runtime tests pass
  without proving that a Draft Preview reaches a Cangine portal.

### Capsule constraints that shape the answer

- Capsule is not the source builder. Vibecanvas owns source snapshotting,
  dependency installation, guest scripts/plugins, network policy, isolation,
  cancellation, limits, and cleanup.
- `buildCapsuleGuest()` ingests an exact closed external distribution and
  produces deterministic, content-addressed artifact bytes.
- External distribution format v1 rejects source maps and
  `sourceMappingURL`. Debug maps therefore must remain separate trusted build
  metadata; they cannot be smuggled into the executable distribution.
- Signing uses explicit trusted Ed25519 keys, preserves the Capsule content
  address, and is separate from building.
- The browser host verifies direct bytes before execution. Its memory artifact
  cache contains only verified copied bytes and re-verifies cache hits against
  current policy.
- A mount container must be empty, unreserved, and without an attached
  ShadowRoot. Capsule owns its internal shell until terminal handle cleanup.
- `ready()` is the supported mount readiness boundary. Lifecycle replacement
  through `resume()` requires an explicit compatible parkability/snapshot
  contract.
- `onError` exposes normalized bounded records, not guest/provider stacks or
  host objects. `handle.diagnostics()` exposes authority, budgets, lifecycle,
  queues, resource ledgers, and counters, but not arbitrary guest internals.
- Testkit exposes only bounded, read-only target geometry and must never be
  attached in production.
- Authority is the intersection of artifact request, host policy, mount grant,
  and live instance-bound binding. Preview cannot gain authority merely because
  its artifact requests it.
- The retained population policy allows at most 24 aggregate live Capsule
  runtimes and fewer active/heavy/GPU runtimes. Preview instances must
  participate in admission and cleanup.

### Existing decisions that are not automatically reopened

- CanvasService remains the only durable canvas authority.
- WidgetStateService remains the only published widget-instance state
  authority.
- A Preview is explicit durable authoring authority owned by its canvas frame.
  It is not a published revision, but it may execute its staged server artifact
  and use the resource bindings selected for that Preview.
- Publication remains explicit and user-confirmed.
- Published widget revisions remain immutable, signed, recoverable, and
  resource-binding checked.
- Capsule capability requests never grant authority.

## Decision record

These answers are the implementation defaults. A measured gate may reject an
implementation technique, but it must preserve the corresponding product and
security decision unless this exploration is explicitly reopened.

### Answers 1-15: Preview product boundary

- **A01:** Preview is one interactive Cangine companion frame beside AI Chat.
  Chat shows status and actions but does not host a second Capsule runtime.
- **A02:** The screen atlas is authoritative: Draft Preview may be represented
  by a durable canvas node. “Drafts live off-canvas” means draft source is not a
  published widget instance, not that authoring UI cannot occupy the canvas.
- **A03:** A trusted widget-create result owns one companion per
  `(draftId, originChatId)`. Direct Draft placement may create additional
  independent frames, each with its own ephemeral state.
- **A04:** The durable draft's originating `chatId` owns automatic diagnostic
  delivery. Other chats may inspect the draft but never receive or trigger
  automatic repairs unless ownership is explicitly transferred.
- **A05:** The first trusted widget-create result creates the companion frame
  immediately in a visible Building state. Closing it is respected; later edits
  do not reopen it automatically.
- **A06:** While a Preview frame is open, it follows every committed latest
  draft revision automatically. Pause Live Updates is an explicit local user
  override.
- **A07:** Add one `draft-source-committed` boundary after a successful tool
  mutation. A multi-file tool call emits one mutation ID and one captured
  digest. Separate rapid tool calls are debounced and latest-wins.
- **A08:** The canvas node survives navigation, chat closure, and application
  restart and owns a durable Preview identity. Its active Preview revision and
  artifact roots survive restart and remount exactly; newer draft edits still
  build and atomically advance that pointer. Discarded drafts render
  unavailable and release their Preview owners.
- **A09:** Keep direct Draft placement because it is an explicit screen-atlas
  contract. It creates a new Preview frame and never a published instance.
- **A10:** Chrome shows `Showing <short digest>`, pending
  `Building <short digest>`, and failed revision separately. Publish is bound
  only to the current displayed build when it also equals the latest draft.
- **A11:** A failed replacement leaves the last-known-good Preview interactive
  with a conspicuous stale/error badge. Publish is disabled.
- **A12:** Required controls are Pause/Resume Live Updates, Cancel Build, Retry,
  Reset Preview State, Ask AI to Fix, Pause Fixes, Publish, and Close. Controls
  are shown only when meaningful.
- **A13:** “Live” means Building feedback within 100 ms, warm source-only
  Preview p95 below 2 seconds, no frozen UI during cold/dependency work, and
  current Preview revision Publish p95 below 1 second without a guest build.
- **A14:** Those values are accepted as release gates on the reference machines
  in A123. Dependency-change and cold-start latency are reported separately
  rather than hidden inside the warm p95.
- **A15:** Non-throwing visual mistakes require user observation. Provide an
  explicit Share Preview with AI action; do not run continuous visual
  surveillance.

### Answers 16-23: full-stack confidence and Preview authority

- **A16:** Confidence means the exact browser UI, server functions, and selected
  resource bindings can be exercised before publication. Preview is a
  full-stack authoring runtime, not a UI-only approximation.
- **A17:** Restore Preview-specific server execution authority. Each Preview
  owner receives a Preview function subject and the real resource bindings the
  user selects for that frame. Calls may have real side effects; mocks are not
  part of the product contract.
- **A18:** Preview chrome shows its active revision, build/readiness state, and
  binding state. It does not claim backend behavior is unavailable or untested.
- **A19:** Function calls execute the exact active Preview server artifact through the
  Preview function subject and its selected bindings. Infrastructure or binding
  failures surface as structured diagnostics to both the frame and AI Chat.
- **A20:** Mocks are rejected because they would provide false behavioral
  confidence. Preview uses real selected resources and their real side effects.
- **A21:** S108 remains a historical record of the cutover simplification, but
  its UI-only/stateless Preview outcome is superseded. A96 restores the durable
  authoring identity, artifact roots, function subject, invocations, and
  bindings needed by a frame-owned full-stack Preview.
- **A22:** The active Preview revision is durable authoring state rooted by at
  least one Preview frame. It has runtime authority and binding references but
  never becomes a published widget revision without explicit Publish.
- **A23:** Exact promotion is required. Rebuilding from nominally identical
  inputs is not “publish what I reviewed,” so the active Preview revision
  survives until its owning frame is removed or it is superseded.

### Answers 24-38: staged identity and promotion

- **A24:** Exact promotion binds the source snapshot, canonical manifest,
  dependency lock, unsigned Capsule content address, server artifact, function
  descriptors, capability/channel/actor contracts, builder identities, policy,
  and provenance. Signature-envelope bytes may differ.
- **A25:** Preview and release are signed separately from the same canonical
  unsigned Capsule bytes. Preview uses the existing Preview key; Publish signs
  the original unsigned bytes with the current release key. Never carry the
  Preview signature into a release envelope.
- **A26:** Every Preview revision contains the full
  source/UI/server/descriptor definition build. The UI mounts through Capsule
  while server functions execute through the Preview function runtime.
- **A27:** Product copy may say “Publish this Preview”: the exact full-stack
  revision was available for exercise. It must not claim the user exercised
  every behavior, only that Preview and publication use the same outputs.
- **A28:** Resource bindings are selected and authorized for Preview, persisted
  against its owner/revision, and used by Preview invocations. Publish
  revalidates and atomically promotes the selected binding plan; a binding
  change advances Preview readiness and invalidates the prior publish choice.
- **A29:** Source, manifest, lock, SDK/contract, builder, Capsule ABI/build,
  target/profile, build policy, approved transforms, Node/npm/platform, or
  executable configuration changes require a new Preview revision. Release-key rotation
  alone does not if the target/policy still admits the same content address.
- **A30:** There is no time expiry while a Preview frame owns the active
  revision. Missing or corrupt active artifacts make the frame visibly
  unavailable, trigger a rebuild, and require review of the replacement before
  Publish.
- **A31:** The active revision, artifacts, maps, and binding plan remain rooted
  as long as at least one Preview frame references them. Superseded revisions
  remain only while mounted handles or in-flight function invocations lease
  them, then enter bounded GC grace. Byte/count limits fail explicitly; they
  never silently expire an active frame.
- **A32:** Use the durable control/artifact stores for Preview identity,
  revision metadata, and exact outputs so restart preserves the reviewed
  Preview. The warm build workspace may be local and reconstructable.
- **A33:** Durable authoring records are required: Preview owner, active
  revision pointer, source/UI/server artifact roots, binding plan, function
  subject, invocation/idempotency state, and cleanup status. They remain
  distinct from immutable published revisions and widget-instance state.
- **A34:** Publish submits the current Preview owner/revision identity plus an
  idempotency key. The server verifies tenant/account/frame/draft ownership,
  source and active-revision CAS, content/contract digests, and binding revision
  so an old or cross-owner Preview cannot be promoted.
- **A35:** `service-agent` owns Preview coordination and durable authoring
  records through injected stores. The Preview function runtime executes its
  server artifact. `WidgetPublicationService` alone release-signs and commits
  the verified active Preview revision.
- **A36:** Release signing and blob writes may precede the metadata transaction.
  The existing mutation fence and grace-owned orphan GC handle crashes before
  commit; the Preview revision remains retryable while owned and publication
  is idempotent.
- **A37:** Existing canvas widget instances remain pinned to their immutable
  stored `revisionId`. Publication changes the active catalog revision for new
  placements only; upgrading existing instances is a separate explicit action.
- **A38:** Rollback changes the definition's active revision and its revision
  bindings. It does not rewind WidgetStateService data, and already pinned
  instances remain on their revisions.

### Answers 39-58: build ownership, trust, and performance

- **A39:** Capsule is the browser guest security boundary. Package install,
  guest build scripts, descriptor extraction, and Preview server functions are
  operator-trusted host execution and are explicitly outside that boundary.
- **A40:** Run the widget project's declared build command, including
  `npm run build`, so ordinary framework configuration and plugins work.
  Exact captured outputs—not a claim of reproducible execution—are the
  promotion authority.
- **A41:** Allow dependency lifecycle/install scripts and guest-selected
  bundler configuration/plugins under normal package-manager semantics.
  Operators who require another boundary may select a Docker/isolated runner.
- **A42:** Keep time, memory, output, descendant-process, and teardown bounds
  for reliability and UX. They are not described as a security sandbox.
- **A43:** The default runner may execute on the application host. Define a
  runner adapter so an operator can choose Docker or another isolated executor;
  absence of that adapter does not block Preview or release.
- **A44:** macOS, Linux, and Windows release targets require full descendant
  cancellation and verified cleanup using process groups or job objects.
- **A45:** A cold npm/Vite workspace per edit will not meet the warm SLO. Keep
  one warm build workspace and incremental graph per draft while any Preview
  frame exists; run install only when package/lock inputs change.
- **A46:** Reuse the package-manager download cache, the draft-private
  `node_modules`, build graph, Capsule ingestion results, and completed Preview
  revisions by exact key.
- **A47:** Each draft owns a private mutable workspace because install/build
  scripts may write to dependencies and generated output. Do not share mutable
  `node_modules` or guest process state across drafts; this is a correctness
  and contamination rule, not a security claim.
- **A48:** Public registry package bytes may be globally deduplicated.
  Tenant-private dependencies and every complete/source-derived build remain
  tenant-scoped. Never share Preview authority across tenants.
- **A49:** The build key contains source snapshot, canonical manifest, lockfile,
  SDK/generated contract, builder/Capsule identities, ABI/target/profiles,
  capability/channel contracts, build policy, approved transforms, Node/npm,
  OS/architecture, and normalized build configuration.
- **A50:** The selected runner defines its environment and host access. Keep
  release-signing keys outside the guest build process by process composition,
  but do not claim the build or server runtime is an isolation boundary.
- **A51:** One coordinator owns each tenant/draft while at least one Preview
  frame exists. A future multi-process deployment adds affinity or a
  build-key single-flight lease without changing durable Preview identity.
- **A52:** Initial scheduling permits one active build per draft, two per tenant,
  and a deployment-configured global ceiling. Publish signing/commit outranks
  background builds; rapid edits debounce for 250 ms and supersede older work.
- **A53:** Validation never constructs an independent artifact. It runs cheap
  checks and then awaits/reuses the current build-key result.
- **A54:** Cheap checks cover snapshot/path/size rules, manifest and schema
  parsing, entry existence, lock/package parity, declared imports/profiles,
  resource slots, and static contract generation.
- **A55:** Progress is emitted only at owned boundaries:
  `queued`, `snapshotting`, `checking`, `installing`, `bundling`,
  `extracting`, `ingesting`, `signing-preview`, `ready`, `failed`,
  `canceled`, and `superseded`. Human stdout is diagnostic input, not progress.
- **A56:** Superseded work is canceled immediately through its complete process
  group. A result that already completed atomically may enter the bounded cache
  but can never mount or publish unless its revision becomes current again.
- **A57:** The current active result remains for the frame lifetime.
  Superseded completed results remain only while mounted/invocation leases
  reference them, then GC; superseded partial output is destroyed immediately.
- **A58:** Capture a no-follow coherent snapshot after the tool's committed
  mutation event, compare-and-set its digest into the draft row, and bind every
  build event/result to that digest and mutation ID.

### Answers 59-71: Capsule host and live replacement

- **A59:** Use the existing `CapsuleWidgetHostCoordinator`, which already pools
  by exact target, policy, and signing key. Preview and release naturally occupy
  distinct host partitions because their required signing keys differ.
- **A60:** Preview uses the same browser target, feature profiles, resource
  budgets, function descriptors, and selected real bindings as release. UI
  function calls route to the Preview function subject for the exact active
  server artifact.
- **A61:** Every Preview handle participates in the same Capsule population
  admission accounting and all 24-runtime/subclass ceilings. Preview never gets
  an unbounded side pool.
- **A62:** A focused visible Preview receives the same priority as a focused
  published widget. Other visible Previews use normal visible priority; hidden
  and distant frames throttle/freeze/destroy under the common policy.
- **A63:** Atomic replacement uses two sibling empty containers inside the
  application-owned frame content root. Mount and ready the new handle, switch
  presentation atomically, then destroy and await cleanup of the old handle.
- **A64:** Stage the new container at the exact final geometry with
  `opacity: 0` and `pointer-events: none`, never `display: none`. Feed the real
  viewport and verify layout/media behavior in the browser spike before relying
  on the technique.
- **A65:** Capsule `ready()` proves mount/guest readiness. For visual stability,
  wait two host animation frames after `ready()`; do not trust a guest-declared
  “ready” message in v1.
- **A66:** Delay replacement during pointer capture or text composition for at
  most one second. Destroy cancels old pending guest/capability work; fullscreen
  and dialogs close. Restore only surface-level focus, not private selection.
- **A67:** Preserve only the external ephemeral Preview state bridge, and only
  when its schema/contract hash is unchanged. Framework heap/DOM state is not
  migrated.
- **A68:** Use a fresh mount for live code replacement. Do not use
  park/resume replacement until widgets declare and pass a compatible snapshot
  contract.
- **A69:** A changed guest-channel/state schema resets ephemeral Preview state
  and shows a one-time `Preview state reset after schema change` notice.
- **A70:** Churn qualification must prove zero remaining handles, hosts when
  idle, shells, listeners, schema/descriptor registrations, queues, timers,
  build processes, scratch directories, Preview artifact leases, and Capsule live
  counters after teardown.
- **A71:** Builds are demand-refcounted. Closing the last frame for a draft
  cancels pending work and releases the warm workspace unless Publish holds it.
  Frame deletion closes its Preview owner; active artifacts/bindings are GC'd
  only after mounted-handle and invocation leases end. Virtualization does not
  close the frame or its owner.

### Answers 72-89: diagnostic fidelity

- **A72:** Normalize source checks, install/dependency, compiler/bundler, server
  extraction, Capsule ingestion/signature/verification, mount/boot, guest
  runtime, channel, capability, budget, lifecycle, browser compatibility, and
  correctness-affecting cleanup failures. Benign cleanup telemetry stays
  operator-only.
- **A73:** `packages/widget-contract` owns the transport-neutral normalized
  diagnostic type and schema. Build, API, service-agent, and UI layers map into
  it without defining competing shapes.
- **A74:** Require format version, fingerprint, origin, phase, stable code,
  severity, safe summary, trust class, draft revision, build ID/sequence,
  occurrence count, retryability, timestamp, and optional normalized
  file/line/column, capability/operation, budget dimension, and cause
  fingerprint.
- **A75:** Vibecanvas/Capsule stable codes and generated summaries are trusted
  infrastructure data. Guest, dependency, compiler, provider, network, and
  browser-supplied text is always marked untrusted and quoted only as bounded
  data.
- **A76:** Normalize paths to `widget://<draft-relative-path>`, collapse
  dependency paths to package identity, allowlist structured fields, redact
  home/temp/registry/env/secret patterns, strip control characters, and enforce
  per-field/event/count byte limits both at producer and server ingress.
- **A77:** Source maps are private Preview-revision outputs with normalized
  virtual paths and the same frame-rooted retention as their artifacts. On
  Publish, retain them only inside authorized source/debug provenance; never
  include or serve them as Capsule distribution resources.
- **A78:** Capsule 0.9.4 exposes no guest module/program-counter location in its
  message-free mount error event. Actionable runtime mapping therefore requires
  a Capsule API change; Vibecanvas must not fabricate source locations.
- **A79:** Add an opt-in authoring-only Capsule diagnostic mode that reports a
  bounded generated module ID and line/column for guest exceptions. It returns
  no guest message, stack, source text, host object, or provider detail.
  Published hosts keep the current message-free contract.
- **A80:** Vibecanvas maps that generated location through the private normalized
  map and emits only authored widget paths. Dependency locations are reported
  as package-level failures without dependency source.
- **A81:** Without a safe location, AI receives the stable code, phase,
  capability/operation or budget dimension, revision/build identity, and a
  statement that no source location is available. It never receives a guessed
  file.
- **A82:** Attach a minimal allowlisted snapshot: lifecycle state, exhausted
  budget dimension, relevant capability/operation, queue/ledger counts, and
  artifact hash. Do not send the full diagnostics object to the model.
- **A83:** Fingerprint normalized
  `(origin, phase, code, authored location, capability, operation, budget,
  buildId)` and aggregate occurrence count/time. Browser callbacks, retries,
  and reconnects update one record.
- **A84:** Reconnect must recover the latest build state and diagnostic set.
  Store revision-specific diagnostics with the durable Preview revision/status
  record and expose one authorized status query; the draft `lastError` remains
  a summary of the latest draft build failure.
- **A85:** The draft row retains at most 20 normalized diagnostics/64 KiB for
  the current revision and clears them on a newer committed source or successful
  applicable build. Relevant chat history records the repair result, not a
  separate authoring event log.
- **A86:** Browser reports are untrusted observations. The server verifies
  tenant/account/frame/draft/origin chat/current Preview revision and build
  identity, rate
  limits them, and never lets them alter signing, publication, bindings, or
  other authority.
- **A87:** Cleanup failures reach user/AI only when they leave the Preview
  unusable, leak capacity, or block a rebuild. Other bounded failures go to
  trusted telemetry.
- **A88:** Non-throwing visual defects are reported by the user. Capsule's
  closed root is not introspected, and production testkit is never attached.
- **A89:** Add an explicit, user-triggered Share Preview with AI capture of only
  the Preview rectangle, at most 1600×1600 and 2 MiB with metadata removed.
  Explain that rendered remote/user data may be included; never capture
  automatically.

### Answers 90-100: AI delivery and repair

- **A90:** Errors appear in Preview/chat status and are delivered as hidden
  structured AI context. During the still-active user-requested generation
  turn, repair follow-ups are automatic. Once the agent is idle, a runtime
  error does not trigger spend; **Ask AI to Fix** starts the turn.
- **A91:** Automatic repair is on only inside the active generation loop that
  the user already requested. Idle/post-interaction runtime repair is off by
  default. **Pause Fixes** stops both immediately.
- **A92:** While streaming, send a hidden Pi custom message with
  `deliverAs: "followUp"`. While idle, persist/inject context with no triggered
  turn; the explicit Ask action prompts the session.
- **A93:** Route by the durable authoring draft `chatId`. A connected session
  receives it immediately; a reconnected session receives current unresolved
  diagnostics before its next prompt. Chat reset/model change does not
  automatically spend or silently change model.
- **A94:** With no live owner, retain visible/status diagnostics only. If the
  user invokes Ask from another chat, require an explicit `Take over fixes`
  action that updates diagnostic-repair ownership; never fan out automatically.
- **A95:** Limit one generation loop to three AI repair turns, six build
  attempts, five wall-clock minutes, and one repeated unchanged fingerprint
  after a repair. Existing per-session token/context ceilings still apply.
- **A96:** User input, Pause Fixes, Preview close, ownership/model/session
  change, manual draft edit, elapsed limit, repeated fingerprint, or no source
  change stops the automatic loop.
- **A97:** Show `AI fixing • attempt n/3` beside Preview status with Pause. The
  user can see every source-changing tool action and resulting build state.
- **A98:** Use a fixed system-produced diagnostic envelope. Untrusted strings
  are JSON data fields with explicit trust markers and instructions to treat
  them only as evidence, never as commands.
- **A99:** Transient/repeated diagnostics update one compact status panel rather
  than append transcript spam. The transcript receives only grouped repair
  start, success, stopped, or needs-user summaries; hidden AI context remains
  revision-bound.
- **A100:** A successful build clears build-time errors for that revision.
  Runtime errors become `awaiting-retest`; they clear only after the relevant
  interaction/test succeeds again or the user explicitly marks the issue
  resolved.

### Answers 101-110: API, event, and ownership

- **A101:** Current `created/changed/validated` events occur after individual
  tool handlers but are transient and lack mutation IDs. Extend them with a
  committed mutation ID and server build sequence, plus a queryable latest
  state for reconnect.
- **A102:** Use the existing tenant-scoped oRPC WebSocket event stream for live
  status and an idempotent `widgetBuild.status(draftId)` query for initial
  load/reconnect. Do not poll during a healthy subscription.
- **A103:** `service-agent` owns draft demand, latest-wins scheduling, chat
  routing, and durable Preview lifecycle. `widget-contract` owns pure/shared
  contracts and prepared-publication validation. Application composition
  injects build runners, Preview stores, artifact storage, function execution,
  resources, clocks, and signing capabilities.
- **A104:** Only the CLI/application build adapter touches scratch files and the
  build process. Preview signing is an injected trusted capability. Release
  private keys remain reachable only from the publication edge. Preview
  orchestration receives narrowly injected durable authoring/artifact stores.
- **A105:** Persist `previewId`, `draftId`, `originChatId`, and Preview role
  (`companion` or `placed`) in the Cangine extension with ordinary frame
  presentation. The backend Preview control record owns the active revision
  pointer and artifact/binding roots; artifact bytes do not live in canvas JSON.
- **A106:** Preview is a durable canvas node and authoring owner. Capsule
  handles and build progress are transient, but active Preview revision,
  artifacts, bindings, and function identity are durable service state.
- **A107:** Deleting a Preview node closes that Preview owner and local state.
  It does not delete the draft. Shared content remains while another Preview,
  mounted handle, invocation, or Publish operation references it, then normal
  lease-aware GC removes it.
- **A108:** Account/draft deletion terminally closes owned Previews, cancels
  builds and invocations, destroys handles/hosts, releases bindings/artifact
  roots, and sweeps workspaces. Application restart reconstructs active Preview
  owners and remounts exact retained revisions instead of invalidating them.
- **A109:** Every coordinator event carries immutable source digest, mutation
  ID, Preview revision/build ID, and monotonic per-draft `buildSequence`. Clients ignore
  lower sequences and any result whose digest is no longer current.
- **A110:** The coordinator alone owns retry policy from structured
  `retryable` codes, with one bounded infrastructure retry. API, UI, and agent
  never layer independent automatic retries.

### Answers 111-119: Publish UX and concurrency

- **A111:** Publish is bound to the exact active Preview revision currently
  displayed by the frame, not merely the latest draft string revision.
- **A112:** Any newer committed source disables Publish immediately while the
  last-known-good output stays visible and labeled stale.
- **A113:** Publish is disabled while a newer revision builds. It neither waits
  behind the user's click nor publishes the older displayed revision; the user
  reviews the new ready result and clicks Publish.
- **A114:** Confirmation shows widget name, short source/content digest, build
  completion time, and the selected Preview binding set. It contains no
  backend-untested warning.
- **A115:** Preview bindings are already active and exercised against real
  providers. Publication revalidates their authorization/revision together
  with draft/source CAS, active Preview revision CAS, deployment compatibility,
  signing, storage, and commit.
- **A116:** Publication verifies tenant/account, Preview and frame owner,
  current draft digest, expected Preview revision, definition
  ID, expected published active revision, selected binding revision, and
  publication idempotency key inside the existing mutation fence.
- **A117:** Release-key rotation may re-sign the same canonical unsigned
  artifact without another visual review if content address, target, policies,
  and build contracts remain compatible. Any executable/policy incompatibility
  requires a new Preview revision.
- **A118:** Successful Publish keeps the Preview attached to the draft and marks
  its displayed revision Published. Further edits return it to live Draft mode.
  Conversion into a published instance is a separate explicit placement action.
- **A119:** Republish creates a new immutable active revision with new binding
  selection/CAS. Existing instances remain pinned and WidgetStateService data is
  unchanged; upgrade and rollback are explicit revision operations.

- **A120:** First spike: wire the current chat Preview callback to a temporary

- **A122:** A Capsule spike throws from boot, event, timer, microtask, and

- **A125:** Fault-inject timeout, output/memory/process limits, cancellation, and

- **A126:** Adversarial fixtures place prompt instructions, secrets, absolute

- **A127:** A builder-spy regression validates, opens multiple Preview watchers,

- **A128:** Assert source, unsigned Capsule content address, server bytes,

- **A130:** Durable Preview control/artifact state must be shared wherever
