# E40 - AI widget live Preview: architecture and product decision ledger
[Overview](../BASED.md)

Resolve the product, security, Capsule, build, diagnostic, and publication
questions that must be answered before implementing [`A96`](../a/A96.md).
This exploration is intentionally question-first: it records what is known,
where current requirements conflict, and every unresolved decision found while
tracing the current implementation.

## Why this exploration exists

The intended experience is:

1. AI Chat edits a widget.
2. The user sees fast live updates in a Preview window.
3. Widget build, host, and guest failures reach the AI with enough safe context
   to repair the source.
4. The user explicitly publishes when confident.

The current product cannot perform step 2. The Cangine cutover removed the
frontend Draft Preview build/mount path, while the backend stateless Preview API
remains. Restoring the deleted UI unchanged would still be too slow and would
not provide browser-runtime diagnostics to the AI.

The architectural direction proposed in A96 is a latest-wins build coordinator,
last-known-good Preview swapping, structured diagnostics, bounded AI repair,
and exact promotion of a short-lived staged build. That direction challenges
some decisions in [`S108`](../s/S108.md), so it must not become implementation
by assumption.

### Confirmed implementation facts

- `onOpenWidgetPreview` in the current Cangine AI Chat extension only shows
  “Publish the widget to place it on the authoritative canvas.”
- Direct Cangine placement accepts published references and rejects Draft
  references.
- No current frontend caller consumes the stateless Preview response's
  `bytesBase64`.
- The earlier `DraftPreviewFrameService`, mount path, and integration tests were
  removed in checkpoint commit `3db71817`.
- The backend Preview API still builds and returns signed Capsule UI bytes.
- `buildPreview()` first performs a complete validation build and then performs
  another complete Preview build.
- Publish similarly validates with a complete build and then performs a
  separate release build.
- Every build currently creates a fresh temporary npm project, probes
  Node/npm, installs dependencies, runs the widget build script, ingests the
  distribution with Capsule, signs it, and discards the scratch directory.
- Successful Preview diagnostics are discarded, mapped Capsule error objects
  lose their safe message in `WidgetUiRuntime`, and browser failures have no
  route to the originating AI session.
- Existing focused service, API, component, and published-runtime tests pass
  without proving that a Draft Preview reaches a Cangine portal.

### Capsule constraints that shape the answer

- Capsule is not the source builder. Vibecanvas owns source snapshotting,
  dependency installation, guest scripts/plugins, network policy, isolation,
  cancellation, limits, and cleanup.
- `buildCapsuleGuest()` ingests an exact closed external distribution and
  produces deterministic, content-addressed artifact bytes.
- External distribution format v1 rejects source maps and
  `sourceMappingURL`. Debug maps therefore must remain separate trusted build
  metadata; they cannot be smuggled into the executable distribution.
- Signing uses explicit trusted Ed25519 keys, preserves the Capsule content
  address, and is separate from building.
- The browser host verifies direct bytes before execution. Its memory artifact
  cache contains only verified copied bytes and re-verifies cache hits against
  current policy.
- A mount container must be empty, unreserved, and without an attached
  ShadowRoot. Capsule owns its internal shell until terminal handle cleanup.
- `ready()` is the supported mount readiness boundary. Lifecycle replacement
  through `resume()` requires an explicit compatible parkability/snapshot
  contract.
- `onError` exposes normalized bounded records, not guest/provider stacks or
  host objects. `handle.diagnostics()` exposes authority, budgets, lifecycle,
  queues, resource ledgers, and counters, but not arbitrary guest internals.
- Testkit exposes only bounded, read-only target geometry and must never be
  attached in production.
- Authority is the intersection of artifact request, host policy, mount grant,
  and live instance-bound binding. Preview cannot gain authority merely because
  its artifact requests it.
- The retained population policy allows at most 24 aggregate live Capsule
  runtimes and fewer active/heavy/GPU runtimes. Preview instances must
  participate in admission and cleanup.

### Existing decisions that are not automatically reopened

- CanvasService remains the only durable canvas authority.
- WidgetStateService remains the only published widget-instance state
  authority.
- A Preview must never silently become a second durable published revision or
  a source of server/resource authority.
- Publication remains explicit and user-confirmed.
- Published widget revisions remain immutable, signed, recoverable, and
  resource-binding checked.
- Capsule capability requests never grant authority.

## Questions to resolve

Every question below needs either an explicit decision, a measured spike, or a
recorded “defer/not required” outcome before A96 is implementation-ready.

### 1. Product boundary: what exactly is Preview?

- [ ] **Q01:** Is Preview a companion Cangine frame on the canvas, a panel
  inside AI Chat, or both views of one Preview session?
- [ ] **Q02:** The supplied lifecycle says drafts live off-canvas, while S108
  describes persisted canvas Preview elements. Which statement is the product
  contract?
- [ ] **Q03:** Does **Open Preview** create one frame per draft, one per
  draft/chat pair, or allow several independently positioned frames for the
  same draft?
- [ ] **Q04:** If two chats edit the same draft, which chat owns the Preview and
  receives its diagnostics?
- [ ] **Q05:** Should Preview open automatically after the AI first produces a
  buildable widget, or only after an explicit user action?
- [ ] **Q06:** After it is opened, does Preview follow every committed draft
  revision until closed, or does each update require user consent?
- [ ] **Q07:** What constitutes one committed AI edit when a tool call modifies
  several files? Can the build coordinator observe one atomic mutation
  boundary rather than several transient intermediate states?
- [ ] **Q08:** May a Preview survive closing its originating chat, application
  restart, canvas navigation, or draft-sidebar navigation? If so, what durable
  identity is permitted without reviving Preview authority?
- [ ] **Q09:** Is direct Draft placement still a desired feature, or should all
  drafts use the single chat-owned Preview surface?
- [ ] **Q10:** How should the UI distinguish the displayed last-known-good
  revision, the currently building revision, and the latest draft revision?
- [ ] **Q11:** When a new build fails, should the old Preview remain fully
  interactive, become visibly read-only, or remain interactive with an error
  badge?
- [ ] **Q12:** Which controls are required: pause live builds, cancel current
  build, retry, reset local Preview state, ask AI to fix, pause automatic fixes,
  and close?
- [ ] **Q13:** What does “live” mean as an acceptance budget on supported
  hardware for warm source edits, dependency changes, cold startup, and first
  Capsule runtime load?
- [ ] **Q14:** Is `p95 < 2s` for a warm source-only edit and `<100ms` to visible
  “building” state accepted, or must those targets be measured and revised?
- [ ] **Q15:** What should happen when the build is valid but visual output is
  wrong without throwing an error? Is user feedback sufficient, or must AI
  receive a screenshot or another bounded visual observation?

- [ ] **Q21:** Is S108's prohibition on every Preview artifact cache absolute,

- [ ] **Q23:** If no staged artifact may outlive one response, is exact

## Required outcomes

This exploration is complete only when it records:

1. the chosen Preview surface and ownership model;
2. the accepted meaning of confidence before Publish;
3. whether S108 permits a non-authoritative staged build cache;
4. the exact artifact/output identity promoted by Publish;
5. the build trust/isolation and caching model;
6. the Capsule host, swap, state, admission, and cleanup model;
7. the diagnostic contract and any required Capsule API change;
8. the AI delivery and bounded repair policy;
9. the event/API ownership and concurrency fences;
10. measurable latency, security, integration, and cleanup gates; and
11. explicit revisions to A96, S108, E33, E34, and architecture documentation.

## Recommended order of resolution

1. Answer Q01-Q23 first because the Preview surface and pre-publication
   authority determine the rest of the system.
2. Resolve Q39-Q58 before promising latency; caching an unsafe guest build
   pipeline would make it faster but not acceptable.
3. Run the Capsule swap and runtime-location spikes in Q121-Q122.
4. Decide staged identity and promotion in Q24-Q38 using the spike results.
5. Finalize diagnostics and AI repair only after the source-location and
   ownership boundaries are known.
6. Rewrite A96 into implementation slices after all blocking answers are
   recorded here.

## NOTES

- This task contains questions rather than presumed answers by request.
- No mockup is needed yet. The first unresolved decision is whether Preview is
  a canvas companion frame, an AI Chat panel, or both; drawing one now would
  prematurely select that answer.
- The highest-risk contradiction is not rendering. It is the combination of
  UI-only Preview, confidence in server-backed widgets, and exact
  “publish what I reviewed” semantics.
- The highest-risk implementation boundary is the application-owned npm/source
  builder. Capsule intentionally does not isolate or reproduce that work.
