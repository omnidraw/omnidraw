# E33 - widget drafts: clarify when edits take effect
[Overview](../BASED.md)

Explore a clearer draft-to-published UX so users understand that saving draft edits does not update the widget they use on the canvas.

## Context

The draft detail page in [`packages/ai-chat/src/sidebar/widgets/WidgetDetailPage.tsx`](../../packages/ai-chat/src/sidebar/widgets/WidgetDetailPage.tsx) allows configuration and file edits while showing a Publish action in the page header. The sidebar distinguishes draft and published entries in [`packages/ai-chat/src/sidebar/widgets/components/WidgetsSidebarSection.tsx`](../../packages/ai-chat/src/sidebar/widgets/components/WidgetsSidebarSection.tsx), but the current UI does not clearly communicate the lifecycle consequence: draft changes remain isolated until the user publishes them.

A user can save or make edits, return to an existing canvas widget, and reasonably expect those edits to already be active. Explore how status, copy, hierarchy, and actions can make the draft/published boundary obvious without adding disruptive confirmations or excessive UI.

## Plan

1. Map the current lifecycle from published widget to draft edit, draft save, validation, publish, and canvas-instance update.
2. Identify every surface where users may incorrectly infer that draft edits are live, including Config, Files, Chat, the header, sidebar entries, and post-save feedback.
3. Compare lightweight UX options such as a persistent draft banner, “unpublished changes” status, clearer save feedback, publish-focused CTA hierarchy, published-vs-draft comparison, and navigation warnings.
4. Define messaging for new unpublished widgets, drafts identical to published content, drafts with unpublished changes, invalid drafts, and successful publication.
5. Recommend the smallest coherent design and document acceptance criteria for implementation.

## NOTES

The central message to preserve is: edits are saved to the draft, but the canvas continues using the published version until Publish succeeds.

E40 fixes the corresponding Preview semantics: an open Draft Preview follows
committed edits automatically and clearly labels the displayed/building/failed
revision. Its frame owns the full-stack Preview and real selected bindings for
as long as the frame remains on the canvas, including across restart. Every
published canvas instance remains pinned to its immutable revision. Publishing
promotes the exact reviewed Preview outputs and changes the active revision for
future placement; upgrading an existing instance is a separate explicit action.
