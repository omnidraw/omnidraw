# D7 - undecided: per-canvas revision is a coarse optimistic concurrency counter
[Overview](../BASED.md)

<Undecided design debt: `canvases.revision` guards all edits, so concurrent edits to the same canvas falsely conflict. We need to remember this; direction is not chosen yet.>

## Context

`canvases.revision` (`packages/service-db/src/migrations/000-initial.sql:35`) is a single
per-canvas integer used as an optimistic-locking counter. It is incremented by exactly 1 for
every committed mutation batch:

- Write path: `CanvasItemStoreTurso.applyMutations` (`packages/service-db/src/CanvasItemStoreTurso.ts:578`),
  guarded `UPDATE canvases SET revision = revision + 1 ... WHERE id = ? AND revision = ?`.
- Conflict handling and retry budget: `CanvasService` (`packages/service-canvas/src/CanvasService.ts:110`
  `maxCommitAttempts`, retry loop at `:322`, `#forceResync` at `:1154`).
- Read/surface: `CanvasItemStoreTurso.getRevision` (`:331`) and `fx.canvas.ts` field reads.
- Contract: `ICanvasStore` / `TCanvasStoreApplyResult` (`packages/service-canvas/src/ICanvasService.ts:35-45`).

### Problem
The counter is one number per whole canvas and bumps on **every** command that touches any item
(by 1, not per item). So two editors changing *different* items on the same canvas both land on
`revision-conflict` even though nothing actually overlapped. Under high-concurrency editing, the
revision would be wrong "almost all the time" for stale clients, producing false conflicts.

### Why it survives today
- The app is single-user per `AGENTS.md` — effectively one writer, so false conflicts are rare.
- `CanvasService` retries up to `maxCommitAttempts` (8), silently re-applying onto the latest version.
- The counter also serves resume/catch-up: events are monotonic, so clients can `subscribe(afterRevision)` to rebuild state (`CanvasService.ts:1076-1089`).

This is acceptable for the current single-writer authoritative-document design, but it is a real
limitation if multi-user editing is ever desired.

## Options
Options are recorded but **not decided**. Each is viable for a different concurrency goal; trade-off
is roughly complexity vs. false-conflict rate.

1. **Keep per-canvas revision (status quo).** Simplest. Correct for single-user. Breaks down for
   concurrent editors on one canvas; any disjoint edit loses.
2. **Per-item revisions + accept all non-conflicting ops.** Add/rely on `item_revision`
   (already exists on `canvas_items`) and gate conflicts per item instead of per canvas. Lets
   disjoint edits both succeed; only overlapping item writes conflict. Middle complexity.
3. **Command IDs + last-writer-wins / today-merge on conflicts.** Keep server authority, let a
   justified merge policy decide on `revision-conflict` instead of forcing full resync. More
   forgiving UX; merging (e.g. Automerge/CRDT) adds real complexity.
4. **CRDT-ledger (e.g. Automerge) over the canvas document.** Optimum concurrency, closest to
   earlier Automerge exploration (`tasks/e/E17.md`, `tasks/e/E20.md`, `tasks/e/E39.md`). Heaviest
   change to the authoritative `CanvasService` model and storage.
